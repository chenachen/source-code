DOMPurify 如何把“不可信字符串”变成可用 DOM

01 · Verdict

先解析为 DOM，再按策略清理

一句话机制： 字符串先由 DOM 解析器生成节点。遍历时先执行结构与元素检查，再处理属性； 常规获准元素还会校验命名空间。最终返回字符串、DOM 或 Fragment。 IN_PLACE 则直接清理传入节点并返回同一引用。

标签获准后仍需检查它与父节点的命名空间关系，否则 SVG、MathML 与 HTML 的解析差异可能在重新插入页面时改变标记含义，这类问题称为 mutation XSS （mXSS）。属性也按分支处理：href 等值要检查协议， data-* 等分支则按属性名接受。后文会逐一说明这些条件。

配置函数、hooks 和调用者提供的 Trusted Types policy 都是受信任扩展点。 它们能扩大允许集合、保留属性或改写输出；使用这些能力时，调用者要负责其规则。

const assert = require('node:assert/strict');
const { JSDOM } = require('jsdom');
const createDOMPurify = require('../dist/purify.cjs.js');

const window = new JSDOM('<!doctype html><body></body>').window;
try {
  const DOMPurify = createDOMPurify(window);
  const dirty =
    '<form id="location">' +
    '<a href="javascript:alert(1)" onclick="alert(2)">go</a>' +
    '<svg><circle pointer-events="all" onload="alert(3)" /></svg>' +
    '<script>alert(4)</script>' +
    '</form>';
  const clean = DOMPurify.sanitize(dirty);
  assert.equal(clean, '<form><a>go</a><svg><circle pointer-events="all"></circle></svg></form>');
  assert.equal(DOMPurify.removed.length, 5);
  console.log(clean);
  console.log('PASS: exact output; removed.length = 5');
} finally {
  window.close();
}

06 · Modules

从基础工具走到节点清理

6.1 utils.ts：缓存原生能力，绕开被污染的对象表面

DOMPurify 不频繁直接调用 node.parentNode、array.push 或 regex.test。它在初始化阶段捕获 descriptor/getter 和原型方法，再通过 Reflect.apply 调用。这样既避免非法 this，也降低原型篡改和 HTMLFormElement 命名属性遮蔽的影响。

源码摘录 · src/utils.ts · unapply() 
function unapply<T>(
  func: (thisArg: any, ...args: any[]) => T
): (thisArg: any, ...args: any[]) => T {
  return (thisArg: any, ...args: any[]): T => {
    if (thisArg instanceof RegExp) {
      thisArg.lastIndex = 0;
    }

    return apply(func, thisArg, args);
  };
}

内置正则由模块共享，部分带 /g；包装器在同 realm 的正则调用前清零 lastIndex，使重复测试从字符串开头开始。addToSet 尽量把查找表原型设为 null； cleanArray 把稀疏槽补成 own null，防止读取 Array.prototype 上的数字键。clone 不是纯浅拷贝： plain object 递归，数组清稀疏槽后复用，其余引用复用。

6.2 tags.ts / attrs.ts / regexp.ts：策略数据

默认 tag 集合由 HTML、SVG、SVG filters、MathML 和文本节点组合；默认 attr 集合由四套属性表组合。svgDisallowed 和 mathMlDisallowed 不直接进默认 allowlist，而是与允许表合并成 ALL_*，供 namespace 分类判断使用。换言之，“识别某标签属于 SVG”与“默认允许该标签”是两件事。

正则 调用方 安全语义
MUSTACHE_EXPR / ERB_EXPR / TMPLIT_EXPR 模板 scrub 替换完整或残缺模板语法；调用点包括单节点、属性及返回前处理。
DATA_ATTR / ARIA_ATTR 属性名准入 按属性名前缀接受，不进入后续 URI 值检查。
IS_ALLOWED_URI URI 值准入 接受相对值与 http、https、mailto、matrix 等明确列出的协议。
ELEMENT_MARKUP_PROBE mXSS canary SAFE_FOR_XML 开启时，节点有 children、没有真实 element child， 且 textContent 与 innerHTML 都含标记起始字符，就判为危险结构。
FALLBACK_TAG_CLOSE noscript/noembed/noframes 检查 这些元素即使被配置放行，内容命中对应闭合标记仍会整棵删除。

6.3 config.ts + _parseConfig()：建立本次使用的策略

顶层非对象配置先回退为 {}，再 clone 为 null-prototype 对象； 集合选项只接受自有数组。HTML 模式把 tag/attr 名小写，XHTML 保持原样。 USE_PROFILES 重建 allowlist，之后再叠加 ADD_*。 普通名称决策先检查 FORBID_*；配置归一有一个特例： 允许 table 会补入 tbody，并删除 FORBID_TAGS.tbody，以保留解析器补出的表格容器。 受信任 attribute hook 的 forceKeepAttr：它在 _isValidAttribute 前继续到下一属性，能绕过 FORBID_ATTR 及之后的常规检查；after hook 新增属性也不会复检。 SAFE_FOR_TEMPLATES 关闭 data-* 自动准入，显式 ALLOWED_ATTR/ADD_ATTR 接受的 data 属性仍能通过普通分支。RETURN_DOM_FRAGMENT 隐含 RETURN_DOM。

CONFIG 是提供给 hook 的配置对象，冻结只作用于顶层， 它与实际允许集合是两套对象。clone 会复用数组、函数和正则引用；数组填洞， 以及随后名称规范化，都可能原位修改调用方数组。因此这里的配置快照并非深度不可变。

6.4 元素阶段：结构威胁先于普通 allowlist

_sanitizeElements 的顺序承载安全语义：before hook → detach 检查 → clobber 检查 → upon hook → 再次 detach → mXSS/PI/comment → forbid/allow → namespace → fallback tag → template text → after hook。这是普通 allowlisted 元素的完整顺序；由受信任 CUSTOM_ELEMENT_HANDLING 接受的非 allowlisted basic custom element 会补发 after hook 后提前返回，刻意跳过 namespace/fallback。

图中的 true/false 只结束 _sanitizeElements。主 walk 不读取这个返回值来跳过后续阶段，仍调用属性清洗并处理可访问的 fragment。hook 主动 detach 与 _forceRemove 都能结束元素检查，但只有后者写入 removed；IN_PLACE 的 detach 分支还会立即中和该节点的普通后代。

_isUnsafeNode 的 mXSS 探针、HTML style 子元素和危险 comment 受 SAFE_FOR_XML 控制，PI 无条件拒绝。右下方的内容提升须同时满足 KEEP_CONTENT && !FORBID_CONTENTS[tag]，并且节点有父级；普通节点移动原 children，walk root 则插入深副本。

属性表从尾到头遍历 live NamedNodeMap，避免删除后跳项。 uponSanitizeAttribute 先拿到 trim 后的值（名为 value 的属性不 trim）； 随后处理 named-props 前缀、XML 危险标记和 SVG animation 的 attributeName/href 检查。

forceKeepAttr 在这些处理之后才生效：它直接进入下一属性，保留当前 DOM 状态， 不写回 hook 修改的 attrValue。若前缀处理已删除旧属性，也不会重新写回。 其余属性继续经过 keepAttr、自闭合标记和模板表达式处理，再进入名称与 URI 准入。

普通名称获准不等于任意值获准。ADD_ATTR: () => true 只放开名称， 不会自动允许 javascript:；但 URI 正则也接受普通 token， 因而它可以放行 onerror="alert(1)"，不能充当事件属性过滤器。 data-*、aria-*，以及由 CUSTOM_ELEMENT_HANDLING.attributeNameCheck 接受的非 allowlisted custom-element 属性会直接通过，不进入通用 URI 检查。

正常准入后，属性继续经过 Trusted Types 包装，并在值发生变化时写回。 遍历结束才执行 after hook，它新增的属性不会复检。 若 custom element 把某属性解释为 URL 或代码 sink，attributeNameCheck 应拒绝该名称；必须保留时，由受信任的 uponSanitizeAttribute hook 根据 attrValue 拒绝或改写其值。

6.6 Shadow DOM 与 template：补齐 NodeIterator 看不到的树

标准 NodeIterator 不进入 template.content 或 attached shadow roots，所以主遍历遇到 content fragment 时调用 _sanitizeShadowDOM，在 fragment 中重新执行元素与属性清理。 DOM-copy 和 IN_PLACE 路径还会在主遍历前调用 _sanitizeAttachedShadowRoots：它用显式栈搜索普通 children、 template.content 和可由 shadowRoot getter 读取的根，closed root 不可见。

对同时有这些分支的节点，LIFO 栈先搜索 shadow 内的宿主并清理其根， 再清理当前 shadow，随后搜索 template.content，最后搜索普通 children。 这里的搜索任务只负责发现 attached roots；template 内容本身的逐节点清理由 fragment 遍历承担。显式栈避免搜索普通深树时递归，但 fragment 清理仍会递归进入 嵌套 template/shadow，嵌套深度仍会受 JS 调用栈限制。

6.7 Trusted Types：包装值与管理 policy 状态

内部 policy 的 createHTML/createScriptURL 原样返回输入，本身不提供净化：createHTML 既会在 parse/walk 前包装 dirty 解析输入，也会包装最终输出；属性值则在相应准入分支后按 sink 类型包装。安全来自随后/此前的 DOM 与属性策略。两个包装函数共用重入计数器：policy 回调尚未退出时， 再次触发 HTML 或 ScriptURL 包装会抛错，阻断策略递归； 它不是 sanitize 入口处的通用重入检查。finally 保证失败也恢复计数。 caller policy 能改写最终值，因此本身是信任边界。

配置输入 活动 policy 变化 失败/后续语义
提供 caller policy 校验两个方法后激活，并用它包装内部空值。 初始化包装失败时恢复先前 policy，再重抛。

07 · Pipeline

sanitize() 的完整同步调用链

归一输入：falsy 值变空输入哨兵；非 string、非 Node 经 stringify。若实例已安装 sanitize 但 isSupported 为 false， 就在配置和 removed 重置前返回归一后的值；完全缺少 DOM 的工厂只提供 isSupported 等基础字段。
解析配置：逐调用 _parseConfig，或恢复 setConfig 持久快照；成功完成 hook allowlist 隔离后才重置 removed。
选择输入路径：字符串不含 <，且 RETURN_DOM、SAFE_FOR_TEMPLATES、WHOLE_DOCUMENT 均关闭时快速返回。其余为字符串 parse、DOM deep import 或 IN_PLACE 原对象。 IN_PLACE 在 SAFE_FOR_XML 开启时先遍历普通 childNodes，删除 PI、含 markup 的注释、 patchsrc 与非 label/output 元素的 for，再做 forbidden/clobber 根预检。
补 shadow 盲区：DOM-copy/IN_PLACE 先扫描 attached shadow roots；string 路径不做该预扫。字符串 parse 无根时按返回模式给 null、emptyHTML 或空串。
NodeIterator 双阶段：每个节点先 _sanitizeElements，再 _sanitizeAttributes。迭代包括元素、文本、注释、PI 与 CDATA； 没有 attributes 的节点仍会执行 beforeSanitizeAttributes，然后提前返回。 主循环不按元素阶段的返回值跳过属性或 template 处理。
主 walk 异常屏障：IN_PLACE 主循环异常 → 清空 live root + 清理已 detached 子树 → 重抛；更早的根预检/attached-shadow 预扫错误只中和 root。
按模式返回：IN_PLACE 先清理 removed 中的元素子树，再返回原引用； DOM/Fragment 返回节点，字符串路径序列化。模板模式在返回前补清理， RETURN_TRUSTED_TYPE 则在有活动 policy 时包装字符串。
源码摘录（省略原注释）· src/purify.ts · sanitize() 主迭代与异常屏障 
try {
  const nodeIterator = _createNodeIterator(walkRoot);
  while ((currentNode = nodeIterator.nextNode())) {
    _sanitizeElements(currentNode, walkRoot);
    _sanitizeAttributes(currentNode);

08 · Deep dive

四个最容易读错的算法

8.1 Namespace 转换：名称获准后为何仍会删除

输入是当前元素与父节点的 namespace/tag，函数判断这对父子关系是否满足当前策略。 HTML→SVG 只能经 <svg>，HTML→MathML 只能经 <math>；SVG/MathML→HTML 只允许 integration points。对实际进入 _checkValidNamespace 的节点，自定义 namespace 仅在 XHTML parser 模式且显式 allow 时通过。例外是由 CUSTOM_ELEMENT_HANDLING 保留的非 allowlisted basic custom element：它在此前提前返回，刻意不执行 namespace/fallback 检查。

源码摘录（删节）· src/purify.ts · _checkValidNamespace() 
if (!ALLOWED_NAMESPACES[element.namespaceURI]) {
  return false;
}

if (element.namespaceURI === SVG_NAMESPACE) {
  return _checkSvgNamespace(tagName, parent, parentTagName);
}

if (element.namespaceURI === MATHML_NAMESPACE) {
  return _checkMathMlNamespace(tagName, parent, parentTagName);
}

if (element.namespaceURI === HTML_NAMESPACE) {
  return _checkHtmlNamespace(tagName, parent, parentTagName);
}

手工走例：HTML body 下的 SVG namespace <g> 即使名字在 SVG 目录，也因 HTML→SVG 非 <svg> 而失败；HTML body 下的 <svg><g> 则先合法切换，再在 SVG 内按 ALL_SVG_TAGS 验证 g。

8.2 Hook allowlist：暴露共享集合前再检查一次

进入 sanitize 时，如果已经注册了 upon hook，就先复制允许名单，免得这次修改污染下次调用。 但 before hook 也可能临时注册 upon hook，所以真正把名单交给回调前，_forkSharedAllowlist 还要再检查一次：仍用着默认名单或 setConfig 保存的名单，就复制；已经是本次调用的副本，就继续共用。 这样，同次清理中的后续节点能看到修改，下次清理仍从原始规则开始。

8.3 DOM clobbering：怎样发现 form 成员被遮蔽

HTMLFormElement 的命名属性可能让 form.attributes 指向名为 attributes 的 child。_isClobbered 先通过缓存 nodeName getter 识别 form，再对关键成员做检查。 大部分成员检查类型，例如 removeChild 必须是函数；attributes、nodeType、childNodes 则与缓存 getter 的结果比较。childNodes 不能只检查 length： 名为 childNodes 的 select 自己就有数值 length，却不是原节点的 NodeList。

8.4 IN_PLACE fail-closed：主遍历失败后的处理

Custom Element reaction 或 hook 可以在同步 walk 中修改树，使迭代/删除抛错。 DOMPurify 的 catch 不恢复旧结构，而是调用 _neutralizeRoot， 先沿普通 children 删除非允许属性，再移除根的 children 和全部根属性； removed 中已脱离的元素子树也会再过一遍 _neutralizeSubtree。 后者只按 ALLOWED_ATTR 删属性名，保留允许属性的值，不再做 URI 检查， 也不进入 template.content 或 shadow。随后重抛原错误。

返回前模板处理：主 walk 成功后，SAFE_FOR_TEMPLATES 在 DOM/IN_PLACE 路径会 normalize 普通子树，将相邻文本合并，再去除模板语法，并递归处理后代 template.content。 字符串路径则在序列化后再次替换模板语法。 例如 $<evil></evil>{x} 删除空容器后形成 ${x}，返回结果为一个空格。这个终局处理不进入 attached shadow， 也不由 querySelectorAll 找到根 template 自身的 content；它在主 catch 外，抛错时不会再清空 root。

一个 TypeScript 入口，四套运行时产物，两套类型出口

npm run build 的完整生命周期是：npm 自动先跑 prebuild 清空 dist，再依次执行 build:types → build:rollup → build:fix-types → build:cleanup。 Rollup 配置含三个独立任务：一个以 src/purify.ts 为入口生成 UMD、min UMD、ESM、CJS；另两个把 tsc 的临时声明汇总为 ESM .d.mts 与 CJS .d.ts。

13 · Boundaries

配置与输入模式怎样影响使用

  • DOMPurify 清理 markup，不隔离受信任 hook、配置函数或 caller Trusted Types policy。
  • DOMPurify.removed 是诊断/清理记录，不应作为“结果安全”的判据。
  • SAFE_FOR_XML=false 会关闭 XML/mXSS 结构探针、相关属性值检查与 IN_PLACE 预处理；混用 SVG/MathML 时需要保留默认 true。
  • IN_PLACE 改原对象且可能在失败时清空它；需要保留原树时使用 copy/string 模式。
  • 跨 realm Node 通过缓存 nodeType getter 识别， IN_PLACE 仍遍历和返回原节点；DOM-copy 则净化 importNode 得到的副本。
  • 对进入 namespace 校验的普通节点，自定义 namespace 只在 XHTML parser 模式按显式 allowlist 放行；配置保留的 basic custom element 会提前返回并跳过此检查。
  • attached shadow 清理只能进入 getter 可见的根。closed root 不可见， 三个 neutralize 辅助函数也只遍历普通 children。

Hook 按注册顺序同步执行，异常会沿调用链传播；IN_PLACE 在前文列出的屏障中补做清理。 DOM 写回则有自己的处理：setAttribute 失败会删除该属性； 回调修改树或过滤结果时，应以实际执行顺序判断后续步骤还能看到哪些节点。

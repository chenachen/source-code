01 · Verdict

DOMPurify 不是“正则替换器”，而是一台受约束的 DOM 解释器

一句话机制： 它先让浏览器解析器把攻击者字符串物化为真实节点，再用实例闭包里的策略状态按 “元素结构 → 元素许可 → namespace → 属性分支链” 顺序筛选，最后按字符串、 DOM、Fragment 或原地修改模式返回。对 IN_PLACE，只有进入根预检后的失败关闭分支才会中和活树后重抛；更早的配置/TT 初始化异常不会触碰输入。配置放行的 basic custom element 会在元素许可阶段提前返回，刻意跳过 namespace/fallback 检查；属性也不是所有分支都执行 URI 值校验。

设计核心不是某一条 allowlist，而是多层不变量叠加：缓存原生 getter 规避 DOM clobbering；配置克隆冻结规避原型污染；namespace 转换规则规避解析差异导致的 mXSS；hook allowlist 每调用分叉规避跨调用污染；Trusted Types policy 有重入守卫和生命周期复位；NodeIterator 不进入的 template/shadow 子树由显式遍历补齐。

最重要的理解：hook 和调用者提供的 Trusted Types policy 都是受信任扩展点。 DOMPurify 保护的是“不可信标记”，不是恶意配置或恶意 hook。

06 · Modules

分模块理解：每层只承担一种失败模式

6.1 utils.ts：缓存原生能力，绕开被污染的对象表面

DOMPurify 不频繁直接调用 node.parentNode、array.push 或 regex.test。它在初始化阶段捕获 descriptor/getter 和原型方法，再通过 Reflect.apply 调用。这样既避免非法 this，也降低原型篡改和 HTMLFormElement 命名属性遮蔽的影响。

源码摘录 · src/utils.ts · unapply() 
function unapply<T>(
  func: (thisArg: any, ...args: any[]) => T
): (thisArg: any, ...args: any[]) => T {
  return (thisArg: any, ...args: any[]): T => {
    if (thisArg instanceof RegExp) {
      thisArg.lastIndex = 0;
    }

    return apply(func, thisArg, args);
  };
}

正则实例被模块级共享，部分带 /g；每次调用前清零 lastIndex 是其可复用不变量。addToSet 尽量把查找表原型设为 null； cleanArray 把稀疏槽补成 own null，防止读取 Array.prototype 上的数字键。clone 不是纯浅拷贝： plain object 递归，数组清稀疏槽后复用，其余引用复用。

6.2 tags.ts / attrs.ts / regexp.ts：策略数据

默认 tag 集合由 HTML、SVG、SVG filters、MathML 和文本节点组合；默认 attr 集合由四套属性表组合。svgDisallowed 和 mathMlDisallowed 不直接进默认 allowlist，而是与允许表合并成 ALL_*，供 namespace 分类判断使用。换言之，“识别某标签属于 SVG”与“默认允许该标签”是两件事。

正则 调用方 安全语义
MUSTACHE_EXPR / ERB_EXPR / TMPLIT_EXPR 模板 scrub 清除跨节点拼接后才形成的表达式。
DATA_ATTR / ARIA_ATTR 属性名准入 名称语义被视为值惰性；命中后直接放行，不进入后续 URI 值检查。
IS_ALLOWED_URI URI 值准入 默认 scheme 含 matrix:；配置文档旧示例曾漂移。
ELEMENT_MARKUP_PROBE mXSS canary 文本/序列化含 markup，但 DOM 没有真实 element child 时视为结构不一致。
FALLBACK_TAG_CLOSE raw-text fallback 阻断老 parser 对 noscript/noembed/noframes 的修复差异。

6.3 config.ts + _parseConfig()：把用户输入变成封闭策略快照

配置先做类型回退，再 clone 为 null-prototype 对象；HTML 模式把 tag/attr 名小写，XHTML 保持原样。USE_PROFILES 重建 allowlist，之后再叠加 ADD_*；FORBID_* 在普通策略决策中优先。例外是受信任 attribute hook 的 forceKeepAttr：它在 _isValidAttribute 前继续到下一属性，能绕过 FORBID_ATTR 及之后的常规检查；after hook 新增属性也不会复检。 SAFE_FOR_TEMPLATES 强制关闭 data attr，RETURN_DOM_FRAGMENT 隐含 RETURN_DOM。

6.4 元素阶段：结构威胁先于普通 allowlist

_sanitizeElements 的顺序承载安全语义：before hook → detach 检查 → clobber 检查 → upon hook → 再次 detach → mXSS/PI/comment → forbid/allow → namespace → fallback tag → template text → after hook。这是普通 allowlisted 元素的完整顺序；由受信任 CUSTOM_ELEMENT_HANDLING 接受的非 allowlisted basic custom element 会补发 after hook 后提前返回，刻意跳过 namespace/fallback。

6.5 属性阶段：分支顺序决定是否进入 URI 值校验

ADD_ATTR: () => true 进入普通 name-permitted 分支，只放开名字，不自动允许 javascript:；URI 型值仍要校验。 但 data-*、aria-*，以及由 CUSTOM_ELEMENT_HANDLING.attributeNameCheck 接受的非 allowlisted custom-element 属性会直接通过，不进入 URI 检查。属性表反向遍历 live NamedNodeMap；未 forceKeepAttr 的值仍先经历相应结构/模板分支。forceKeepAttr 与 after hook 新增属性属于受信任绕过能力。若 custom element 会把自定义属性解释为 URL 或代码 sink，调用者必须让 attributeNameCheck 只收窄可接受的属性名，并拒绝这类 sink 名称；若必须保留名称，则应由受信任的 uponSanitizeAttribute hook 根据 attrValue 拒绝或改写值。

6.6 Shadow DOM 与 template：补齐 NodeIterator 看不到的树

标准 NodeIterator 不进入 template.content 或 attached shadow roots。DOMPurify 对 template fragment 递归；attached-root 入口发现预扫使用显式 heap stack，因此 light DOM 深度不会在这一步消耗 JS 调用栈。实际 LIFO 顺序为：shadow 子树发现 → shadow 清理 → template.content → light DOM children。剩余 _sanitizeShadowDOM 对嵌套 template/shadow 仍有递归调用，这部分不享受同一深度保证。

6.7 Trusted Types：签名不是过滤，policy 生命周期才是关键

内部 policy 的 createHTML/createScriptURL 是 identity，本身不提供净化：createHTML 既会在 parse/walk 前包装 dirty 解析输入，也会包装最终输出；属性值则在相应准入分支后按 sink 类型包装。安全来自随后/此前的 DOM 与属性策略，而不是“已签名”这一事实。共享重入计数器阻止 caller policy 回调再次调用 sanitize 导致无限递归；finally 保证失败也恢复计数。 caller policy 能改写最终值，因此本身是信任边界。

配置输入 活动 policy 变化 失败/后续语义
提供 caller policy 校验两个方法后激活，并用它签名内部空值。 初始化签名失败时恢复先前 policy，再重抛。
null 本次明确不签名，也不创建内部 policy。 丢弃此前 caller policy；下一次 absent 配置可恢复内部默认。
字段 absent 复用当前活动 policy；若为 undefined，惰性解析内部默认一次。 caller policy 可跨 config-less 调用保留。
clearConfig() 恢复已缓存的内部默认 policy，清空签名空值。 caller policy 不再污染后续默认输出；内部 policy 不重复创建。

07 · Pipeline

sanitize() 的完整同步调用链

归一输入：空值变哨兵；非 string/non-Node 经安全 stringify；不支持 DOM 时在配置和 removed 重置前原样退化。
解析配置：逐调用 _parseConfig，或恢复 setConfig 持久快照；成功完成 hook allowlist 隔离后才重置 removed。
选择输入路径：纯文本满足条件时快速返回；其余为字符串 parse、DOM deep import 或 IN_PLACE 原对象。IN_PLACE 先在 SAFE_FOR_XML 门控下断开 declarative-patch linkage，再做 forbidden/clobber 根预检。
补 shadow 盲区：DOM-copy/IN_PLACE 先扫描 attached shadow roots；string 路径不做该预扫。字符串 parse 无根时按返回模式给 null、空 TrustedHTML 或空串。
NodeIterator 双阶段：每个节点先 _sanitizeElements，再 _sanitizeAttributes。
主 walk 异常屏障：IN_PLACE 主循环异常 → 清空 live root + 清理已 detached 子树 → 重抛；更早的根预检/attached-shadow 预扫错误只中和 root。
按模式返回：原引用、DOM/Fragment、string 或 TrustedHTML；模板模式再做终局字符 scrub。

08 · Deep dive

四个最容易读错的算法

8.1 Namespace 转换：tag allowlist 通过后仍可能被杀

输入是当前元素的 namespace/tag 与父节点 namespace/tag；输出是“规范 parser 是否可能生成此关系”。 HTML→SVG 只能经 <svg>，HTML→MathML 只能经 <math>；SVG/MathML→HTML 只允许 integration points。对实际进入 _checkValidNamespace 的节点，自定义 namespace 仅在 XHTML parser 模式且显式 allow 时通过。例外是由 CUSTOM_ELEMENT_HANDLING 保留的非 allowlisted basic custom element：它在此前提前返回，刻意不执行 namespace/fallback 检查。

源码摘录 · src/purify.ts · _checkValidNamespace() 
if (!ALLOWED_NAMESPACES[element.namespaceURI]) {
  return false;
}

if (element.namespaceURI === SVG_NAMESPACE) {
  return _checkSvgNamespace(tagName, parent, parentTagName);
}

if (element.namespaceURI === MATHML_NAMESPACE) {
  return _checkMathMlNamespace(tagName, parent, parentTagName);
}

if (element.namespaceURI === HTML_NAMESPACE) {
  return _checkHtmlNamespace(tagName, parent, parentTagName);
}

手工走例：HTML body 下的 SVG namespace <g> 即使名字在 SVG 目录，也因 HTML→SVG 非 <svg> 而失败；HTML body 下的 <svg><g> 则先合法切换，再在 SVG 内按 ALL_SVG_TAGS 验证 g。

8.2 Hook allowlist copy-on-write：封住动态安装的时间缝

sanitize 开始时只要已有 upon hook 就 clone。但 before hook 可以在 walk 中才安装 upon hook；所以元素/属性真正暴露 allowlist 前还要调用 _forkSharedAllowlist。仅当当前引用仍指向默认或 setConfig 基线时 clone， 已是 call-local 时保持原引用，既防污染又允许同调用内多节点共享 hook 修改。

8.3 DOM clobbering：比较“直接读”与“缓存 getter 读”

HTMLFormElement 的命名属性可能让 form.attributes 指向名为 attributes 的 child。_isClobbered 将直接属性与缓存 Node/Element.prototype getter 的结果比较；两者不同即认为被遮蔽。 这比 typeof 探针更强，因为 select 等 named child 自己也可能有 length，伪装成集合。

8.4 IN_PLACE fail-closed：不能回滚，就把活树清空

Custom Element reaction 或 hook 可以在同步 walk 中修改树，使迭代/删除抛错。 DOMPurify 无法可靠恢复先前结构，也不能继续遍历已变形树；选择先去掉整个 root 的危险属性和 children，再重抛原错误。_neutralizeSubtree 只按属性名 allowlist 取消 removed subtree 的事件 handler，并不是第二次完整 sanitize。

边界：IN_PLACE 不可逆地修改 caller 对象。对已连接且攻击者可并发影响的 live DOM， sanitize 开始前已经发生的浏览器副作用无法被撤销；源码注释也明确保留此 caveat。

09 · Example

一个可执行、从输入到断言闭环的 Node 示例

下面使用仓库真实 CJS 产物和 jsdom；与 test/jsdom-node.js 的初始化方式一致。 前提：使用项目要求的 Node.js 20+，已在仓库运行 build，且依赖已安装。示例同时验证元素、URI 属性、事件属性和 DOMPurify.removed。

教程可运行示例 · 保存为 demo.cjs 后在仓库根执行 node demo.cjs 
const assert = require('node:assert/strict');
const { JSDOM } = require('jsdom');
const createDOMPurify = require('./dist/purify.cjs.js');

const jsdomWindow = new JSDOM('<!doctype html><body></body>').window;
const DOMPurify = createDOMPurify(jsdomWindow);

const dirty =
  '<form id="location">' +
  '<a href="javascript:alert(1)" onclick="alert(2)">go</a>' +
  '<svg><circle pointer-events="all" onload="alert(3)" /></svg>' +
  '<script>alert(4)</script>' +
  '</form>';

const clean = DOMPurify.sanitize(dirty);

assert.equal(clean.includes('<script'), false);
assert.equal(clean.includes('onclick'), false);
assert.equal(clean.includes('onload'), false);
assert.equal(clean.includes('javascript:'), false);
assert.equal(clean.includes('pointer-events="all"'), true);
assert.ok(DOMPurify.removed.length >= 4);

jsdomWindow.close();
console.log(clean);

已用 Node.js 24.5.0 对当前仓库产物运行：输出为 <form><a>go</a><svg><circle pointer-events="all"></circle></svg></form>， removed.length = 5。

  1. createDOMPurify(window) 捕获该 realm 的 DOM constructors/getters。
  2. 字符串经 DOMParser 变成 HTML/SVG 混合树。
  3. form 的 id=location 被 SANITIZE_DOM 拒绝。
  4. href 名字允许，但值在 URI 层失败；onclick/onload 在属性名层失败。
  5. pointer-events 位于当前 SVG attr allowlist，且普通 token 值通过。
  6. script 标签被删除；最终序列化 body innerHTML。

12 · Distribution

一个 TypeScript 入口，四套运行时产物，两套类型出口

npm run build 的完整生命周期是：npm 自动先跑 prebuild 清空 dist，再依次执行 build:types → build:rollup → build:fix-types → build:cleanup。 Rollup 配置含三个独立任务：一个以 src/purify.ts 为入口生成 UMD、min UMD、ESM、CJS；另两个把 tsc 的临时声明汇总为 ESM .d.mts 与 CJS .d.ts。

运行时任务里 TypeScript 与 Babel 负责转换，replace 注入 NODE_ENV/VERSION；nodeResolve 是 Rollup 的模块解析 hook，不是夹在转换器之间的“编译阶段”。随后 fix-types.js 尝试为 CJS 声明追加 export = _default，最后删除临时 dist/types。 注意该脚本内部捕获错误后只警告、不重抛，因此 build:fix-types 命令成功本身不能证明声明补丁已落盘，仍应检查产物或运行类型验证。

13 · Boundaries

正确使用时仍需记住的边界

  • DOMPurify 清理 markup，不隔离受信任 hook、配置函数或 caller Trusted Types policy。
  • DOMPurify.removed 是诊断/清理记录，不应作为“结果安全”的判据。
  • 允许 SAFE_FOR_XML=false 会关闭多条结构防线；源码配置注释明确警告只适用于纯 HTML 边界。
  • IN_PLACE 改原对象且可能在失败时清空它；需要保留原树时使用 copy/string 模式。
  • 跨 realm Node 通过缓存 nodeType getter 识别，但宿主 DOM 实现差异仍需目标浏览器测试。
  • 对进入 namespace 校验的普通节点，自定义 namespace 只在 XHTML parser 模式按显式 allowlist 放行；配置保留的 basic custom element 会提前返回并跳过此检查。
  • 教程固定到 commit 8cc5ae1；未来 allowlist、浏览器 parser 和 Trusted Types 行为可能改变。

从当前实现推断：将 parser、策略快照和 fail-closed 清理放在同一同步调用中，减少了异步状态竞争； 但也意味着任何 hook/custom-element reaction 抛错会直接成为调用者可见异常。源码与测试明确支持异常传播， “减少竞争”是基于同步结构的推断，不是仓库历史声明。

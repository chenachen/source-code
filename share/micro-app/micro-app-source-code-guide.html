3. 公开入口与启动

3.1 默认单例与共享全局环境

src/index.ts 重导出 micro_app.ts 的 default；模块末尾只创建一次 new MicroApp()。但 MicroApp 类也公开导出，因此严格说默认导入是单例， 调用方可以手工 new MicroApp()。重复启动约束只检查该实例的 hasInit，并没有跨实例锁。各实例仍共享 globalEnv 和 Custom Element 注册表， 元素、资源与生命周期模块又直接读取默认单例的 options，因此新建门面不会得到独立运行环境。

启动控制流节选 · src/micro_app.ts · 省略能力检查、tagName 与 options 处理
export class MicroApp extends EventCenterForBaseApp {
  tagName = 'micro-app'
  hasInit = false

  start (options) {
    if (this.hasInit) return logError('microApp.start executed repeatedly')
    this.hasInit = true
    initGlobalEnv()
    if (window.customElements.get(this.tagName)) {
      return logWarn(`element ${this.tagName} is already defined`)
    }
    defineElement(this.tagName)
  }
}

const microApp = new MicroApp()
export default microApp

3.2 start 的真实顺序

  1. 能力检查。必须是浏览器且有 window.customElements，否则只报错并返回。
  2. 重复检查。hasInit 为真直接报错；随后立即把它设为真。
  3. tagName 校验。用 /^micro-app(-\S+)?/ 检查前缀；通过后保存到 this.tagName。该正则没有结束锚点，浏览器还会在 customElements.define 时校验完整名称。
  4. initGlobalEnv。保存原生 window/document、DOM 原型方法、timer、event、history 等快照，并注入全局微应用样式。
  5. 已有元素检查。若 tag 已注册，只告警返回。
  6. 规范化 options。兼容 disable 配置名，安排 prefetch/globalAssets，格式化插件模块名。
  7. defineElement。闭包内定义 MicroAppElement，调用 customElements.define。
边界：hasInit = true 早于 tagName 合法性判断。一次非法 tagName 会消耗该实例的启动机会； 再调用将命中“executed repeatedly”。已有自定义元素检查也发生在 initGlobalEnv 之后。

4.2 连接、属性与断开的异步边界

入口同步动作微任务动作目的
connectedCallback 递增 connectedCount，把本次连接记为 true 若本次仍有效，发 base created；连接瞬间已有 name/url 才调用 handleConnected 抑制框架瞬时插入/删除造成的重复渲染
attributeChangedCallback 初始 name/url 立即格式化保存；运行中变化只设 isWaiting 同一轮多次变化合并到一次 handleAttributeUpdate 让 name 与 url 成对校验、避免中间态重建
disconnectedCallback 把当前连接记为 false，立即分派隐藏或 unmount 无额外 defer 取消尚未执行的旧连接任务，同时及时启动清理

defer 是 Promise.resolve().then(...)，这里的“异步”是微任务，不是 timer。

4.3 name/url 校验与冲突决策

  • formatAppName 删除开头数字及非字母数字、下划线、连字符字符；空结果非法。
  • formatAppURL 以基座地址补全，只接受 http/https/file，去掉 hash，保留 pathname/search。
  • 同名运行中实例不能被替换；即使 keep-alive 已隐藏，它仍被视为 active。
  • 目标 URL/SSR URL 相同且旧实例已 unmount 时直接复用；此分支不检查 scopecss/sandbox/iframe 是否变化。
  • handleConnected 复用同 URL 的 prefetch 前，检查 scopecss/sandbox/iframe 三项核心配置；不一致则替换。
  • URL 不同的 unmount/prefetch 实例会被销毁后新建。核心配置变化本身不会迫使同 URL 的 unmount 实例重建，源码在属性迁移处仍留有对应 TODO。
两种入口的区别：连接回调只对 prefetch 检查核心配置；运行中的 name/url 迁移走 actionsForAttributeChange，目标为已卸载或 prefetch 实例时仅比较 URL 与 SSR URL。切换同 URL 实例的沙箱类型或 CSS 隔离，需显式 destroy 后重建。

5.3 loadSourceLevel 是两方屏障，不是百分比

资源完成控制流简写 · src/create_app.ts · 省略 prerender 分支
private loadSourceLevel: -1 | 0 | 1 | 2 = 0

public onLoad ({ html }): void {
  if (++this.loadSourceLevel === 2) {
    this.source.html = html
    if (this.isUnmounted()) return
    if (!this.isPrefetch) {
      getRootContainer(this.container).mount(this)
    }
  }
}
值含义触发者
0尚未收到任一资源通道的完成信号；HTML 或两条通道都可能仍在加载构造初值
1样式准备链 或 脚本准备链 任一完成；先后不固定第一次 app.onLoad
2两条通道都完成；保存模板并允许 mount第二次 app.onLoad
-1HTMLLoader 的 Promise 链进入 catchonLoadError

CSS 无外链且没有 fiber style 任务时立即完成；有 fiber 任务则等待它们处理完。JS 无登记脚本时立即完成。CSS 有外链时所有请求 settle（成功或失败都结束等待）后完成， 即便某个失败；脚本准备链 在首次阶段只等待没有 defer/async 标记的普通脚本预取， defer、async、module 的执行及外链补取留到 mount。因此 level 2 表示挂载准备完成，脚本尚未执行。

5.4 sourceCenter 的共享边界

catalog 的 theme.css 首次插入无代码缓存，需要 fetch；后续同地址插入可复用已经取回的文本，但仍建立本次替代 style。bootstrap 静态地址由 Set 去重，动态 feature 每次插入仍会调度执行。destroy 只删本实例静态 inline 项，远程缓存及 appSpace（该应用在共享资源项中的专属记录）保留。

共享 Map、请求不去重和同名 appSpace 失效边界统一见主稿：资源缓存与执行分派，不从一次命中推广到所有请求。

5.5 加载失败的实际语义

  • HTMLLoader 链 reject：抓取拒绝、processHtml 抛错或同步资源抽取抛错都会进入 catch，写 loadSourceLevel = -1；实例尚未卸载时发 error，随后设 LOAD_FAILED，已卸载时只写 level。
  • HTML 空字符串：发 error 并返回，但不调用 onLoadError；内部状态仍为 LOADING、level 仍为 0，子应用却先收到 detail=LOAD_FAILED 的 statechange。
  • 缺 head/body：同样出现“对外 LOAD_FAILED、内部 LOADING/0”的分裂。
  • 静态 CSS 或由框架 fetchSource 管理的 JS reject：记录错误，但对应准备链/批次仍完成，应用可缺资源继续 mount；原生外链 module 例外见 6.3。
  • fetchSource 直接调用 res.text()，没有显式检查 res.ok；HTTP 错误是否变成失败取决于自定义 fetch 或返回正文的后续解析。
错误事件与内部状态：空 HTML 与结构缺失通常只调用 onerror，因此已经发出错误事件却仍停在 LOADING/0； 进入 HTMLLoader 的 catch 才会把 level 写成 -1，再由 onLoadError 更新未卸载实例的状态。

6.3 脚本类型与执行顺序

脚本准备执行mounted 边界
普通外链 classicHTML 阶段并行获取按 source Set 的 DOM 插入顺序同步执行执行完继续；fiber 时逐个 idle 串行
普通 inline classic静态代码登记为唯一 inline key按 DOM 顺序执行同上
defer 外链mount 阶段批量获取全部 settle 后按 DOM 顺序执行非 module 执行完计入完成
async 外链与 defer 同组批量获取当前实现仍在全部 settle 后按 DOM 顺序执行不是浏览器原生“谁先下载谁先执行”
module + 默认 With 沙箱被视作 defer，但 isTypeModule 为 false代码经 with 包装后按函数路径执行按非原生 module 路径完成

exclude / noModule 不适配 / 不支持 module换注释不执行不阻塞

原生外链 module 失败边界：iframe/关闭沙箱下，框架不预抓取外链 module；真实 script 只绑定 onload，没有 onerror。网络失败可能让 moduleCount 无法归零，挂载收尾停滞，不能套用“promiseStream 失败后仍结算”的 classic JS 结论。

execScripts 先把 defer/async 收集起来，普通脚本立即按顺序调用 runScript； 待 defer 组全部 settle 后再遍历执行。fiber 只把这些动作包进 requestIdleCallback Promise 并串行。静态脚本等待下一次 idle 时，独立调度的动态脚本可能先执行，因此二者没有共享的执行队列。

例如 DOM 中依次是 A(defer)、B(classic)、C(async)，当前调度先执行 B，再等 A/C 这一批下载结算，按 A、C 顺序执行。 脚本执行期间新建的动态 link/script 另走动态管线，不加入 execScripts 的首次挂载计数。

默认 With 的 module 边界：它只借用 defer 调度，不使用浏览器 module 解析器；代码仍进入 Function。若源码保留原生 import/export，必须由插件 loader 先转译，否则 Function 编译会失败。iframe 或关闭沙箱才保留原生 type=module。

7. CSSParser / scopedCSS：算法与手工推演

7.1 目标与算法

输入是一段 CSS、应用前缀、app URL 与可选 CSS 文件地址；输出是保留声明和 at-rule 结构、 改写普通选择器与相对 URL 的 CSS 字符串。解析器重复识别三类 token：style rule、at-rule、comment。 它不是浏览器 CSSOM，而是顺序消费字符串的专用 parser。

  1. matchRules。跳过空白和注释，循环尝试 at-rule，否则尝试 style rule。
  2. formatSelector。先用占位符保护属性选择器的值，再按剩余逗号拆分，为每段选择器决定前缀。它没有跟踪圆括号深度。
  3. body 特例。未命中根选择器放行规则的 body 被换为“应用前缀 + micro-app-body”；html body 先命中 html 放行，保持原文。
  4. root 特例。默认 html/:root 不加前缀；optionCss: ['isolation-root'] 时只放过 html，:root 会被前缀化。
  5. 声明与 URL。递归消费大括号；相对 URL 通过 CSS 文件目录或 app URL 补全。
  6. at-rule。media/supports/container/layer 等递归处理子规则；font-face 直接处理声明；page 先原样记录其选择器，再处理声明；keyframes 保留名称与关键帧位置，只改写声明中的 URL。
  7. 注释开关。disable-next-line 关闭下一条普通规则的选择器改写，在进入声明前复位，因此该规则的 URL 仍会补全；disable 持续关闭，按 selector disable 只放过列出的选择器，enable 恢复改写。

9. mount 与执行完成

  3. 等待 sandboxReady。With 构造时同步完成初始化但 Promise 回调仍在微任务；iframe 通过 0ms 轮询等待独立 document。
  4. BEFORE_MOUNT。进入 nextAction 后先设状态；非 prerender 路径发 base beforemount。
  5. MOUNTING 与模板。设 MOUNTING、发 child statechange；从 source.html 深克隆到宿主（UMD remount 则转移活 DOM）。
  6. sandbox.start。初始化路由状态、请求代理与全局 DOM/history 补丁，active 变 true。
  7. 执行前。patchElementTree 标记静态 DOM；劫持 window.mount/unmount 和 window['micro-app-'+name] 识别 UMD hooks。

  9. UMD 判定。沙箱 setter 同时捕获函数型 mount 与 unmount 时，立即设 umdMode = true 并调用 mount(data)，可能发生在当前脚本尚未执行完时；之后 remount 跳过初始化脚本。关闭沙箱时没有这组 setter，不识别 UMD 导出。

11.4 UMD 与 keep-alive 的差异

资源完成后的两者都保留 DOM、timer 并快照 listener，但 UMD 已执行完整 unmount，sandbox 变 inactive、 global 引用计数递减，remount 会调用 UMD mount hook；keep-alive 只是隐藏，sandbox 仍 active、 app state 不进入 UNMOUNT，show 只恢复 DOM 与副作用，不走 mount hook。

12. 四条真实调用链

链 1：microApp.start 到首次 mounted

  1. 公开入口：src/index.ts default → micro_app.ts microApp.start。
  2. 全局初始化：initGlobalEnv → rejectMicroAppStyle → defineElement。
  3. DOM 连接：connectedCallback → defer → handleConnected → handleCreateApp。
  4. 实例与 I/O：new CreateApp → appInstanceMap.set → loadSourceCode → HTMLLoader.run → fetchSource。
  5. 资源屏障：formatHTML → extractSourceDom → 样式准备链 + 脚本准备链 → onLoad × 2。
  6. 挂载：MicroAppElement.mount → CreateApp.mount → sandboxReady → cloneContainer → sandbox.start。
  7. 执行：actionsBeforeExecScripts → execScripts → runScript → bindScope。
  8. 完成：handleMounted → actionsAfterMounted → MOUNTED → child hooks/events → base mounted。

链 2：动态 style/link/script 到副作用

  1. 归属：proxyDocument.createElement → updateElementInfo(__MICRO_APP_NAME__)。
  2. 插入拦截：patched appendChild/insertBefore → commonElementHandler → appInstanceMap.get。
  3. style：handleNewNode → scopedCSS → CSSParser / MutationObserver → 插入 micro-app-head。
  4. link：extractLinkFromHtml → sourceCenter.link → formatDynamicLink → fetch/cache → style → 原 link load/error。
  5. script：extractScriptElement → runDynamicRemote/InlineScript → runScript → plugin → bindScope → Function/inline module。
  6. 最终副作用：针对全局 head/body 的插入重定向到 app 容器；其他父节点仍按原父节点处理。window/document event 与 timer 进入沙箱记录；全局写入通常进入 proxy target，逃逸配置和宿主 on 属性另有写回规则。

链 3：基座与子应用双向数据

  1. 基座发：microApp.setData → EventCenterForBaseApp.setData → __catalog_from_base_app__。
  2. 合并：EventCenter.dispatch → tempData 浅合并 → defer(process) → isEqual。
  3. 子应用收：EventCenterForMicroApp.addDataListener 的 callbacks 被调用；autoTrigger 可读已有缓存。
  4. 子应用回：window.microApp.dispatch → __catalog_from_micro_app__ → base addDataListener。
  5. 宿主事件：同次有效 dispatch 在 base listener 后向 <micro-app> 发 datachange，合并数据位于 detail.data，随后执行 nextStep。
  6. 卸载：listener 清理与 data 清理由不同 API 控制；默认保留缓存。只有真实 unmount 到达 active sandbox 时，非 reload 的 clear-data/destroy 才清 per-app 双向数据；直接结算/no-op 分支可忽略它。

链 4：普通卸载、keep-alive、destroy

  1. 公共入口：remove element → disconnectedCallback → handleDisconnected。
  2. 普通：unmount → child hooks → sandbox.stop(default) → 清 event/timer → base unmount → clearOptions。
  3. keep-alive：hiddenKeepAliveApp → HIDDEN → afterhidden；level 2 时 DOM 移到 div 并 snapshot/release，未完成时退化普通 unmount。show 先把实例 container 指向新宿主并重建监听器，再发 beforeshow，随后移回活 DOM、恢复 search 路由，最后发 aftershow。
  4. destroy：unmount(destroy) → sandbox.stop(destroy) → clearData → clearOptions → actionsForCompletelyDestroy。
  5. 结果：普通与 UMD 可由同一 Map 实例复用；完成加载的 keep-alive 不真正 unmount；destroy 迫使下一次新建实例，但外链缓存及旧 appSpace 仍可复用。

13.5 加上可失败的断言闭环

下面与 13.3 的 main.js 合用，限定新页面、默认 With、无 fiber、一个普通静态 bootstrap，以及上面给出的子应用文件。先注册数据/资源事件，再插入；资源成功上报是浅合并字段，因此可同时检查 ready、themeReady 与 featureReady。此组合浏览器例本轮未运行，不能把隔离脚本的 PASS 当作它的结果。

// 接在 base/main.js 末尾。每次等待都有限时；包括没有 error 转发的失败分支。
function check(condition, message) {
  if (!condition) throw new Error(message)
}
function waitFor(predicate, label, checkFailure = true) {
  return new Promise((resolve, reject) => {
    const started = Date.now()
    const timer = setInterval(() => {
      try {
        if (checkFailure && failure) throw new Error(failure)
        if (predicate()) { clearInterval(timer); resolve(); return }
        if (Date.now() - started > 5000) throw new Error(label + ' timeout')
      } catch (error) { clearInterval(timer); reject(error) }
    }, 20)
  })
}
async function verifyCatalog() {
  try {
    await waitFor(() => mounted && childData.ready, 'mounted + ready')
    check(getActiveApps().includes('catalog'), 'catalog must be active')
    check(element.querySelector('.catalog-card')?.textContent.includes('CNY'), 'currency DOM')
    await waitFor(() => childData.themeReady && childData.featureReady, 'dynamic resources')
    check(element.querySelector('small')?.textContent === 'feature loaded', 'feature DOM')
    check([...element.querySelectorAll('style')].some(style =>
      style.textContent.includes('border-radius: 8px')), 'theme CSS text')
    console.log('PASS: catalog data, DOM and dynamic resource assertions')
  } finally {
    try {
      disposeCatalog()
      await waitFor(() => unmounted, 'unmount', false)
      check(!getActiveApps().includes('catalog'), 'catalog must be inactive')
      check(element.innerHTML === '', 'default unmount clears live DOM')
    } finally {
      microApp.removeDataListener('catalog', receive)
    }
  }
}
verifyCatalog().catch(error => console.error('FAIL: catalog verification', error))

运行需要基座打包器解析 @micro-zoe/micro-app，并明确指向本地 rc.32 构建产物，不能使用未固定的最新版包；子应用 HTTP 服务需允许基座跨域抓取且提供所列资源与 paper.png。用真实地址替换示例域名后启动基座页面。预期局部顺序：child onmount → base mounted → child → base ready → host datachange；theme/feature 谁先完成没有保证。看到 PASS 后还须无清理 FAIL；超时将拒绝并进入 finally。样式断言只证明 CSS 文本插入，不证明图片可见或布局正确。

13.6 示例与框架完成时机

  • 首次 mounted：等待入口登记的静态脚本调度结束，不等待 bootstrap 创建的 theme.css 或 feature.js；link 可观察原节点 load/error；普通 script 未命中缓存时的 fetch/Function 异常才由该 Promise 链转 error。缓存命中执行异常和原生外链 module 失败没有对应原节点 error 转发，等待必须设超时，不能只等 error。
  • 路径：main.css、theme.css、bootstrap.js 和 feature.js 都基于 app 目录补全；main.css 内的 paper.png 基于 CSS 文件目录，解析为 https://child.example/app/img/paper.png，部署时需提供该图片。
  • 本例清理：本例没有成对的 window.mount/unmount，属于普通默认 With 模式。框架先从代理窗口读取并调用子应用 window.onunmount，本例在其中主动清 heartbeat；随后 stop 的 releaseGlobalEffect 还会清除沙箱账本中其余已记录的 interval/timeout。UMD 软卸载、keep-alive 隐藏和预渲染保留这些 timer；destroy 则清除。
  • 禁用沙箱是另一条件：框架不调用宿主 window.onunmount，也没有 With timer 账本兜底；业务需要自己安排资源清理，不能把这个限制套到上面的默认 With 示例。决定分支见 create_app.ts · handleUnmounted、with/index.ts · releaseGlobalEffect、with/window.ts · release。

Proxy 兼容优先于强安全

缺失值回落 rawWindow 支持旧库；代价是隔离为工程命名空间，不是恶意代码安全容器。

从当前实现推断

确定性脚本顺序优先

async 与 defer 聚合后按 DOM 顺序执行，减少框架内竞态；代价是与浏览器原生 async 语义不同。

从当前实现推断

UMD/keep-alive 以常驻换速度

保留 DOM、timer 和副作用快照提升二次展示；代价是隐藏或卸载后仍可能有 timer/EventSource 等持续工作。

从当前实现推断

通信批处理降低噪声

同微任务合并与浅去重减少重复 render；代价是嵌套对象按引用判断，且 nextStep 在相同数据时也不执行。

15.3 prefetch/prerender 与首次 mount 的接点

prefetch 在 idle + 默认 3 秒后串行处理配置，若 Map 中无同名 app，仍直接 new CreateApp({ isPrefetch: true, prefetchLevel })，所以复用同一 HTML/sourceCenter 管线。 “串行”只等前一应用的 CSS/JS 任一 lane 第一次调用包装后的 onLoad；它可能在 level 1 就放行下一应用， 并非逐应用等待完整双屏障。preFetch 返回 void，延时 timer 没有公开取消句柄。 level 2 可预解析 JS；level 3 prerender 会在临时 div 以强制 fiber 挂载。真实元素出现时， handleConnected 检查 URL 与 scopecss/sandbox/iframe 核心配置，兼容则把 isPrefetch 置 false 并进入普通 mount；不兼容则销毁后新建。

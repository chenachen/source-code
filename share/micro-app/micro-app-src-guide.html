结论、范围与证据基线

主线可以压缩成一句话：<micro-app> 决定“何时运行”，CreateApp 决定“运行到哪一步”，source 与 sandbox 决定“代码在哪里、以什么全局语义运行”。

控制面

MicroAppElement 把连接、断开和 name/url 变化路由到创建、复用、隐藏或卸载。

状态面

CreateApp 持有主状态、keep-alive 状态、资源进度、DOM 容器和 UMD 钩子。

执行面

source 解析与缓存资源；with/iframe 沙箱隔离全局对象，并记录可恢复副作用。

源码事实

核心对象与所有权

microApp

基座单例门面。持有全局配置、路由和数据中心 API；在受支持浏览器中，start() 的初始化门禁最多进入一次，重复调用报错。

MicroAppElement

每个宿主 DOM 节点一个控制器。持有连接代次、元素配置与未命名时的数据缓存。

CreateApp

每个应用名一个可复用运行实例。持有状态机、资源、容器、沙箱、UMD 钩子和预渲染队列。

appInstanceMap

进程级注册表。预取、隐藏、mounted、未销毁的 unmount 实例都可能继续存在。

sourceCenter

按完整 URL 共享原始 CSS/JS；按应用 appSpace 隔离属性、转换代码和函数缓存。

Sandbox

with 使用 Proxy 作用域；iframe 使用隐藏同源 realm。两者统一提供 ready、start/stop 与副作用快照。

关键不变量：元素不是应用实例。移除元素可能只隐藏应用；销毁才从 appInstanceMap 删除。判断“应用是否存在”与“应用是否活跃”必须分开。
源码摘录

启动与 DOM 控制：先建立环境，再允许元素回调

MicroApp.start() 捕获原生全局引用、归一化配置、安排预加载，最后注册自定义元素。这个顺序重要：一旦 customElements.define() 完成，页面中已有元素可能立即升级并进入生命周期。

元素连接不是直接同步挂载。它先增加连接代次，再进入微任务；断开会把当前代次标为无效。Vue keep-alive 或框架重排造成的“同一轮插入后立刻删除”因此不会留下过期挂载。

同名实例的四路分派

  • 隐藏且 URL 相同：恢复 keep-alive，不创建实例。
  • URL/SSR URL 相同且旧实例已卸载：直接复用，不检查 scopecss/sandbox/iframe 是否变化。
  • URL 相同且核心配置一致的 prefetch：复用；同 URL 但配置不兼容的 prefetch，或 URL 不同的 prefetch/unmounted：销毁旧实例后创建。
  • 同名实例仍活跃：记录冲突错误，拒绝覆盖。
配置切换边界：sameCoreOptions 只保护 prefetch 复用。普通 unmount 后若仍使用同 URL，改变沙箱类型或 CSS 隔离不会触发重建；需要显式 destroy。
控制面补全

命令式 API：元素事件与实例直调共用一套应用状态

renderApp 创建元素，reload 调元素方法，active app 的 unmountApp 也通过移除元素触发断开；但 prefetch/unmounted/hidden 分支会直接调用 CreateApp、直接销毁或无操作结算。共同底座是 CreateApp 状态与生命周期，不是 Custom Element 这一条唯一执行路径；公开 Promise 既可能等元素事件，也可能等 unmountcb 或同步 resolve。

API入口分派Promise/返回边界保留与清理
renderApp(options)创建当前 tagName 元素；data、datachange、生命周期单独绑定，其余配置转属性；最后 appendmounted → true，error → false不自动卸载；调用方仍需移除元素或调用卸载 API
reload(name, destroy?)找到实例宿主 → 元素 reload → disconnect → reconnect等待 mounted 或 aftershowisReloading 强制卸载阶段保留 data，完成后再下发旧快照
unmountApp(name, options)按 prefetch/unmounted、hidden、active 三类状态分派；只有 active 通过移除元素触发断开无实例为 false；其余等待 unmount/afterhidden/unmountcb，或同步结算 truedestroy 删除实例；clearAliveState 可把 hidden 变 UNMOUNT；clearData 只有进入真实 unmount + active sandbox release 时才生效
unmountAllApps对 Map 键快照做 Promise reduce按注册顺序串行；返回最后一次 unmountApp 的布尔值，空 Map 才由初值返回 true策略原样传给每个应用
getActiveApps过滤 UNMOUNT、纯预取及可选 hidden/prerender返回当次名称数组不等于 getAllApps：后者包含预取、hidden、未 destroy 的 UNMOUNT 实例
Promise 悬空边界：executor 内非法 options/容器只 return logError(...)，没有 resolve/reject；name/url 校验若只记录日志、未派发 error，同样没有结算事件。因此 renderApp 不是“所有失败都返回 false”。这是源码事实，不是测试证明。

这里存在两套所有权：Map 决定“实例是否仍可找到”，app state 决定“是否活跃”。默认卸载只令实例进入 UNMOUNT；getActiveApps() 不再返回它，但 getAllApps() 仍会返回。完成 destroy 路径后才执行 appInstanceMap.delete(name)。

测试边界：默认套件中的 create_app.test.ts · test unmountApp method 包含普通、已卸载、hidden keep-alive、destroy、clearAliveState 场景，但 hidden+destroy 的实例删除断言被注释，只能说明该异步路径按测试写法没有挂起，不能证明完整清理；micro_app.test.ts 的 reload/unmount Promise 又未 await/return。

源码摘录

资源系统：两条异步链，一个完成门禁

HTML 入口

HTMLLoader 先抓取入口，再运行“全局插件 → 应用插件”，最后把原生 head/body 改写为 micro-app-head/body。JS 入口会合成最小 HTML。

资源提取

extractSourceDom() 扫描 link/style/script/img。exclude 变注释占位；ignore 保留原生元素；相对 URL 基于应用入口补全。

缓存边界

远程 CSS/JS 原码按完整 URL 全局共享。应用相关 attrs、CSS 前缀、插件后代码、Function 缓存放进 appSpace[appName]。销毁只删当前应用内联脚本；远程缓存及该 name 的 appSpace 元数据都保留。

脚本执行分派

  • 应用/元素 inline、带 id 的特殊脚本，以及 iframe/关闭沙箱下的 module：创建真实 script 节点，交给浏览器执行。
  • 默认 With 沙箱中的 module：按 defer 调度，但不保留原生 module，仍走 scope 包装 + Function；裸 import/export 需 loader 预先转译。
  • 普通脚本：插件转换后绑定沙箱作用域，缓存 Function 并调用。
  • fiber：对框架自行抓取的 classic/defer/async 批次，等待对应批次 settle 后按源顺序串行放入空闲任务；原生外链 module 的浏览器加载不在这条抓取链。
  • 动态远程脚本：优先命中应用/全局缓存；否则抓取后执行，并向原节点模拟 load/error。

缓存不是请求去重器，也不是浏览器脚本列表

  • 无 in-flight Promise：资源项初次登记时 code === ''。两个应用并发遇到同 URL 都会各自 fetchSource；只有先完成并写入的文本能被后来者复用。
  • 同应用静态地址折叠：source.links/scripts 是 Set。同一 app 的重复远程 href/src 只调度一次；远程 script 不再像浏览器那样按重复标签执行多次。静态 inline 各有 nonce，动态 script 每次插入仍执行。
  • destroy 不清远程 appSpace：同名同 URL 新实例再次提取时使用 appSpace[name] ||= newData；第一次登记的 attrs、async/defer/module/inline/pure 与 parsed metadata 可能继续生效。缓存换来复用，也带来同名重建配置陈旧边界。

动态 DOM：节点归属先于资源分派

proxyDocument 创建节点时写 __MICRO_APP_NAME__；全局 Node 原型补丁在 append/insert 前读取该标记，找到实例并补全 URL。style、link、script 再走各自转换器，document.head/body 插入被重定向到应用容器。WeakMap 保存“调用方原节点 → 实际 style/script/comment”，让 remove/replace 仍能操作正确节点。

失败边界：单个 CSS 或由 fetchSource 管理的 JS 请求失败，会由 promiseStream 记录并在最终回调结算；iframe/关闭沙箱下的原生外链 module 不预抓取，只给真实 script 注册 onload 而没有 onerror，加载失败可能让 moduleCount 门禁不再结算。HTML 抓取失败、空 HTML 或缺少隔离 head/body 又是另外两类错误路径。

副作用所有权

window/document 与数据监听通过 effect hook 记录、释放并在 UMD、keep-alive、预渲染恢复时重建。With timer 只进入活动账本：默认/destroy 清除，可恢复态让原生 timer 继续运行；iframe effect 不跟踪 timer，主要靠 realm 删除终止。Worker 与 EventSource 也不进快照：只有在应用作用域内由 WorkerProxy 登记的 Worker、以及 With 请求补丁登记的 EventSource 才受框架批量清理；禁用沙箱、原生/逃生资源不在保证内。

所有权深挖

请求与副作用：两个沙箱，共用协议但不共用实现

沙箱不只决定变量写到哪个 window，还必须回答两个更难的问题：相对请求以谁为基准，以及卸载时谁负责撤销事件、timer、长连接和 Worker。With 沙箱靠包装器与显式账本；iframe 沙箱更多依赖独立 realm 和 <base> 的浏览器语义。

effect 不是一份“DOM 快照”

record：复制监听账本→ release：按账本尝试解绑→ rebuild：重新绑定并消费快照

recordAndReleaseEffect 根据模式先选 record 或 reset，再统一 release。UMD、keep-alive、prerender 需要恢复，所以记录 window/document/data listener；默认卸载和 destroy 不应恢复，所以清空旧快照。当前四套 window/document release 调用 removeEventListener 时没有带回注册时保存的 capture option：capture:true 监听可能仍绑定，但活动账本已被清空。data 缓存是否删除则由 clearData 单独控制。

副作用With：默认 / UMD·keep·prerender / destroyiframe：默认 / UMD·keep·prerender / destroy
window/document listener对默认 capture=false：解绑不记 / 记录后解绑、恢复时重绑 / 解绑并丢快照；capture=true 有漏解绑边界同一 capture 限制；真实目标还可能是 iframe window、宿主 window 或宿主 document
timer清除 / 保持原生 timer 继续运行、不进入 snapshot / 清除effect 不跟踪 timer；默认与 destroy 通过删除 realm 终止，UMD/keep/prerender 保留 realm
EventSource请求补丁已登记的实例：默认/destroy 批量 close，UMD/keep 保留；原生/逃生实例不受保证无应用级 EventSource Map；主要随 realm 删除或保留
WorkerWorkerProxy 仅在创建时存在 current appName 才登记；已登记项由沙箱 stop 的默认/destroy 路径终止。keep-alive 不 stop，UMD 软卸载保留；禁用沙箱、原生/逃生 Worker 不受保证
数据 listener / datalistener 释放并可快照恢复；data 默认保留，只有真实 unmount 到达 active sandbox 的 releaseGlobalEffect(clearData) 才清双向缓存。直接 prefetch/unmounted 与 hidden no-op 分支可忽略 clearData
Proxy 注入键默认/destroy 删除 injected/escape keys；UMD 软卸载保留写入属于 iframe realm；删除 realm 即整体失效
不能泛化“沙箱会清 timer”。这句话只对 With 默认/destroy 的显式账本，以及 iframe 默认/destroy 的 realm 删除成立。UMD、keep-alive、prerender 都可能让 timer、连接或 Worker 继续工作；应用仍需为禁用沙箱和业务资源提供自身清理。

iframe ready 与销毁边界

iframe 插入主 document 后，patchIframe 每个 setTimeout(0) 轮询一次 document 身份；浏览器重建完成才 stop 初始页面并安装补丁。此 Promise 没有超时、reject 或取消路径：若自定义 iframeSrc 造成持续不可访问，源码会 catch 后继续轮询。这是从当前实现推断的卡住风险。已 start 的常规默认/destroy 路径使用 defer（Promise 微任务）删除 iframe；但 ready 前卸载时 stop 因 inactive 返回，非空 container 又令 clearOptions 跳过补删，随后 sandbox 引用可被置空，轮询与 iframe 存在残留风险。

静态测试边界：默认选中的 main.test.ts 在 UMD 首挂与重挂处都写了 window/document listener 的 toHaveBeenCalledWith；但中间未清 mock、比较次数或在卸载间隙派发，因此第二处可被首次调用满足，不能排他证明恢复，也不涉及 timer。非默认 sandbox/effect.test.ts 主要涉及 UMD 重挂与一个 iframe instanceof 场景；request、EventSource、Worker 清理没有默认套件直接断言。

子应用 history.pushState、location setter 或公开 router.push() 最终都要更新 microLocation；需要同步宿主时，再构造新 URL/state 并调用原生 history。浏览器回退则反向读取每个活跃应用路径，更新代理 location，派发子应用 popstate/hashchange。

宿主 popstate 监听器会过滤已卸载、隐藏、预渲染和 onlyForBrowser 事件，再按容器的 router-event-delay 进入宏任务。这个异步边界让可能懒加载或卸载页面的基座先响应，之后才更新子应用 location；更新顺序固定为 microLocation → 子应用 popstate → hash 真变化时的 hashchange。

守卫边界：URL/location 先更新，再写 router.current 并运行 beforeEach；守卫没有 next/return 协议，不能取消已经发生的导航。afterEach 被放入 idle callback。runGuards 没有 try/catch：前置异常同步向上传播，后置异常发生在空闲回调边界。

宿主框架在同 URL 上用新对象调用 replaceState 时，全局 history 补丁会保留已有 __MICRO_APP_STATE__；基座 History 调用完成后，再为仍活动但记录缺失的应用补回路由。补丁不能观察基座直接通过 location 发起的导航。

测试边界：当前 src/__tests__ 没有独立 router 测试，默认 7 文件也未直接断言五模式、反向 popstate、守卫或 keep-router-state 清理。此章均为生产源码证据，不宣称测试保证。
源码摘录

数据通信：微任务批处理，不是同步 EventEmitter

基座→子应用、子应用→基座使用不同内部事件名；全局数据使用 global 通道。同一同步栈连续 dispatch 会合并到 tempData，一个微任务只处理一次该事件，并按调用顺序保存每个 nextStep。只有整批被 force 或浅比较确认变化时，监听器与这些 nextStep 才会执行。

浅比较只比较顶层键数量和值引用。对象内部原地修改不会被检测；需要通知时使用 force API。子应用上行数据提交后，还会在根元素派发 datachange，把非 DOM 数据中心桥接到宿主事件。

预取与预渲染：复用的前提是执行环境一致

  • level 1：加载 HTML/CSS，并因“prefetch 且非 prerender”提前抓取包括 defer/async 在内的全部 JS 原码。
  • level 2：在 level 1 基础上执行插件与 bindScope；未进入 isInlineMode 的脚本还预编译 Function。
  • level 3：标记为 prerender，不走 level 2 预编译；双屏障后在临时 <div prerender> 中强制 fiber 挂载并真实执行脚本。

预取在 requestIdleCallback 后再等待配置延时，应用按数组顺序调用 preFetchAction。这里的“串行”边界要精确理解：合法应用覆写的 onLoad 在 CSS/JS 任一链首次结算时就 resolve，随后才调用原 onLoad；因此下一应用可以在前一应用尚未达到双屏障 2 时开始，不能把它描述成“逐个等待全部资源完成”。preFetch() 返回 void，额外 timer 没有保存句柄；进入调度后没有公开等待或取消路径，源码仍留有清 timer TODO。

最终元素挂载时，URL、CSS 隔离、沙箱开关和 iframe 类型一致才复用；不一致就销毁预取实例重建。

预渲染不把路由附加到宿主 URL，不向浏览器派发 popstate/hashchange，也不派发可见生命周期。转真实挂载时，先替换容器引用，再恢复副作用快照和积压事件。

测试边界：prefetch.test.ts 与 ssr_env.test.ts 都不在默认 7 文件中；前者还导入当前源码不存在的 globalLinks/globalScripts，不能作为 rc.32 可执行证明。当前测试没有直接断言 level 2 预编译、level 3 转真实挂载、取消边界或“首条 lane 即放行下一应用”的时序；这些结论来自生产源码。

手工推演

三个关键算法

1. 资源双屏障

时刻动作loadSourceLevel结果
T0构造实例0进入 LOADING
T1JS 先下载完成，调用 onLoad1不挂载
T2CSS 与 fiber style 完成，调用 onLoad2写 source.html，进入挂载或预渲染

若顺序相反，结果相同。关键不变量不是“哪个先完成”，而是两条准备链各且仅结算一次。单个 CSS 或由框架 fetchSource 管理的 JS 下载失败会记录错误，promise stream 最终回调仍让该链结算；原生外链 module 的浏览器加载发生在这之后，不受该保证。

2. EventCenter 批处理

决定性源码见前文 EventCenter.enqueue/process 摘录。输入 dispatch({a:1})、dispatch({b:2})、dispatch({a:3}) 位于同一同步栈：第一次创建通道并把 force 置真；队列只有一个事件名，tempData 最终为 {a:3,b:2}。process 先交换队列，再提交快照、通知监听器和三次 nextStep。若是既存通道且整批浅比较无变化、也没有 force，则监听器和 nextStep 都不执行。监听器内重入 dispatch 会进入下一批，不污染当前 tempData。

3. Scoped CSS

解析器按 style rule、at-rule、comment 三类消费文本。普通选择器前加 micro-app[name=xxx]；body 改成 micro-app-body；:root/html 受 optionCss 策略控制；相对 url(...) 基于外链 CSS 文件目录补全。scopecss-disable 注释可全局、选择器级或下一行关闭改写。

body .mask, .card { background:url("../img/a.png") }
prefix=micro-app[name=demo]
linkPath=https://cdn.example/assets/css/main.css		 顶层逗号拆成两个选择器；body 分支替换根；普通 .card 加前缀；URL 基准改为外链 CSS 目录 micro-app[name=demo] micro-app-body .mask, micro-app[name=demo] .card { background:url("https://cdn.example/assets/img/a.png") }

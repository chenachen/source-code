Mechanism first · src evidence only

一个 DOM 元素，如何变成完整微前端运行时

micro-app 的核心不是“加载一段 HTML”，而是把自定义元素的连接状态，翻译成资源双屏障、应用状态机、两类沙箱、路由同步、数据批处理和可恢复副作用。

结论、范围与证据基线

主线可以压缩成一句话：<micro-app> 决定“何时运行”，CreateApp 决定“运行到哪一步”，source 与 sandbox 决定“代码在哪里、以什么全局语义运行”。

控制面

MicroAppElement 把连接、断开和 name/url 变化路由到创建、复用、隐藏或卸载。

状态面

CreateApp 持有主状态、keep-alive 状态、资源进度、DOM 容器和 UMD 钩子。

执行面

source 解析与缓存资源；with/iframe 沙箱隔离全局对象，并记录可恢复副作用。

证据边界：v1.0.0-rc.32 / dd445c483a7c 仅用于固定本次分析快照；正文的机制、摘录、测试和文件链接全部限定在 src/**。不讨论构建、发布、包配置或仓库外实现，也不把当前结构虚构成历史演进。

当前实现推断 项目把 DOM 自定义元素选作控制面，换来与任意主框架较低耦合；代价是连接回调、属性回调、资源异步任务和沙箱 ready 之间存在竞态，源码必须显式维护连接代次与应用状态。

核心对象与所有权

microApp

基座单例门面。持有全局配置、路由和数据中心 API；在受支持浏览器中，start() 的初始化门禁最多进入一次，重复调用报错。

MicroAppElement

每个宿主 DOM 节点一个控制器。持有连接代次、元素配置与未命名时的数据缓存。

CreateApp

每个应用名一个可复用运行实例。持有状态机、资源、容器、沙箱、UMD 钩子和预渲染队列。

appInstanceMap

进程级注册表。预取、隐藏、mounted、未销毁的 unmount 实例都可能继续存在。

sourceCenter

按完整 URL 共享原始 CSS/JS；按应用 appSpace 隔离属性、转换代码和函数缓存。

Sandbox

with 使用 Proxy 作用域；iframe 使用隐藏同源 realm。两者统一提供 ready、start/stop 与副作用快照。

关键不变量：元素不是应用实例。移除元素可能只隐藏应用；销毁才从 appInstanceMap 删除。判断“应用是否存在”与“应用是否活跃”必须分开。
源码摘录

启动与 DOM 控制：先建立环境，再允许元素回调

MicroApp.start() 捕获原生全局引用、归一化配置、安排预加载，最后注册自定义元素。这个顺序重要：一旦 customElements.define() 完成，页面中已有元素可能立即升级并进入生命周期。

元素连接不是直接同步挂载。它先增加连接代次，再进入微任务；断开会把当前代次标为无效。Vue keep-alive 或框架重排造成的“同一轮插入后立刻删除”因此不会留下过期挂载。

同名实例的四路分派

  • 隐藏且 URL 相同：恢复 keep-alive，不创建实例。
  • URL/SSR URL 相同，且旧实例已卸载或是核心配置一致的 prefetch：复用并挂载。
  • 旧实例仅 prefetch 或已卸载，但 URL 不同，或同 URL 下核心隔离配置不兼容：销毁旧实例后创建。
  • 同名实例仍活跃：记录冲突错误，拒绝覆盖。

源码摘录

资源系统：两条异步链，一个完成门禁

HTML 入口

HTMLLoader 先抓取入口，再运行“全局插件 → 应用插件”，最后把原生 head/body 改写为 micro-app-head/body。JS 入口会合成最小 HTML。

资源提取

extractSourceDom() 扫描 link/style/script/img。exclude 变注释占位；ignore 保留原生元素；相对 URL 基于应用入口补全。

缓存边界

远程 CSS/JS 原码按完整 URL 全局共享。应用相关 attrs、CSS 前缀、插件后代码、Function 缓存放进 appSpace[appName]。销毁只删当前应用内联脚本；远程缓存保留。

脚本执行分派

  • inline / module / iframe 特殊场景：创建真实 script 节点，交给浏览器执行。
  • 普通脚本：插件转换后绑定沙箱作用域，缓存 Function 并调用。
  • fiber：等待静态脚本全部下载后，按源顺序串行放入空闲任务。
  • 动态远程脚本：优先命中应用/全局缓存；否则抓取后执行，并向原节点模拟 load/error。
失败边界：单个 CSS/JS 请求失败由各自的 promiseStream 记录，整条链仍在最终回调结算；但 HTML 抓取失败、空 HTML 或缺少隔离 head/body 走另一条错误路径，不能据此声称“所有资源错误都能继续挂载”。

双沙箱：作用域代理与独立 realm

维度with 沙箱iframe 沙箱
全局对象CustomWindow + Proxy + with隐藏同源 iframe 的真实 Window realm
DOMdocument/window 补丁把查询和插入定向到应用容器iframe document 代理回宿主容器，Node/Element 也做桥接

with：隔离存储，宿主回退

iframe：等待真实 realm 稳定后再补丁

两者共享全局补丁引用计数：第一个活跃沙箱安装 DOM/history 补丁，最后一个停止时释放。这样不会因某个应用先卸载而破坏其他仍活跃应用。

副作用所有权

window/document 事件、定时器和数据监听通过 effect hook 记录、释放并在 UMD、keep-alive、预渲染恢复时重建。Worker 与 EventSource 不是这类快照：with 沙箱按应用登记它们，默认卸载或 destroy 时终止；可恢复的 UMD/keep-alive 阶段则保留。iframe 的同类资源还受 iframe realm 是否删除控制。destroy 才进入删除 iframe、内联脚本应用缓存和实例注册表的不可恢复清理。

路由闭环：内部 location、宿主 URL、history.state

模式宿主可见路径子应用 location 来源
search（默认）编码进 search 或 hash 查询段从编码路径恢复
state路径不变；写入 history.state.__MICRO_APP_STATE__从 state 快照恢复
native直接使用宿主路径origin 也指向宿主
native-scope直接使用宿主路径origin 映射到子应用
pure不更新宿主 URL只维护内部位置

子应用 history.pushState、location setter 或公开 router.push() 最终都要更新 microLocation；需要同步宿主时，再构造新 URL/state 并调用原生 history。浏览器回退则反向读取每个活跃应用路径，更新代理 location，派发子应用 popstate/hashchange。

宿主 popstate 监听器会过滤隐藏、预渲染和 onlyForBrowser 事件，再按容器的 router-event-delay 进入宏任务。这个异步边界让可能懒加载或卸载页面的基座先响应，之后才更新子应用 location。

守卫边界：URL/location 先更新，再写 router.current 并运行 beforeEach；守卫没有 next/return 协议，不能取消已经发生的导航。afterEach 被放入 idle callback。runGuards 没有 try/catch：前置异常同步向上传播，后置异常发生在空闲回调边界。

宿主框架在同 URL 上用新对象调用 replaceState 时，全局 history 补丁会保留已有 __MICRO_APP_STATE__；基座 History 调用完成后，再为仍活动但记录缺失的应用补回路由。补丁不能观察基座直接通过 location 发起的导航。

源码摘录

数据通信：微任务批处理，不是同步 EventEmitter

基座→子应用、子应用→基座使用不同内部事件名；全局数据使用 global 通道。同一同步栈连续 dispatch 会合并到 tempData，一个微任务只处理一次该事件，并按调用顺序保存每个 nextStep。只有整批被 force 或浅比较确认变化时，监听器与这些 nextStep 才会执行。

浅比较只比较顶层键数量和值引用。对象内部原地修改不会被检测；需要通知时使用 force API。子应用上行数据提交后，还会在根元素派发 datachange，把非 DOM 数据中心桥接到宿主事件。

源码事实

预取与预渲染：复用的前提是执行环境一致

  • level 1：加载 HTML/CSS/JS 原始资源。
  • level 2：进一步完成脚本插件处理与沙箱绑定准备。
  • level 3：在临时 <div prerender> 中强制 fiber 预渲染。

预取在 requestIdleCallback 后再等待配置延时，应用按数组顺序调用 preFetchAction。这里的“串行”边界要精确理解：合法应用覆写的 onLoad 在 CSS/JS 任一链首次结算时就 resolve，随后才调用原 onLoad；因此下一应用可以在前一应用尚未达到双屏障 2 时开始，不能把它描述成“逐个等待全部资源完成”。

最终元素挂载时，URL、CSS 隔离、沙箱开关和 iframe 类型一致才复用；不一致就销毁预取实例重建。

预渲染不把路由附加到宿主 URL，不向浏览器派发 popstate/hashchange，也不派发可见生命周期。转真实挂载时，先替换容器引用，再恢复副作用快照和积压事件。

测试边界：src/__tests__/prefetch.test.ts 覆盖参数分支和全局资源入缓存，ssr_env.test.ts 覆盖非浏览器错误；当前 src/__tests__ 没有直接断言 level 2 预编译、level 3 预渲染或上述“首条资源链即放行下一应用”的时序，这些结论来自生产源码。

阶段解释

  1. 连接代次先消除 DOM 框架造成的瞬时插入/移除。
  2. 同名注册表决定复用或创建，避免两个活跃实例共享隔离键。
  3. 资源链允许 CSS 与 JS 并行，但双屏障阻止半完成挂载。
  4. iframe ready 是显式异步边界；ready 后再次检查 !isUnmounted()。
  5. 脚本首次执行可能动态识别 UMD 模式；Promise mount 拒绝只记录错误，仍推进 mounted 收尾。

手工推演

三个关键算法

1. 资源双屏障

时刻动作loadSourceLevel结果
T0构造实例0进入 LOADING
T1JS 先下载完成，调用 onLoad1不挂载
T2CSS 与 fiber style 完成，调用 onLoad2写 source.html，进入挂载或预渲染

若顺序相反，结果相同。关键不变量不是“哪个先完成”，而是两条链各且仅结算一次。单个 CSS/JS 下载失败会记录错误，但 promise stream 最终回调仍让该链结算。

2. EventCenter 批处理

决定性源码见前文 EventCenter.enqueue/process 摘录。输入 dispatch({a:1})、dispatch({b:2})、dispatch({a:3}) 位于同一同步栈：第一次创建通道并把 force 置真；队列只有一个事件名，tempData 最终为 {a:3,b:2}。process 先交换队列，再提交快照、通知监听器和三次 nextStep。若是既存通道且整批浅比较无变化、也没有 force，则监听器和 nextStep 都不执行。监听器内重入 dispatch 会进入下一批，不污染当前 tempData。

3. Scoped CSS

解析器按 style rule、at-rule、comment 三类消费文本。普通选择器前加 micro-app[name=xxx]；body 改成 micro-app-body；:root/html 受 optionCss 策略控制；相对 url(...) 基于外链 CSS 文件目录补全。scopecss-disable 注释可全局、选择器级或下一行关闭改写。

输入逐步状态输出
body .mask, .card { background:url("../img/a.png") }
prefix=micro-app[name=demo]
linkPath=https://cdn.example/assets/css/main.css		 顶层逗号拆成两个选择器；body 分支替换根；普通 .card 加前缀；URL 基准改为外链 CSS 目录 micro-app[name=demo] micro-app-body .mask, micro-app[name=demo] .card { background:url("https://cdn.example/assets/img/a.png") }

复杂度从当前实现推断为近似线性游标扫描，但每条选择器与声明还会经历多轮正则替换；matchAllDeclarations 使用递归，极长或深嵌套声明还受调用栈限制。解析失败走日志与 reset，不让一个样式阻断应用资源屏障。

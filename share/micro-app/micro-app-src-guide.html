Mechanism first · src evidence only

一个 DOM 元素，如何变成完整微前端运行时

插入一个自定义元素后，micro-app 会下载和整理资源，选择沙箱执行子应用，再把路由、数据和动态 DOM 操作接回宿主。移除元素时，它还要决定哪些内容清理、哪些内容保留，才能支持普通重挂载、UMD 和 keep-alive。

结论、范围与证据基线

主线可以压缩成一句话：<micro-app> 决定“何时运行”，CreateApp 决定“运行到哪一步”，source 与 sandbox 决定“代码在哪里、以什么全局语义运行”。

控制面

MicroAppElement 把连接、断开和 name/url 变化路由到创建、复用、隐藏或卸载。

状态面

CreateApp 持有主状态、keep-alive 状态、资源进度、DOM 容器和 UMD 钩子。

执行面

source 解析与缓存资源；with/iframe 沙箱隔离全局对象，并记录可恢复副作用。

源码事实

核心对象与所有权

microApp

基座单例门面。持有全局配置、路由和数据中心 API；在受支持浏览器中，start() 的初始化门禁最多进入一次，重复调用报错。

MicroAppElement

每个宿主 DOM 节点一个控制器。持有连接代次、元素配置与未命名时的数据缓存。

CreateApp

每个应用名一个可复用运行实例。持有状态机、资源、容器、沙箱、UMD 钩子和预渲染队列。

appInstanceMap

当前模块实例的注册表。预取、隐藏、mounted、未销毁的 unmount 实例都可能继续存在；另一份 bundle 有自己的 Map。

sourceCenter

按完整 URL 共享原始 CSS/JS；按应用 appSpace 隔离属性、转换代码和函数缓存。

Sandbox

with 使用 Proxy 作用域；iframe 使用隐藏同源 realm（独立全局对象与内建原型）。两者统一提供 ready、start/stop 与副作用快照。

关键不变量：元素不是应用实例。移除元素可能只隐藏应用；销毁才从 appInstanceMap 删除。判断“应用是否存在”与“应用是否活跃”必须分开。
源码摘录

启动与 DOM 控制：先建立环境，再允许元素回调

MicroApp.start() 捕获原生全局引用、归一化配置、安排预加载，最后注册自定义元素。这个顺序重要：一旦 customElements.define() 完成，页面中已有元素可能立即升级并进入生命周期。

元素连接不是直接同步挂载。它先增加连接代次，再进入微任务；断开会把当前代次标为无效。Vue keep-alive 或框架重排造成的“同一轮插入后立刻删除”因此不会留下过期挂载。

同名实例的四路分派

  • 隐藏且 URL 相同：恢复 keep-alive，不创建实例。
  • URL/SSR URL 相同且旧实例已卸载：直接复用，不检查 scopecss/sandbox/iframe 是否变化。
  • URL 相同且核心配置一致的 prefetch：复用；同 URL 但配置不兼容的 prefetch，或 URL 不同的 prefetch/unmounted：销毁旧实例后创建。
  • 同名实例仍活跃：记录冲突错误，拒绝覆盖。
配置切换边界：sameCoreOptions 只保护 prefetch 复用。普通 unmount 后若仍使用同 URL，改变沙箱类型或 CSS 隔离不会触发重建；需要显式 destroy。
控制面补全

命令式 API：元素事件与实例直调共用一套应用状态

renderApp 创建元素，reload 调元素方法，活跃应用的 unmountApp 通过移除元素触发断开。预取、已卸载、隐藏实例则按状态直接调用 CreateApp、销毁或立即结算。因此公开 Promise 的完成点随分支变化：可能是元素事件、unmountcb，也可能是同步 resolve。

API入口分派Promise/返回边界保留与清理
renderApp(options)创建当前 tagName 元素；绑定 datachange/生命周期监听；其余配置交给元素 setAttribute，其中 data 由元素重写方法转发数据中心；最后 appendmounted → true，error → false不自动卸载；调用方仍需移除元素或调用卸载 API
reload(name, destroy?)找到实例宿主 → 元素 reload → disconnect → reconnect等待 mounted 或 aftershowisReloading 强制卸载阶段保留 data，完成后再下发旧快照
unmountApp(name, options)按 prefetch/unmounted、hidden、active 三类状态分派；只有 active 通过移除元素触发断开无实例为 false；其余等待 unmount/afterhidden/unmountcb，或同步结算 truedestroy 删除实例；clearAliveState 可把 hidden 变 UNMOUNT；clearData 只有进入真实 unmount + active sandbox release 时才生效
unmountAllApps对 Map 键快照做 Promise reduce按注册顺序串行；返回最后一次 unmountApp 的布尔值，空 Map 才由初值返回 true策略原样传给每个应用
getActiveApps过滤 UNMOUNT、纯预取及可选 hidden/prerender；LOADING、LOAD_FAILED 也可被列出返回当次名称数组，不能据此判断已经 mountedgetAllApps 则直接返回 Map 键，包括预取、hidden、未 destroy 的 UNMOUNT 实例
Promise 结算条件：非法 options/容器只记录日志并提前返回，没有 resolve/reject；name/url 校验失败若未派发 error，也不会结算。false 来自 error 事件，并不覆盖这些提前返回。反之，executor 中真正抛出的异常（如非法 CSS 容器选择器）会使 Promise 拒绝。

这里存在两套所有权：Map 决定“实例是否仍可找到”，app state 决定“是否活跃”。默认卸载只令实例进入 UNMOUNT；getActiveApps() 不再返回它，但 getAllApps() 仍会返回。完成 destroy 路径后才执行 appInstanceMap.delete(name)。

对照用例：create_app.test.ts · test unmountApp method 依次操作普通、已卸载和 hidden 实例，观察 destroy 与 clearAliveState 分支。事件、DOM 清空和实例删除发生在不同位置：宿主 unmount 事件先于 clearOptions，直接调用分支的 unmountcb 则在其后。

源码摘录

资源系统：两条异步链，一个完成门禁

HTML 入口

HTMLLoader 先抓取入口，再运行“全局插件 → 应用插件”，最后把原生 head/body 改写为 micro-app-head/body。JS 入口会合成最小 HTML。

资源提取

extractSourceDom() 扫描 link/style/script/img。exclude 变注释占位；ignore 保留原生元素；相对 URL 基于应用入口补全。样式链等待外链 CSS 与内联 style 隔离；脚本链在普通挂载中只准备同步脚本，defer/async 留到 execScripts 下载和执行。

缓存边界

远程 CSS/JS 原码按完整 URL 全局共享。应用相关 attrs、CSS 前缀、插件后代码、Function 缓存放进 appSpace[appName]。销毁只删当前应用内联脚本；远程缓存及该 name 的 appSpace 元数据都保留。

脚本执行分派

  • 应用/元素 inline、带 id 的特殊脚本，以及 iframe/关闭沙箱下的 module：创建真实 script 节点，交给浏览器执行。
  • 默认 With 沙箱中的 module：按 defer 调度，但不保留原生 module，仍走 scope 包装 + Function；裸 import/export 需 loader 预先转译。
  • 普通脚本：插件转换后绑定沙箱作用域，缓存 Function 并调用。
  • fiber：把静态脚本执行拆成空闲任务。同步脚本按资源 Set 登记顺序入队；defer/async 先并行补齐代码，整批请求结算后仍按登记顺序入队，所以 async 不按网络完成先后执行。原生外链 module 交给浏览器加载和求值。
  • 动态远程普通脚本未命中缓存：fetch Promise 链下载并执行，成功发原节点 load，下载或 Function 同步执行异常经 catch 转成 error。
  • 缓存命中的动态普通脚本：defer 微任务执行，成功才发 load；执行异常没有该 fetch catch，不会在这里转成原节点 error。
  • 原生外链 module：替代 script 交浏览器加载，本版只转发 load，没有对应 error 转发。真实 inline script 的浏览器求值异常也不能等同于 Function 同步 throw。

缓存不是请求去重器，也不是浏览器脚本列表

  • 无 in-flight Promise：资源项初次登记时 code === ''。两个应用并发遇到同 URL 都会各自 fetchSource；只有先完成并写入的文本能被后来者复用。
  • 同应用静态地址折叠：source.links/scripts 是 Set。同一 app 的重复远程 href/src 只调度一次；远程 script 不再像浏览器那样按重复标签执行多次。静态 inline 各有 nonce，动态 script 每次插入仍执行。
  • destroy 不清远程 appSpace：同名同 URL 新实例再次提取时使用 appSpace[name] ||= newData；第一次登记的 attrs、async/defer/module/inline/pure 与 parsed metadata 可能继续生效。缓存换来复用，也带来同名重建配置陈旧边界。

动态 DOM：节点归属先于资源分派

proxyDocument 创建节点时写 __MICRO_APP_NAME__；全局 Node 原型补丁在 append/insert 前读取该标记，找到实例并补全 URL。style、link、script 再走各自转换器，document.head/body 插入被重定向到应用容器。WeakMap 保存“调用方原节点 → 实际 style/script/comment”，让 remove/replace 仍能操作正确节点。

失败后的推进：单个 CSS 或由 fetchSource 管理的 JS 下载失败会记录错误，promiseStream 仍结算本链。iframe/关闭沙箱下的原生外链 module 不预抓取，真实 script 只有 onload、没有 onerror；加载失败时 moduleCount 可能不归零，普通模式的 mounted 收尾便会停住。HTML 空响应、结构缺失与 Promise 链抛错的差别见 异常表。

with：隔离存储，宿主回退

这段 Proxy 负责显式 window.x 等读写，但脚本包装的 with 对象是 proxyWindow.__MICRO_APP_WINDOW__，即独立的 microAppWindow，并非 Proxy 本身。source/scripts.ts · bindScope 把 window、document、location 等 GLOBAL_CACHED_KEY 成员读出，作为内层函数参数传入，函数 this 也绑定 proxyWindow。普通裸标识符按 with 对象和函数作用域查找；scopeProperties 会先在 microAppWindow 上置 undefined，遮住宿主同名全局。由此，显式窗口访问、缓存参数和未预置裸标识符各走不同查找路径。

iframe：等待真实 realm 稳定后再补丁

两者共享全局补丁引用计数：第一个活跃沙箱安装 DOM/history 补丁，最后一个停止时执行释放清单。这样不会因某个应用先卸载而破坏其他仍活跃应用。计数归零并不保证所有方法恢复：Document.createComment、DocumentFragment.append/prepend 和 Element.insertAdjacentElement 不在本版释放清单中。keep-alive 隐藏不停止沙箱，计数不变。

副作用所有权

副作用快照记录 window/document 与数据监听，UMD 重挂载、keep-alive 显示和预渲染转挂载时再重绑。With timer 只进入活动账本：默认卸载或 destroy 清除，UMD、keep-alive、预渲染期间继续运行；iframe effect 不跟踪 timer，删除 realm 才结束其定时器。Worker 与 EventSource 也不进快照：登记条件与清理分支见下一章。

所有权深挖

请求与副作用：两个沙箱，共用协议但不共用实现

沙箱不只决定变量写到哪个 window，还必须回答两个更难的问题：相对请求以谁为基准，以及卸载时谁负责撤销事件、timer、长连接和 Worker。With 沙箱靠包装器与显式账本；iframe 沙箱更多依赖独立 realm 和 <base> 的浏览器语义。

effect 不是一份“DOM 快照”

record：复制监听账本→ release：按账本尝试解绑→ rebuild：重新绑定并消费快照

recordAndReleaseEffect 根据模式先选 record 或 reset，再统一 release。UMD、keep-alive、prerender 需要恢复，所以记录 window/document/data listener；默认卸载和 destroy 不应恢复，所以清空旧快照。当前四套 window/document release 调用 removeEventListener 时没有带回注册时保存的 capture option：capture:true 监听可能仍绑定，但活动账本已被清空。data 缓存是否删除则由 clearData 单独控制。

timer清除 / 保持原生 timer 继续运行、不进入 snapshot / 清除effect 不跟踪 timer；默认与 destroy 通过删除 realm 终止，UMD/keep/prerender 保留 realm
EventSource请求补丁已登记的实例：默认/destroy 批量 close，UMD/keep 保留；原生/逃生实例未进此 Map，不经批量 close无应用级 EventSource Map；主要随 realm 删除或保留
WorkerWorkerProxy 仅在创建时存在 current appName 才登记；已登记项由沙箱 stop 的默认/destroy 路径终止。keep-alive 不 stop，UMD 软卸载保留；未经 WorkerProxy 或没有应用归属的 Worker 不进此 Map
数据 listener / datalistener 释放并可快照恢复；data 默认保留，只有真实 unmount 到达 active sandbox 的 releaseGlobalEffect(clearData) 才清双向缓存。直接 prefetch/unmounted 与 hidden no-op 分支可忽略 clearData
Proxy 注入键默认/destroy 删除 injected/escape keys；UMD 软卸载保留写入属于 iframe realm；删除 realm 即整体失效
恢复期间仍在运行的资源：UMD、keep-alive、prerender 保留 timer，UMD/keep-alive 还保留已登记的连接和 Worker。快照恢复重绑的是监听器，不会重新创建这些资源。禁用沙箱或从 rawWindow 创建的资源由应用自己的卸载逻辑管理。

iframe ready 与销毁边界

iframe 插入主 document 后，patchIframe 用 setTimeout(0) 轮询 document 身份；浏览器重建完成才 stop 初始页面并安装补丁。这个 Promise 没有超时、reject 或取消路径：自定义 iframeSrc 若持续不可访问，catch 后会继续轮询。已 start 的默认卸载/destroy 在 Promise 微任务中删除 iframe；ready 前卸载时，stop 因 inactive 返回，非空 container 又使 clearOptions 跳过补删。iframe 默认模式随后置空沙箱引用，此时 iframe 与轮询可能继续存在。

With 的补丁在构造器的 Promise executor 中同步装好，但 CreateApp.mount 仍经 sandboxReady.then 才进入实际挂载，所以 With 也有一个微任务边界；iframe 的 ready 则要额外等待文档重建。

路由闭环：内部 location、宿主 URL、history.state

模式宿主可见路径子应用 location 来源
search（默认）编码进 search 或 hash 查询段从编码路径恢复
state路径不变；写入 history.state.__MICRO_APP_STATE__从 state 快照恢复
native直接使用宿主路径origin 也指向宿主
native-scope直接使用宿主路径origin 映射到子应用
pure内部路由切换不更新宿主 URL维护内部位置；需真实 reload 的 location 导航另有一次性 state 传递

三类入口共享路径/state 合成工具，但通知时序不同。子应用 history.pushState/replaceState 在非 pure 模式先提交宿主 history，再同步更新 microLocation，不主动派发子应用 popstate。公开 router.push/replace 在 search 模式借宿主模拟 popstate 异步回流，其余模式直接更新并派发子应用事件。浏览器回退也从宿主记录恢复路径，再通知各活跃子应用。

因此，search 模式的 router.push() Promise 完成只表示沙箱已 ready、宿主导航已提交，子应用 location 更新与 popstate 仍在后面的宏任务中。需要读取新子路由的代码应跟随子应用事件，而不能仅依赖这个 Promise。pure 模式的公开 push/replace 跳过宿主 history；location 的 href/assign/search/pathname 若触发整页 reload，则会先把路径写入当前宿主条目的应用 state，供重载后初始化读取。

宿主 popstate 监听器会过滤已卸载、隐藏、预渲染和 onlyForBrowser 事件，再按容器的 router-event-delay 进入宏任务。这个异步边界让可能懒加载或卸载页面的基座先响应，之后才更新子应用 location；更新顺序固定为 microLocation → 子应用 popstate → hash 真变化时的 hashchange。

过滤发生在收到事件时，定时器执行时才重新从当时的 URL/state 读取路径，没有保存该事件的目标快照，也没有再次检查活跃状态。stop 解除 popstate 监听器会阻止新事件入队，已排入的定时器仍会执行。

守卫执行点：microLocation 提交新位置后，才写 router.current 并同步调用 beforeEach；需要同步宿主的路径此前也已提交 history。守卫没有 next/return 协议，不能取消导航。afterEach 在 idle callback 中执行；runGuards 不捕获异常，beforeEach 抛错还会跳过本次 afterEach 的安排。

宿主框架向同 URL 调用 pushState/replaceState 时，若明确传入 URL、旧 state 有 __MICRO_APP_STATE__ 而新 state 没有，补丁会合入旧应用快照。原 History 调用完成后，再为仍活动但记录缺失的应用补回路由。直接通过 location 导航不经过这个 History 包装器。

五种模式、反向 popstate 和卸载清理分别由 router/core.ts、router/event.ts、router/index.ts 的这些分支决定；当前测试目录没有独立 router 用例。

源码摘录

数据通信：微任务批处理，不是同步 EventEmitter

基座→子应用、子应用→基座使用不同内部事件名；全局数据使用 global 通道。先记两个槽位：data 是现在能读到的数据，tempData 是本轮等待提交的数据。已有通道的连续 dispatch 把新字段合并到 tempData；下一微任务 process 才更新 data 并通知监听器。同名事件只占一个队列位置，各次 nextStep 仍按顺序保留。

首次创建有一个例外：dispatch 自己创建通道时直接填入 data 并设 force，紧接着 getData 就能读到首份数据；通知仍等微任务。若通道已被 addDataListener 建好，仍走 tempData 的异步提交路径。

只有 force || !isEqual(data, tempData) 为真时，正常无同步异常时才按顺序执行监听器 → DOM datachange → 所有 nextStep。监听器返回的真值（转成布尔值为 true）进入 resArr；返回 Promise 也只作为一个值收集，不等待其完成。嵌套对象原地修改、整批没有变化时，普通通知和 nextStep 都会被跳过，需要通知可用 force API。clearData 只清已写入的 data，不取消 tempData 或排队任务，待提交数据仍可能在下一批写回来。

重入的准确范围：process 先换出队列与 nextStep 表，再逐个通道清空 tempData/force。监听器再次派发当前已消费通道时，新数据留给下一批；若派发的是本批尚未消费的另一通道，其共享 eventInfo 会先被当前批读到。具体输入与两次通知见 批处理推演。
同步抛错边界：同批队列为 A/B 时，若 A 的第一个 listener 抛错，A 的其余 listener、datachange、nextStep 和旧批次 B 都不再执行。process 已交换旧 queue/recordStep，没有自动重试旧批次；已提交的 A.data 也不回滚。可预期错误应由业务监听器自行捕获。这是 src/interact/event_center.ts · process 的直接分支；新增隔离验证见 学习验证，不是现有 Jest 浏览器测试的覆盖承诺。

预取与预渲染：复用的前提是执行环境一致

  • level 1：加载 HTML/CSS，并因“prefetch 且非 prerender”提前抓取包括 defer/async 在内的全部 JS 原码。
  • level 2：在 level 1 基础上执行插件与 bindScope；未进入 isInlineMode 的脚本还预编译 Function。
  • level 3：标记为 prerender，不走 level 2 预编译；双屏障后在临时 <div prerender> 中强制 fiber 挂载并真实执行脚本。

预取在 requestIdleCallback 后再等待配置延时，按数组顺序调用 preFetchAction。每个合法应用覆写的 onLoad 在样式/脚本任一链首次结算时就 resolve，随后才调用原 onLoad；onLoadError 也放行下一项。因此下一应用可能在前一应用尚未达到资源计数 2 时开始，更不会等待三级预渲染 mounted。preFetch() 返回 void，额外 timer 没有保存句柄，公开 API 不提供等待或取消入口。

尚为 prefetch 的实例在元素挂载时，URL、CSS 隔离、沙箱开关和 iframe 类型一致才复用；不一致就销毁重建。普通已卸载实例的同 URL 复用则不检查这些核心配置，见 实例分派。

预渲染执行脚本并产生真实 DOM，但先缓存 beforemount 和 mounted 收尾，不把路由附加到宿主 URL，也不向浏览器派发 popstate/hashchange。转真实挂载时，先把 DOM 移入真实容器并更新 container，再恢复快照、执行积压生命周期，最后解除 prerender 标记并把路由附加到宿主。脚本仍在 fiber 队列中时也可以转挂载，剩余脚本继续执行后按普通路径完成 mounted。

2. EventCenter 批处理

决定性源码见 EventCenter.enqueue/process 摘录。同一同步栈向同一新通道依次提交 {a:1}、{b:2}、{a:3}：首次同步写 data 并置 force，后两次合并 tempData，最终为 {a:3,b:2}。队列只有一个事件名，但保留三次 nextStep。微任务提交最终数据，依次通知监听器、DOM 数据事件和三次 nextStep。既存通道若整批浅比较无变化且没有 force，这些回调都跳过。

再看跨通道重入：同一批已排入 A、B，图中仅 A 监听器再向 B 提交一次，B 监听器和两组 nextStep 只记录结果。B 待提交 {value:1}；A 的监听器再向 B 提交 {value:2}。process 虽换出了队列，B 的 tempData 仍在共享 eventInfo 上，所以本批处理 B 时就读到 value=2，通知 B 监听器并执行旧 nextStep。新 dispatch 留下的 B 队列项在下一微任务再次被消费；此时 tempData 已清空，isEqual(data, null) 返回 false，于是再次通知 value=2，并执行新 nextStep。交换队列保证新步骤有自己的批次，却没有冻结所有通道的数据。

3. Scoped CSS

解析器按 style rule、at-rule、comment 三类消费文本。普通选择器前加 micro-app[name=xxx]，单独的 body 根映射为前缀下的 micro-app-body。根正则先于 body 分支：html body、html > body 含 html，整体保留；默认 :root 也保留，optionCss 的 isolation-root 仅使它改为“前缀 + :root”，没有替换成应用根。scopecss-disable 注释可以关闭全局、特定选择器或下一行改写。

选择器列表只先保护属性值中的逗号，再按其余逗号分段，并非完整 CSS 语法解析。:is(.a,.b) 这样的函数参数会被拆开并重复插入前缀，body :not(.a,.b) 也受同样影响。下例选用普通列表，展示它支持的 body 映射与 URL 补全。

仓库提供 verify-learning-boundaries.mjs。在 micro-app 目录运行 node docs/examples/verify-learning-boundaries.mjs；无需 npm 依赖，本轮使用 Node 24.19.0。脚本读取本地 TS、擦除类型，在受控环境中运行真实 EventCenter、CSSParser 与动态脚本调度函数。断言 A 抛错后 B 未通知且没有自动重排队、CSS 全局/按选择器/声明内禁用的 URL 差异、非缓存同步执行异常发 error 而缓存路径不发。

这是隔离算法验证：defer 改为可控队列，DOM、下载与 CSS URL 辅助函数使用范围明确的替身；不证明真实浏览器 module、全局补丁安装/释放或 catalog 组合应用端到端成功。测试输出不能替代浏览器回归。

断言对应的行为：mounted 回调能从活跃查询中找到应用，unmount 回调则已找不到，因为 unmount() 在派发该事件前先写了 UNMOUNT。活跃查询在 LOADING 阶段也可能包含应用，所以 mounted 断言并不表示它此刻才加入活跃列表。卸载回调用 defer 结算等待，后续代码才在当前清理调用栈结束后运行。

另外几个会影响行为的分支

  • source/patch.ts 在媒体元素 setAttribute 已调用原生方法之后，才检查 includeCrossOrigin。回调返回 true 时写入的是未在局部声明的 node.crossOrigin；若环境也没有同名全局变量，会在属性已经写入后抛出 ReferenceError。
  • source/scripts.ts · getExistParseResult() 只按相同 parsedCode 复用其他应用的 Function，适用于非 inline 的 With/关闭沙箱路径。正常 iframe 应用被强制设为 inline，走真实 script 节点，不进入这份 Function 缓存。
  • prefetch.ts 的额外延时通过未保存句柄的 setTimeout 安排；一旦进入该阶段，当前 src API 没有取消这批预取的路径。
  • UMD mount/unmount setter 收齐成对函数时立即触发识别；若较早的静态脚本已经导出 hooks，同步 mount 可在后续静态脚本执行前进入 MOUNTED。其余脚本仍按资源队列继续执行；需要先于 mount 的初始化应放在导出成对 hooks 之前。

#阅读边界

本章研究插件初步转换完成后，Vite 怎样理解源码中的 import 语义：先展开 import.meta.glob/变量动态 import，再由开发态 Import Analysis 解析 specifier、改写浏览器 URL、 注入 env/HMR runtime，并把依赖边写入 ModuleGraph。

普通 resolve 算法见第 07 章，ModuleGraph/软失效见第 08 章，HMR 更新传播见第 12 章。本章只解释 “源码如何产生正确 URL、依赖边与 HMR 边界”。构建态动态 import preload 由 importAnalysisBuild.ts 完成，留到生产构建章节。

读完应能回答：

  1. 为什么 import.meta.glob 和变量动态 import 必须早于主 Import Analysis？
  2. resolved ID 怎样变成 root URL、/@fs/ 或 /@id/？
  3. 非 JS/CSS 为何附加 ?import，CSS 本身为什么不需要？
  4. 同一文件里的 import 为什么并行 resolve，却仍用按源码索引的数组收集结果？
  5. 字面量动态 import、模板变量 import 和不可分析表达式分别走哪条分支？
  6. @vite-ignore 抑制了什么，又没有替用户完成什么？
  7. import.meta.hot.accept/acceptExports 怎样变成模块图边界？
  8. optimizer 已把 CJS 转换过，为何 Import Analysis 仍可能补 named import interop？
  9. glob 的文件新增/删除为何也能触发 HMR？

#推荐阅读顺序

  1. plugins/index.ts：确认 importGlobPlugin、dynamicImportVarsPlugin、importAnalysisPlugin 顺序。
  2. importMetaGlob.ts 的 parseImportGlob() 与 transformGlobImport()。
  3. dynamicImportVars.ts 的 transformDynamicImport() 与运行时 helper。
  4. importAnalysis.ts 文件头的 URL helper 和插件总注释。
  5. transform() 中 es-module-lexer 解析、normalizeUrl() 与并行 import 循环。
  6. 同循环的 HMR/env/dynamic import/CJS interop 分支。
  7. 循环后的 runtime 注入与 moduleGraph.updateModuleInfo()。
  8. transformCjsImport()：最后单独理解 CJS 兼容，不要让它打断 URL 主线。
  9. glob/动态 import/CJS 三组单元测试与 dynamic-import playground。

#三段式调用链

前两步把可枚举的动态语法变成普通 imports，主分析器才能把每个候选模块写入图。无法枚举的表达式 保留到运行时，并由主分析器选择警告/?import helper。

bundled Environment 中 glob 与变量 import 委托 Rolldown 原生插件；unbundled Environment 使用 TypeScript 实现以支持开发态 HMR 文件 matcher。两边目标语义相同，但不要误以为主 vite:import-analysis 也在构建时运行。

#parser 为什么要词法定位后再 AST 校验

stripLiteral() 先屏蔽字符串/注释中的伪调用，正则快速找到 import.meta.glob(；随后只对单个调用 片段做 AST 解析，验证：

  • 1–2 个参数；
  • pattern 是字符串、无插值模板或它们的数组；
  • 第二参数是可静态求值对象；
  • option key/type 合法；
  • base 以 /、./、../ 开始，不能是否定 pattern。

动态变量不能作为 glob 参数，因为 Vite 必须在变换时枚举完整文件集。代码本身若不是合法 JS，glob 快路径不抢先报错，交给后续语言插件/Import Analysis 给出更准确诊断。

寻找闭括号不是简单 indexOf：选项对象或表达式中可能有嵌套括号；字符串/注释已经被 stripLiteral 屏蔽，因此计数剩余括号即可。

#pattern、import path 与对象 key

三者身份不同：

/ pattern 相对项目 root；.//../ 相对 importer 或显式 base；裸 pattern 可经 alias/package imports resolver。resolver 返回路径中的 [、( 等 glob 字符必须转义，但用户声明的 * 动态后缀 要保留，所以 globSafeResolvedPath() 从末尾找共同后缀，只转义静态前缀。含括号路径的变量 import 相关修复见 PR #17940。

虚拟模块没有可靠磁盘 dirname，因此相对 glob 无法定义，必须用 root 绝对 pattern 或显式 base。 即使 pattern 当前零命中也必须报错，不能因结果 {} 而隐藏非法语义；见 PR #22497。

#选项如何改变生成代码

选项 作用
eager 静态 import，而非返回 import() 的函数
import 只取指定 named/default export
query 给每个 import specifier 拼资源 query
base 改变枚举基准和暴露 key，不改变模块真实文件
exhaustive 包含 dot files/node_modules，不应用默认忽略
caseSensitive 同时控制枚举和开发态 HMR matcher

旧 as:'raw'/'url' 被规范成 query + default import，并给迁移警告。query 对象先经 stringifyQuery 变 字符串；importGlobRestoreExtension 可为 query 补 lang.<ext>，让下游插件恢复原扩展名语义。

Object.keys(import.meta.glob(...)) 不观察 value，因此只生成 key/0 对象，不生成真实 imports； Object.values 则省略 key。这个优化减少扫描与 bundle 体积，同时保持调用结果。

文件 create/delete 时不一定已有 ModuleNode，普通文件→节点索引找不到受影响模块。hotUpdate 反向用 matcher 检查新/删文件，把声明该 glob 的 importer 加入更新集合。正 pattern、负 pattern、 dot/node_modules、caseSensitive 选项必须与 tinyglobby 枚举完全一致；否则初次结果与 HMR 结果漂移。 数组否定 pattern 修复见 PR #20872，caseSensitive matcher 对齐见 PR #22711。

#resolved ID 到浏览器 URL

normalizeUrl() 先 resolve，再用 normalizeResolvedIdToUrl() 选择公开协议：

transform 中间件收到 /@id/ 后会 unwrap，再把原 ID 交给插件。/@fs/ 则让浏览器可表达绝对路径， 同时仍受 server.fs 控制。

client 还要做：

  1. 非 JS/CSS 资源加 ?import；
  2. 相对 JS/CSS 和同文件虚拟子模块继承 optimizer version；
  3. 已 HMR 更新的依赖加 ?t=；
  4. 最后补公开 base。

?import 是“把资源作为模块处理”的协议，不是任意 cache buster。CSS import 不加它，因为 CSS 插件根据非 direct 请求自然返回 JS 注入模块；<link> 则由 HTML/CSS 管线显式形成 direct 身份。

SSR 不补浏览器 base，不重写 external/builtin，缺失 external 留给 Node/Module Runner；但本地依赖 仍 resolve 并入 server Environment 的独立模块图。

#并行 resolve，稳定收集

一个文件可有大量 imports，插件用 Promise.all(imports.map(...)) 并行 resolve。但每项结果写入以 lexer index 分配的槽位：

最后再按数组顺序 filter/merge。若直接在异步任务完成时 push，网络/文件系统时序会改变集合顺序， 导致调试输出、HMR 边与结果不稳定。顺序修复见 PR #14465，并行优化见 PR #12754。

escaped specifier 使用 lexer 的 .n 解码值解析，MagicString 仍用原始位置覆盖；否则 import './foo\\ bar.js' 一类路径会解析错误，早期修复见 PR #2162。

#动态 import 的三类结果

@vite-ignore 表示“这是有意的运行时 import”，只抑制警告/静态展开，不保证目标会被打进 bundle， 也不保证 bundled dev 能服务项目源码。dynamic-import playground 对 bundled dev 跳过源码直取，正是 这个真实缺口（#23028），不能把 skip 误读成能力已支持。

__vite__injectQuery 只给 .// 路径加 query，协议/裸包原样保留；手工处理 pathname 是为了保留 ../ 相对语义。classic worker 不能 prepend ESM import，所以直接内联 helper 函数体。

#import.meta.env 与 import.meta.hot

只有 lexer 实际看到 .env/.hot 才注入 runtime，避免所有模块膨胀。

import.meta.env 在开发态变成当前 Environment 的对象赋值；client/SSR 仅 SSR 布尔值不同，用户 define['import.meta.env.*'] 合并进去。classic worker 不是 ESM，不能注入。

import.meta.hot 会 prepend：

词法 helper 同时提取：

  • accept() 无参数 → self accepting；
  • accept('./dep') → acceptedHmrDeps；
  • acceptExports(['foo']) → acceptedHmrExports；
  • 接受全部实际 exports → 实践上升级为 self accepting。

accept URL 必须再走与 import 相同的 resolve，并改写成 ModuleGraph 中节点的规范 URL。解析失败时 不能用历史 fallback 猜路径；相关简化见 PR #21382。

实验性 partial accept 还记录每个依赖使用的 binding。namespace、dynamic import 与 import.meta 记 为 *；named/default 静态 import 可精确记录。第 12 章会解释它如何缩小更新传播。

#优化 CJS 的二次互操作

optimizer 通常已把 CJS 变成浏览器 ESM，但两类输入仍需 Import Analysis 补桥接：

  1. 优化入口需要 named/default/namespace 语义对齐；
  2. 其他插件向优化文件注入的新 import 不属于 optimizer 原始输出 （PR #23029）。

内部 chunk-XXXXXXXX.js 已是 optimizer 标准格式，不再 interop。动态 import 改成 .then() 包装 namespace；静态 import/export 改成唯一默认导入和属性赋值：

Node mode 与 Web mode 的 default 选择不同。生成赋值插到 shebang/directive 后的安全文件起点， 多条同 ID import 用 importIndex 避免变量冲突。改写补回原换行数，维持 Source Map 行号。

export * from CJS 无法静态枚举且不支持动态重赋值，只能警告并保留 URL 改写；named re-export 则生成内部变量后重新 export。单元快照逐一锁住这些语义。

#建议断点

  1. parseImportGlob：观察 stripLiteral 后 match 与 AST 参数范围。
  2. transformGlobImport：比较 globsResolved、importPath、filePath。
  3. hotUpdate：新增一个匹配文件，看无 ModuleNode 的新文件如何反向找到 importer。
  4. transformDynamicImport：比较 userPattern、rawPattern 和 query params。
  5. importAnalysisPlugin.transform：记录 lexer 的 s/e/ss/se/d/a/n 字段。
  6. normalizeUrl：分别导入 root 文件、root 外文件、裸包、虚拟模块与资源。
  7. 并行循环结束后比较 orderedImportedUrls 和 importedUrls。
  8. updateModuleInfo：删除最后一个 import，观察 prunedImports。
  9. transformCjsImport：对 named/default/namespace/re-export 比较生成代码。

纯注释任务不需要运行测试。以后若修改异步收集算法，可用两个故意延迟不同时间的 resolve hook 验证最终 importedUrls 仍按源码顺序；这是对“并行执行、索引归位”思路的最小实验。

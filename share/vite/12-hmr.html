12. HMR

HMR 从 watcher 经插件与图传播生成 update 或 reload，再由客户端执行 dispose、import、accept。

证据基线：v8.2.1commit 421615865dad约 30 分钟查看 Markdown 原稿

本页重点

HMR 从 watcher 经插件与图传播生成 update 或 reload，再由客户端执行 dispose、import、accept。

推导边界

WebSocket 只是 transport；找到接受边界也不保证循环、死端或执行错误绝不 reload。

证据口径

正文保留目标版本中的真实源码、状态说明与代表性测试映射。测试源码用于锁定设计契约；本轮没有执行测试命令。

#阅读边界

本章研究普通 unbundled 开发模式下，一次文件变化怎样从 watcher 事件变成浏览器中的局部模块替换：

模块图节点和失效状态见第 08 章，Import Analysis 怎样写入 acceptedHmrDeps、 acceptedHmrExports、importedBindings 见第 10 章。本章从这些图数据出发，解释传播与运行时生命周期。

实验性的 bundledDev 会让客户端根据 changedIds 自行计算边界，走 bundledDevHmrClient.ts/server/bundledDev.ts 的另一套协议；本章先完成普通按模块 URL 更新主线， 再单列一节对照 bundled-dev，避免混读。Module Runner 的服务端 HMR 执行器留到第 15 章。

读完应能回答：

  1. self accept、dependency accept、acceptExports 各在哪个节点停止传播？
  2. 为什么文件变化后要先使模块图失效，再让客户端重新 import？
  3. 一个没有 importer 的模块为何通常是 full reload 死端，但 acceptExports 模块可以例外？
  4. path 与 acceptedPath 在 update payload 中分别代表谁？
  5. 为什么循环 import 内找到了 accept 边界，客户端仍可能需要 reload？
  6. import.meta.hot.invalidate() 为什么会产生第二轮服务端传播？
  7. dispose、prune、hot.data 的生命周期有何区别？
  8. 同一文件变化产生的多个 update 为什么并行 fetch、串行执行 callback？
  9. HMR WebSocket 为什么同时校验 allowedHosts、Origin token，却允许 vite-ping 无 token？
  10. HTML、<link> CSS、JS import CSS 分别怎样更新？
  11. bundled-dev 为什么改由浏览器按实际执行图寻找 boundary？
  12. ErrorOverlay 如何避免 CSP、应用 CSS、恶意错误文本和非 DOM realm 的影响？

#三层协议不要混读

HMR 可以拆成三个相对独立的层次：

server/hmr.ts 不执行用户模块；shared/hmr.ts 不推导模块图边界；ws.ts 更不理解 accept 语义。按这 三层阅读，可以避免把网络重连、传播算法和模块生命周期搅在一起。

#Import Analysis 给 HMR 留下什么数据

每次模块转换后，Import Analysis 把以下信息写进 EnvironmentModuleNode：

字段 来源 传播用途
isSelfAccepting hot.accept()/CSS 当前节点直接成为边界
acceptedHmrDeps hot.accept('./dep', cb) importer 接受特定直接依赖
acceptedHmrExports hot.acceptExports(['foo']) 判断部分导出能否停止传播
importedBindings importer 实际导入的 named bindings 与 accepted exports 做集合比较
importers 普通 import 反向边 从变更模块向上遍历
lastHMRTimestamp 模块图 invalidate/prune 给重新获取的 URL 加 ?t=

isSelfAccepting === undefined 很重要：它表示该模块还没经过 Import Analysis，通常也没在浏览器加载。 传播此时停止且不 reload，不能把“未分析”当成“明确不接受”。这个边界来自 Issue #7561。

#文件事件总入口

handleHMRUpdate(type, file, server) 先处理几类全局特例：

  • Vite 配置、配置依赖或当前 mode 的 env 文件：重启 server；
  • @vite/client 自身：所有 Environment full reload；
  • 普通 HTML 但模块图无节点：client 定向页面 reload；
  • 其他 watcher 文件：按每个 Environment 查 getModulesByFile(file)。

create 事件会额外把 _hasResolveFailedErrorModules 加入候选。新文件可能正好修复此前失败的 import；若 只按“新文件当前对应的节点”查询，失败模块根本不会重新 transform。

函数进入时保存 server.environments 快照。任一插件 hook 都可能调用 server.restart()，await 返回后 若快照已被替换，本次事务立即停止，不向新 Environment 发送旧模块图结果。这个竞态修复见 PR #22992。

#插件怎样参与更新

新 API plugin.hotUpdate(options) 在每个 Environment 独立运行：

hook 返回模块数组时，会替换后续传播起点。插件可以：

  • 过滤普通模块；
  • 把一个真实 watch file 映射到虚拟模块；
  • 返回额外受影响模块；
  • 自行发送 custom/full-reload 后返回空数组。

旧 handleHotUpdate 只在 update 事件执行，并通过 mixed module graph 同时表达 client/SSR 节点。兼容 期间 client 新 hook 的过滤结果会同步回 mixed context，再把旧 hook 结果映射回各 Environment；这段 复杂桥接是迁移代码，不是新 API 推荐的数据模型。hotUpdate 支持可从提交 ba77cee60 和 fc1d72654 继续追踪。

默认所有 Environment 的传播并行运行；server.hotUpdateEnvironments 可接管环境选择与调度顺序。

#3. acceptExports

acceptExports 是“有条件的自接受”。模块先成为自身边界，但每个 importer 仍要检查：

若实际使用的 bindings 全被接受，该 importer 分支停止；只要使用一个未接受导出，就继续向上传播。 side-effect import 的 binding 集为空，因此自然满足子集关系。namespace import 与动态 import 无法安全 证明只使用部分导出，通常按使用全集处理。

acceptExports 最初以 partial accept 实验能力进入，见 PR #7324。它不是 tree-shaking：判断依据是开发态导入语法和 模块图记录，不分析任意运行时代码对 namespace 的属性访问。

#4. 死端

以下任一分支会要求 full reload：

  • 未接受模块没有 importer，已到图根；
  • HTML 是顶层页面模板；
  • hot.invalidate() 在同一轮闭合回 firstInvalidatedBy；
  • 任一 importer 链递归返回死端。

多个变更模块合并处理时，只要一条路径需要 reload，最终就发送 full-reload；已收集的精确 updates 不再 单独发送，避免页面先局部替换又立刻刷新。

#遍历去重与路径状态

traversedModules 是整轮共享集合，避免菱形图重复遍历；currentChain 是当前 DFS 路径，用来避免递归 环并诊断循环 import。边界列表保留 boundary + acceptedVia，同一边界接受不同依赖时仍可生成不同 update。

#循环 import 为什么特殊

ESM 循环依赖的值和副作用依赖首次求值顺序。普通 dynamic import 带时间戳只能重新执行局部模块，无法 可靠重建整条循环的初始顺序。

找到 accept 边界后，isNodeWithinCircularImports() 从边界继续沿 importers 搜索；若重新遇到从原 变更节点走到边界的 nodeChain 中节点，就标记 isWithinCircularImport。例如：

服务端仍发送精确 update，让简单循环有机会成功；浏览器重新 import 若失败，importUpdatedModule() 的 catch 会解释原因并 reload，恢复执行顺序。循环检测改进见 PR #14867。

这不同于 invalidate 循环。后者会持续发起下一轮 HMR，必须在服务端识别并直接 full reload；无限循环 修复见 PR #19870。

#invalidate() 是第二轮传播

模块在 accept callback 或执行阶段发现自己无法安全接管更新时调用：

HMRContext 向本地事件监听器和服务端都发送 vite:invalidate，payload 记录：

  • path：当前模块；
  • message：诊断原因；
  • firstInvalidatedBy：整条 invalidate 链的最初模块。

服务端重新以该模块为起点调用 updateModules()，从 importer 继续寻找更高边界。firstInvalidatedBy 在 回调执行期间由 HMRClient 暂存，后续 invalidate 才能继承同一根；事务结束后必须清空。

多标签页会同时对同一个更新发送 invalidate，服务端按同一轮身份去重，否则 parent 会更新两次。

#客户端为什么分“获取”和“执行”两阶段

HMRClient.queueUpdate() 把同一 microtask 内收到的 updates 先全部交给 fetchUpdate()：

重新获取可以并行，减少网络等待；accept callbacks 必须保持服务端顺序，否则 HTTP 往返快慢会改变模块 副作用顺序。更外层 createHMRHandler() 又把完整 HotPayload 串行化，因为一次 invalidate 可能在当前 payload 处理过程中触发下一轮更新。这个竞态修复见 PR #19793。

合格 callback 必须在重新 import 前固定：新模块执行会创建新 HMRContext，清空旧 callbacks 并登记 新一代回调；若 import 后才筛选，就会错误调用新代码的 callback 处理旧更新。

代码分割分支可能在服务端模块图存在，但当前页面尚未加载，hotModulesMap 找不到 path 时静默跳过；见 Issue #721。

#HMRContext 生命周期

每次模块执行都会调用 createHotContext(ownerPath) 创建新 context：

  • dispose 是“当前实例即将被替换或移除”；可写 data 交给下一代。
  • prune 是“模块已没有 importer，不再属于当前运行图”；用于最终撤销样式、事件等副作用。
  • data 在普通更新中保留，在 prune 后必须删除；否则未来重新导入会继承已结束生命周期的状态。修复见 PR #23002。

prune callbacks 需要全部 await 完成，下一轮 HMR 才可开始，否则旧副作用清理会与新模块执行交错；见 PR #20698。即使模块本身不是 self-accepting，删除其 import 边也要触发 prune；相关修复见 PR #20768 和 PR #21093。

#两轮传播的决定性源码

#入口与第一轮：静态声明先把 child 选成边界

watcher 收到本次 change 后，server/index.ts::onFileChange() 的当前实现顺序是：等待所有 Environment 的 pluginContainer.watchChange，调用各自 moduleGraph.onFileChange(file) 清旧转换结果，再进入 onHMRUpdate。这说明本版本实际采用的顺序，不单独证明任何其他排列必然错误。图失效清 transform/ETag/SSR 结果，但保留 ModuleNode、importer 边和最近一次成功分析留下的 accept 状态。

server/hmr.ts::propagateUpdate() 首先命中 child 的 self-accept 分支：

因此第一轮 boundary === acceptedVia === child，updateModules() 生成 path=acceptedPath=/invalidation/child.js 的 js-update，并用本轮 timestamp 失效 child 及受影响 importer。服务端此时只读取静态 accept 声明，不执行 callback，也不知道它随后会调用 invalidate()。

客户端处理第一轮时，HMRClient.fetchUpdate() 先冻结 child 的旧 callback，执行 dispose，再 import 带 timestamp 的新 child。新模块执行会创建新 HMRContext、登记下一代 callback；提交 closure 执行的仍是 import 前冻结的旧 callback。

#第二轮：服务端去重，并从 child 的 importers 继续

DevEnvironment.invalidateModule() 不把 child 再当边界，而是把它的 importers 交给 updateModules()。来源：packages/vite/src/node/server/environment.ts：

本例的新起点是 child.importers = { parent }。parent self-accept，于是第二个 payload 为 path=acceptedPath=/invalidation/parent.js，沿用 child 的 lastHMRTimestamp，并携带 firstInvalidatedBy=/invalidation/child.js。lastHMRInvalidationReceived 只允许第一个客户端上报启动 这轮传播；下一次真实 HMR 失效会把它重置为 false。

若 child 已是图根，importers 为空，updateModules() 会 full reload；若新边界又闭合到 firstInvalidatedBy，也会以 circular import invalidate 退回刷新。这些是同一入口的保护分支，不是本 fixture 的实际结果。

#accept 参数为什么用轻量 lexer

服务端只需要从以下受限语法中提取字面量：

lexAcceptedHmrDeps() 从调用左括号后开始，用 call/array/string/template 几个状态扫描。依赖参数只允许 字符串或字符串数组，所以没必要为整个模块再跑一次重型 AST parser。无参数或首参是 callback 返回 selfAccepts=true；模板含 ${} 直接报错，因为依赖路径必须静态确定。

lexer 同时记录每个字符串的源码 start/end，Import Analysis 随后 resolve 并改写 URL。acceptExports 复用同一个 lexer，只把字符串收集为 export name。

#HotPayload 协议

普通开发模式的重要 payload：

type 服务端含义 客户端动作
connected WS 握手成功 标记连接完成
update 一个或多个 JS/CSS 传播边界 queueUpdate 或替换 link
full-reload 无安全边界、HTML/config 等全局变化 定向或整页 reload
prune 路径已脱离图 dispose → prune → 删除 data
error transform/plugin 错误 overlay 或 console
custom 用户事件、invalidate、invoke、生命周期 分发自定义 listener
ping transport 保活 无业务动作

实验 bundledDev 的 bundled-dev-update 不携带普通 boundaries，而是发送 changedIds、客户端专属 patch URL 和序号；不要用普通 Update.path/acceptedPath 心智解释它。

#HotChannel：算法与传输的隔离层

HotChannel 允许 HMR 运行在：

  • 默认 WebSocket；
  • 用户自定义 channel；
  • Environment/Module Runner 的进程内 EventEmitter transport。

normalizeHotChannel() 统一：

  • send(payload) 与 send(event, data) 两种调用；
  • 单客户端 send 包装；
  • on/off listener 身份映射；
  • vite:invoke 请求/响应 RPC；
  • HMR 禁用时仍允许 connected/ping/custom/error 通过。

进程内 createServerHotChannel() 设置 skipFsCheck=true，因为 transport 不暴露到网络；网络 channel 不得 随意开启，否则远程客户端可借 fetchModule 读取受限文件。

#WebSocket 安全与生命周期

默认 WS 可以复用 Vite 主 HTTP server、挂到 server.ws.server，或在 middleware 模式创建独立 HTTP(S) server。

浏览器连接需依次满足：

  1. protocol/path 是 vite-hmr 对应地址；
  2. Host 通过 server.allowedHosts；
  3. 带 Origin 的浏览器请求提供本进程生成的 token；
  4. token 用 timingSafeEqual 比较，并且必须在 handleUpgrade() 前校验。

这防止恶意网页连接本机开发服务器实施 Cross-site WebSocket hijacking。token 校验相关安全修复可从 提交 029dcd6d7 追溯。

无 Origin 的 CLI/本地工具为兼容可无 token 连接；它们不受浏览器同源策略限制，本来就能发普通 HTTP 请求。

vite-ping 是特殊探测协议：允许任意来源，握手后立即正常关闭，不进入 clients，也不收发有意义 payload。客户端断线后先用 ping 确认 server 已重新可用，再 reload 获取新 @vite/client。这个策略 避免盲目 HTTP 轮询，见 PR #17891。SharedWorker 会合并同源 多窗口的探测，并在页面全部隐藏时暂停轮询；见 PR #19057。

重启时若旧 WS upgrade listener 不从用户 server 移除，它会继续吞掉新连接。close 因而不仅 terminate clients，还要解绑 listener，并关闭独立 HTTP server。

#浏览器消息处理细节

#error overlay 的首次更新

页面打开时若嵌套模块 transform 返回 500，入口模块根本没执行，页面虽有 overlay，却没有任何 accept 回调。第一次 update 到来时普通 HMR 不可能修复这条未建立的执行图，所以 client 先 full reload；新页面 重新加载整个入口。

#<link> CSS

只有 HTML <link> 直接引用的 CSS 收到 css-update。client 根据规范化 URL 找旧 link，克隆并附加 ?t=，等新 link load/error 后才移除旧节点，避免样式空窗导致 FOUC。由 JS import 的 CSS 会生成自接受 JS 模块，走普通 js-update 和 updateStyle()。

SSR 已注入的 style[data-vite-dev-id]/link[data-vite-dev-id] 在 client 启动时收集复用，防止第一次 HMR 插入重复样式。相关修复见 PR #20767。

#HTML 定向 reload

服务端对单个 HTML 变化发送其 root 相对 path。客户端只有当前 location 正好对应该 HTML、根 index.html 或目录形式 index 时才 reload，避免多页面应用所有标签页一起刷新。middlewareMode 无法 可靠推断页面路由时，服务端使用 *。

#无客户端时缓冲

页面 reload 期间 transform 可能立刻失败，error payload 早于新 WS 建立；优化器也可能在连接前要求 reload。WS server 因此在 clients 为空时缓冲最后一个 error/full-reload，新连接收到 connected 后立即 补发。普通 update 不缓冲，因为新页面会重新构建模块图状态。

#ErrorOverlay 的隔离与安全边界

overlay.ts 没有把服务端错误拼成 innerHTML，而是用 document.createElement() 与 TextNode 构造 Shadow DOM。这样同时解决：

  • 用户源码、插件名或堆栈中的 HTML 只能显示为文本，不能注入 DOM；
  • Shadow DOM 隔离应用 CSS，避免浮层被全局 reset 隐藏，见 PR #9971；
  • style 继承 meta[property=csp-nonce]，通过严格 CSP，见 PR #20791；
  • module 在 Worker/SSR realm 求值时，缺少 document、HTMLElement、customElements 也不抛错，相关修复见 PR #16318 与 PR #4856。

构造时把 message 中的 code frame 拆到独立区域；全局正则每次必须重置 lastIndex，否则第二个错误会 漏判，见 PR #11132。stack 中匹配到的 POSIX、Windows 或 file URL 位置才转成 <a>；点击后请求 ${base}__open-in-editor?file=...。base、自定义后端与 file URL 兼容分别见 PR #11337、 PR #14879 和 PR #20040。

点击 window 内部会停止冒泡；点击 backdrop 或按 Escape 调用 close()。close 不只移除元素，还注销 document keydown listener，避免多轮 transform error 累积全局监听。

#Forward Console：复用 HMR transport 的诊断通道

server.forwardConsole 启用后，客户端 setupForwardConsoleHandler() 包装指定 console 方法，并可监听 window error/unhandledrejection：

原 console 方法总是先同步执行，再异步发送；开发服务器断开不能吞掉浏览器本地日志。包装前保存原始 console.error，发送失败时用它回落，防止报告错误又递归进入 forward handler。client 早于 transport.connect 产生 SendBeforeConnectError 是正常启动竞态，静默忽略；其他发送错误必须显示。发送失败处理见 PR #22450，功能最初见 PR #20916。

formatter 支持 %s/%d/%i/%f/%j/%o/%O/%c/%%，并为 BigInt、Symbol、函数、Error、嵌套 Error 与循环对象 提供稳定文本。%j 遇到循环返回 [Circular]，不能让一次 console.log 破坏整个 HMR 消息链。

服务端必须使用消息所属 Environment 的 moduleGraph、root 与 logger。堆栈 id 查询依次尝试：

  1. 原 id；
  2. 相对 root 还原的磁盘路径；
  3. 浏览器（尤其 Safari）丢失 query 时，该 file 对应的第一个模块 id。

transformResult 没有内联 map 时，再从预构建依赖产物末尾读取外置 sourcemap。映射后展示完整帧列表，但 只给“第一个属于 Vite 图、已 transform 且磁盘存在”的帧展开 code frame；这样依赖调用链仍可见，终端 又不会被每一帧的源码淹没。

playground/forward-console 验证普通 error、Promise rejection、console 格式符与依赖外置 map。依赖报错 应保留 node_modules 帧，但 code frame 选择最近的项目源码调用点。

#Bundled-dev：边界算法移到浏览器

本节只建立普通 HMR 与 bundled-dev 的对照坐标。Rolldown 后台整包、首屏 fallback、内存文件、lazy payload 交付确认、浏览器执行图、单次 reload 门闩与关闭链，见独立章节 12B：Bundled Dev。

普通 HMR 的服务端 ModuleGraph 知道每个 URL 的 importer 和 accept；bundled-dev 真正执行的是 Rolldown runtime 中的模块 factory，浏览器才知道哪些模块已执行。因此服务端只推送：

BundledDevHMRClient.computeHmrUpdate() 在 runtime 图中从 changed id 向已执行 importer 冒泡：

每轮同时收集 updateSet：从 changed module 到 boundary 之间的全部模块都要清缓存。应用顺序不能交换：

  1. 确认 updateSet 的新 factory 全部存在；
  2. 在删缓存前冻结 accept callbacks；
  3. 清除 updateSet 缓存，runtime hook 同步执行 dispose；
  4. 初始化 acceptedVia 并读取新 exports；
  5. 调用 boundary callback，最后发送 afterUpdate。

push 与模块主动 hot.invalidate() 共用 applyQueue 串行执行。push 先校验 seq，缺号说明某个 patch 已 丢失，只能 reload；invalidate 没有服务端 rebuild，因此从当前 importers 开始，用 runtime 已有 factory 重新计算边界。

客户端决定需要 full reload 时不直接调用 location.reload()，只发 vite:bundled-dev:reload-needed。服务端等新完整 bundle 可服务后再发 full-reload，页面因此不会先加载 fallback 再二次导航；见 PR #23106。浏览器侧 HMR 主体由 PR #22961 引入。

服务端 BundledDev 同时维护四类状态：

状态 用途
memoryFiles 当前完整输出、HMR patch、sourcemap 与客户端 runtime
pendingPayloadFilenames 已生成但 HTTP 响应尚未确认送达的 payload
fullReloadPending 所有客户端等待最新完整输出后 reload
reloadNeededClientIds 只有计算出死端的特定客户端等待 reload

Rolldown 回调的时序是关键：onHmrUpdates 决定 patch 或刷新意图，onOutput 才表示新完整 bundle 已经写入 内存。刷新必须后置到 onOutput；若 HMR 生成阶段失败，下一次页面访问会强制 full build，提供自愈通道。 新连接客户端会立即收到缓存的最后一次构建错误，否则它可能只看到空白页面。

MemoryFiles 支持惰性值：构建回调先保存读取函数，浏览器首次请求时才提取 code/source 并计算 ETag。 增量构建不能清空整个 Map，因为未变化文件会被 Rolldown 复用。内存文件中间件处理 304、MIME 与自定义 header；响应 finish 后才调用 markPayloadDelivered()，服务端只有确认 payload 送达，才允许后续 chunk 依据 per-client ship map 省略其中模块。

HMR patch 末尾强制追加 export {}，让响应只能作为 ESM 执行，不能被恶意跨源页面当 classic script 读取。这是 full-bundle 本地服务器安全边界的一部分，不是无意义的空导出。

playground/hmr-full-bundle-mode 用页面全局标记区分“patch 原地更新”和“整页刷新”，并覆盖新增 asset、 ?worker、new URL worker、nested worker、hot.data 与 invalidate。patch 必须包含 ESM 语法，避免被 跨源页面当普通 script 标签读取响应内容。

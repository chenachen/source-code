14A. 生产构建编排与 Environment

传统 build 是单 Environment 兼容层；真正编排由 createBuilder、BuildEnvironment 与 Rolldown 完成。

证据基线：v8.2.1commit 421615865dad约 17 分钟查看 Markdown 原稿

此版本主构建器是 Rolldown，默认转译与压缩使用 Oxc；esbuild 用于显式兼容路径。

#两层 API

#build()：兼容单环境入口

它保留传统 Vite Build API：只建立 client 或 ssr 环境，返回一个 output、output 数组或 watcher。 true 表示使用 legacy Builder 兼容路径。

#createBuilder()：多环境编排器

Builder 暴露：

  • environments：已初始化的 BuildEnvironment；
  • build(environment)：构建指定环境并标记 isBuilt；
  • buildApp()：让插件和框架决定构建顺序；
  • runDevTools()：可选构建工具集成。

Environment API 引入 Builder 的演进见 PR #18432，buildApp hook 见 PR #19971。

#Build 配置归一化

resolveBuildEnvironmentOptions() 不只是填默认值。它把多个历史形态归一成后续可直接消费的协议。

#与环境相关的默认值

配置 client server / SSR bundled-dev
platform browser node 按 consumer
minify oxc false false
emitAssets true false 按 consumer
cssCodeSplit 非 lib 时 true 非 lib 时 true 非 lib 时 true
cssMinify !!build.minify（true 使用 Lightning CSS） lightningcss 默认 false

SSR target=webworker 是例外：platform 使用 browser；若 external 中残留 CJS require，再追加 esmExternalRequirePlugin()，因为 worker 运行时没有 Node createRequire。对应修复见 PR #21963。

#特殊值

  • baseline-widely-available 展开成固定浏览器 target 数组；默认 target 更新见 PR #21193；
  • target 数组去重，因为 Oxc 不接受重复值；
  • 字符串 'false' 归一成布尔 false，minify: true 归一成 oxc；
  • modulePreload 最终只有 false 或完整对象；
  • 旧 rollupOptions 与新 rolldownOptions 通过 getter 保持兼容。

对象展开会把 getter 求值成普通数据属性，所以 resolved 对象上必须再次建立兼容访问器。相关修复见 PR #22691。

顶层 input 可补给缺少 entry 的 build.lib，但必须复制 lib 对象，不能修改用户配置；回归见 PR #23135。

#Rolldown 输入配置

Vite 为 Rolldown 补默认值，并设置构建协议：

  • preserveEntrySignatures 默认：SSR=allow-extension，lib=strict，应用=false；用户 rolldownOptions 可覆盖；
  • plugins：全部经 Environment wrapper；
  • onLog：进入 Vite 日志适配；
  • transform.target：build target；
  • define：禁止 Rolldown 重复替换 NODE_ENV；
  • .css 暂按 JS 模块代理；
  • experimental.viteMode=true；
  • chunkImportMap：按当前环境配置并注入 baseUrl。

用户 rolldownOptions 在内部默认值之后展开，但 Vite 会对 input、plugins、onLog 等关键协议再明确设值。

#压缩与 ES 库纯标注

ES 库是给下游打包器消费的中间产物。若压缩空白时删除 /* @__PURE__ */，下游无法 tree-shake 构造调用， 所以 Vite：

插件可能是 class 实例，克隆时必须保留原型。对象式 hook 还带 filter/order；sharedPlugins 下同一原 hook 会产生多个环境 wrapper，wrappedHookMap 让后续 filter/order 赋值同步到全部副本。每环境独立 hook 对象的 修复见 PR #21472。

#ChunkMetadataMap

Vite 插件需要给 chunk/asset 追加：

  • importedCss；
  • importedAssets；
  • 暂时共享的 modules 对象。

这些数据被 CSS、manifest、SSR manifest、preload 等多个插件跨 hook 使用。Rolldown 在不同阶段可能给出 不同 chunk 对象，因此用 preliminaryFileName/fileName 作为 key 放入外置 Map，再用 defineProperty 把同一 metadata 挂回对象。

使用 defineProperty 而非赋值，是为了不被 Rolldown 误判为输出发生修改。metadata 的枚举性和 build 返回值 修复可沿 PR #261、 PR #262 阅读。

watch 模式每轮第一次 renderChunk 重置该 chunk metadata，防止旧 CSS/asset 集合残留；修复见 PR #342。

#构建 URL 运行时

资源插件只知道最终 filename 后，统一调用：

  • toOutputFilePathInJS()：允许返回 runtime 表达式；
  • toOutputFilePathWithoutRuntime()：CSS/HTML 只能接受字符串；
  • createToImportMetaURLBasedRelativeRuntime()：按 format 生成相对 URL 代码。

相对 base 的运行时机制：

format 基准
es import.meta.url
cjs Node __dirname 或浏览器 currentScript/baseURI
iife currentScript/baseURI
umd Node、location、document 三路兼容
worker-iife self.location.href

experimental.renderBuiltUrl 可直接返回字符串、要求 relative，或为 JS 返回 runtime 表达式。CSS/HTML 无法 嵌入任意 JS，收到 runtime 时必须报错。

文档基准 URL 构造还需防 DOM Clobbering，相关修复见 PR #18115。

#输出目录准备

prepareOutDirPlugin 在每个环境首次 renderStart：

  1. 汇总所有 output dir；
  2. 解析 emptyOutDir 安全默认值；
  3. 清空目录，但保留 .git 与嵌套的其他 output dir；
  4. 检查 publicDir/outDir 是否重叠；
  5. 把 publicDir 复制到每个输出目录。

决定“首次”的不是进入过 renderStart，而是已经执行过一次写盘准备。源码中的 rendered 只在 write=true 时登记 Environment：

来源：packages/vite/src/node/plugins/prepareOutDir.ts，prepareOutDirPlugin()。

所以第一次 write=false 只生成内存产物，不会消费“已准备”机会；同一 Environment 下一次改为 write=true，仍会清理安全目录并复制 publicDir。多个 output dir 存在父子关系时，prepareOutDir() 把嵌套 output 加入 skipDirs，避免清父目录时删掉同轮其他输出。

worker 子构建不运行它，避免嵌套构建清空主输出，修复见 PR #20556。

Vite Task 会追踪读写输入；emptyDir 对目录的枚举不是真正构建输入，需要 ignoreInput(outDir) 排除，集成见 PR #22453。首轮 write=false 后再次 write=true 仍须复制 public， 回归见 PR #22328。

#多 Environment 共享策略

默认：每个环境重新 resolveConfig，并创建新插件实例。原因是构建插件通常假定一个实例一次只处理一个 bundle；开发态才长期并发服务多个 Environment。

选项 行为
sharedConfigBuild 环境间复用同一 ResolvedConfig
sharedPlugins 复用首次解析的全部插件实例
sharedDuringBuild 单个插件主动选择复用

即使共享插件，插件也必须通过 this.environment.config 读取环境级 minify/chunkImportMap 等配置，不能捕获 顶层 config 的某个环境值。sharedPlugins 下 chunkImportMap 的隔离回归见 PR #23184。

buildApp() 顺序：pre/normal 插件 hooks → builder.buildApp → post hooks。若全部自定义逻辑结束后仍没有 任何 Environment 标记为 built，Builder 回退为构建全部环境，保证最小配置有产物。

#两个 Environment 如何各用各的配置？

来源：packages/vite/src/node/build.ts，createBuilder()。

控制关系不是“复制一个配置对象再改 name”。默认每个环境重新跑配置解析，patchConfig 把对应的 environment build 选项镜像到旧插件仍会读取的顶层 config.build；patchPlugins 再选择性把新解析出的 插件替换为首次解析实例。最后才并行执行 createEnvironment → init → environments[name] = environment。 因此配置解析是所有权决策，Environment 初始化是登记阶段。

#Rolldown 调用插件时，当前 Environment 从哪里来？

来源：packages/vite/src/node/build.ts，resolveRolldownOptions()。

入口优先级已在前文完整列出；这里的新增事实是 Rolldown 收到的不是裸插件，而是绑定当前 Environment 与 本轮 metadata map 的 wrapper；随后同名变量写入 rolldownOptions.plugins。

#共享插件如何拿到本次构建的 metadata？

来源：packages/vite/src/node/build.ts，wrapEnvironmentHook()。

这段是 14A 到 14B 的桥。renderChunk 先为新轮次重置该 chunk 的 metadata； augmentChunkHash、generateBundle、writeBundle 再把同一份集合挂到阶段性输出对象，最后才调用业务 hook。 于是 CSS 插件在前一 hook 写入的 importedCss，manifest/preload 插件能在后一 hook 读取。 顺序反过来会让插件看到未注入或上一轮的 metadata。

#多个 output 如何排队，失败后谁来关闭 bundle？

来源：packages/vite/src/node/build.ts，buildEnvironment() 一次性分支。

同一函数的清理尾部（与上段之间省略日志和 catch 增强逻辑）：

多 output 不是多次解析模块图：一个 RolldownBuild 按数组顺序执行多个 write()/generate()。 任何 output 抛错，后续 output 不再执行，catch 增强原错，finally 关闭 bundle；此实现没有“删除已写入前序 output”的事务回滚。调用方应把失败理解为“构建资源已释放”，不能理解为“磁盘恢复到构建前”。

write=false 只把输出副作用改为内存 generate()，不会跳过 render/generate hooks，所以 preload、manifest 仍可被测试读取。反之，watch 分支返回长期 watcher，不进入这里的 bundle.close()；关闭 watcher 是调用方责任。

#建议断点

  1. resolveBuildEnvironmentOptions()：比较 client/ssr/custom 的 resolved 值。
  2. createBuilder()：观察 sharedConfigBuild=false 时 resolveConfig 次数。
  3. resolveRolldownOptions()：记录 input、platform、preserveEntrySignatures、outputs。

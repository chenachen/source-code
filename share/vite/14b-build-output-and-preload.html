#import 与 marker 配对

简单输出可以按“import 后的下一个 marker”配对；嵌套时不成立：

wrapper 嵌套后，marker 顺序可能是：

算法单次从左到右：

  1. imports 已按源码位置排序；
  2. 遇到 marker 前，把结束位置在它之前的 imports 压栈；
  3. marker 弹出最近的未闭合 import；
  4. 记录 marker 起点到与 imports 平行的数组。

这就是“括号闭合”而非“邻近文本”模型。嵌套 CSS preload 修复见 PR #22759，用例中的 #22700 是最小复现场景。

#递归收集依赖

对每个可静态解析的动态 import，addDeps() 从其输出 chunk 开始深度遍历：

Set 同时去重并保存遍历插入顺序。当前 chunk 的 CSS 在递归静态依赖之后追加，保证依赖样式先加载，当前 chunk 样式后加载，避免依赖规则意外覆盖当前模块。

#纯 CSS 动态入口

CSS 插件会删除没有运行时代码的 JS proxy chunk，详情见 13A。此时 bundle 中查不到 filename，但 removedPureCssFilesCache 保存其 metadata。

处理方式：

  1. 收集被删 chunk 的 importedCss；
  2. 把动态 import 表达式替换为 Promise.resolve({})；
  3. 仍把 CSS 传给 preload helper；
  4. 尽量用等长空格保持 sourcemap 位置。

未插入 preload helper 的库、worker、server ES 输出仍会把失效 import 改成 Promise.resolve({})， 但不会在此加载 CSS。带 preload helper 的客户端应用输出才把被删除目标的 CSS 交给 helper 等待。 相关修复见 PR #17601、 PR #17371；chunkImportMap 开启时的组合回归见 PR #22841。

#modulePreload=false 仍需加载 CSS

module preload 是性能优化；动态 chunk 对应 CSS 是正确性依赖。两者复用同一个 helper，但语义不同：

同理，modulePreload.resolveDependencies(filename, deps, context) 可以修改/删除 JS preload，却不能删除 CSS。 实现先拆成 cssDeps/otherDeps，只把 otherDeps 交给用户，最后重新附加 cssDeps。

传给用户的是相对 outDir 的输出文件路径，尚未转成公开 URL 或 import map specifier；hostId/hostType 告诉框架该列表属于哪个 JS chunk。

#压缩依赖表

直接为每个 import 重复写字符串数组会放大 bundle。插件为当前 chunk 建立唯一 fileDeps，marker 只写 __vite__mapDeps([0, 1]) 一类索引；真实生成源码见后文证据 B3。

依赖表惰性挂到函数属性，只有动态 import 真正执行时才求值；优化见 PR #17602。没有任何依赖时不注入映射器，见 PR #16271。

文件有 hashbang 时，额外代码必须插到第一行之后。对不常见换行符的修复见 PR #23038。

动态 import 被内联后可能没有对应输出依赖；所有未改写 marker 最终变成 void 0，不允许占位符泄漏到产物。

#浏览器 Preload Helper

运行时顺序：

  1. 现代格式且 deps 非空才工作；
  2. 读取 CSP nonce meta，兼容浏览器 nonce hiding；
  3. 把 dep 转绝对 URL；
  4. 用全局 seen 去重；
  5. 再扫描现有 <link>，避免与 SSR markup 重复；
  6. CSS 创建 stylesheet link；JS 使用 scriptRel：启用 polyfill 时固定 modulepreload，否则探测原生支持， 不支持时使用 preload as=script；
  7. 等待本次新建的 CSS link 的 load/error；已见 URL 或 SSR 已有 stylesheet 会直接跳过；
  8. 执行真正动态 import factory。

CSP nonce 支持见 PR #16052，CSS link crossorigin 修复见 PR #17930。

为兼容 Chrome 64–75、Firefox 67–70、Safari 11.1–12.1，helper 自带小型 allSettled 实现，修复见 PR #19805。

任何 CSS preload 或动态 import 错误都会派发：

事件的 payload 保存原始错误。CSS 失败未取消时，helper 抛错且不调用 import factory；取消后仍会继续调用它。 动态 import 自身失败被取消后，catch 返回 undefined，helper Promise 因而成功兑现为 undefined，并不自动重试。 未 preventDefault 时重新抛错；可取消机制见 PR #18046，module 本身错误也进入同一事件见 PR #18098。

#Modulepreload Polyfill 虚拟入口

用户或 HTML 构建可导入稳定 ID vite/modulepreload-polyfill。插件把它解析为 \0 虚拟模块：

  • bundled client：交给 Rolldown 原生 modulepreload polyfill 插件生成兼容实现；
  • bundled server/CJS：按非现代目标让无用分支被 tree-shake；
  • unbundled dev：load 返回空模块，因为浏览器直接加载开发模块图，不需要构建产物级 polyfill。

公共 ID 与内部虚拟 ID 分离，既允许用户显式导入，也防止其他 resolve 插件把它当 npm 包。对应快照用例 对照 ES 与 CJS 输出，验证不是“始终塞一份 polyfill”。

#Esbuild 的两个阶段

#单模块转译 esbuildPlugin

目标是快速把 TS/TSX/JSX 变成 JS：

  • 按完整 id/query 推断 loader；
  • 读取最近 tsconfig 的少数有意义字段；
  • 开发态把所有 tsconfig extends 文件加入 watcher；
  • 用户显式 JSX options 覆盖 tsconfig；
  • 强制 sourcemap；
  • 关闭 minify、treeShaking、keepNames；
  • 可选拼接 jsxInject。

优化在此阶段关闭，因为同一模块可能继续被 Rolldown tree-shake，最终 chunk 还会统一 target/minify。多次 keepNames 破坏 tree-shaking 的背景见代码中的 #9164。

transformWithEsbuild() 是旧公开 API，现要求项目自行安装可选 esbuild，并提示迁移 Oxc。

#最终 chunk buildEsbuildPlugin

它在 renderChunk 按 build.target 和 build.minify='esbuild' 工作：

  • legacy chunk 跳过，避免再次生成旧环境不安全语法；
  • ES/CJS 映射成 esbuild format；
  • IIFE 不再指定 format，避免给 Rolldown wrapper 多包一层；
  • ES lib 永远禁用 whitespace minify，保留 pure annotations；
  • 用户细粒度 minifyIdentifiers/Syntax/Whitespace 优先。

保留 ES lib 标注见 PR #20522。

helper 位于 wrapper 外会污染全局，且短变量可能碰撞。injectEsbuildHelpers() 用固定头部匹配或 indexOf 定位 wrapper，再用 slice 移动代码， 把 helper 移到 "use strict" 后。不用复杂正则，是为避免历史回溯性能问题。

#Terser Worker

Terser 是可选依赖，首次真正需要压缩时才解析和创建 worker pool；项目安装版本优先于 Vite自身位置。

以下选项让 worker helper 回退主线程：函数不能结构化克隆，nameCache 则需要保留调用方原对象的修改。

  • mangle.nth_identifier.get 函数；
  • properties nth_identifier；
  • format.comments / output.comments 函数；
  • 可变 nameCache。

nameCache 回退修复见 PR #20750。worker 抛出的 Error 会展开成普通对象，显式保留 不可枚举 stack；主线程再根据 line/col/pos 补 chunk 文件位置与 code frame，后者见 PR #20642。

即使首选 minifier 是 Oxc，plugin-legacy 仍可能对 legacy chunk 请求 Terser，所以插件 apply 条件是任意 非 false minify，renderChunk 再判断当前 output 是否真的需要它。

#Manifest

原生 manifest 插件生成基础字段，兼容层再从 viteMetadata 补：

  • chunk 的 importedCss；
  • chunk 的 importedAssets；
  • standalone CSS entry 的 assets；
  • 多个 originalFileNames 指向同一去重资产的 key。

manifest key 优先使用相对 root 的 facadeModuleId；虚拟 null byte 被移除。无原始输入名时使用 _<basename>，避免与真实入口 key 混淆。

当用户显式把 build.rolldownOptions.output 配成数组时，每个 output 都会触发 generateBundle。 perEnvironmentState 累计 manifest 与 outputCount：中间 output 删除 manifest asset；当兼容 manifest 的 generateBundle hook 计数达到配置长度时，才输出合并 JSON 并 reset。默认 library formats 自动展开的 ES+UMD 不会被这里的原始 output 长度识别为 2，不能拿它作为本分支的例子。失败边界见证据 B4。

standalone CSS assets 字段见 PR #21015，同 basename CSS entry 隔离见 PR #22039。

#证据 B1：CSS 发射后立刻登记到所属 chunk

来源：packages/vite/src/node/plugins/css.ts，CSS post plugin 的 renderChunk。

lazy.css 不只是 emitFile() 后出现在 bundle 里；插件还把最终文件名写入 lazy chunk 的 importedCss。14A 的 hook wrapper 保证这里拿到的 metadata 与稍后 generateBundle 读取的是同一集合。 若 CSS 是被删除的纯 CSS proxy，插件会把 metadata 转移给 importer 或放入 removedPureCssFilesCache， 因此“删空 JS chunk”不等于“删交付边”。

#证据 B2：从动态入口递归合并 JS 图与 CSS 边

来源：packages/vite/src/node/plugins/importAnalysisBuild.ts，generateBundle() 内部 addDeps()。

本案例从 lazy chunk 递归静态 JS 边后追加 lazy-*.css；若目标是已删纯 CSS chunk，则保留 CSS，并把 失效 import 改成 Promise.resolve({})。算法模型已在“递归收集依赖”和“纯 CSS 动态入口”说明。

#证据 B3：marker 变索引，文件表只注入一次

来源：packages/vite/src/node/plugins/importAnalysisBuild.ts，marker 重写与依赖表注入。

同一 generateBundle 处理完当前 chunk 的全部 marker 后，再注入共享文件表：

最终 entry 不重复内联 ['lazy.js', 'lazy.css']；marker 变成索引数组，文件表在 chunk 顶部惰性初始化一次。 开启 chunkImportMap 后，依赖文件名先经 reverse mapping 变 specifier；仓库测试正是从 importmap.json 找到 CSS specifier，再断言 entry 代码含该 specifier，直接卡住这条数据链。

#证据 B4：多 output manifest 延迟到最后一次发射

来源：packages/vite/src/node/plugins/manifest.ts，native:manifest-compatible.generateBundle()。

同一个 RolldownBuild 对用户显式配置的 output 数组逐项 generate/write，每项都会运行 generateBundle。中间 output 若都 发同名 manifest，会得到互相覆盖或不完整文件；实现把 manifest 累计到 Environment 隔离状态，删除中间资产， 最后一次才发合并结果并 reset。这里的“最后”按配置 output 数量计数，不按文件系统扫描推断。

边界：若后序 output 在兼容 manifest hook 达到配置计数前失败，前序 output 可能已写盘，合并 manifest 尚未发射，插件状态也可能残留；复用同一 Builder/Environment 可能继承旧计数或条目。若最终一次该 hook 已经执行并 reset，随后其他 hook 或写盘再失败，则不会残留这份计数。bundle.close() 只释放构建资源，已写入文件不会回滚；复用环境前需要考虑上述累计状态。

#GWTMS 拆解

  • Given：真实 entry → lazy → lazy.css 图；client 开 chunkImportMap，SSR 关；两环境 sharedPlugins=true，均使用内存输出。
  • When：createBuilder() 建立两 Environment；自定义 buildApp() 依次调用 builder.build(client) 与 builder.build(ssr)。
  • Then：client 同时有 entry、CSS、importmap.json；SSR 不得有 import map；client entry 代码必须含 映射到该 CSS 文件的 specifier。
  • Mechanism：Environment wrapper 让共享插件从 this.environment.config 读取各自开关；CSS 插件发资产并 写 metadata；import analysis 经 import-map reverse mapping 把 CSS specifier 写进 entry 依赖表。
  • Source：14A 的 createBuilder()、resolveRolldownOptions()、wrapEnvironmentHook()；14B 的 CSS renderChunk() 与 import analysis generateBundle()。
  • Cleanup：write=false 不创建交付目录；每次 builder.build() 进入一次性 buildEnvironment()，其 finally 关闭内部 RolldownBuild。测试没有额外长期 watcher 需要关闭。

写盘与浏览器加载使用另外两条路径：copies public directory after building same environment with write false first 覆盖目录准备和 public 复制；上文 manifest 聚合源码与 preload helper 分别说明多 output 的合并时机、 CSS 等待及错误处理。

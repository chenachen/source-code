11. 依赖预构建

预构建允许先启动、后台发现、候选构建、hash 比较和目录换代，是并发状态机而非一次扫描。

证据基线：v8.2.1commit 421615865dad约 25 分钟查看 Markdown 原稿

本页重点

预构建允许先启动、后台发现、候选构建、hash 比较和目录换代，是并发状态机而非一次扫描。

推导边界

Scanner 是预测；真实 crawl 会校验与补漏，候选结果也可能丢弃重跑。

证据口径

正文保留目标版本中的真实源码、状态说明与代表性测试映射。测试源码用于锁定设计契约；本轮没有执行测试命令。

#阅读边界

本章研究开发服务器怎样发现第三方依赖、把它们预构建为浏览器可消费的 ESM、缓存结果，并在运行期 发现漏网依赖时安全换代。它不只是一次打包，而是一套允许“服务器先启动、优化在后台完成、请求按需 等待”的并发状态机。

上游的裸包解析见第 07 章，Import Analysis 怎样把裸包 URL 指向优化产物见第 10 章。本章重点是：

读完应能回答：

  1. 依赖预构建同时解决了 CJS 兼容和请求数量的什么问题？
  2. scanner 与浏览器触发的真实模块 crawl 为什么要并行运行、最后再比较？
  3. optimized、discovered、chunks 分别代表什么状态？
  4. 依赖文件还未落盘时，Import Analysis 为什么已经能返回优化 URL？
  5. hash、browserHash、fileHash 各自保护哪一层一致性？
  6. 什么情况下新增一个依赖可以无感提交，什么情况下必须 full reload？
  7. 为什么打包期间又发现依赖时，有时要直接丢弃已经完成的候选结果？
  8. 正式缓存目录为什么用两次 rename 换代，而不是先删除再复制？
  9. preAliasPlugin 和 optimizedDepsPlugin 怎样把异步优化接入普通 resolve/load？
  10. holdUntilCrawlEnd 用首屏等待换取了什么稳定性？

#推荐阅读顺序

  1. optimizer/index.ts 的类型区：DepsOptimizer、OptimizedDepInfo、DepOptimizationMetadata。
  2. plugins/preAlias.ts：看 alias 后的裸依赖怎样提前命中优化器。
  3. optimizer/scan.ts 的 scanImports()、computeEntries()、rolldownScanPlugin()。
  4. optimizer/resolve.ts：看 include 的嵌套语法、glob 与 package exports 边界。
  5. optimizer/optimizer.ts 的 createDepsOptimizer()：先只读 init()、registerMissingImport()、 onCrawlEnd()。
  6. 回到 optimizer/index.ts 的 runOptimizeDeps() 和 prepareRolldownOptimizerRun()。
  7. optimizer/rolldownDepPlugin.ts：理解入口映射、external、CJS facade 和资源 URL。
  8. 再读 runOptimizer()：串起批次、提交、重跑与 reload 决策。
  9. plugins/optimizedDeps.ts：从请求侧观察 processing、旧 hash 和缺文件错误。
  10. 最后读 scanner、竞态、exports glob、插件兼容四组测试。

不要从 runOptimizer() 的所有分支开始硬读。先建立元数据状态和请求等待协议，再看调度分支，复杂度会 明显下降。

#模块边界与对象所有权

依赖优化器不是全局单例。每个未禁用依赖优化、且未进入 Bundled Dev 的 DevEnvironment 各持有一份 DepsOptimizer。创建发生在 DevEnvironment 构造期，但冷缓存读取、scanner 与首轮优化延迟到 environment.listen()；关闭则由同一个 Environment 负责。这解释了一个看似反常的合法场景： createServer() 后、listen() 前可以先 transformRequest()，此时优化器对象已经存在，init() 却还没 执行。

模块 负责 不负责 上游 → 下游
server/environment.ts 创建、启动、关闭 Environment 私有优化器 依赖发现和打包决策 Server 生命周期 → DepsOptimizer.init/close
optimizer/scan.ts 从入口快速预测裸依赖集合 生成正式产物、决定 reload entries/config/plugins → id → src
optimizer/optimizer.ts 协调 scanner、真实 crawl、批次 Promise、重跑和 reload 具体 bundle 输出、HTTP 响应 发现结果/运行时 missing → runOptimizeDeps/metadata/HMR
optimizer/index.ts 元数据/hash、Rolldown 构建、临时目录与目录换代 决定哪轮候选应发布 完整依赖快照 → DepOptimizationResult
plugins/preAlias.ts / plugins/resolve.ts 把裸包解析到 optimized/discovered URL 读取优化文件 import specifier → registerMissingImport/getOptimizedDepId

middlewares/transform.ts 把优化器错误码映射为 HTTP 504/404 判断优化结果新旧 plugin error → HTTP response

DepsOptimizer 闭包同时持有调度标志、scanner/构建取消句柄与 discovered 批次 Promise；这些状态都不跨 Environment 共享。

#为什么需要预构建

#统一模块格式

浏览器原生 ESM 不能直接理解 Node 风格 require()、module.exports。很多包还是纯 CJS，另一些包同时 出现 ESM 语法与 CJS 导出。优化器让 Rolldown 提前把这些入口整理为 ESM，并记录 needsInterop，供 Import Analysis 在必要时补 named/default import 兼容。

#压缩请求瀑布

一个看似单入口的 ESM 包可能由数百个内部模块组成。开发态逐文件服务会产生大量 HTTP 请求。预构建 把稳定的第三方依赖合并为较少入口和共享 chunk；项目源码仍保持按文件转换，继续享受快速 HMR。

#两条发现路径：预测与校验

#scanner：快速预测

冷启动时 scanImports() 创建一个轻量 ScanEnvironment，复用插件容器和 resolve 配置，但不允许访问 模块图或完整 server 状态。它计算入口后调用 Rolldown，只做依赖图遍历，不生成正式产物：

结果按 ID 排序。异步解析完成顺序可能每次不同，固定顺序能让依赖集合序列化、browserHash 和日志保持 稳定。

scanner 追求低成本，不追求成为完整编译器。以 Vue <script setup lang="ts"> 为例，直接转译 TS 可能删除“只在模板使用”的 import；extractImportPaths() 因而用轻量正则把静态 import 重新附加为 side-effect import。它允许少量假阴性，因为真实 crawl 会补齐；误识别的候选也会在 resolve 时过滤。

#真实模块 crawl：运行语义的事实来源

服务器开始处理首个页面后，正常插件管线会转换源码，Import Analysis/resolve 遇到尚未优化的裸依赖时 调用 registerMissingImport()。这条路径看到的是插件真实转换后的模块图，所以用于校验 scanner 的预测。

两者并行是冷启动优化：

如果 scanner 没漏依赖且 interop 预测一致，就直接采用已经在后台生成的候选结果；如果真实 crawl 补出 新依赖，则取消候选，把双方并集重打包。这样宁愿首轮多做一次后台工作，也避免浏览器先拿到马上过期的 模块 URL 后再整页刷新。

这套冷启动 scanner 最初见 PR #8869。 更早的非阻塞发布与 URL 版本协议可沿 PR #6758、 PR #7379 和 PR #7568 追溯；后文只讨论目标版本的最终实现。

#scanner 怎样处理 HTML、SFC、JSX 与 glob

#HTML/SFC 脚本隔离

扫描器先去掉 HTML 注释，再为每个 <script> 块创建独立虚拟模块。不能把多个块简单拼到一个作用域： Vue/Svelte 可能同时有 module/local script，重复变量会让扫描器误报语法错误。

  • 纯 HTML 只收集 type="module"。
  • Vue/Svelte/Astro 等框架文件允许普通 script。
  • Svelte module script 可以重导出；组件实例 script 的 export 通常表示 props，不应 export *。
  • 虚拟 script resolve 时恢复原 SFC 文件作为 importer，让 alias/相对路径语义与真实编译一致。

#JSX 隐式 runtime

automatic JSX runtime 的 import 是转换器注入的，源文件未必写出 react/jsx-runtime 或 vue/jsx-runtime。scanner 必须采用依赖优化专用的 JSX transform 配置，否则首个 JSX 请求才发现 runtime，会触发优化器重跑。相关历史修复见 PR #20495。

#import.meta.glob

scanner 在遍历前展开 glob，因此 glob 命中的文件也能贡献依赖。package.json imports 子路径模式需要 先解析，不能把 #alias/*.js 当普通磁盘 pattern；对应修复见 PR #22018。

#入口解析必须复用插件与 root

顶层 input 可能是插件提供的虚拟 ID，所以入口也要经过插件容器解析；支持该场景见 PR #23101。相对 build.rolldownOptions.input 必须以项目 root 为基准，而不是 process.cwd()；回归修复见 PR #22769。

服务器在后台扫描期间关闭时，插件容器会用 ERR_CLOSED_SERVER 拒绝解析。结果本来就会丢弃，因此这是 取消控制流，不应变成未处理 rejection；见 PR #22784。

#显式 include：嵌套依赖、glob 与 exports

optimizeDeps.include 不只是普通包名。createOptimizeDepsIncludeResolver() 支持：

它表示从 foo 的安装位置找 bar，再从 bar 的安装位置解析 baz，用于强制优化没有被应用源码直接 导入的嵌套依赖。

include 含 glob 时，expandGlobIds() 要尊重 package.json exports：

DepOptimizationMetadata 不只是写入 _metadata.json 的缓存描述，它也是运行时协调对象。

区域 含义
optimized 已成功打包并提交的入口依赖
discovered 已发现、最终文件名已确定，但当前批次尚未提交的入口

关键设计是“路径先确定，内容后落盘”。registerMissingImport() 可以立即把 file?v=browserHash 返回给 Import Analysis，但 optimizedDepsPlugin.load() 在读文件前等待 processing。因此单个请求被精准 阻塞，服务器其他初始化和源码转换不必等待整个依赖打包。

每批新依赖共享一个 processing Promise。开始一轮打包时，当前 Promise 被封存进队列，新发现项绑定 下一批 Promise。只有某次真正包含这些依赖的结果提交后，队列才统一 resolve；被丢弃的中间结果不能 提前放行等待请求。

#决定性源码 2：missing 先获得稳定 URL，再等待内容

来源：packages/vite/src/node/optimizer/optimizer.ts，registerMissingImport() 与 addMissingDep()。这是“路径先确定、文件后落盘”的真正写入点。

registerMissingImport() 的返回不是“已经可读的文件”，而是一张未来文件的凭证。resolve.ts 马上把它 变成 ${file}?v=${browserHash}；真正的 load() 必须尊重 processing。初始化前只登记、不 debounce 的分支也在这里，不是 listen() 禁止转换。

#三种 hash 各管一层一致性

  • hash 决定磁盘缓存能否跨启动复用。
  • browserHash 是浏览器 URL 版本，防止旧请求与新优化目录混用。
  • fileHash 判断新增依赖是否改变旧入口的共享 chunk 图。

若 lockfile/config hash 一致，启动直接复用 _metadata.json，跳过扫描与打包。force 会无条件清缓存。 空依赖结果也写元数据；否则每次启动空项目都要重复扫描。

配置 hash 只序列化会影响优化结果的字段。函数/正则转字符串，插件只记录名称，避免不可序列化对象让 缓存随机失效。lockfile 搜索优先检查常见包管理器以缩短路径遍历；同时兼容多个新旧 lockfile 格式。

#初始化、首轮候选与验收

initState 有 idle → initializing → initialized 三态。createServer() 与 listen() 之间也允许用户 主动发起 transform，此时可能早于 init() 发现依赖。若立即启动打包，init() 随后重置 metadata， 提交阶段就会拿到错配状态。现在 pre-init 只登记 missing，等待 initialized 后再调度；修复见 PR #22852。

#决定性源码 3：init 同时启动真实 crawl 闸门与 scanner 候选

来源：packages/vite/src/node/optimizer/optimizer.ts，init()。这是源码删节摘录；仅用教程注释标出 日志与错误处理的省略，保留三条并行线的原始语句。

#决定性源码 4：crawl 结束后验收候选，而非盲目提交

来源：同文件 onCrawlEnd()。以下为源码删节摘录，省略零依赖与日志分支；保留“采用预测”或“取消后 取并集”的原始决定语句。

crawlDeps 当前包含 include、scanner 已登记项与真实请求漏项，所以 scannerMissedDeps 只需问“crawl 集合中有没有 scan 输出没有的项”。反向差集不能丢：循环把 scanner 独有项补回 discovered，保证重跑 输入是并集。needsInteropMismatch 同样会使候选过期，因为 Import Analysis 的导入改写取决于它。

#holdUntilCrawlEnd

默认 true：scanner 可以提前构建，但候选结果等真实静态 crawl 结束后才发布。优点是首屏几乎不会因 漏依赖改变共享 chunk 而 reload；代价是浏览器更晚拿到优化文件。

设为 false：scanner 完成即可提交，浏览器能更早并行请求；若真实 crawl 随后发现新依赖，则进入普通 重跑，旧 fileHash 稳定时仍可无感，否则 full reload。这一权衡由 PR #15244 引入。

#一轮优化怎样生成并发布

runOptimizeDeps() 先创建唯一 processing 目录，并写局部 package.json 声明 type: module。随后 prepareRolldownOptimizerRun()：

  1. 等待每个入口的 exportsData；
  2. 把 react-dom/client 一类 ID 扁平化为稳定输出名；
  3. 将扁平入口映回 Vite 已解析的真实 src；
  4. 合并用户 Rolldown 选项、兼容转换后的 esbuild 插件与内置 dep 插件；
  5. 创建可取消、可延后 build() 的 Rolldown context。

打包结果把入口写进 optimized，非入口写进 chunks。入口 fileHash 主要取决于 chunk.imports；代码 内容变化本身由 lockfile/config hash 和开发重启处理，这里关心的是“旧浏览器模块引用的 chunk 图是否 还成立”。

#提交前为什么仍可能丢弃结果

runOptimizer() 比较新旧结果：

  • 无需 reload：提交目录，但保留浏览器已经使用的旧 browserHash；新依赖可无感加入。
  • 需要 reload，且打包期间没有再发现依赖：提交新版本、清模块图、广播 full reload。
  • 需要 reload，但打包期间又发现依赖：取消当前结果，接续 missing 登记时已经安排的 debounce/rerun，再打包 更完整快照，避免连续两次 reload；这条分支不执行 onCrawlEnd() 的 scan∪crawl 合并代码，也不保证立即开始。

最后一种分支最容易漏读：已经花时间打好的结果仍不能发布，因为它一发布就知道还要再次换代。批次 Promise 继续等待，直到真正包含依赖的后续结果提交。

#决定性源码 5：reload 判定、无感合并与丢弃重批

来源：packages/vite/src/node/optimizer/optimizer.ts，runOptimizer()。源码删节摘录用教程注释标出 原位补全与日志省略；决定分支保持原样。

无 reload 分支保留旧 browserHash 不是性能小优化，而是模块身份协议：浏览器已执行的 react?v=old 与 新依赖一起打包后，若旧入口 import 图未变，就必须仍叫 react?v=old，避免同一逻辑包出现第二实例。 反之，fileHash 变化说明旧入口引用的共享 chunk 图变了，仅替换磁盘而不 reload 会让现有模块图与新 目录错配。

#缓存目录换代：双 rename 的保证与缺口

构建始终写唯一临时目录；Rolldown build 失败或 commit 开始前取消时，只删除该目录，不触碰当前正式缓存。 commit 成功路径先写 _metadata.json，再执行：

相较“删除正式目录，再移动新目录”，两次 rename 把缓存不可用窗口压到最小，也避免请求读到半写文件。 POSIX 使用同步 rename；Windows 的杀毒软件可能短暂锁目录，所以 safeRename() 对 EACCES/EPERM 重试， 并验证目标是否已经落地。临时目录换代方案见 PR #12622。异常退出残留超过 24 小时的临时目录在下次启动 异步清理，不阻塞当前冷启动。

这不是跨两次 rename 的事务：若旧正式目录已移到 backup，而 processing→正式目录这一步仍失败，源码没有 回滚，旧内容可能只留在 backup、正式路径暂时缺失。因此“保留旧 cache”的保证只适用于 build 失败和 commit 前取消，不能扩大到 commit 中途 I/O 失败。

这里的“提交”不是把两个 rename 合成一次不可分割事务；旧目录移到 backup 与新目录移到正式名 之间仍有很短窗口。保证是正式路径不会指向半写目录；“旧 cache 不受影响”只适用于 build 失败或 commit 前取消。Windows 的 safeRename() 还会对 EACCES/EPERM 最多退避 5 秒。

#Rolldown 依赖插件的边界

rolldownDepPlugin() 统一把 Vite 的解析语义接入预构建：

  • ESM import 和 CJS require 使用不同 resolve 条件与 package cache；
  • 入口 ID 必须映回 Vite 预先解析的 src，避免 Rolldown 再选到不同条件入口；
  • CSS、WASM、SFC、已知 asset 默认 external；用户声明可优化扩展名可移出该集合；
  • require() 静态资源先经虚拟 facade 变成 import，再 external；
  • browser external 用 Proxy 在访问属性时给出明确兼容警告；
  • 相对 new URL('./asset', import.meta.url) 要按原依赖文件解析，再改写为相对 deps 输出目录。

资源 new URL 的相对位置修复见 PR #21434。动态模板需要 glob 枚举，仍交给主 asset 插件；优化器 只安全处理可静态确定的相对字面量。

rolldownCjsExternalPlugin() 只在 browser 平台把 external require 改成 import facade。Node 原生支持 require，保留语义更准确；neutral 平台无法推断目标运行时能力，也保守跳过。

pluginConverter.ts 只实现依赖扫描/预构建需要的 esbuild 插件子集：onResolve、onLoad、 onStart、onEnd 与有限 BuildResult。它是迁移兼容层，不代表任意 esbuild 插件都可无损运行在 Rolldown 上。

#alias 与请求侧怎样接入

#preAliasPlugin

普通 alias 插件把 react 改成某个 replacement 后，后续逻辑可能看不出它原本是裸依赖。 preAliasPlugin 提前解析 replacement：

  • replacement 已在 optimized/discovered 中：直接返回优化 URL；
  • replacement 可优化但尚未登记：调用 registerMissingImport()；
  • SSR 未显式 include：保守不优化，因为单凭文件路径无法可靠判断 package/CJS 身份。

这个桥接修复了 alias 指向的依赖绕过优化器的问题；历史起点见提交 54dab71e4。

#optimizedDepsPlugin

load() 先校验 URL 版本，再等待 discovered 所属批次，等待后重新读取 metadata，最后才读正式 cache。 默认不容忍旧 URL，因为同一逻辑模块的两个优化版本可能产生重复实例；具体错误条件见下表。

#决定性源码 7：请求等待、二次验版本、再读正式目录

来源：packages/vite/src/node/plugins/optimizedDeps.ts，optimizedDepsPlugin().load()。源码删节摘录省略 debug 与外围 ID 判定，等待、二次校验、读文件和错误分支保持原样。

等待后必须再次比较 metadata 引用。原因：等待期间 commitProcessing() 可能整体替换快照；只做等待前 校验存在 TOCTOU 窗口。错误分支也要按源码精确区分：

触发条件 稳定错误码 HTTP 含义
请求 hash 与 info.browserHash 不同 ERR_OUTDATED_OPTIMIZED_DEP 504 旧页面请求；reload 后换 URL
info.processing 自身 reject ERR_OPTIMIZE_DEPS_PROCESSING_ERROR 504 优化等待异常
等待期间 metadata 换代且 hash 改变 ERR_OUTDATED_OPTIMIZED_DEP 504 等候者已落后于新快照
readFile 失败且 URL 带 hash、未忽略过期 ERR_OUTDATED_OPTIMIZED_DEP 504 优先按换代处理，不武断判文件永久缺失
readFile 失败且无 hash，或显式忽略过期 ERR_FILE_NOT_FOUND_IN_OPTIMIZED_DEP_DIR 404 真正走缺文件提示，建议检查 exclude

当前 createDepsOptimizer() 协调代码只显式 resolve() 批次 Promise，没有找到主动 reject()；因此 processing-error 504 是插件协议的防御分支，不能把它写成“每次 Rolldown 构建失败都会走 504”。构建 失败在 runOptimizer() 自己的 catch 中记录并清 discovered，实际 HTTP 结果还取决于 URL/hash 与文件 读取分支。

#结论与证据边界

依赖预构建的核心不是“用 Rolldown 打一次包”，而是让预测扫描、真实 crawl、请求等待与候选发布共享一套 版本化状态机。processing 让单个请求等待自己的批次；fileHash 与 interop 决定能否无感发布；双 rename 只保证不暴露半写目录，不构成可回滚事务。

本章的完整测试直接证明 JSX 场景的执行次数与模块对象复用。optimizer 是否重跑、每个 reload/rebatch 布尔组合、rename 中途失败以及 504/404 的所有条件，主要由决定性源码与专项测试共同限定，不能从这一条 成功测试外推。

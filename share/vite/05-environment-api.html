05. Environment API

每个 DevEnvironment 隔离配置视图、插件容器和模块图；依赖优化器与运行时 transport 只在相应类型和配置下存在。

证据基线：v8.2.1commit 421615865dad约 10 分钟查看 Markdown 原稿

本页重点

每个 DevEnvironment 隔离配置视图、插件容器和模块图；依赖优化器与运行时 transport 只在相应类型和配置下存在。

推导边界

Build、Scan、Unknown 等 Environment 能力不同；类继承层级不等于运行时所有权层级。

证据口径

正文保留目标版本中的真实源码、状态说明与代表性测试映射。测试源码用于锁定设计契约；本轮没有执行测试命令。

#阅读边界

本节研究 Vite 怎样把“一台开发服务器”拆成多个运行目标，以及每个目标如何拥有独立配置、 插件、模块图、依赖优化器和运行时通信。模块图的内部数据结构、transform 细节、HMR 传播算法 留给后续章节；生产构建的 BuildEnvironment 留给生产构建章节。

读完应能回答：

  1. Environment API 解决了旧 ssr: boolean 模型的什么限制？
  2. environment.config 为什么既像 ResolvedConfig，又能读到环境覆盖项？
  3. client、默认 server、自定义远端运行时分别使用哪种 Environment？
  4. init()、listen()、close() 各负责什么，为什么不能合成一个构造函数？
  5. RunnableDevEnvironment 与 FetchableDevEnvironment 的通信能力边界是什么？
  6. 同一插件实例跨多个 Environment 时，怎样避免缓存和状态串线？

#推荐阅读顺序

  1. config.ts 的 EnvironmentOptions、resolveEnvironmentOptions()：先理解配置怎样分层。
  2. baseEnvironment.ts：看顶层配置与环境覆盖项如何合成。
  3. environment.ts：看类型总入口和 perEnvironmentState()。
  4. server/environment.ts 构造函数：看每个开发环境拥有的运行状态。
  5. 同文件的 init()、listen()、close()：看生命周期。
  6. runnableEnvironment.ts 与 fetchableEnvironments.ts：比较通信模型。
  7. environment.spec.ts：从 resolve conditions 的开发/构建场景验证隔离性。

#配置的三层结构

#用户输入

SharedEnvironmentOptions 对开发与构建都有效，包括 input、define、resolve、consumer、 keepProcessEnv、optimizeDeps、isBundled。dev 和 build 子对象只放阶段专属选项。

#已解析覆盖项

resolveEnvironmentOptions() 为每个名称分别确定：

  • consumer：client 名称默认是 client，其他名称默认是 server；
  • resolve conditions/mainFields/builtins；
  • keepProcessEnv 和依赖优化策略；
  • 默认 Environment 工厂；
  • 开发态是否 recoverable、是否执行 Module Runner transform；
  • 构建输出选项和 isBundled；
  • 最终适用于该 Environment 的插件列表。

默认 client 创建普通 DevEnvironment，使用共享 WebSocket、禁止服务端 fetchModule；默认 非 client 创建 RunnableDevEnvironment，供服务端 Module Runner 执行模块。

#environment.config 代理

PartialEnvironment 不复制整份配置，而是建立 Proxy：

所以插件可以写 this.environment.config.resolve.conditions，也能读取共享 root、server、mode。 getTopLevelConfig() 在确实需要未覆盖的全局对象时显式返回原配置。

日志器也不复制底层输出逻辑，只在 info/warn/error 选项中附加 (environmentName)。名称字符 哈希产生稳定 info 颜色，warn/error 继续使用黄/红色。Environment 名称只允许字母数字、 _、$，因为它还会用于目录和 environments.<name> 访问，不应要求额外转义 （PR #18255）。

#类层级不是运行时层级

不要写 environment.mode !== 'build' 来判断开发态：未来可能新增模式。应正向判断 environment.mode === 'dev'，或使用 isRunnableDevEnvironment() 等能力型 type guard。

UnknownEnvironment 的意义就是阻止“除了 build 都是 dev”的封闭世界假设。

#DevEnvironment 的独占状态

构造函数依次建立：

  1. 读取 config.environments[name]，再合并工厂传入的单实例 context.options；
  2. 选择普通 transform 或完整打包开发模式；
  3. 创建本 Environment 独占的 EnvironmentModuleGraph；
  4. 创建首轮静态 import 稳定检测器；
  5. 标准化 HotChannel，并注册 fetchModule/getBuiltins/invalidate 消息；
  6. 按配置创建显式或自动发现依赖优化器。

插件容器没有在构造函数中创建，因为它要异步执行 Environment 插件派生和 options hook。 这部分由 init() 完成。pluginContainer getter 在 init 前主动报错，把错误生命周期访问暴露在 最近的位置。

每个模块图的 resolve 回调绑定自己的插件容器，因此相同 URL 可以在 client、ssr、edge 中 解析为不同 ID，具有不同 importers、transformResult 和 HMR 边界。

#三阶段生命周期

#init()：装配，不启动外部工作

init() 幂等创建插件容器，并接收 watcher。重启时还能得到 previousInstance；自定义子类只有 确认旧实例来自同一类/同一工厂后才应迁移状态。

入口在插件容器 buildStart 前通过 _registerInputsAsSafeModules() 解析并加入 fs 安全集合。 解析必须带 scan: true，否则会形成：

默认 index.html 不存在是合法库/中间件场景，可静默忽略；用户显式声明 input 时，解析失败 必须暴露。PR #23101 让顶层 input 同样经过插件解析。

#listen()：启动与预热

listen() 启动 HotChannel，初始化完整 bundle 或依赖优化器，再按配置 warmup 文件。它不创建 HTTP Server；顶层 Dev Server 负责网络监听，Environment 只启动自己的运行时能力。

服务器重启的严格顺序是：

先 init 新实例可在配置/插件创建失败时保留旧服务；先 close 旧实例再 listen 新实例可防止两套 优化器、通道或运行时同时工作。独立 listen 生命周期来自 PR #18263。

#close()：等待而不是只发出停止信号

关闭时先置 _closing，取消首轮爬取检测，再并行等待：

顶层 WebSocketServer 可能被多个 Environment 共享，不能由单个实例关闭；它由 Dev Server 统一释放。自定义 HotChannel 是 Environment 独占资源，必须在这里关闭。所有分支使用 allSettled()，单个插件清理失败不能制造其他资源泄漏。

#transform、warmup 与首轮爬取

transformRequest(url) 进入当前 Environment 的 resolve → load → transform 管线并更新其模块 图。自定义 transport 可以声明远端已经执行 fs 安全校验，Vite 才允许跳过本地检查；普通 WebSocket 不能借这个字段绕过 /@fs/ 边界。该安全修复见 PR #22159/#22163。

warmupRequest(url) 是投机预转换：

  • 完整打包开发模式无需逐 URL 预热；
  • 优化依赖已换代、服务器已关闭属于正常取消；
  • 其他错误记日志，但不能产生无人等待的 rejection；
  • 它不改变真实请求遇错时仍应失败的语义。

首轮静态 import 发现使用 CrawlEndFinder：每个 id 只登记一次；在途集合清空后再等待 50ms 静默期，吸收刚发现的下一层 import。waitForRequestsIdle(id) 若在插件 hook 内调用，必须传入 当前 id 把自己排除，否则 hook 等待的正是由自己完成的任务。

#运行时通信的三个级别

#原始 DevEnvironment

只提供 transform、模块图和 HotChannel 原语。框架/运行时集成者自行定义怎样执行模块、怎样 把请求和结果跨边界传输，能力最底层也最灵活。

#RunnableDevEnvironment

runner.import() 可以直接返回函数、类实例等活的 JavaScript 值，无序列化成本。但它要求用户 模块与 Vite Server 运行在同一个 runtime，不能代表独立 Worker/边缘沙箱。

Runner 惰性创建并缓存：未使用 SSR 执行时不修改进程 Source Map 行为，也不承担模块执行成本。 关闭时只有已经创建的 Runner 才会被关闭，避免为清理反向创建资源；漏关 Runner 曾导致模块 缓存/HMR listener 存活（PR #18282）。

#FetchableDevEnvironment

它只承诺标准 Fetch Request/Response，因此可以把处理放到无法与 Vite 共进程的运行时， 也更接近 Worker/Edge 的生产请求模型。代价是任意函数、类实例不能直接跨边界。

工厂先检查全局 Request/Response 和 handleRequest；dispatch 时再用 instanceof 检查输入输出， 尽早发现 polyfill/realm 不一致或错误返回普通对象。该实验接口来自 PR #19664。

#插件状态怎样按 Environment 隔离

同一个插件实例会跨 Environment 调用 hook：

perEnvironmentState(initial) 内部使用 WeakMap<Environment, State>：

  • key 是实例，不是名称；同名重启后的新实例拥有新状态；
  • 值只在该 Environment 第一次调用时创建；
  • Environment 不可达后，WeakMap 不阻止回收；
  • 必须用 stateMap.has(environment) 判断是否初始化。

最后一点很容易写错。若用 if (!stateMap.get(environment))，合法的 false、0、'' 会在 每次 hook 调用时重新初始化；PR #22715 就修复了 这个 falsy 状态缓存问题。

场景 经过的解析路径 证明什么

dev external ModuleRunner 原生外部加载 externalConditions 也随 Environment 隔离

#建议断点

  1. resolveEnvironmentOptions()：比较 client、ssr、worker 的 consumer 和默认 dev 工厂。
  2. PartialEnvironment Proxy 的 get trap：分别读取环境覆盖字段与顶层字段。
  3. DevEnvironment 构造函数：比较 client WebSocket 和 server HotChannel。
  4. init()：确认 pluginContainer 在构造后、初始化前确实不可访问。
  5. CrawlEndFinder.registerRequestProcessing()：观察多层静态 import 怎样延长静默期。
  6. RunnableDevEnvironment.runner：确认首次读取才创建，之后身份稳定。
  7. perEnvironmentState()：用两个 Environment 调同一个插件 hook，观察 WeakMap 槽位。

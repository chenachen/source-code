12B. Bundled Dev：Rolldown 增量整包、内存文件与浏览器 HMR 图

实验性 bundled dev 用 Rolldown 维护增量整包与内存输出，再由浏览器真实执行图决定 HMR 边界。

证据基线：v8.2.1commit 421615865dad约 31 分钟查看 Markdown 原稿

Rolldown 管构建图，浏览器管实际执行图；reload 请求等最新内存产物发布后再触发导航。

代码结论均限定于该版本；本工作树已在对应源码和测试上补充中文解释性注释，涉及注释原文时会另行标明。

#先给结论

普通 Vite 开发模式把浏览器请求当作模块转换入口；Bundled Dev 则让 Rolldown 长期维护一份可增量更新的 完整 bundle，再由 Vite 把输出存在内存、按 HTTP 请求交付，并把 HMR 边界计算移动到浏览器中的真实执行图。

两者最重要的差别不是“有没有 bundle”，而是谁拥有运行时事实：

问题 普通 unbundled dev Bundled Dev
模块何时转换 浏览器请求 URL 时 Rolldown DevEngine 构建/增量构建时
长期图状态 服务端 EnvironmentModuleGraph Rolldown 构建图 + 浏览器 DevRuntime 执行图
HMR 边界由谁算 服务端 server/hmr.ts 浏览器 BundledDevHMRClient
未执行分支的 accept 静态分析后可能进入服务端图 不形成边界；浏览器知道它没有执行
动态入口 浏览器请求源码模块 /@vite/lazy 触发按客户端编译入口
输出落点 transformResult + HTTP 响应 MemoryFiles
full reload 时机 服务端直接发 payload 必须等最新完整输出已进入内存
依赖预构建 独立 optimizer 禁用；完整 bundle 自己处理依赖

因此，不能把第 08、11、12 章的 pending、optimizer、服务端 HMR 边界直接套到本章。Bundled Dev 仍复用 Vite 配置、插件、HTTP、HotChannel、ErrorOverlay 与客户端 HMR 生命周期，但重新分配了状态所有权。

#启动：listen 只完成装配，不等待首轮 bundle

server/index.ts::initServer() 在 HTTP server 真正 listen 前调用所有 Environment 的 listen()。 Bundled client 同时启动 HotChannel 和 BundledDev；optimizer 因 constructor 中的互斥标记不会创建。

目标版本源码摘录，来源：packages/vite/src/node/server/environment.ts，DevEnvironment.listen()：

BundledDev.listen() 做五件事：

  1. 从普通 build 配置派生 DevEngine 配置；
  2. 注册 client connect/disconnect、reload-needed 等 HotChannel 事件；
  3. 创建 DevEngine，安装 onHmrUpdates/onOutput/onAdditionalAssets；
  4. 调用 devEngine.run()，但不 await 整个长期任务；
  5. 载入 bundled 版 HMR runtime，后台等待首轮输出。

派生配置设置：

  • experimental.devMode.lazy 默认 true，用户已有 devMode 对象中的 lazy 可覆盖它；
  • skipCommonRuntimeInjection = true，由 Vite 自己注入客户端 runtime；
  • optimization.inlineConst = false，规避当前已知正确性问题；
  • 固定 entry/chunk/asset 文件名模板；
  • 关闭 minify，开启 sourcemap；
  • watcher skipWrite = true，输出只进内存。

listen() 返回时 DevEngine 已可工作，但 memoryFiles 可能仍只有客户端 runtime。这样 HTTP server 能尽快 响应，首轮等待通过专用 fallback 页表达，不把一个长构建绑死在 server listen Promise 上。

storeOutputFiles() 故意不先 clear()。Rolldown 增量输出只报告本轮新增或变化的部分，未变化文件仍由旧 Map 项提供；整表清空会让 HTML 引用的稳定 chunk 突然 404。同名新输出则直接覆盖旧值。

客户端 runtime 与普通构建文件略有不同：

  • bundledDevClient.mjs 在 Vite 读取时已经是字符串，立即算弱 ETag；
  • chunk/asset 延迟物化，避免生成后从未被浏览器请求的输出浪费转换与哈希成本；
  • HMR patch 是短生命 payload，handleHmrOutput() 直接放入字符串；
  • onAdditionalAssets 把 HMR 期间新发射的图片、Worker 等补进同一表。

#客户端身份：一个页面对应一个 runtime client

Bundled 客户端入口不是普通 client.ts 的另一份完整复制，而是：

  1. 继续复用 transport、overlay、CSS helper 和公共 createHotContext；
  2. 创建稳定 clientId 并告诉服务端；
  3. 每个页面保存一个全局 ViteDevRuntime；
  4. 用 BundledDevHMRClient 接管 bundled payload；
  5. 把 runtime 缓存删除与 HMR dispose 连接起来。

#Patch 事务：先冻结，再统一删缓存

handlePush() 与本地 invalidate 共用一个 applyQueue。队列不是性能优化，而是事务边界：两个 patch 若并行 删除相同模块缓存，dispose、factory 注册与 callback 会跨版本交错。

applyPush() 固定顺序：

  1. reloadPending 时忽略；
  2. 校验 seq === lastSeq + 1，并立即更新 lastSeq；即使随后为 noop 也消费序号；
  3. 计算边界；
  4. 通知 vite:beforeUpdate 并清 overlay；
  5. 动态 import patch，注册新 factory；
  6. applyUpdate() 分阶段应用；
  7. 通知 vite:afterUpdate。

patch import 失败不能继续使用一半更新的 factory 图，直接请求 full reload。

applyUpdate() 的顺序更加严格。

先校验 updateSet 每个模块都有 factory，防止删完旧缓存才发现无法重执行。hasFactory() 检查 存在性，已有 factory 也可用于本地 invalidate，它不检查每个 factory 是否来自本次 patch。删除缓存 会通过 runtime hook 同步调用 dispose，dispose 又可能改变 hot context；所以 callback 必须提前冻结。acceptedVia 初始化完成后再读取 exports， callback 才拿到新 namespace。finally 在同步 callback 调用返回或抛错后清空当前来源。dispose 和 accept callback 返回的 Promise 都未被这条实现等待；若同步 dispose、initModule 或 callback 抛错，已删缓存不会回滚，外层队列 记录失败后继续接收后续任务。因此这里的“事务”指队列中一组操作按序执行，不是原子回滚。

Bundled 版 hot.invalidate() 不回服务端模块图。BundledDevHMRContext.invalidate() 把模块加入同一个客户端 队列，applyInvalidate() 从它的已执行 importers 开始重新计算边界，不下载新 patch，使用 runtime 现有 factory。applyInvalidate() 执行时才读取 currentFirstInvalidatedBy ?? id，并在这一轮传播中检测回到该来源。 invalidateLocally() 只把 id 排队，前轮 callback 的 finally 会在队列任务开始前清空来源，所以 嵌套 invalidate 通常以各次调用模块重新作为来源，不能据此保证整条链都保留最初模块。相应循环 用例目前因 Rolldown #10340 被 skip。

触发条件 状态变化 用户可见结果 恢复

onOutput(Error) 保存 lastBuildError 很重要：错误可能发生在页面建立 HotChannel 连接之前。新页面连接时， 服务端重放同一 prepared error；否则用户只看到空白 fallback，却不知道构建为什么无法完成。

ensureOutputAndFlushReloadNeeded() 的失败回调故意不发 reload。构建失败时留在当前页面和 overlay，比刷新到 不可用输出更安全；修复后下一轮成功 HMR 会再次检查 reloadNeededClientIds 并补做输出。

错误类型也不能混为一个标志：

  • HMR patch 生成错误来自 onHmrUpdates；
  • 最新完整输出错误来自 onOutput，写 lastBuildError；
  • DevEngine 的 getBundleState() 另带 lastErrorStage，用于访问时判断是否强制 full build。

#关闭：DevEngine 是插件构建生命周期的唯一收口者

DevEnvironment.close() 在 bundled 模式关闭 BundledDev，否则才关闭普通 PluginContainer。两者不能一起 执行：DevEngine 已经驱动插件 buildStart/buildEnd，再关一次容器会重复结束同一插件生命周期。

首轮等待在入口、ensureCurrentBuildFinish() 与重试等待后检查 _closed；getBundleState() 后 没有立即检查，但外层回调发送 fallback reload 前还会检查一次，拦截关闭后的刷新。 memoryFiles.clear() 释放 chunk、asset、map 与 runtime 引用；devEngine.close() 停止 Rolldown watcher 和插件 构建生命周期；首轮标记在 engine close 成功后复位。此方法没有清空 clients、pending payload、reload 集合， 也没有取消 debounce timer；HotChannel 断连事件另行移除已登记客户端。

Promise.allSettled() 保证 bundled engine、HotChannel 与在途 transform 中任一清理失败，都不跳过其他项。 虽然 bundled 模式不走普通 transform 主线，Environment 仍保持统一的关闭契约。

真实测试 build-hooks.spec.ts 创建计数插件，启动 bundled server 后等待 buildEndCount === 1，再 server.close()，最后断言 buildStartCount 和 buildEndCount 仍都等于 1。它直接证明“关闭不重复触发 build hooks”这条资源所有权约束。

三次 click，为什么只提交 count=3

本页只追一条可核验链：仓库测试在同一个 act 中连续点击三次，组件从 0 更新到 3，只运行一次本轮 passive effect；随后两次各自进入独立 act，依次提交 4 和 5。 每个阶段都回答四件事：谁持有状态、哪个函数改变它、改变前后是什么、测试断言怎样证明。

同一 Demo 的完整控制流

起点是首次挂载完成后的 button=0；图中沿测试中的三个 click 追到本轮 passive 日志 [3]。createRoot 与初次 root.render 的准备工作见下面阶段 1–2。泳道区分状态所有者与执行阶段；跨泳道箭头仍表示同一条控制流。

调度与恢复的条件可直接核对 ReactFiberRootScheduler.js、ReactAct.js 和 ReactDOMUpdateBatching.js。

阶段 1：createRoot 建根，也先装好事件入口

createRoot 不渲染 App。它创建空 FiberRoot、把 HostRoot Fiber 记到 container，并在真实事件容器上安装根委托监听器。 这解释了测试为什么无需给 button 单独调用 addEventListener。

时刻FiberRootcontainerDOM

createContainer 后current=HostRoot，尚无 App child尚未公开返回空
createRoot 返回由 ReactDOMRoot._internalRoot 持有缓存 HostRoot；装好根监听仍为空

阶段 2：root.render 被建模为 HostRoot Update

公开句柄最终调用 updateContainer(children, root, null, null)。reconciler 先为 HostRoot 请求 Lane，再创建 payload 为 {element} 的 Update； 因此首次挂载和后续 root.render 都走更新模型，不存在“首次直接递归创建 DOM”的旁路。

状态变化：HostRoot.updateQueue 创建根时已经初始化；本次 element Update 经并发缓冲转移后进入它的 shared pending 环。对应 Lane 合入 root.pendingLanes； 真正消费 payload 发生在 render，而不是 enqueue 当下。队列与 Lane 的逐位推演见 11 · Update Queue 与 Lane。

阶段 3：原生 click 先判断 hydration blocker

根分别监听 click 的原生 capture/bubble 阶段，本例 onClick 由 bubble 路径调用。正常已挂载树中 findInstanceBlockingEvent 返回 null，事件才进入插件系统；若返回 Suspense/container blocker， click 在 capture 阶段会尝试同步 hydration；仍被阻塞则停止原生传播。当前 replay 槽只保存特定的 focus/drag/mouse/pointer 事件。

  1. target。DOM 节点缓存反查 HostComponent Fiber。
  2. listener。插件沿 Fiber return 链读取最新 props cache 中的 onClick。
  3. act 调度边界。三个 click 各自经过一次原生事件派发与事件批处理；不能把它们叫成“同一事件批”。但测试仍处于同一个同步 act 回调中，根调度回调被登记并去重到 actQueue；同步 act 回调返回后先冲刷这个队列（真实微任务也已登记，但要等宿主栈结束才执行），因此三个 action 都先入队，没有在 click 之间形成可见提交。

完整 capture/bubble、受控恢复和 blocker 重放见 15 · 事件与 hydration。

阶段 4：setCtr 不直接改 ctr，而是保存 action

mount 时生成的 dispatch 闭包已经绑定 Counter Fiber 与 Hook queue。每次 click 提交的是函数 action x => x + 1； current Hook 的 state 仍为 0。首个 action 可在 dispatch 中得到 eagerState=1，保存到 Update；下一轮 render 复用该结果，再依次计算第二、第三个 action，得到 3。eager 计算不会发布新 current 或更新 DOM。

函数 action 如何累计：函数 action 在 queue 重放时接收前一 action 的结果。若三次都是 setCtr(ctr + 1)， 三个 payload 都是 1；那是不同输入，不是批处理丢更新。

Hook 链、baseQueue、eager bailout 和 render-phase 更新见 13 · Hooks 状态机。

阶段 5：WIP 树计算到 3，current 与 DOM 仍保持旧值

RootScheduler 选择本批 Lane 后，work loop 在 Fiber 单元边界调用 beginWork。Counter 的 update dispatcher 克隆 Hook，重放 queue 得到 3； button element 随之变成 children=3。此时只修改 WIP Fiber 的 memoized state、props 与 flags，不修改可见 DOM。

Fiber 形状和双缓冲见 10 · Fiber 对象模型；key/type 复用与 Placement 见 12 · children 协调。

阶段 6：mutation 写 DOM，随后 current 才切换

commit 不能像 render 一样任意丢弃。mutation 先把 button 的宿主状态更新到 3；之后 root.current = finishedWork，layout 才能观察新树。 顺序反过来会让 unmount/layout 在错误的 current 上运行。

updateProperties 把 button 的文本从 0 写成 3；updateFiberProps 同时把事件系统将来读取的 handler 更新为本轮 props。 DOM 更新与事件闭包因此在同一次 commit 后一致。flags、Deletion、ref、错误和 effect 顺序见 14 · commit/effects/deletion。

阶段 7：passive effect 观察已提交的 3

测试中的 useEffect(() => yields.push(ctr)) 会在 render 中被调用，以登记 Effect 记录、依赖与 Fiber flags；但它传入的 create 回调不会在 render 或 mutation 阶段执行。 新 current 和 DOM 建立后，passive mount 运行 create。click 的 SyncLane 提交会在 flushSpawnedWork 中同步调用 flushPendingEffects，因此 effect 可在同一次 act 冲刷的提交尾部运行；它的闭包来自 ctr=3 的 render，日志增加 3。初次挂载的 passive 也会由 act 冲刷完，才返回对应的测试边界。

异常与清理：完整链必须解释出口

UNMOUNTED HANDLE

公开句柄先拒绝复用

root.render 读取到空 _internalRoot 时抛出 Cannot update an unmounted root.，不会再入队。

RENDER ERROR

候选树可丢弃或恢复

组件/reducer 抛错由 work loop 找边界并重试；未提交 WIP 不会成为 current。fatal error 才交根错误出口。

COMMIT ERROR

提交错误传播

已完成的 DOM mutation 保留；错误交给最近仍已挂载的边界或 root，提交遍历继续并安排恢复。

root.unmount() 先把句柄置空，再以同步 element=null Update 进入同一协调/提交管线，最后移除 container root marker。 因此 ref detach、layout/passive cleanup、portal 与 Fiber/DOM cache 清理不会被直接 innerHTML='' 绕过。

边界

  • 测试运行在 DEV + act；这里“三次 click 后只提交一次”依赖 actQueue 的测试调度语义，不能直接扩大为任意三个生产原生事件都会合成一次提交。生产由真实事件、host task/microtask 与根优先级共同决定。
  • 本例没有 key 移动、Suspense、hydration blocker 或 commit error；对应分支分别在 12、15、14 页展开。
  • Lane 具体 bit 由当前事件、transition、render context 与根模式决定；本页只证明控制权和状态所有权。
  • 源码版本以本仓库 package version 与证据页指纹为准，不从版本号推断缺失的 Git commit。

Suspense：一次 throw，为什么会经历两次 render

Suspense 不是“捕获 Promise 后直接把 DOM 换成 loading”。组件在 render 中抛出 thenable；reconciler 标记最近边界并退栈；同一个边界第二遍 render 才构造隐藏的 primary Offscreen 与可见 fallback。thenable 就绪后，ping 让根或已提交边界重新调度，下一遍 render 再决定能否提交主内容。

真实版本 19.3.0 连续源码 + 连续测试 Lane 所有权 Offscreen / effects 错误与卸载出口

先用一句话建立正确模型

Suspense 是 render 控制流 + 调度协议：“抛 thenable”中止当前 Fiber 完成；“边界捕获”选择替代子树；“ping/retry”只声明可能可运行；最终显示什么仍由下一次 render 计算，再由 commit 改宿主树。 本页的 wakeable 是 React 内部对“可订阅 thenable”的称呼：它是带 then 方法、可在 settle 时通知回调的对象；在本页流程中，wakeable 与组件抛出的 thenable 指同一个对象。

NOT DATA FETCHING

React 不拥有请求

资源层拥有 pending/resolved/rejected 记录和 thenable。React 只读取抛出的对象、订阅它，并在回调触发时重试。

NOT TRY / CATCH UI

fallback 不是 catch 里的 DOM

throwException 不创建 fallback DOM；它设置捕获标志。退栈返回边界后，beginWork 第二遍才协调 fallback。

NOT A PROMISE LANE

Lane 属于工作，不属于 Promise

同一 wakeable 可被多个根、边界或 Lane 读取。pingCache 以 root + wakeable + lanes 去重，而非给 Promise 永久绑定优先级。

  1. 第一次 render primary。函数组件执行资源读取；pending 记录抛出 thenable，source Fiber 加 Incomplete。
  2. 选择捕获者。Suspense handler 栈给出最近边界；边界记 ShouldCapture，wakeable 同时写入边界 retry queue，并给根安装 ping listener。
  3. 退栈并返回边界。unwindWork 恢复 context，把 ShouldCapture 换成 DidCapture，返回该 Fiber，工作循环从边界重来。
  4. 第二次 render fallback。updateSuspenseComponent 看到 DidCapture，构造 hidden primary Offscreen + fallback Fragment。到这里仍只是 WIP Fiber。
  5. commit fallback。mutation 隐藏或保留 primary 宿主节点并放入 fallback；commit 还会给边界 retry queue 中的 wakeable 安装 retry listener。
  6. resolve/reject 只发“可能就绪”信号。回调清理 cache、标 Lane、确保根进入调度链；它不读取组件，也不直接改 DOM。
  7. retry 再执行 primary。resolved 时资源返回值，Suspense 产出 visible primary，删除 fallback；rejected 时资源抛普通 Error，转交错误边界或 HostRoot。

阶段 1：用户组件读取 pending resource，并抛出 thenable

仓库测试没有把网络实现藏进 mock。readText 明确展示三态协议：resolved 返回 cache 版本；rejected 抛 Error；pending 抛 thenable。首次读取则原子创建 pending record，再抛同一个 thenable。真实组件 AsyncText 调用它时，这个 throw 会穿过组件调用栈进入 reconciler 的 render 异常入口。

资源状态readText 行为reconciler 分类下一步
pending抛带 then 的对象Wakeable / Suspense捕获边界、监听、可能 fallback
resolved返回值普通 renderprimary 可以完成
rejected抛 Error普通错误Class Error Boundary 或 HostRoot capture update

一个容易错的说法：不是“Promise resolve 后 React 从 Promise 里取数据”。ping 回调不消费 resolved value；retry 时组件再次执行 readText，由资源层返回值。

阶段 2：throwException 先区分 thenable，再找最近边界

throwException 先把 source Fiber 标成未完成。只有非 null object 且 then 是函数，才进入 Wakeable 路径；否则落到普通错误路径。最近边界不是沿 DOM 找，也不是运行时 try/catch 猜出来，而是 beginWork 进入 Suspense/Offscreen 时维护的 handler 栈由 getSuspenseHandler() 给出。

找到 Suspense/Activity/SuspenseList 后，函数做三件互不替代的事：

  1. 捕获控制流。markSuspenseBoundaryShouldCapture 给边界加 ShouldCapture，使退栈停在这里。
  2. 保存边界重试证据。把 wakeable 放入边界 Fiber 的 updateQueue Set；fallback commit 时将它转成真实 retry listener。
  3. 保存提交前唤醒机会。并发模式立即调用 attachPingListener(root, wakeable, rootRenderLanes)。如果资源赶在 fallback 提交前就绪，原 render lanes 可以重启。

ShouldCapture 表示“退栈时应由这个边界接住”；它还不是“已经选择 fallback”。并发路径同时把 boundary.lanes 记为本轮 rootRenderLanes，防止边界在第二遍过早 bailout。

阶段 3：ShouldCapture → DidCapture → 第二次 render fallback

工作循环沿 return 路径 unwind。到 Suspense Fiber 时，unwindWork 恢复 handler/hydration 栈，把“应该捕获”换成“本轮已经捕获”，然后返回边界 Fiber 本身。这个返回值让它再次成为工作单元，而不是继续退到根。

第二遍 beginWork 再进入 updateSuspenseComponent。此时才把 DidCapture 解释成 showFallback=true，并清掉标志，避免无限重复进入 fallback pass。

fallback Fiber 不是替换 primary：它与 hidden Offscreen 并存

首次 fallback pass 的 Fiber 形状是：Suspense 的 child 为 mode:'hidden' 的 primary Offscreen；Offscreen 的 sibling 是 fallback Fragment。保留 primary 让 React 能保存状态、继续预热和在恢复时复用；fallback 则是本次可见输出。

首次挂起与“已有内容退回 fallback”观察语义不同：首次可以直接挂载 hidden Offscreen；更新时会复用 current primary，是否立刻显示 fallback还受 Transition、shell、节流和 SuspenseList context 影响。因此本页讲状态机，不承诺所有更新都立即闪 loading。

阶段 4：pending / suspended / pinged 三个位集怎样变化

设触发首次 render 的 Lane 为 L；首次普通 render 因挂起跳过 sibling 时，React 为后台预热派生 RetryLane P；wakeable settle 后，已提交边界还可选择 RetryLane R。 这三者是不同来源，不能都叫“Promise 的 Lane”。真实值是位集，表中用符号避免把具体 bit 当 API。

markRootSuspended 把本次尝试并入 suspended，并从 pinged 移走同 Lane；这一步避免旧 ping 永久污染下一次挂起。markRootPinged 又只取 root.suspendedLanes & pingedLanes 的交集：已完成或不再挂起的旧 Lane 不会凭过期回调复活。

阶段 5：attachPingListener 用 root + wakeable + lanes 去重

pingCache 由 FiberRoot 持有。外层 key 是 wakeable，值是已订阅的 Lane 集合（源码称 thread IDs）。因此：

  • 同一 root、同一 wakeable、同一 lanes：只调用一次 then；
  • 同一 wakeable 被不同 Lane 读取：每组 lanes 仍可各有回调；
  • 同一 wakeable 被不同 root 读取：各 root 独立拥有 cache 和调度状态；
  • resolve 与 reject 都绑定同一个 ping：settle 只表示“再读一次可能得到不同结果”。

pingSuspendedRoot 首先删掉该 wakeable 的 root cache，再标记当前仍 suspended 的交集。若相同 root 正在相同 lanes 上 render，启发式规则可准备 fresh stack 或记录 WIP ping；最后一律调用 ensureRootIsScheduled，让 microtask 重新基于最新字段选 Lane。

阶段 6：fallback 提交后，边界 retry 不保证复用原 Lane

render 期存在边界 updateQueue 的 wakeable 集合。commit 的 attachSuspenseRetryListeners 为每个 wakeable 安装以边界 Fiber 为目标的回调，并在边界 retry cache 去重。settle 后 resolveRetryWakeable 删除 cache，再调用 retryTimedOutBoundary：

EARLY ROOT PING

通常复用原 render lanes

attachPingListener 闭包捕获 rootRenderLanes；fallback 提交前 resolve 时，原 L 可从 suspended 变 pinged。

PREWARM P

fallback 提交时派生

首遍挂起跳过 siblings 会写 ScheduleRetry；completeWork 申请 P，commit 后保留为 pending+suspended，并因尚未 warm 立即预热未探索 siblings。

COMMITTED BOUNDARY RETRY

常见是新 RetryLane

边界 state 中若没有保存 retryLane，requestRetryLane(boundaryFiber) 选择 R。dehydrated Suspense 等路径可复用已经保存的 retryLane。

为什么 resolve 不等于成功：回调只知道 thenable settled，不知道资源记录是 resolved 还是 rejected，也不知道其他 primary 子项是否仍 pending。retry 必须重新执行组件；只有整棵候选 primary 完成，才能提交它。

阶段 7：retry 成功后，显示 primary、删除 fallback，按连接状态更新或重连 effects

retry render 再次读取资源。若不再抛出，updateSuspenseComponent 走 primary 分支，把 Offscreen props 改为 mode:'visible'，把 fallback sibling 加入父边界 deletions，并清空 sibling。注意：这些仍是 render 期 Fiber 变更。

测试没有声称：每次挂起都必须先画 fallback；Transition 可能保留旧 UI，shell/节流可能延迟提交，资源若在 commit 前 ping 也可能直接完成 primary。这个用例只锁定“fallback 已提交后，多 wakeable 全部解决能恢复主内容”。

reject：同一个 ping 入口，下一遍转成普通 Error

wakeable.then(ping, ping) 对 resolve/reject 使用同一回调，因为调度层只负责再次尝试。测试资源的 rejectText 先把 record 变成 rejected，再广播 pings；retry 时 readText 命中 rejected 分支，抛出的已不是 thenable。throwException 随后落入普通错误路径，沿 return 找 Class Error Boundary；没有类边界时 HostRoot 建 root error update。

没有错误边界时：并发 render 的错误最终由 HostRoot capture update 与根的 onUncaughtError 路径处理；不是继续永久显示 Suspense fallback。Suspense 处理“仍在等待”，Error Boundary 处理“读取已经失败”。

过期 ping、边界卸载与无边界挂起的安全出口

STALE ROOT PING

只唤醒仍 suspended 的交集

markRootPinged 不把回调携带的 Lane 全量写入，只写 root.suspendedLanes & pingedLanes。Lane 已完成时，旧 ping 不制造新工作；scheduler 复查为 NoLanes。

DETACHED BOUNDARY

找不到 HostRoot 就停止

边界删除时 return 指针被断开。稍后 retry 调用 enqueueConcurrentRenderForLane，向上找不到 HostRoot 会得到 null，于是不会 markRootUpdated 或调度。

NO SUSPENSE BOUNDARY

并发根等待；legacy 同步报错

并发根仍可安装 root ping 并保持挂起，不提交半成品；legacy 同步输入缺少边界会转成明确错误，要求用 Suspense/Transition 建立恢复语义。

这里的“安全”是“不把已脱离工作重新接回树、不凭旧 ping 复活已完成 Lane”。React 无法取消用户资源本身；请求取消、订阅释放、cache 淘汰仍由资源层负责。自定义 thenable 也应遵守只 settle 一次的 Promise 约定。

边界说明：读完后仍不要过度外推

  • 版本边界：本页对应仓库 packages/react/package.json 的 19.3.0；Activity、CPU Suspense、View Transition、特性开关会增加分支。
  • renderer 边界：测试使用 ReactNoop 锁定 reconciler 语义；DOM renderer 的 hide/unhide 最终由 HostConfig 实现，具体节点样式/属性不在该测试中证明。
  • 调度边界：表中的 L/R 是符号。Lane 选择受事件、Transition、hydration、entanglement、retry lane 池和根模式影响，不是公开稳定常量。
  • 可见性边界：fallback 何时提交由 shell、Transition、JND/节流、SuspenseList、prewarm 等规则决定；状态机不等于固定时间表。
  • 资源边界：React 的 wakeable 协议不定义网络缓存、去重、取消和一致性。测试 cache 是证据 fixture，不是生产数据层建议。
  • hydration 边界：dehydrated Suspense 还包含 selective hydration、ForceClientRender 和 replay；请结合 15 · 事件与 hydration 阅读。

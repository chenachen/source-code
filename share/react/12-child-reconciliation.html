一次重排，怎样变成可提交的 Fiber flags

[A, B, C] → [B, A, D] 看似一次数组比较，实际要同时回答三件事：谁仍是同一个组件、谁需要移动或插入、谁必须在 commit 清理。React 先顺序试配；首个 key 失配后才建立 Map，并用单调的 lastPlacedIndex 生成副作用。

react-reconciler 0.34.0React 19.3.0真实源码 + 手工推演真实 GWT 测试

算法输入与输出：它不直接改 DOM

教学页序不等于函数组件运行序。本指南先讲通用 child identity 算法，再讲 Hooks，便于单独手算 key；但一次函数组件更新的真实顺序是 11 · 调度/选 Lane → 13 · renderWithHooks 计算 state 并返回新 children → 本页 reconcileChildren 把新 children 变成 child WIP/flags。 类组件或 HostRoot 产生 children 的方式不同，进入 ReactChildFiber 后的 key 算法相同。

return Fiber共同父 Fiberflags、deletions记录 ChildDeletion 与待删 child
WIP childrenB(0) → A(1) → D(2)alternate、新 index、Placementcommit 阶段才转成宿主移动、插入、删除

身份判定不是只看 key。同一父 Fiber 下，key 先找到候选 current Fiber；updateElement 还要确认 elementType 兼容。兼容才创建带 alternate 的 WIP，组件 state 随 Fiber 身份保留；同 key 不同 type 仍会重建。

reconcileChildrenArray 不先构造“DOM diff”。它边生成 WIP sibling 链，边给 child 写 Placement，并把未复用 current child 收集到父 Fiber 的 deletions。这使 render 仍可被丢弃：真实宿主树尚未变化。

匹配 key 后，还要通过类型兼容检查

调用方先用 key 找到候选，updateElement 再决定是否复用。普通元素比较 current.elementType === element.type；开发期 Refresh Family 与解析后的 lazy type 也有兼容路径。通过检查才调用 useFiber，把旧状态带进 WIP；未通过则新建 Fiber，由外层把旧节点记录为删除。

源码 1：删除链与剩余项 Map

deleteRemainingChildren 服务于“新数组先结束”的快出口；本例进入 Map 慢路径，最后通过相同的 deleteChild 删除 Map 剩余项。两条路径最终写入同一父 Fiber。

显式 key 使用 key；无 key child 退化为旧 index。因此“没写 key”不是没有身份规则，而是把易变化的位置当身份。REACT_OPTIMISTIC_KEY 是当前版本受 feature flag 控制的额外分支，本页主例不走它。

源码 2：updateSlot 只负责同槽试配

顺序快路径拿当前 oldFiber 与同一 newIdx 的新 child 试配。元素 key 不同就返回 null；这个 null 不是“删除 B”，而是通知外层停止顺序扫描、保留当前 old 链并转入 Map。

节选边界：本段只保留文本与 Element 决策，省略区间内说明注释和 optimistic key 分支；函数后半还处理 Portal、Lazy、Fragment、thenable、Context 与非法类型。

源码 3：Map 找身份，lastPlacedIndex 判断位置

updateFromMap 先按显式 key（或无 key 的 newIdx）取候选 Fiber，再交给 updateElement 比 type。placeChild 不决定身份，只读取复用结果的 alternate.index 决定位置副作用。

alternateoldIndex 比较判断相关 flags
存在oldIndex ≥ lastPlacedIndex仍在已确认的单调旧序列中，可留位不加 Placement；返回 oldIndex
存在oldIndex < lastPlacedIndex旧位置落在已放置节点之前，需要移到其后Placement；不加 PlacementDEV
不存在没有旧 index新挂载插入Placement | PlacementDEV

源码 4：慢路径消费 Map，最后删除剩余项

只有真的复用了 current（newFiber.alternate !== null）才从 Map 删除。若 key 找到了但 type 不兼容，updateElement 创建无 alternate 的 Fiber：旧项仍留在 Map，末尾进入 deletion；新项由 placeChild 标为插入。

完整手推：[A,B,C] → [B,A,D]

TEACHING TRACE 假设 A/B/C/D 都是同一组件 type，key 分别为字母；这是对上面真实分支的逐步求值。lastPlacedIndex 是“已确认可不移动节点的最大旧 index”，不是当前 DOM 下标。

为什么移动 A，不移动 B？处理 B 后，算法选择旧 index 1 作为单调基线。之后 A 的旧 index 0 落后于它，所以移动 A 到 B 后即可得到 B,A。flags 描述一种正确提交方案，不承诺“直觉上被拿到前面的节点一定带移动标志”。

state 为什么跟 key 走，而不是跟屏幕位置走

TEACHING TRACE 假设提交前 A、B、C 各自 Hook state 为 17、42、9。Map 只负责找到 candidate；真正保留发生在 updateElement → useFiber → createWorkInProgress 建立 alternate 时。

新位置key / typecandidatealternate渲染后 state原因
0B / Rowold B / Row有42同父、同 key、兼容 type
1A / Rowold A / Row有17位置变化不破坏已找到的身份
2D / Row无无初始值新 Fiber mount
—C / Row未消费 old C不进入 WIP 链不再可见commit 删除时执行 ref/effect/宿主清理

换成 <Other key="A" /> 时，Map 仍能找到 old A，但 type 不兼容；结果是 old A 删除、new Other 插入，原 state 不保留。把 A 移到另一个父节点也一样：每个父 Fiber 的 child 协调是独立身份域，没有跨父 Map。

第二个测试把“身份保留”落实到真实 DOM 引用：交换后仍是原来的两个节点，只是位置对调。它不直接观察 Fiber flags；flags 到 DOM 操作的桥接由 commit/HostConfig 负责。

源码注释明确当前 Fiber 没有 child 的 backpointer，因此没有双端搜索；Iterable 若要双端处理还需先复制全集。lastPlacedIndex 是贪心单调扫描，目标是在线性流程中得到正确宿主顺序，不承诺全局最少移动数。

失败边界：key 不是万能身份证

输入边界真实行为可见风险对应分支
无 key 列表前插顺序路径按槽位匹配；进入 Map 时按 index 匹配相同 type 的 state 可能跟位置而非业务项绑定key === null ? newIdx : key
重复 keyDEV 警告；Map 的单值槽不能表达两个稳定身份child 可能重复或遗漏，行为不受保证warnOnInvalidKey
同 key、不同 type候选命中但 updateElement 新建 Fiber旧 state/effect 清理，新组件 mountalternate === null，旧项留 Map
跨父节点移动两个父级各自协调旧父删除，新父插入；state 不保留Map 仅含当前 returnFiber children
null/boolean/undefined 空槽当前快路径无法区分 miss 与空结果，可能提前进 Map主要是性能边界，不等于错误删除源码中的 TODO
新数组先结束调用 deleteRemainingChildren剩余所有 sibling 等待 commit 清理数组快出口
旧链先结束剩余新 child 直接创建全部标插入；无需 Map批量插入快路径
新建父 Fiber 的首轮 children 协调mountChildFibers 不记删除/Placement；列表节点标 Forked新建子树由上层 Placement 插入；HostRoot 首次客户端 render 仍走 reconcileChildFibers，hydration 另由游标认领宿主placeChild 早退

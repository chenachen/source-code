02 · Host scheduling

scheduler：把工作切成 host 可接受的片段

Scheduler 接收带优先级、可延迟的回调；回调返回函数时，表示剩余工作由 continuation 继续。 默认 DOM/Node 实现用两个最小堆排序，再通过 host API 分批执行。它调度函数，不知道 Fiber、Lane 或 DOM。

scheduler 0.28.0 25 个手写 JS 目标 默认时间片 5ms

先纠正三个常见误解

NOT FIBER

它不选择 React 更新

reconciler 先把根级工作归约成回调与 Scheduler Priority；Scheduler 只决定哪个 callback 先获得 CPU。

NOT PREEMPTION

它不能强行中断 JavaScript

只有 callback 主动返回，或 React 在工作单元边界检查 shouldYield，控制权才回到 host。

NOT DEADLINE ABORT

“过期”不是取消

过期任务会绕过时间片让步并尽快执行；取消则把 callback 置空，之后由堆顶路径惰性清理。

同一 Task 在任一时刻最多属于一个堆。迁移时才把排序键从 startTime 改成 expirationTime； 这让延迟任务不会因“最终很高优先级”而在可运行之前挡住 ready work。

算法一：稳定的数组最小堆

push 把节点放到数组末尾并向上修复，pop 用末尾节点替换根再向下修复，均为 O(log n)；peek 为 O(1)。 比较器先看当前队列的主排序键，再用单调递增 id 保持同键 FIFO。

为什么取消不在任意下标删除？当前 Task 没有维护 heap index；查找并修复任意节点会增加状态与热路径成本。 把 callback 置 null 是 O(1)，代价是节点仍留在堆数组中，直到到达堆顶被扫描清理。

算法二：delay 与 priority 共同决定队列

schedule 先得到 startTime = 当前时间 + 正数 delay；未提供有效正数 delay 时直接使用当前时间。 再从 startTime 加优先级预算：Immediate 为 −1ms、UserBlocking 250ms、Normal 5000ms、 Low 10000ms、Idle 用最大 31 位整数。未知优先级按 Normal 预算计算，但 Task 仍保留调用方原值。 因此延迟 Immediate 任务也必须先等到 startTime；迁入 ready 堆时才以已过期任务执行。

work loop：让步、continuation 与重新竞争

workLoop 总是查看 ready 堆顶。默认模式下，未过期任务在 host 要求让步时停止；过期任务绕过这项检查。 执行前先把 callback 置 null，防止错误或重入把同一函数重复消费。返回函数时把它写回同一 Task， 但立即结束本轮 slice，让 continuation 在新的 host task 中重新与更高优先级工作竞争。

callback 内部可能安排更早到期的任务，所以完成后只在当前任务仍是堆顶时直接 pop；否则它以 callback=null 留在堆中，后续扫描再清理。下一次选择始终重新 peek，因而不会误弹新任务。

非 always-yield 模式且 enableRequestPaint 开启时，shouldYieldToHost 优先响应 renderer 的 paint 请求，再比较本轮耗时与 frameInterval。默认 5ms，WWW fork 为 10ms； 时间片不对齐显示器帧边界。开启 enableAlwaysYieldScheduler 时，每轮先处理一个堆顶节点， 然后只连续处理已过期节点，把后续未过期工作留给下一 host task。

host loop：只保留一次唤醒，错误后仍不饿死队列

模块初始化时捕获当时的 setImmediate/setTimeout 引用，后续改写全局函数不会替换这些引用。 默认优先 setImmediate，其次 MessageChannel，最后才用 setTimeout，后者可能受到嵌套 timer clamp。

这里故意不 catch 并吞掉用户错误。初始 hasMoreWork=true 意味着 flush 抛错时 finally 仍发送下一条 host message， 原错误照常离开当前 task，后续队列也不会永久滞留。

手工推演：高优先级工作如何插入 continuation

下面跟随 Mock 测试：虚拟时间从 0 开始，Normal 工作依次处理 A/B/C/D，每段耗时 100ms；测试先只允许输出 A。

  1. t=0。Normal Task N 入 ready 堆，expiration=5000，id=1。
  2. t=100。waitFor(['A']) 限制本次日志数量。A 输出后 shouldYield 返回 true，N 留下 continuation；expiration 与 id 均不变。
  3. 插队。UserBlocking Task H 入 ready 堆，expiration=100+250=350，小于 N 的 5000，成为堆顶。
  4. 继续 flush。waitForAll 重新驱动 workLoop，先执行 H；H 推进到 t=200，完成并 pop 后才再次看到 N。
  5. 恢复。排空时没有日志数量限制，N 可以在同一个 callback 内处理 B/C/D，最终时间为 t=500。日志严格按 High pri、B、C、D 排列。

这条 Mock 测试说明堆顶会重新竞争。生产默认实现另有一条规则：只要 callback 返回 continuation， 就立即结束当前 host task；Mock 的普通 flush 可以在同一轮继续，paint flush 才要求 continuation 先让出。

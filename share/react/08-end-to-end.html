A. 初次挂载：root.render 如何到达 DOM

  1. react · 描述。JSX 工厂创建 Counter element；shared Symbol 将它标成可被 renderer 识别的元素记录。
  2. react-dom · 入口。createRoot 已校验 container、创建 FiberRoot、标记容器并安装根事件监听；root.render 把 element 交给 updateContainer。
  3. reconciler · 入队。HostRoot 得到包含 {element} 的 Update 与 Lane；scheduleUpdateOnFiber 标记 pendingLanes 并安排根。
  4. scheduler · 获得 CPU。非同步根工作被映射为 priority callback；Scheduler 在 host task 中调用 performWorkOnRoot，时间片边界可 yield。
  5. reconciler · begin。HostRoot 消费 update queue，协调 Counter；renderWithHooks 安装 mount dispatcher，useState 建 hook；Counter 返回 button element。
  6. reconciler · complete。HostComponent completeWork 调 DOM HostConfig 创建 button、缓存 Fiber/props、设置文本与初始属性，再冒泡 Placement 等 flags。
  7. reconciler → bindings · commit。mutation 找 container 并 append button；current 切换；layout/ref 执行；根监听器早已存在，无需每个 button 单独装 onClick。

挂载完成后保存的是两类关联：Fiber 保存 state/update queue 与宿主 stateNode；DOM 节点缓存最近 Fiber 与 props。 前者服务 render/commit，后者服务原生事件 target → Fiber/handler 的反向查询。

B. click：控制权从 DOM bindings 返回 Fiber

  1. 原生输入。浏览器把 click 交给 root 容器 listener，不直接调用 JSX 中的函数。
  2. 事件优先级。ReactDOMEventListener 识别 click 为 discrete，临时设置 DiscreteEventPriority。
  3. 定位。通过 DOM 节点缓存找到 button 的 HostComponent Fiber；确认它没有被 hydration 边界阻塞。
  4. 提取。SimpleEventPlugin 建 SyntheticMouseEvent，沿 Fiber return 链累积 onClick capture/bubble listeners。
  5. 批量派发。DOMPluginEventSystem 在 batchedUpdates 中按顺序调用 handler；handler 执行 setCount。
  6. 恢复表单。派发结束时，如有受控表单节点被浏览器临时改变，统一 restore committed state；本例没有额外恢复。

D. 更新 render：旧树提供基线，新树记录差异

  1. 选择 lanes。RootScheduler 取最高优先 pending lanes；离散同步工作通常在当前事件后的微任务边界 flush。
  2. 准备 WIP。从 root.current 的 alternate 创建/复用 WIP，保留旧 Fiber 作为比较基线。
  3. 执行 Counter。update dispatcher 克隆旧 hook，按 Lane 重放 queue：0 → 1；返回同 type/key 的 button element。
  4. 协调。Counter 与 button Fiber 均可复用；文本 child 从 0 变 1，HostText 或 HostComponent 路径获得 Update flag。
  5. 完成。completeWork 不把 button 重新插入，只汇总更新 flags；若其他 props 相同，onClick 函数身份变化仍会进入 props 提交/缓存更新路径。
  6. 提交。commitTextUpdate 写 nodeValue 或属性路径更新文本；DOM props cache 更新为本轮 props；root.current 指向完成树。

E. hydration 事件：click 与连续事件从 blocker 后分叉

  1. 共同入口。原生事件到达根 wrapper；若 target Fiber 对应 dehydrated Suspense 或未完成 HostRoot，attemptToDispatchEvent 返回 blocker，不先调用组件 handler。
  2. 离散 click 分支。capture 阶段的 click 会尝试同步 hydration 并重新 lookup；若成功，立刻走正常插件派发。
  3. click 仍阻塞。当前实现停止这次原生传播并返回；它不会进入下面的通用连续事件 replay 槽，因此不能承诺 commit 后补发这次 click。
  4. 受支持连续事件分支。focus/drag/mouse/pointer 等把 native event、flags、container 与 blocker 保存到对应槽；同类后续事件按连续状态语义合并最新目标。
  5. 提交解锁连续槽。hydration/client-render commit 调 retryIfBlockedOn；只解锁匹配 blocker，随后重新定位最新 Fiber 与 latest props。
  6. 重放或清理。已可用则 clone 原生事件并重新走根 listener；仍阻塞则换 blocker 等待；mouseout、节点失效或边界被替换时按槽规则清除，而非调用陈旧 handler。

这条链解释了为什么 hydration 与事件不能分开读：事件系统不仅合成浏览器事件，还是 selective hydration 的外部优先级入口。

Scheduler 不等待 Promise；它只在 React 安排 callback 时执行函数。thenable listener 属于 reconciler，resolve 后再把根送回调度管线。 若 fallback 被提交，DOM bindings 负责隐藏/显示或插入相应宿主子树；effect reconnect 由 commit 语义处理。

G. unmount：同一条管线提交“空树”

root.unmount 不是直接清空 container.innerHTML。 它同步 enqueue element=null，让协调生成 deletions。mutation 窗口 detach ref、运行 insertion/layout cleanup、移除 portal/host descendants，并先断 deleted Fiber 的 return； passive 窗口再运行 passive destroy、彻底 detach Fiber，并清 DOM→Fiber/latest-props cache。公开 root 更新同步冲刷后，react-dom 解除 container 的 root marker。 这两个清理窗口不能压成“先 passive、再删 DOM”的单一顺序。

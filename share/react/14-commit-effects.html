14 · Deep dive / commit effects

同一棵 Fiber 树，怎样变成唯一可见现实

render 构建 WIP/finishedWork、flags，并可在 completeWork 创建和组装尚未接入页面的宿主候选；它不修改已提交宿主树。commit 才依次读取旧 DOM、写宿主树、切换 root.current、连接 ref/layout effect，并在后续冲刷 passive effect。下面不再只列阶段名，而是让一棵带 Snapshot / Placement / Update / ChildDeletion / Ref / Passive 的树完整跑一遍。

先记住一个结论

FLAGS

flags 是待办位，不是补丁对象

fiber.flags 描述本节点；fiber.subtreeFlags 只汇总后代，用于按阶段 mask 跳过整棵无关子树。

SWITCH

DOM 先变，current 后切

mutation 期间卸载逻辑仍按旧 current 判断；DOM 完成后才执行 root.current = finishedWork，layout 因而读到新树。

ERROR

提交错误触发下一轮恢复

React 把错误排到最近边界或 HostRoot 的 SyncLane；已经完成的 DOM/ref/effect 动作不会事务式撤销。

“commit 同步”不等于所有 effect 同步。before-mutation、mutation、current 切换与 layout 构成可见提交关键区；useEffect 属于 passive 阶段，通常由后续调度冲刷。若同步工作要求，React 也可能更早冲刷 passive。

四个字段决定遍历，不需要一条全局 effect 链

字段由谁写commit 怎样用不代表什么
flagsbegin/complete/reconcile 与 Hook 处理决定当前 Fiber 的 Placement、Update、Ref、Snapshot、Passive 等动作不自动包含后代工作
subtreeFlagsbubbleProperties 在 complete 阶段上冒与阶段 mask 按位与；为 0 就跳过后代不是按执行顺序排列的队列
deletionschild reconciliation 的 deleteChild父 Fiber 在 mutation/passive 路径访问被删旧 Fiber删除节点已不在 finishedWork 的 child 链上
alternate双缓冲 Fiber 克隆读取旧 props/state/ref；切换后互为 current/WIP不是第三棵历史树

这段代码给出关键因果：子节点的自身 flags 与其后代 flags 都被 OR 到父节点；所以根能用一个 mask 判断“某阶段整树有没有工作”， 阶段遍历也能在任意层剪枝。但执行次序仍由 ReactFiberCommitWork 的深度优先函数决定。

本页唯一示例：列表更新、快照、ref 与两类 effect 同时发生

设已提交页面包含 Measure、标题文本与列表 [A, B]。本轮更新把标题 old 改为 new，列表改成 [B, C]，同时替换 <section> 的 ref，且 App 的 layout/passive 依赖都变化。B 复用且保持相对顺序；删除 A 后它自然成为首项，不需要 Placement。C 是唯一新增项。

为什么 A 不出现在新 child 链：它属于旧 current 树。协调器把它放进 section.deletions，再给 section 写 ChildDeletion；否则只遍历 finishedWork 会永远找不到待卸载子树。

时刻root.current浏览器 DOMref/effect
render 刚结束旧树old + [A,B]oldRef、旧 create 已连接
before-mutation 后旧树仍是 old + [A,B]Measure 已保存 snapshot
mutation 后仍是旧树new + [B,C]A/oldRef/layout 旧连接已拆；passive 旧连接待拆

阶段 1 · before-mutation：必须在 DOM 变化前读快照

prepareForCommit保存 selection / 焦点
→
Snapshot mask剪枝到 Measure
→
getSnapshotBeforeUpdate读取 old DOM

Measure.flags & Snapshot 使 getSnapshotBeforeUpdate(prevProps, prevState) 在这里运行。 返回值暂存在 class instance 的内部字段 __reactInternalSnapshotBeforeUpdate，随后由 componentDidUpdate 读取；它不属于 class updateQueue。若把它放到 mutation 后，列表位置、滚动高度等已属于新 DOM， “修改前快照”便失去定义。

示例状态：snapshot = {oldHeight, oldScrollTop} 被保存；DOM、current、ref 与 effect 均未变。 prepareForCommit 还让 DOM renderer 保存 selection/active instance，为 mutation 后的恢复做准备。

阶段 2 · mutation：先消费 deletions，再进入带 mask 的 child

  1. 删除 A。section 的 deletions=[A] 先被消费。React 运行 class componentWillUnmount、layout/insertion cleanup、ref detach，并移除正确的顶层宿主节点；Portal 会切换宿主 parent，不能化约成一次固定 removeChild。
  2. 更新标题。HostText 的 Update 最终进入 HostConfig 的 commitTextUpdate，DOM 文本从 old 变为 new。
  3. 复用 B。B 的 oldIndex=1，而此时 lastPlacedIndex=0，所以不写 Placement。删除 A 后 B 在 DOM 中自然成为首项；本例没有已有节点移动。
  4. 插入 C。C 无 alternate；commitHostPlacement 递归找到其宿主 descendants 并插入。
  5. 更新 section 并换 ref。old/new props 交给 commitHostUpdate；旧 ref 在 mutation detach。新 ref 此时不能 attach，因为整树 mutation 还未完成。
  6. 拆旧 layout effect。函数组件更新时，旧 insertion/layout destroy 在 mutation 路径运行；App 的 layout destroy 发生在其后代 mutation 后。不能把“所有 layout cleanup 都先于所有 DOM 写入”当成不变量。

清掉 Placement 表示动作已经消费，避免后续生命周期把节点误判为未插入。它不清除 PlacementDEV 等静态/开发标志。

阶段 3 · current 切换：只有一行，却定义观察边界

这不是复制 DOM，也不是交换两棵树全部字段，只是把根的权威指针转向 finishedWork。旧树仍由各 alternate 可达，供下一轮复用；但公开查询、事件的 mounted 判断和 layout 生命周期从此以新树为已提交树。

本例切换瞬间：DOM 已是 new + [B,C]，但 newRef/createL 尚未执行。 这是短暂的内部窗口，不会让浏览器事件循环在两行同步 JS 中间任意插入普通任务；layout 紧随其后。

阶段 4 · layout：连接能同步观察新 DOM 的工作

递归在本节点动作前发生，所以普通 layout mount/update 是后代先、祖先后。本例中：

  • newRef attach 后指向完成更新的 section 宿主实例；对象 ref 写 current，函数 ref 的返回 cleanup 存入 fiber.refCleanup。
  • Measure.componentDidUpdate(prevProps, prevState, snapshot) 同时看到新 current、新 DOM 和 before-mutation 保存的旧快照。
  • App 的 createL 读到 new + [B,C]；若它同步 setState，会产生另一轮工作，但不把本轮回退到 render。
ref 情形mutationlayout失败时
对象 ref 替换oldRef.current = nullnewRef.current = instancesafe wrapper 路由到 commit error
函数 ref 返回 cleanup下次 detach 优先调用已保存 cleanup调用新 ref(instance)，保存返回值cleanup/create 都受 commit 错误捕获
Fiber bailout 但 ref 变Ref flag 仍拆旧 ref仍附加新 ref宿主输出可完全不变

阶段 5 · passive：先拆旧订阅，再建新订阅

主提交把状态推进到 PENDING_PASSIVE_PHASE 后，flushPassiveEffects 以不高于 Default 的事件优先级进入实现。 实现先清空 pending root/finishedWork 引用，再在 CommitContext 中执行全树 passive unmount 与 mount。

本例结果是 destroyP(oldDeps) 先于 createP(newDeps)。删除 A 的 passive cleanup 也在 unmount 遍历完成；删除树随后断开 child/sibling 等引用，避免已卸载 Fiber 长期保留组件与 DOM。DEV Strict Effects 可能额外模拟一次拆装，不能把开发日志次数当生产次数。

lastEffect.next 是首节点，所以无需额外数组即可遍历环。只有 (effect.tag & flags) === flags 的 effect 执行；依赖未变的 effect 仍留在链中，但没有本轮 HookHasEffect，不会无故 destroy/create。

删除不是一个 DOM API：它跨两个提交窗口清理

资源删除树 mutation后续 passive原因
class 生命周期componentWillUnmount无类卸载属于同步提交语义
layout/insertion effectdestroy无不能让已删除组件继续同步观察布局
refcleanup / null / current=null无DOM 移除后不得继续暴露为 mounted instance
宿主节点从正确 host parent/container 移除无当前可见提交必须完成
passive effect标记并保留必要 Fiber 关系destroy不阻塞本次可见提交
Fiber / DOM 内部关联detachFiberMutation 只断 deleted Fiber 与 alternate 的 return，使 mounted 检查立即失败detachFiberAfterEffects 清 child/sibling/state/updateQueue，并由 detachDeletedInstance 移除 DOM→Fiber/props cache既要立即失去 mounted 身份，又要保留 passive cleanup 遍历，最后才允许 GC

若 cleanup 抛错，safe wrapper 捕获后继续其余清理。一个 destroy 失败不能成为跳过兄弟 ref、DOM 删除或其他 destroy 的理由。

错误路径：记录恢复更新，不回滚已经发生的动作

  1. 归属 source。HostConfig、lifecycle、ref、effect wrapper 都把抛错 Fiber 传入捕获函数。
  2. 向 return 搜边界。可用 class error boundary 优先；否则到 HostRoot。
  3. 排 SyncLane。错误 fallback 是下一次 render/commit，不是当前调用栈里反向执行 DOM API。
  4. 当前遍历继续。捕获函数返回，调用侧可继续兄弟 effect 和必要清理。
  5. 恢复树再提交。边界 fallback 删除失败子树；这会产生新的 flags、mutation 和 cleanup。

不回滚的可观察含义：若 C 已插入，随后某个 ref 或 componentDidMount 抛错，React 不先把 C 移回“提交前 DOM”。它完成当前必要工作，再同步调度错误边界；下一次提交可能删除整棵失败子树并显示 fallback。

真实测试 2 · bailout 也不能吞掉 ref 所有权交换

Given：shouldComponentUpdate 恒 false。When：只替换 ref。 Then：没有 Render 日志，输出不变，但 ref1 清空、ref2 附加。测试直接证明的是 bailout 不能吞掉 ref1→ref2 的最终所有权交换， 以及 Ref 工作独立于 DOM Update。old ref 在 mutation detach、root.current 随后切换、new ref 在 layout attach 的中间顺序，则由 WorkLoop/CommitWork 阶段源码证明，不能只靠终态断言反推。

把示例压成一条可复述调用链

  1. render / complete：协调、Hooks、begin/complete 各自写本节点 flags，deleteChild 在协调时保存 section.deletions；completeWork 主要完成宿主候选，bubbleProperties 再把后代 flags 上冒到 HostRoot。
  2. before-mutation：按 BeforeMutationMask 剪枝；Measure 读取旧 DOM snapshot，renderer 保存 selection。
  3. mutation：section 先卸载 A，再改标题、复用原位 B、插 C、写属性、detach oldRef；旧 layout cleanup 在对应 Fiber 路径执行。
  4. HostConfig 收尾：resetAfterCommit 恢复 DOM 选择/事件状态。
  5. 逻辑提交点：root.current = finishedWork。
  6. layout：didUpdate 收到旧 snapshot；newRef attach；新 layout create 观察新 DOM。
  7. passive：全树 passive unmount 后 mount；删除树完成 passive cleanup 与最终 detach。
  8. 若任一步用户代码抛错：捕获到边界/根的 SyncLane；当前必要遍历继续，下一轮提交 fallback，不回滚既有动作。

边界与本页没有偷换的概念

  • 示例 flags 树是教程状态模型（不可执行）；flags 名称、字段关系与阶段顺序来自当前源码，具体 Fiber 组合用于集中展示机制。
  • 代码框标“连续原码/连续测试原码”时可在链接文件逐字连续匹配；“删节源码”明确写出省略内容；状态模型统一标“教程伪代码”。
  • View Transition、Offscreen 隐藏/重连、资源 hoist、persistence renderer 有额外 phase/flag 分支；本页主线针对 DOM mutation renderer。
  • “通常 paint 后 passive”不是浏览器时序硬保证；同步 flush、离散更新或嵌套更新可能改变实际 paint 机会。
  • commit 不回滚是当前控制流事实；不是建议用户依赖某个失败提交留下的瞬态 DOM。

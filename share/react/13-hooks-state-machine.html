Hooks：dispatcher 怎样读取位置链、重放状态并登记 Effect

公开 useState 只转发到当前 dispatcher。reconciler 在函数组件求值前安装 mount、update 或 rerender 实现；每次 Hook 调用推进同一条位置链。state 更新进入带 Lane 的环形队列，低优先级项被保留并在未来 rebase；Effect 则进入另一条提交队列，render 只登记，commit 才 create 或 cleanup。

dispatcher：同一个 useState，三种阶段实现

react 包页面已经说明公开 API 从 ReactSharedInternals.H 取 dispatcher。本页从 reconciler 接手：renderWithHooks 先清空 WIP 的旧链与组件级更新队列，再根据 current 形状安装 mount/update dispatcher。

上块由三处各自连续的相邻条目并列展示，不是一个连续文件区间。每组条目本身逐字来自当前三个 dispatcher 对象；完整对象还映射 Context、Effect、Memo、Transition、Id、ActionState 等 Hook。

dispatcher进入条件state 行为Effect 行为退出
Mount没有可更新的 current Hook 链创建 Hook、初始 state、queue 与绑定 dispatch创建 Effect，标 HookHasEffect 与 Fiber flags组件返回；finish 恢复 ContextOnlyDispatcher
Updatecurrent 有有状态 Hook 链按位置克隆 current Hook，合并 pending/baseQueue，按 renderLanes 重放比较 deps；相等则不加 HookHasEffect保存 WIP 链，检查少调用 Hook
Rerender同一次函数求值中发生 render-phase update，或 DEV Strict 额外 pass复用刚建的 WIP Hook，消费 render-phase pending 环，不再检查 Lane沿 WIP 链重新登记直到没有新 render-phase update；每次额外循环最多 25 个 pass

生产选择依赖 current.memoizedState，所以只用不分配状态节点的 Hook 时存在形状边界；DEV 额外用 _debugHookTypes 区分并校验。这里的“mount/update”是 Hook 实现阶段，不等于组件是否拥有一个 current Fiber 的唯一判断。

位置不变量：两个游标必须同步前进

TEACHING TRACE 上一轮是 #1 useState(count) → #2 useRef(node) → #3 useEffect。若本轮条件分支跳过 #1，第一次位置调用会拿到 old #1，却按 useRef 解释；后续 queue/type 形状错位。React 不是读取变量名纠正，而是用 DEV hook type 序列报警、在更多/更少 Hook 时抛错。

use 是边界例外。本页的位置链规则针对 useState/useReducer/useRef/useEffect 等普通位置型 Hook；当前 React 的 use 有独立 thenable/context 路径，不应把这里的 Hook 节点模型机械套到它允许的条件调用场景。

mount：一次 useState 建立 Hook、共享 queue 与稳定 dispatch

dispatch 闭包绑定 Fiber 与共享 queue，所以事件回调不需要知道当前 render pass 的 Hook 游标。updateState 后续直接复用 basicStateReducer 的 reducer 队列实现；值 action 返回该值，函数 action 接收前一 state。

dispatch：先选 Lane，再尝试 eager 快路径

普通事件 dispatch 不会立刻改写 queue.pending。enqueueConcurrentHookUpdate 先把 Fiber、queue、Update、Lane 四元组暂存到模块级 concurrentQueues；进入 render 前，finishQueueingConcurrentUpdates 才把它接入各 Hook 的 pending 环，并把 Lane 沿 return 路径传播到 root。 这样 render 中途收到的更新不会立即改动当前正在遍历的父链。空闲时 eager bailout helper 会立即调用 finishQueueingConcurrentUpdates，因此“先暂存”不保证 queue.pending 会一直为空。另有“组件渲染自己时又 setState”的 render-phase 分支会直接写本组件 queue.pending。

eager bailout 仍保留 update。enqueueConcurrentHookUpdateAndEagerlyBailout 仍保存更新，使随后其他 Lane 插队时能够按原顺序 rebase。它只是在当前 Fiber 与 alternate 都没有待处理 Lane、eager 结果按 Object.is 相同时不安排本次 render。

派发输入eager 结果当次调度update 去向
setCount(1)，当前 1，队列可 eager1，与当前相同不调度；函数组件可完全不进入 render仍入队保留 rebase 语义；空闲时 helper 会立即转入 pending 环
setCount(2)，当前 1，队列可 eager2，不同按 Lane 调度 root先入全局并发缓冲；转移后携 hasEagerState/eagerState 进入 pending，render 可免算 reducer

当前函数组件 render 内派发自己不走普通并发队列标记额外 render pass进入 render-phase pending 环

baseQueue：低优先级可以跳过，但不能从历史中消失

updateReducerImpl 先用 O(1) 指针交换把 queue.pending 环并入 baseQueue，合并后的环尾先写回 current.baseQueue，然后清空共享的 queue.pending：本次 WIP 若中止，下次仍能从 current 找回这些更新。随后从 baseState 顺序重放。某项 Lane 不在本轮 renderLanes 中就克隆保留；它之后已经执行的普通高优先更新，也必须以 NoLane 克隆到新 baseQueue，未来重放才能保持原始顺序。

上块省略了高级 Hook 分支。真实函数在 Lane 判断中还处理 Offscreen 隐藏更新、GestureLane、乐观 revertLane 与 async action 纠缠；这里保留普通 state 主线并删除了这些条件分支。普通 useState 的 action 在这里仍按原队列顺序处理；useReducer 派发不预计算 eagerState，而在 render 时调用当前 reducer。

第二块同样是两段真实原码的机制拼接。真实代码在两段之间处理乐观更新与 DEV reducer 双调用；正文不声称该块可直接替换完整函数。

render-phase update：不调另一个 root task，而是重跑当前组件

上块是连续主循环的删节版。真实连续实现还重置 thenable 计数、DEV Hook 类型索引，并通过 callComponentInDEV 调用组件；控制流与 25 次上限保持一致，完整细节见链接。

rerenderReducer 直接从 queue.pending 环取本 pass 更新，按顺序应用到 WIP Hook 的 memoizedState；这些更新与当前 render 同优先级，所以不做 Lane 筛选。若 render 抛错并 unwind，resetHooksOnUnwind 清空本轮 render-phase pending，防止泄漏到下一次尝试。

Effect：render 建环，commit 才 create / destroy

Effect Hook 节点的 memoizedState 指向 Effect；所有 Effect 还被 O(1) 追加到 FunctionComponentUpdateQueue.lastEffect 环。mount 总是带 HookHasEffect；update 的 deps 按 Object.is 逐项相等时仍登记 Effect 节点，但不带 HookHasEffect，因此普通更新 commit 不执行该节点的 create/cleanup；Offscreen 重连与 DEV Strict Effects 可另走挂载路径。

最后一块并列两个真实连续局部，不是同一连续文件区间。完整 commit 函数遍历环、按 Hook flags 过滤、处理 DEV 返回值诊断、Profiler 与 commit-phase 错误捕获。关键所有权事实是：create 的返回值存到稳定 EffectInstance.destroy，调用 cleanup 前先清空槽，避免重复调用同一函数。

  1. 同步入口。稳定 dispatch 绑定 Fiber 与 queue；派发选择 Lane，创建 Update。若满足 eager 相等条件，更新保留但不调度。
  2. 并发暂存。正常路径先把 Update 四元组放入全局并发缓冲并安排 root；render 前批量转移到各 Hook pending 环、传播 Lane。何时执行由 Scheduler 与 RootScheduler 决定。
  3. render 路由。函数组件进入 renderWithHooks，安装 Update dispatcher；每次 Hook 调用同步推进 current/WIP 两个位置游标。
  4. 状态计算。pending 合并到 baseQueue；本轮 Lane 可处理的 action 更新 memoizedState，跳过项和其后的已执行项构成新 rebase 基线。
  5. 组件输出。组件继续同步执行并返回 children，reconciler 再协调 child Fiber、complete 并汇总 flags。只有本轮实际调用了 Effect Hook 才会登记 Effect 环/flags；state queue 与 Effect queue 并不互相依赖。
  6. 同轮重渲染分支。组件 render 内更新自己时，不离开当前组件；Rerender dispatcher 从链头重跑，直至稳定；额外 rerender 循环最多执行 25 个 pass，首次组件求值不计入。
  7. 提交。state 本身没有独立“提交回调”。组件输出产生 Fiber/DOM flags；Effect create/cleanup 由 commit 各阶段遍历组件 Effect 环执行，错误走 commit-phase 捕获。
  8. 清理。组件删除时，child deletion 找到其子树；对应 EffectInstance 的 destroy 被清槽后安全调用。render 被放弃时则清掉仅本轮有效的 render-phase update，不执行尚未提交的 Effect create。

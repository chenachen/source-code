05 · Fiber engine / commit

reconciler：把 finishedWork 提交到宿主树

commit 不再决定组件“应该渲染什么”。它按 flags 遍历 finishedWork，先保存修改前快照，再执行宿主 mutation， 切换 current，最后运行能观察新宿主树的 layout 与后续 passive effects。

同步关键区flags 驱动遍历HostConfig 边界passive 单独冲刷

为什么 commit 不能像 render 一样任意中断

CONSISTENCY

可见提交不由 Scheduler 分段

普通 mutation 与 layout 在同一段同步工作中完成。若中途让出浏览器任务，会把一半更新的 DOM、ref 与生命周期状态暴露到页面。

ORDER

每类 effect 有固定观察窗口

snapshot 读旧宿主树；layout 读新宿主树；passive 不阻塞当前可见提交。

OWNERSHIP

current 切换是逻辑提交点

它晚于 mutation、早于 layout，使卸载读旧 current，挂载/更新读新 current。

同步完成仍有中间观察窗口：mutation 中的 cleanup/ref 回调可能看到部分 DOM 已更新，而 current 仍是旧树。 用户代码抛错后，React 记录边界或根的恢复更新，已完成的宿主操作不会回滚。

阶段状态机

阶段典型工作读到的 current / DOM主要 flags
before mutationgetSnapshotBeforeUpdate、失焦前处理旧 current，DOM 尚未修改Snapshot、BeforeMutationMask
mutationPlacement、Deletion、属性/文本更新、可见性、insertion effect旧 current，DOM 正变成新树Placement、Update、ChildDeletion、MutationMask

commitRoot 先把根状态收口

commitRoot 计算 remaining lanes，合并 render 期间并发进入的更新，调用 markRootFinished， 清理 callback 状态，并在真正 effect 前安排可能存在的 passive flush。然后才进入 before-mutation 与 pending-effects 状态机。

View Transition 启用时，mutation/layout/after-mutation 可能由宿主 transition callback 驱动；未启用时同步连续 flush。 无论哪条分支，pendingEffectsStatus 都防止阶段重复或乱序进入。

mutation：flags 决定动作，HostConfig 决定怎样写宿主

ReactFiberCommitWork.js 遍历带 MutationMask 的子树。 父 Fiber 的 deletions 先处理，再递归 child mutation，最后处理当前 Fiber 的 Placement/Update/Ref/Visibility 等。

为什么删除不是简单 parent.removeChild：删除子树中可能有 portal、class、hook effect、ref、cache 与隐藏边界。 reconciler 必须先按 Fiber 语义清理，再让 HostConfig 移除正确宿主根。

effect 顺序：先清旧，再装新

函数组件的 updateQueue.lastEffect 指向环形 effect 链尾，每个 effect 通过 next 连接。 普通更新先在 mutation 执行变化项的 layout destroy，再在 layout 执行 create；passive 则先完成整树 unmount，再开始 mount。 依赖未变的 effect 缺少 HookHasEffect，普通更新不拆装；删除会按 effect 类型清理全部已连接项。 删除 mutation 只断开删除树根部的 return，为 passive 清理保留子树关系，passive 后才清理其余 Fiber 字段和 DOM 内部关联。

LAYOUT

同步观察新布局

useLayoutEffect、class didMount/didUpdate 与 ref attach 在 paint 前执行；其中同步更新可能让 passive 被提前冲刷。

PASSIVE

默认不阻塞当前提交

useEffect 通常由 Normal Scheduler callback 冲刷。现代根提交包含 SyncLane 时，提交末尾会在当前任务冲刷；新 render 前或同步更新也可能提前冲刷。它可以产生新更新，因此另有 nested passive update 计数。

ref：detach 与 attach 分属不同观察窗口

更新 ref 时，旧 ref 在 mutation 路径 detach，新的 ref 在 layout attach。 对象 ref 写入 current；函数 ref 返回的 cleanup 会被保存，下一次 detach 优先调用 cleanup，否则以 null 调用 ref。 这样新 ref 回调看到的 host tree 已完成 mutation，且 root.current 已是新树。

错误隔离：继续遍历，但不假装回滚

  1. 捕获。生命周期、effect、ref 或 HostConfig 调用抛错时，safe wrapper 记录 source Fiber。
  2. 定位。从调用者传入的最近已挂载祖先寻找 class error boundary 或 HostRoot；删除树内已卸载边界不能接管清理错误。
  3. 排队。构造 capture update，选择 SyncLane 并重新调度根。
  4. 继续。cleanup 逐项捕获，失败后仍能清理其余项；create 的 catch 包住同一 Fiber 整条 effect 链，失败会跳过该链剩余 create，外层继续其他 Fiber。
  5. 恢复。下一轮 render 产生 fallback 或根级空树；已发生的 mutation 不被事务式撤销。

passive 与根缓存怎样收尾

flushPassiveEffects 把事件优先级设为不高于 DefaultEventPriority，保存本轮 root/lanes，清空 pending 引用，再执行 passive unmount/mount。 组件有机会 retain 所需 cache 后，外层 finally 按 remaining lanes 释放 root pooled cache；本轮没有 passive 工作时，flushSpawnedWork 直接释放该池。 若 effect 调度同步工作，flushPassiveEffectsImpl 末尾冲刷同步根；新提交可能再产生 passive，下一次 commit 入口会先处理这些待办。

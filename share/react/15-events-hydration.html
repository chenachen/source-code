15 · Deep dive / events and hydration

DOM 事件怎样找到 Fiber，又怎样等到它可交互

React 不给每个 JSX handler 都安装一个 DOM listener。根容器接住原生事件，按事件类别设置更新优先级， 从 DOM 缓存反查 target Fiber，经插件生成 SyntheticEvent 与 listener 队列，在批次内按 capture/bubble 派发，最后恢复受控表单。 若 target 仍在 dehydrated 边界内，同一入口改走同步 hydration 或连续事件排队/重放。

一条正常链，两条 hydration 分支

READY

target 已 mounted

直接进入插件事件系统；handler 更新共享当前事件优先级并在事件批次边界收口。

DISCRETE BLOCKED

click 等离散事件

capture listener 循环尝试同步 hydration；成功就立即派发同一个原生事件，仍阻塞则停止传播。

CONTINUOUS BLOCKED

mouseover 等连续事件

按事件种类/指针 ID 合并保存，提升 hydration 优先级；边界提交后克隆原生事件重放。

React 19.3 当前实现没有“所有阻塞事件统一 FIFO 重放”。离散事件优先同步 hydration； 连续事件只有 focus/drag/mouse/pointer 的指定进入类事件进入 replay 槽，后来的同类事件可覆盖旧槽，退出类事件会清槽。form action 与可选 hydration change event 另有专用队列。

两个“连续”不要混为一谈：ContinuousEventPriority 是 handler 更新优先级； queueIfContinuousEvent 是可合并 replay 类别。比如 focusin 的更新优先级属于 Discrete，阻塞时仍使用 focus replay 单槽。

第 1 步 · 根委托：一次安装覆盖整棵动态子树

createRoot/hydrateRoot 建根时最终调用 listenToAllSupportedEvents。随机 marker 写在容器上防止重复安装； 大部分事件各装 capture 与 bubble listener，selectionchange 特殊绑定 document；nonDelegatedEvents 内的事件在具体节点监听 bubble，根仍监听 capture。

设计收益：新增、移动、删除 HostComponent 时不用同步维护成千上万个浏览器 listener。 代价：React 必须自己恢复 target Fiber、Root/Portal 所属边界、传播次序与 controlled input 收尾。

第 2 步 · priority wrapper：事件类别变成更新上下文

类别当前源码中的代表事件进入 dispatch 时对 handler 更新的影响
Discreteclick、input、change、keydown、focusin、submitsetCurrentUpdatePriority(DiscreteEventPriority)setState 请求 lane 时能读取离散事件上下文；通常要求更快完成
Continuousmouseover、mousemove、pointermove、scroll、wheel设置 ContinuousEventPriority允许连续输入合并，优先级低于离散输入
Default未落入专门 case 的事件直接 dispatchEvent，不覆盖已有 priority无显式 priority 时，resolveUpdatePriority 按 window.event 映射；无事件时回退 Default

离散与连续 wrapper 在 finally 恢复先前 priority 与 Transition 上下文。它不直接调用组件，也不保证每次 setState 立刻单独 render；它只是给随后 requestUpdateLane 提供事件上下文，真正调度仍归 reconciler。

第 3 步 · DOM target → 最近 mounted Fiber

创建宿主节点时，renderer 用 precacheFiberNode 在 DOM 节点上缓存 Host Fiber identity；Host Fiber 的 stateNode 反向指回 DOM。 每次 commitUpdate 又用 updateFiberProps 更新同一 DOM 节点上的独立 latest-props cache。getListener 由 inst.stateNode 找 DOM， 再调用 getFiberCurrentPropsFromNode 读取该 cache，而不是读 fiber.memoizedProps。所以 mutation 可以先更新 handler cache，之后 WorkLoop 才切 root.current。

边写入/读取用途
DOM → Host Fiber identityprecacheFiberNode / getClosestInstanceFromNode定位 React 所有权与 hydration blocker
Host Fiber → DOMfiber.stateNode取得 currentTarget、宿主实例与 props cache 所在节点
DOM → latest props/listenersupdateFiberProps / getFiberCurrentPropsFromNode派发时读取最新 handler，不被挂载时闭包冻结

返回值分成两部分：模块字段 return_targetInst 保存可派发 target Fiber；函数返回的非 null 值表示阻塞对象 （Container、SuspenseInstance 或 ActivityInstance）。若最近 Fiber 已卸载或尚未完成 mount，target 被置 null，避免向陈旧组件 handler 派发。

Root/Portal 边界：dispatchEventForPluginEventSystem 还会沿 return 找与当前 targetContainer 匹配的 HostRoot/HostPortal。Portal 容器自有 listener；祖先 root 遇到已由 portal 路径负责的事件会返回，避免同一 React 路径重复冒泡。

第 4 步 · 插件 extraction：一个原生事件可产生不同 React 语义

dispatchEventsForPlugins 创建空 dispatchQueue，让插件按固定顺序提取，再统一处理队列。 SimpleEventPlugin 覆盖基础映射；Change、EnterLeave、BeforeInput、Select、FormAction 等把多种浏览器输入归一为 React 事件。

本例原生类型是 input，SyntheticEvent 的 React 名称/公开类型是 onChange/change。 登记 restore 发生在 listener 执行前，所以 handler 不更新 state、bailout、嵌套触发另一控件事件等情况都不会漏掉受控恢复。

第 5 步 · capture/bubble：沿 Fiber 路径，不是重新依赖 DOM 冒泡

accumulateTwoPhaseListeners 从 target Fiber 沿 return 到 HostRoot；每到 HostComponent、HostHoistable 或 HostSingleton，都通过其 stateNode 上的 latest-props cache 收集 onChangeCapture/onChange。捕获是 root → target，冒泡是 target → root；SyntheticEvent 的 target 保持原生 target，currentTarget 每次调用前设为当前宿主节点，调用后清空。

异常语义：一个 handler 抛错会交给全局错误报告，不会把 SyntheticEvent 交给 React error boundary； 事件边界不是 render/commit 错误边界。currentTarget 随后被清空，队列仍可继续。外层 batching 的 finally 仍执行受控恢复。

停止传播的细节：代码在准备跨到“另一个 Fiber instance”前检查 stop 状态；同一 instance 上的内部 listener 槽不被错误当成一条新的祖先边。普通使用可理解为停止后续 Fiber 路径传播。

第 6 步 · batched dispatch：最后才能恢复 controlled DOM

  1. 同一次插件派发共享 batch。根原生 capture 与 bubble listener 各自进入 batching；本例 Change 插件在 bubble 中一次派发两阶段回调。handler 重入触发原生事件时，isInsideEventHandler=true，恢复延后到最外调用结束。
  2. 先 flush 更新。handler 若把 value 提交成 tiger，restore 应读取最终 props=tiger，而不是旧 lion。
  3. 清队列并 restore。restoreTarget/restoreQueue 先转存并清空，再逐节点读取最终 props 恢复；无更新时 giraffe 被 lion 覆盖，checkbox/radio 恢复 checked 与组状态。
  4. 异常后的队列状态。恢复抛错时旧队列已经移出模块状态，不会在下一事件再次消费；尚未遍历的目标不会继续恢复。

Hydration 第 1 步 · target Fiber 存在，但它只代表 dehydrated 边界

服务端 DOM 已可见不等于对应组件已可交互。getClosestInstanceFromNode 向上遇到 Suspense 注释边界时可返回 Suspense Fiber；getNearestMountedFiber 与 getSuspenseInstanceFromFiber 发现边界仍 dehydrated， 于是 findInstanceBlockingEvent 返回那枚真实 DOM 注释节点作为 blockedOn，而不把事件交给尚未连接的 handler。

Hydration 第 2 步 · 同一个 dispatchEvent 分出排队与同步水合

输入立即动作成功条件失败/清理
mouseover / focusin / dragenter / pointerover写对应 replay 槽，提升 continuous hydration，stopPropagation边界提交后 retry 解锁，再 clone+dispatch后续 mouseout/focusout 等清槽；同类新事件可替换旧槽
click / input / keydown 等离散 captureattemptSynchronousHydration，重新查询 blocker本次调用栈内 blocker 变 null，立即派发原事件blocker 不变则 break + stopPropagation；不进入通用连续 replay 槽
不可重放且不可同步的阻塞事件以 targetInst=null 进入插件系统只执行不依赖该 target 的追踪/边界逻辑组件 handler 不应获得陈旧 target

Hydration 第 3 步 · commit 发出 retryIfBlockedOn 解锁通知

事件模块不知道边界何时真正提交；DOM HostConfig 在 hydration commit 或边界被清除时回调它。这是 commit 页与事件页的连接点：

retryIfBlockedOn(unblocked) 只把 queuedEvent.blockedOn === unblocked 的槽置 null；其他边界的事件不被误放行。 首次解锁会安排一个 NormalPriority replay callback（相关 feature flag 开启时可由显式 flush 路径处理）。显式 hydration target 也按 priority 队列重新尝试。

Hydration 第 4 步 · 重放不是直接调用旧 handler，而是重新走原生管线

  1. 重新验证。解锁旧边界后，target 可能又受更内层 dehydrated 边界阻塞；因此先重新执行 blocking lookup。
  2. 克隆事件。不直接复用已经传播过的 Event 对象；新 Event 重新进入浏览器 capture/bubble listener。
  3. 打 replay marker。避免 legacy click defer 等分支把重放再当首次事件；结束后重置模块状态。
  4. 消费容器记录。同一 native event 被多个 root/portal listener 观察时会合并容器列表。循环为剩余记录创建克隆，经 DOM 重新传播成功后 shift；实际命中的 listener 与 flags 由新传播决定。
  5. 再次阻塞。保存新的 blockedOn，提升对应 hydration，等待下一次 commit retry；不丢失剩余容器。

什么时候会“丢弃”而不是重放

场景当前实现行为含义
mouseover 排队后先发生 mouseoutclearIfContinuousEvent('mouseout') 清 queuedMouse指针已离开，补发旧“进入”会制造错误当前状态
同类连续事件再次到达槽更新为新 queued event；相同 native event 的多容器则合并 flags/containers连续状态看最新值，不承诺逐个重放历史采样
离散 click 同步 hydration 仍挂起停止传播，不放进连续 replay 槽当前版本选择交互优先的同步尝试，不把所有离散事件延后复制
重放前 target Fiber 已卸载blocking lookup 得到 targetInst=null；不会调用旧组件 listener已卸载组件不再拥有事件；保留原生事件不等于保留陈旧 Fiber 所有权
脱水边界被清除，改走 client render清边界代码也调用 retryIfBlockedOn解除 blocker 后重新 lookup，按新 client Fiber 决定派发或忽略

“重放保持因果”有边界：React 保留必要交互状态，不承诺逐字节复刻事件发生时 DOM。 handler 读取重放时节点的最新 props；连续槽保留当前仍有效的进入状态，同类新事件会覆盖旧槽，退出事件会清槽。

两条完整调用链，逐步复述

普通受控 input

  1. 根 bubble listener 接到原生 input；priority wrapper 设置 DiscreteEventPriority。
  2. getClosestInstanceFromNode 找 input Host Fiber，mounted 检查通过，blockedOn=null。
  3. Root/Portal 匹配选出 ancestorInst；batchedUpdates 包住插件分发。
  4. ChangeEventPlugin 比较 value tracker，登记 restore target，合成 onChange 并累积两阶段 listeners。
  5. capture root→target、bubble target→root；每次设置/清空 currentTarget，错误报全局，stopPropagation 截断后续 Fiber。
  6. handler 更新在 batch 内调度；finally 先 flushSyncWork，再取出并清空 restore 队列，按最终 props 恢复 DOM。

dehydrated Suspense 中的 mouseover

  1. continuous wrapper 设置 ContinuousEventPriority；DOM 查找返回 Suspense blocker。
  2. queueIfContinuousEvent 写 queuedMouse，尝试 continuous hydration，停止本轮原生传播。
  3. 若随后 mouseout，立即清槽；若另一 mouseover 到来，槽代表更新后的目标/容器。
  4. hydration commit 调 commitHydratedSuspenseInstance → retryIfBlockedOn，仅解锁匹配 blocker。
  5. replay callback 再查 blocker；仍阻塞则换 blocker并提升 hydration，已解锁则 clone 原生事件重新 dispatch。
  6. 重放事件重新经过 root listener、priority、target、plugin、batch 与 cleanup；不是直接调用缓存 handler。

边界、异常与清理清单

  • handler 错误：reportGlobalError，不由 React error boundary 捕获；currentTarget 清空，事件 batch finally 仍运行。
  • DOM 删除：mutation 先断 deleted Fiber 的 return，因此 mounted 检查立即拒绝它；DOM→Fiber/latest-props cache 不必在这一刻全部消失，删除树的 passive cleanup 后才由 detachFiberAfterEffects → detachDeletedInstance 清除。节点本地 non-delegated listener 记账按节点生命周期另行维护。
  • Portal：每个 Portal container 有 listener，但 Fiber Root/Portal 匹配避免同一路径重复派发；SyntheticEvent 传播仍按 React 所有权。
  • hydration mismatch/client render：清除旧边界也发 retry；重放时重新定位新 Fiber，不能保留旧 targetInst。
  • event priority ≠ Scheduler priority 常量：二者会映射，但属于不同抽象层；本页不把 click 直接称为某个固定 Scheduler task。
  • 源码/示例界线：“连续原码/连续测试原码”可在链接文件逐字连续匹配；“删节源码”写明裁剪；状态模型标为“教程伪代码”。
  • 未展开：createEventHandle、legacy FB click defer、FormAction server replay、多 React 实例交错、Activity 边界与 enableHydrationChangeEvent 分支。

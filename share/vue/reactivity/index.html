01

响应式到底在解决什么问题？

数据变化本身并不神秘。困难在于：系统怎样知道哪些计算和副作用依赖这次变化， 并且只让真正受影响的部分重新工作？

核心命题

Vue 不理解“购物车总价”或“按钮是否可用”这样的业务概念。它只在函数执行期间记录： 当前订阅者读取了哪个原始对象的哪个位置。响应式系统因此不是一个值同步器， 而是一套运行时依赖分析与失效传播机制。

先从最小闭环开始：counter.num → effect → dummy。 counter.num 是可被读取和写入的位置，effect 是消费它的函数， dummy 是用户最终看见的结果。第 03 章才把这条直线升级成 src → c1 → c2 → effect 的计算链；这里不提前重复 computed 细节。

Vue 的选择是让依赖关系在运行时自然暴露。某个函数执行时读取了 counter.num，就说明它依赖这个位置；以后 num 改变，系统沿着已经记录的边 找回函数。开发者只声明“结果如何由状态得到”，依赖图则由真实执行路径生成。

① 创建不是登记后就返回

effect() 内部直接执行 e.run()，所以第一条断言之前 dummy 已经是 0。

② 依赖来自这一次真实读取

run() 暂时把 activeSub 指向当前 effect；只有此时真正读取的 num 才会建边。

③ 写入先分类，再通知

本例的 num 是已有属性，setter 在 hasChanged 确认新旧值不同时发出 SET；新属性则走 ADD。

④ 重新执行也会重新确认依赖

第二次 run 仍经过 prepare / track / cleanup。第 04 章会用条件分支把这套动态清理完整走一遍。

连续原文 · effect.ts · effect() 
export function effect<T = any>(
  fn: () => T,
  options?: ReactiveEffectOptions,
): ReactiveEffectRunner<T> {
  if ((fn as ReactiveEffectRunner).effect instanceof ReactiveEffect) {
    fn = (fn as ReactiveEffectRunner).effect.fn
  }

  const e = new ReactiveEffect(fn)
  if (options) {
    extend(e, options)
  }
  try {
    e.run()
  } catch (err) {
    e.stop()
    throw err
  }
  const runner = e.run.bind(e) as ReactiveEffectRunner
  runner.effect = e
  return runner
}
决定性分支：e.run() 在 runner 返回前执行；若首次执行抛错，catch 会先 stop 再继续抛出，避免留下半建成订阅。

最小心智模型只有一句话：读操作建立边，写操作让边另一端的消费者失效。 Proxy 负责看见读写，Dep 保存“一个位置”的订阅者，Link 表示一条关系， Subscriber 决定收到通知后怎么做。

PRINCIPLE / 01

透明代理

Proxy + Reflect 保持普通对象的使用方式，在 get/set/has/ownKeys 等语言操作中插入追踪与触发。

PRINCIPLE / 02

属性级粒度

依赖并不挂在整个对象上，而是挂在具体 key 上。数组长度、对象遍历、Map 键遍历另有专门的抽象依赖键。

PRINCIPLE / 03

按需深层转换

创建 reactive 时不会递归遍历对象；只有属性读取到嵌套对象时，才继续把返回值包装为代理。

PRINCIPLE / 04

延迟计算

computed 收到通知时先标脏。读取 .value，或下游执行前的 isDirty() 检查，都可以按需刷新它的缓存。

PRINCIPLE / 05

身份兼容

对象依赖按原始 target 定位；集合读取按传入 key 与 toRaw(key) 兼查和追踪，传入 raw 不会反向寻找 proxy。预存的 raw/proxy 双项不会合并。浅层集合保存传入值；深层集合按 isShallow(value)／isReadonly(value) 判断是否还原 value。

PRINCIPLE / 06

可回收的图

依赖关系必须能增量复用，也必须能在分支变化、停止 effect 或结束 scope 时解绑，避免过期触发与内存泄漏。

Constraint A

依赖必须来自真实执行，而不是静态猜测

对 ok ? state.a : state.b 而言，依赖会随分支切换。Vue 每次执行订阅者时重新确认实际读取过的 Dep，并删除本轮没有再次出现的旧 Link。 这使依赖图与控制流始终一致，也解释了为什么 effect 不能只在首次执行时收集一次。

Constraint B

“可能变化”与“结果已变化”必须分开

上游通知说明 computed 可能过期。读取或依赖检查时，Vue 才按需求值；dep.version === 0 时成功求值会发布第 1 版，后续正常求值结果变化才发布新版本，抛错也会递增版本。结果未变时，默认 runIfDirty() 可跳过下游函数；自定义 scheduler 仍会收到调度调用。

i

阅读时不要把 reactive 当成“数据自动变了”。数据本来就会变；响应式层真正增加的是： 记录读取关系、识别写入类型、安排订阅者重新执行。

02

Proxy 是对象入口，不是响应式引擎

reactive 对象从 Proxy 进入，Ref 从 .value 进入；两条路径最终汇入同一套 Dep、Link 与 Subscriber 图。

很多响应式介绍停在 new Proxy(target, { get, set })， 仿佛拦截器本身就完成了响应式。实际 Proxy 只是把语言操作翻译成内部事件： 读取属性变成 track(target, GET, key)，写入属性变成 trigger(target, SET/ADD, key)。如果没有活动订阅者， 一次普通读取甚至不会创建 Dep。

这种分层让容器语义与调度策略彼此独立。代理层负责保持 JavaScript 行为； 依赖层不知道对象是通过普通属性、数组方法还是 Map API 被访问；effect 层也不关心变化来自哪个容器。各层只通过“目标、键、访问类型与操作类型”这组协议协作。

① reactive 只包根，不遍历 nested

createReactiveObject 只创建根 Proxy。直到 effect 读取 state.nested，getter 才对 nested 调 reactive。

② 读 nested 也会建边

第一次 getter 追踪 raw 的 nested key；第二次 getter 追踪 raw.nested 的 count key。替换整个 nested 或修改 count 都能影响 effect。

③ Ref 不需要 targetMap

Ref 只有一个公开响应式位置 .value，实例直接持有 Dep 更短；对象代理则必须用 target + key 找 Dep。

④ “同图”不等于“同入口”

二者只在 Dep / Link / Subscriber 层汇合。把 Ref 说成“用 Proxy 包了 value”会直接带错后续源码阅读。

对象入口 · Proxy

  • state.count 由 Proxy getter/setter 拦截。
  • track/trigger(target, key) 在 targetMap 中定位 Dep。
  • 适合对象、数组与 Map/Set；一个容器通常对应多个 key Dep。

值入口 · Ref

  • src.value 直接进入 RefImpl getter/setter。
  • Ref 自带一个 Dep，直接调用 dep.track()/trigger()。
  • 它不是 Proxy；ReactiveFlags.IS_REF 只是统一身份标记。

function createReactiveObject(
  target: Target,
  isReadonly: boolean,
  baseHandlers: ProxyHandler<any>,
  collectionHandlers: ProxyHandler<any>,
  proxyMap: WeakMap<Target, any>,
) {
  if (!isObject(target)) {
    if (__DEV__) {
      warn(
        `value cannot be made ${isReadonly ? 'readonly' : 'reactive'}: ${String(
          target,
        )}`,
      )
    }
    return target
  }
  // 已有代理通常原样返回，不因本次 API 的深浅模式而重建。只读 API 包装可变代理时，
  // 才继续创建外层只读代理，使读取沿内层收集依赖，同时禁止从外层写入。
  if (
    target[ReactiveFlags.RAW] &&
    !(isReadonly && target[ReactiveFlags.IS_REACTIVE])
  ) {
    return target
  }
  // markRaw() 标记或不可扩展对象不能安全安装/维持代理语义，直接返回。
  if (target[ReactiveFlags.SKIP] || !Object.isExtensible(target)) {
    return target
  }
  // 同一输入目标、同一模式复用缓存；readonly(reactive(raw)) 的目标是内层代理。
  const existingProxy = proxyMap.get(target)
  if (existingProxy) {
    return existingProxy
  }
  const targetType = targetTypeMap(toRawType(target))
  if (targetType === TargetType.INVALID) {
    return target
  }
  const proxy = new Proxy(
    target,
    targetType === TargetType.COLLECTION ? collectionHandlers : baseHandlers,
  )
  proxyMap.set(target, proxy)
  return proxy
}
先读返回分支：非对象、SKIP/不可扩展对象直接返回。已有代理通常复用，不比较深浅模式；例外是 readonly 包装 reactive，此时传入的内层代理可以成为只读 WeakMap 的缓存键。可代理且未缓存的 target 才创建 Proxy，创建过程不遍历 nested。

class RefImpl<T = any> {
  /** `.value` 实际返回的值；深层对象通常是响应式代理。 */
  _value: T
  /** 用于变更比较的值；深层对象通常是原始对象。 */
  private _rawValue: T

  /** 管理所有读取 `.value` 的订阅者。 */
  dep: Dep = new Dep()

  /** Ref 运行时身份标记。 */
  public readonly [ReactiveFlags.IS_REF] = true
  /** 当前 Ref 是否只追踪根值替换。 */
  public readonly [ReactiveFlags.IS_SHALLOW]: boolean = false

  /** @param value 初始值。 @param isShallow 是否按原样保存内部值。 */
  constructor(value: T, isShallow: boolean) {
    this._rawValue = isShallow ? value : toRaw(value)
    this._value = isShallow ? value : toReactive(value)
    this[ReactiveFlags.IS_SHALLOW] = isShallow
  }

  /** 读取当前值，并让活动 effect/computed 订阅本 Ref 的 Dep。 */
  get value() {
    if (__DEV__) {
      this.dep.track({
        target: this,
        type: TrackOpTypes.GET,
        key: 'value',
      })
    } else {
      this.dep.track()
    }
    return this._value
  }

   * 设置新值；按 `Object.is` 语义确认实际变化后才更新两种存储并触发订阅者。
   *
   * 新值本身若已是浅层或只读代理，必须直接保留：还原再经 `toReactive()` 包装会丢失
   * 原有浅层/只读约束。
   */
  set value(newValue) {
    const oldValue = this._rawValue
    const useDirectValue =
      this[ReactiveFlags.IS_SHALLOW] ||
      isShallow(newValue) ||
      isReadonly(newValue)
    newValue = useDirectValue ? newValue : toRaw(newValue)
    if (hasChanged(newValue, oldValue)) {
      this._rawValue = newValue
      this._value = useDirectValue ? newValue : toReactive(newValue)
      if (__DEV__) {
        this.dep.trigger({
          target: this,
          type: TriggerOpTypes.SET,
          key: 'value',
          newValue,
          oldValue,
        })
      } else {
        this.dep.trigger()
      }
    }
  }
}
与 Proxy 对照：Ref 直接拥有 dep；getter 无 targetMap 查询，setter 先比较 raw 值，再更新 raw/public 双存储并触发。若 value 是对象，toReactive 仍会让公开值成为 Proxy。

Identity and lazy conversion

身份稳定是正确性条件

  • reactive(raw) === reactive(raw) 必须成立，否则同一个对象会出现多个代理身份。
  • 可变、浅可变、只读、浅只读语义不同，因此分别使用四个 WeakMap 缓存。
  • WeakMap 不会阻止原始对象被回收，代理缓存不会永久留住业务对象。

深层响应是惰性的

  • 创建 reactive 时不会递归遍历整棵对象树。
  • getter 读到嵌套对象后，才调用 reactive/readonly 返回代理。
  • 创建成本只与根对象相关，真正访问到的分支才承担包装成本。

  track(debugInfo?: DebuggerEventExtraInfo): Link | undefined {
    if (!activeSub || !shouldTrack || activeSub === this.computed) {
      return
    }

    let link = this.activeLink
    if (link === undefined || link.sub !== activeSub) {
      link = this.activeLink = new Link(activeSub, this)

      // 新 Link 按读取顺序追加到当前订阅者依赖链尾。
      if (!activeSub.deps) {
        activeSub.deps = activeSub.depsTail = link
      } else {
        link.prevDep = activeSub.depsTail
        activeSub.depsTail!.nextDep = link
        activeSub.depsTail = link
      }

      addSub(link)
    } else if (link.version === -1) {
      // 复用上轮 Link，确认本轮仍读取该依赖；是否接入 Dep 通知链由 TRACKING 控制。
      link.version = this.version

      // 非尾节点说明本轮访问顺序改变，将其移到尾部，使依赖链始终反映本轮读取顺序。
      if (link.nextDep) {
        const next = link.nextDep
        next.prevDep = link.prevDep
        if (link.prevDep) {
          link.prevDep.nextDep = next
        }

        link.prevDep = activeSub.depsTail
        link.nextDep = undefined
        activeSub.depsTail!.nextDep = link
        activeSub.depsTail = link

        // 若移动的是原链表头，下一节点成为新头。
        if (activeSub.deps === link) {
          activeSub.deps = next
        }
      }
    }

    if (__DEV__ && activeSub.onTrack) {
      activeSub.onTrack(
        extend(
          {
            effect: activeSub,
          },
          debugInfo,
        ),
      )
    }

    return link
  }
本例三次首次命中：effect→c2.dep、 c2→c1.dep、c1→src.dep。写入后的 c1 重算命中 link.version === -1 分支，把旧 Link 更新而非重复建边。

   * 在批处理中通知当前 Dep 的所有订阅者，但不递增版本。
   *
   * 计算属性脏传播使用 `notify()`：其自身 Dep 的值尚未重新计算，不能提前递增版本，
   * 只需继续把“可能变化”传给下游。用 `finally` 配对批处理，调试钩子或通知抛错时
   * 也能正确冲刷/恢复批深度。
   */
  notify(debugInfo?: DebuggerEventExtraInfo): void {
    startBatch()
    try {
      if (__DEV__) {
        // 生产通知从链尾逆序入栈，批结束后又按栈顺序执行，最终仍是原订阅顺序。
        // onTrigger 在此处立即调用，故开发模式额外从链头正序遍历才能保持相同顺序。
        for (let head = this.subsHead; head; head = head.nextSub) {
          if (head.sub.onTrigger && !(head.sub.flags & EffectFlags.NOTIFIED)) {
            head.sub.onTrigger(
              extend(
                {
                  effect: head.sub,
                },
                debugInfo,
              ),
            )
          }
        }
      }
      for (let link = this.subs; link; link = link.prevSub) {
        if (link.sub.notify()) {
          // 返回 true 表示订阅者是 computed；继续通知依赖 computed.value 的下游。
          // 在当前循环中传播而非 Computed.notify() 内递归，可压低长计算链的调用栈深度。
          ;(link.sub as ComputedRefImpl).dep.notify()
        }
      }
    } finally {
      endBatch()
    }
  }
调用展开：src.dep.trigger() 先把 src 版本 0→1，再进入 notify；c1 的 notify() 返回 true，于是这里调用 c1.dep.notify()；c2 同理；effect 的 notify 返回 void，传播停止。 三层 notify 形成嵌套 batchDepth，最外层退出时统一冲刷。

为什么 computed 的 notify() 返回 true？因为 computed 既是 上游 Dep 的 Subscriber，又拥有一个供下游订阅的 dep。它先把 自己标成 DIRTY；若本批尚未入队且不是正在递归通知自己，调用 batch(this, true) 加入 computed 队列，再用 true 告诉 Dep.notify()：“请继续通知我自己的下游”。这里仍没有执行 getter。

export function batch(sub: Subscriber, isComputed = false): void {
  sub.flags |= EffectFlags.NOTIFIED
  if (isComputed) {
    sub.next = batchedComputed
    batchedComputed = sub
    return
  }
  sub.next = batchedSub
  batchedSub = sub
}

/**
 * 开始一层批处理。嵌套调用只增加深度，由最外层 `endBatch()` 负责统一冲刷。
 *
 * @internal
 */
export function startBatch(): void {
  batchDepth++
}

/**
 * 结束一层批处理，并在最外层结束时运行所有待处理 effect。
 *
 * 先清空计算属性的入队标记，再执行普通 effect；执行期间新产生的 effect 会形成新一段
 * 链表，由外层 `while` 继续冲刷。某个 effect 抛错不会阻止其余 effect 执行，最终抛出
 * 捕获到的第一个错误。
 *
 * @internal
 */
export function endBatch(): void {
  if (--batchDepth > 0) {
    return
  }

  if (batchedComputed) {
    let e: Subscriber | undefined = batchedComputed
    batchedComputed = undefined
    while (e) {
      const next: Subscriber | undefined = e.next
      e.next = undefined
      e.flags &= ~EffectFlags.NOTIFIED
      e = next
    }
  }

  let error: unknown
  while (batchedSub) {
    let e: Subscriber | undefined = batchedSub
    batchedSub = undefined
    while (e) {
      const next: Subscriber | undefined = e.next
      e.next = undefined
      e.flags &= ~EffectFlags.NOTIFIED
      if (e.flags & EffectFlags.ACTIVE) {
        try {
          // ACTIVE 仅 ReactiveEffect 拥有，因此此处分支可安全收窄类型。
          ;(e as ReactiveEffect).trigger()
        } catch (err) {
          if (!error) error = err
        }
      }
      e = next
    }
  }

  if (error) throw error
}

function isDirty(sub: Subscriber): boolean {
  for (let link = sub.deps; link; link = link.nextDep) {
    if (
      link.dep.version !== link.version ||
      (link.dep.computed &&
        (refreshComputed(link.dep.computed) ||
          link.dep.version !== link.version))
    ) {
      return true
    }
  }
  // @ts-expect-error：兼容旧库手动设置 `_dirty`，例如 Pinia testing 模块。
  if (sub._dirty) {
    return true
  }
  return false
}

/**
 * 按需刷新计算属性的缓存。
 *
 * 快速路径从便宜到昂贵依次为：仍在追踪且未标脏、全局版本没有任何变化、逐依赖版本
 * 检查后确认结果不可能变化；只有这些判断都失败才真正执行 getter。
 *
 * @returns 当前实现只返回 `undefined`；调用方通过计算属性 `dep.version` 判断值是否变化。
 * @internal
 */
export function refreshComputed(computed: ComputedRefImpl): undefined {
  if (
    computed.flags & EffectFlags.TRACKING &&
    !(computed.flags & EffectFlags.DIRTY)
  ) {
    return
  }
  computed.flags &= ~EffectFlags.DIRTY

  // 全局触发版本未变时复用缓存，无需扫描依赖链；它不等于整个系统没有发生过赋值。
  if (computed.globalVersion === globalVersion) {
    return
  }
  computed.globalVersion = globalVersion

  // SSR 求值仍收集并保留依赖 Link，但 !computed.isSSR 会跳过下面的依赖版本快路径。
  // 全局版本相同仍复用缓存；全局版本变化后，即使自身依赖版本没变，也会重新求值。
  // issue #12337 场景：`computed(() => constant)` 不读取任何响应式数据。它求值一次后
  // 非 SSR 下，已发布结果、无 deps 且未设置兼容 _dirty 的 computed 会直接复用缓存，
  // 不因别处触发使 globalVersion 增长而再次执行 getter。
  if (
    !computed.isSSR &&
    computed.flags & EffectFlags.EVALUATED &&
    ((!computed.deps && !(computed as any)._dirty) || !isDirty(computed))
  ) {
    return
  }
  computed.flags |= EffectFlags.RUNNING

  const dep = computed.dep
  const prevSub = activeSub
  const prevShouldTrack = shouldTrack
  activeSub = computed
  shouldTrack = true

  try {
    prepareDeps(computed)
    const value = computed.fn(computed._value)
    // 只有首次求值或结果按 Object.is 语义真正变化，才递增自身 dep.version，
    // 从而让依赖 computed.value 的下游 effect 精确跳过“上游变、派生值未变”的更新。
    if (dep.version === 0 || hasChanged(value, computed._value)) {
      computed.flags |= EffectFlags.EVALUATED
      computed._value = value
      dep.version++
    }
  } catch (err) {
    // getter 抛错时递增版本并继续抛出，保留现有 _value；不会回退 globalVersion 或补设 DIRTY。
    // 后续读取仍由前面的快速路径判断是否重算，不能据此保证立即重试。
    dep.version++
    throw err
  } finally {
    activeSub = prevSub
    shouldTrack = prevShouldTrack
    cleanupDeps(computed)
    computed.flags &= ~EffectFlags.RUNNING
  }
}
写 2 的精确落点：c1 的 src Link v0 与 src.dep v1 不同， 所以 c1 getter 执行；所得 0 与旧值 0 相等，未进入 dep.version++。返回 c2 后，c1.dep v1 仍等于 c2 的 Link v1， c2 走“已求值且 !isDirty”快速返回；effect 对 c2 同理。

SSR 与 getter 抛错

SSR 仍会记录读取产生的 Link，但跳过非 SSR 的无 deps／逐依赖快路；全局版本快路仍然有效。getter 抛错时版本递增并继续抛出，该次刷新也已保存 globalVersion、清除 DIRTY。下次读取若命中未标脏或全局版本快路，可以直接返回缓存；版本递增本身不保证立即重试。

Link：一条边，服务两种遍历方向

每个 Dep—Subscriber 关系由一个 Link 表示。Link 先进入 Subscriber 的依赖链；只有 Subscriber 带有 TRACKING，它才接入 Dep 的通知链。没有下游的 computed 可以只保留依赖与版本元数据。

依赖图需要回答两个相反的问题。状态变化时，要从 Dep 出发找到“谁依赖我”； effect 停止或切换分支时，又要从 Subscriber 出发找到“我依赖谁”。如果只在 Dep 中保存订阅者 Set，第二种操作就需要额外索引，动态清理也会频繁创建临时集合。

prevDep/nextDep 把 Link 串进 Subscriber 的依赖链；启用 TRACKING 后，prevSub/nextSub 再把同一节点串进 Dep 的订阅者链。任一方向都能 O(1) 摘除已知节点；版本和嵌套上下文也保存在 Link 上。

versionDep.trigger 递增版本；computed 发布首个或变化的结果，以及 getter 抛错时也递增。Link 保存上次确认的版本。
globalVersionDep.trigger 或尚无 depsMap 的对象 trigger 会递增；同值 setter 通常不触发，手动 triggerRef 则可递增。一次写入可能影响多个 Dep。
activeLink同一 dep 当前追踪上下文中的 Link 缓存，避免重复创建。
scDep 的订阅登记计数。addSub 递增，普通 removeSub 递减；computed 软退订不减，恢复时会再次登记。归零时可删除 key→Dep 条目。
prevDep / nextDepLink 在 Subscriber 依赖链中的前驱与后继。
prevSub / nextSubLink 在 Dep 订阅链中的前驱与后继。
flags用位掩码组合 ACTIVE、RUNNING、TRACKING、DIRTY、NOTIFIED 等状态。
computedcomputed 的输出 Dep 指向所属 computed，供 isDirty 先刷新缓存，再比较输出版本。

function prepareDeps(sub: Subscriber) {
  for (let link = sub.deps; link; link = link.nextDep) {
    // -1 是本轮未使用标记；Dep.track() 再次命中时会同步成当前 dep.version。
    link.version = -1
    // 保存嵌套执行前的 activeLink，清理时恢复。
    link.prevActiveLink = link.dep.activeLink
    link.dep.activeLink = link
  }
}
为什么不先全删：先把旧 Link 作为 activeLink 缓存，下一轮读到同一 Dep 时能 O(1) 复用；只把真正没读到的边留给 cleanup 删除。
完整函数 · effect.ts · cleanupDeps() 
function cleanupDeps(sub: Subscriber) {
  let head
  let tail = sub.depsTail
  let link = tail
  while (link) {
    const prev = link.prevDep
    if (link.version === -1) {
      if (link === tail) tail = prev
      // 本轮未使用：从依赖源的订阅者链移除。
      removeSub(link)
      // 同时从当前订阅者的依赖链移除。
      removeDep(link)
    } else {
      // 逆序扫描中最后遇到的保留节点就是新链表头。
      head = link
    }

    // 恢复进入本轮收集前的 activeLink，支持 computed/effect 嵌套求值。
    link.dep.activeLink = link.prevActiveLink
    link.prevActiveLink = undefined
    link = prev
  }
  // 写回经过删减后的链表边界。
  sub.deps = head
  sub.depsTail = tail
}
两个 remove 都需要：removeSub 让 prop Dep 不再通知 effect；removeDep 让 effect 自己也不再持有 prop Link。随后还要恢复嵌套 activeLink。
sc 记录订阅登记，computed 订退由 dep.subs 决定

sc 随 addSub 登记而增加，随普通 removeSub 注销而减少；computed 软退订不递减，恢复上游通知链时调用 addSub 又会递增，所以它不能严格等同于不同 Link 对象的数量。普通注销使 sc 归零时，才从所属 key→Dep Map 删除 Dep。computed 是否接入上游通知链，则看它自己的输出 dep.subs 是否出现首个下游或失去最后一个下游。

ref、computed、effect、watch：四个角色怎样接成一条业务链？

第 03 章已经拆完 computed 的内部刹车。本章不再复讲同一算法， 而用“单价 × 数量 = 总价”走完整生命周期：谁提供值、谁派生、 谁同步更新结果、谁比较新旧值并负责清理。

price 与 quantity 是 Ref：持有可变源值和 Dep； total 是 computed：向上消费两个 Ref，向下提供自己的 Dep； effect 把 total 同步投影到 renderSpy；watch 也消费 total， 但额外维护 oldValue、回调与 cleanup。

同一条通知可以抵达两个消费者。默认 effect 先检查依赖版本，必要时重跑函数；watch 的 job 重新求值，判断是否需要回调，清理上一轮资源，把本轮值保存为 oldValue，再调用用户回调。停止 watcher 时还会执行最后一次 cleanup。

一个订单 · 四种角色

改数量、改单价、停止订阅：每一步都能从断言看到

先建 computed，再让 effect 与 watch 同时订阅它。两次源值写入应得到 total=15、12；第二次 watch 回调前清掉第一轮资源，永久停止时再清最后一轮； 停止后继续写 quantity，render/watch 都不再执行。

① Ref：拥有状态

它负责存值、比较新旧值、触发自身 Dep；不决定谁是派生值，也不保留业务 oldValue。

② computed：拥有缓存边界

它既是上游 Subscriber，又通过自身 Dep 成为下游 Source；第 03 章已证明结果未变时如何刹车。

③ effect：拥有重执行函数

默认创建即执行；无 scheduler 时，通知到达后先检查依赖版本，确需更新才重跑同一函数。配置 scheduler 后先交给调度器。effect 不向用户提供新旧值对。

④ watch：拥有回调政策

它内部仍用 ReactiveEffect，但 job 负责 active/dirty 早退、getter 求值、比较、cleanup、oldValue 更新和 callback。

快速路径 1 · 未标脏

仍在 TRACKING 且没有 DIRTY，说明上游没有发出失效通知，直接返回缓存。

快速路径 2 · 全局未变化

自身保存的 globalVersion 等于全局版本，说明这段时间没有走到递增全局版本的触发路径，无需扫描依赖。

快速路径 3 · 依赖版本未变

非 SSR 且已经 EVALUATED 时，即使全局版本变化，仍可检查自身依赖；刷新其中的 computed 后，所有 Link 版本仍匹配就复用结果。无 deps 且未被手工标脏时可直接返回。

最终路径 · 执行 getter

只有前面判断都失败才执行 getter；dep.version === 0 的首次求值会发布第 1 版，后续结果按 Object.is 变化才发布新结果版本。getter 抛错也会递增版本。

export function refreshComputed(computed: ComputedRefImpl): undefined {
  if (
    computed.flags & EffectFlags.TRACKING &&
    !(computed.flags & EffectFlags.DIRTY)
  ) return
  computed.flags &= ~EffectFlags.DIRTY

  if (computed.globalVersion === globalVersion) return
  computed.globalVersion = globalVersion

  if (
    !computed.isSSR &&
    computed.flags & EffectFlags.EVALUATED &&
    ((!computed.deps && !(computed as any)._dirty) || !isDirty(computed))
  ) return

  // 省略 activeSub 保存、prepareDeps 与异常处理。
  const value = computed.fn(computed._value)
  if (computed.dep.version === 0 || hasChanged(value, computed._value)) {
    computed.flags |= EffectFlags.EVALUATED
    computed._value = value
    computed.dep.version++
  }
}

  • 读取 .value 直接在自己的 Dep 上追踪。
  • 写入时通过 hasChanged 过滤相同值。
  • triggerRef 用于 shallowRef 内部对象被原地修改后的手动通知。
Cocomputed可缓存的派生订阅者

ComputedRefImpl 既是 Subscriber，又拥有自己的 Dep：向上订阅输入，向下被消费者订阅，因此是依赖图中的中间节点。

  • 通知阶段只设置 DIRTY 并入队，不立刻执行 getter。
  • 读取时使用 globalVersion 与依赖版本做快速路径。
  • 正常重算结果未变时，自身 Dep 版本保持不变，默认 runIfDirty 可跳过下游函数；自定义 scheduler 仍会被调用。
Efeffect立即执行并持续重确认依赖

effect(fn) 创建活动 ReactiveEffect 后立即 run；活动 effect 每次 run 都重新确认真实读取，映射为 Link，并在 finally 清理本轮没有再次读取的旧边。

  • 默认无 scheduler 时，依赖触发后同步 runIfDirty。
  • 自定义 scheduler 接管“何时执行”，但不接管依赖图。
  • stop 后解除该 effect 的自动订阅；runner 仍可手动执行，读取不再记到这个已停止 effect 名下。
Wawatch：回调监听与 effect 语义把依赖变化变成回调

@vue/reactivity 导出底层 watch：有 cb 时监听 getter 的结果，函数 source 且无 cb 时采用 watchEffect 语义。Vue 公共 watchEffect() 由 runtime-core 封装。内部仍以 ReactiveEffect 追踪，scheduler 决定具体调度，cleanup 负责清理上一轮资源。

  • 普通深层 reactive 源未指定 deep 时默认深遍历；shallowReactive 默认、deep:false 或 deep:0 只读根层。getter 源追踪真实读取，配置 deep 后再遍历返回结果。
  • 普通数组参数是多来源列表，逐项求值并比较；reactive 数组先命中 isReactive 分支，作为单个响应式对象来源处理。
  • pause/resume 暂停实际调度并记录期间的通知；恢复后有待处理通知才补调度一次，最终是否重跑仍取决于版本检查或 scheduler。
SceffectScope批量生命周期边界

作用域保存 ReactiveEffect、cleanup 与子作用域；停止父作用域会递归停止这些资源。computed 实例本身不登记到 scope.effects，scope 通过停止消费它的 effect 与 watcher 解除相关订阅。

  • 嵌套 scope 默认挂到当前活动 scope；scope.run 只为同步执行 fn 的这段时间提供归属，await 之后不会自动延续该上下文。
  • detached scope 拥有独立生命周期。
  • 移除子 scope 时用尾项覆盖空位，避免线性搬移。
Watch is a policy layer

watch 把 Ref、reactive 对象、getter 或普通多来源数组统一为 getter，再交给 ReactiveEffect 追踪。有 cb 时，job 还负责 immediate、once、deep、旧值与 cleanup；函数 source 且无 cb 时执行该函数并追踪其中的读取。reactive 数组属于单个 reactive 来源，不走普通数组的多来源分支。

deep 借助 traverse 递归读取对象、数组、Ref、Map 和 Set 的可观察成员，从而建立深层依赖；它不做递归的新旧值深比较。深层原地修改时，回调的新旧值可以是同一个对象。读取越多，首次收集与后续重跑的成本越高。

  const job = (immediateFirstRun?: boolean) => {
    // 已停止无需执行；非首次且依赖版本未变化时，跳过 watch getter 求值和后续回调判定。
    if (
      !(effect.flags & EffectFlags.ACTIVE) ||
      (!effect.dirty && !immediateFirstRun)
    ) {
      return
    }
    if (cb) {
      // watch(source, cb)：重新求值，再根据配置与新旧值判断是否调用 cb。
      const newValue = effect.run()
      if (
        immediateFirstRun ||
        deep ||
        forceTrigger ||
        (isMultiSource
          ? (newValue as any[]).some((v, i) => hasChanged(v, oldValue[i]))
          : hasChanged(newValue, oldValue))
      ) {

        if (cleanup) {
          cleanup()

        activeWatcher = effect

            newValue,

                : oldValue,

        }
      }

export enum EffectFlags {
  /** 副作用尚未停止；仅 `ReactiveEffect` 使用。 */
  ACTIVE = 1 << 0,
  /** 订阅者函数正在执行，用于阻止意外的同步自递归。 */
  RUNNING = 1 << 1,
  /** 当前订阅者应实际挂到依赖的订阅链。 */
  TRACKING = 1 << 2,
  /** 已加入本轮批处理队列，防止同一订阅者重复入队。 */
  NOTIFIED = 1 << 3,
  /** 计算属性的上游可能变化，下次读取需检查或重算。 */
  DIRTY = 1 << 4,
  /** 允许订阅者在执行过程中由自身写操作再次排队。 */
  ALLOW_RECURSE = 1 << 5,
  /** 暂停实际调度；期间收到的通知记录到恢复队列。 */
  PAUSED = 1 << 6,
  /** 计算属性至少成功发布过一次结果。 */
  EVALUATED = 1 << 7,
}
位不是互斥状态：ACTIVE、TRACKING、RUNNING 可同时存在；NOTIFIED 只是短命的批内去重位；DIRTY/EVALUATED 主要服务 computed。把它们画成只能择一的枚举状态机会读错。
notify 的两个条件

RUNNING 且未允许递归时早退；本批尚未 NOTIFIED 才入队。完整方法见 第 03 章 ReactiveEffect.notify()。

ACTIVE 与 TRACKING 不完全相同

ReactiveEffect 活动时通常两者都有；computed 可以保留缓存和依赖元数据，却在没有下游时退出 TRACKING 链。

DIRTY 是“可能过期”

它触发进一步版本检查，不等价于结果一定变化。computed 的新旧结果比较会给出最终答案。

NOTIFIED 是批内去重锁

Subscriber 第一次入队时设置；批处理冲刷前清除。同一批被多个 Dep 命中也只有一个队列节点。

RUNNING 防止默认自递归

运行中的 effect 修改自身依赖时默认不再次入队；只有显式 ALLOW_RECURSE 的调度场景允许。

07

主流程很短，正确性藏在边界里

数组会隐式读写 length，Map 的键可能同时存在 raw 与 proxy 身份， readonly 还可能包着 reactive。Vue 的工程成熟度主要体现在这些语义交叉处。

如果只实现普通对象的 get/set，一个响应式原型大约几十行就够了； 但它还不是可以支撑框架的内核。生产实现必须保证代理对象尽量遵守原生 JavaScript 的直觉，同时把每种操作映射到正确的依赖集合，并避免响应式系统自身的读写造成递归更新。

一间实验室 · 五个边界

shift、Map raw/proxy key、Set member、watch cleanup、scope.stop 一次走完

所有 effect 与 watcher 都在同一个 scope 内创建。数组与集合先展示容器读写，Ref 连续写入展示 watch 清理，最后 scope.stop 关闭这些消费者；后续写入不再增加外部调用次数。

import { expect, test, vi } from 'vitest'
import { effect, effectScope, reactive, ref, watch } from '../src'

test('container and lifecycle boundaries stay coherent', () => {
  const list = reactive([1, 2, 3])
  const rawKey = {}
  const proxyKey = reactive(rawKey)
  const map = reactive(new Map<object, string>())
  const set = reactive(new Set<object>())
  const source = ref(0)
  const listSpy = vi.fn()
  const collectionSpy = vi.fn<(value: string) => void>()
  const watchCalls: Array<[number, number]> = []
  const cleanups: number[] = []
  const scope = effectScope()

  scope.run(() => {
    effect(() => {
      for (let i = 0; i < list.length; i++) list[i]
      listSpy()
    })
    effect(() => collectionSpy(`${map.get(proxyKey)}:${set.has(proxyKey)}`))
    watch(source, (value, oldValue, onCleanup) => {
      watchCalls.push([oldValue, value])
      onCleanup(() => cleanups.push(value))
    })
  })

  list.shift()
  map.set(rawKey, 'mapped')
  set.add(proxyKey)
  source.value = 1
  source.value = 2

  expect(listSpy).toHaveBeenCalledTimes(2)
  expect(collectionSpy).toHaveBeenLastCalledWith('mapped:true')
  expect(watchCalls).toEqual([[0, 1], [1, 2]])
  expect(cleanups).toEqual([1])

  scope.stop()
  list.push(4)
  map.set(rawKey, 'ignored')
  source.value = 3

  expect(cleanups).toEqual([1, 2])
  expect(listSpy).toHaveBeenCalledTimes(2)
  expect(collectionSpy).toHaveBeenCalledTimes(3)
  expect(watchCalls).toHaveLength(2)
})

同一实验室：容器读写与停止结果

按实验操作顺序排列；数组、集合、watch 分别进入各自的处理路径。

01 · SCOPE RUN收集 2 effects + 1 watcherscope.effects 持有三项；首次 list/collection effect 已执行
02 · ARRAYlist.shift()暂停内部 length 追踪；多个索引/length 写入在 batch 后只让 listSpy +1
03 · MAP / SETraw 写，proxy 读get/has 兼查与追踪 raw、proxy 身份；本例新成员按深层可变规则保存，最终得到 mapped:true
04 · WATCH ×2source 0→1→2回调得到 [0,1]/[1,2]；第二轮前先 cleanup(1)
05 · SCOPE STOPeffects.stop + cleanup逐个停止三项 effect；watch onStop 再 cleanup(2)
06 · AFTER STOP继续写，无外部执行容器仍能变化；listSpy/collectionSpy/watchCalls 均保持原次数

① 数组难点：方法内部也会读写

shift 是索引移动、删除与 length 更新的一串操作。Vue 暂停这些内部读取的 tracking，再用 batch 让订阅者在操作结束后读取最终数组。

② Map/Set 难点：身份有两种

读取按 key 与 toRaw(key) 兼查并追踪，传入 raw 不会反向寻找 proxy。写入按已有身份和实际深浅检测保存；原集合若已同时保存 raw 与 proxy，两项仍各自存在。

③ watch 难点：失效还带资源

第二次有效回调前清上一轮，stop 时清最后一轮；无有效变化时不会无条件清理仍在使用的资源。

scope：管理归属、停止与暂停

scope.run 在同步调用期间设置归属；scheduler 决定 effect 的具体调度。scope.stop 批量解除订阅、执行 cleanup、停止子 scope；scope.pause/resume 还可递归暂停与恢复这些 effect。computed 本身不加入 scope.effects。

Array / #2137

数组原型方法可能意外追踪 length

push/splice 内部读取 length 后又写 length。若多个 effect 执行这些方法并把内部 length 读成业务依赖，后续写入会相互触发。RUNNING 只挡住默认的自身重入，挡不住其他 effect；因此变更方法暂停内部 tracking，并用 batch 合并通知。

Collection / #3604

readonly(reactive(Map)) 仍需保持响应性

只读代理禁止写入，不代表它不应该响应底层 reactive Map 的更新。集合 handler 需要正确穿透代理层并在真实响应式来源上建立读取依赖。

Array / #11760

用户扩展 Array 的重写方法

Array 子类可以重写 find 等方法，其参数顺序与类型不再受原生签名约束。 插桩检测到方法不是 Array.prototype 上的原实现时，必须以代理 self 直接调用用户方法， 既尊重子类语义，也保留方法内部的响应式读取。

Memory / #11979

长期存活 target 的动态 key

外层 targetMap 是 WeakMap；target 仍存活时，内部 key→Dep Map 也会保留。普通 removeSub 注销到 sc 为 0 时删除对应条目，减少动态 key 的遗留 Dep。computed 的软退订保留登记，不按“最后一个活动订阅者”直接删除。

Prototype chain

只由真正持有写入的代理触发

setter 要比较 target === toRaw(receiver)。若写入只是沿原型链落到子对象，父代理不应重复触发，否则一次赋值会造成两轮通知。

Iteration

遍历依赖不等于单键依赖

Object.keys、for...in、Map 的 keys() 与 values/entries 对结构变化的敏感度不同，因此 Vue 使用 ITERATE_KEY 与 MAP_KEY_ITERATE_KEY 分开建模。

写入类型怎样选中 Dep

trigger(target, type, key) 先定位该 target 的 key→Dep Map，再选择被写入影响的位置。单键依赖与迭代依赖可以同时命中同一个 effect；外层 batch 用 NOTIFIED 去重，使它只入队一次。以下规则来自 dep.ts 的 trigger()。

目标与操作 通知哪些 Dep 具体后果
普通对象 SET 当前 key 已有属性换值，键集合不变。
对象／Set ADD、DELETE 当前 key + ITERATE_KEY 对象键集合或 Set 成员变化。
Map ADD、DELETE 当前 key + ITERATE_KEY + MAP_KEY_ITERATE_KEY 键和值的遍历都变化。
Map SET 已有键 当前 key + ITERATE_KEY values/entries/forEach 更新；keys 不更新。size 共享 ITERATE_KEY，也会被通知。
集合 CLEAR 该目标已建立的全部 Dep 单键、size 与各种迭代一起失效。
数组数字索引 SET、DELETE 当前索引 + ARRAY_ITERATE_KEY 该位置与数组值迭代变化；DELETE 不改 length。
数组数字索引 ADD 当前索引 + ARRAY_ITERATE_KEY + length 新增超出原长度范围的索引，同时改变长度。
数组 length 写入 length + ARRAY_ITERATE_KEY + 索引 ≥ 新长度的 Dep 缩短时被截断索引也必须更新；增大长度仍通知长度与值迭代。
数组非整数属性 SET／ADD／DELETE 仅当前 key 不通知 length 或 ARRAY_ITERATE_KEY。
同一个 Map · 已有键换值

值变了，keys 与 size 为什么表现不同？

从 new Map([['a', 1]]) 开始，分别读取 get('a')、keys()、values() 和 size。首次读取分别订阅 key 'a'、MAP_KEY_ITERATE_KEY、ITERATE_KEY、ITERATE_KEY。写 map.set('a', 2) 命中 SET，只通知 key 与 ITERATE_KEY：get、values 和 size 的 effect 各重跑一次，keys 的 effect 保持一次。size 的结果仍是 1，但它与值迭代共享 Dep，所以函数仍会重跑。

    get(this: MapTypes, key: unknown) {
      // #1772：保留内层 reactive Map 的读取链，再给结果增加 readonly 约束。
      const target = this[ReactiveFlags.RAW]
      const rawTarget = toRaw(target)
      const rawKey = toRaw(key)
      if (!readonly) {
        // key 若是代理，同时追踪 proxy key 与 raw key：集合可能由用户以任一身份建键。
        if (hasChanged(key, rawKey)) {
          track(rawTarget, TrackOpTypes.GET, key)
        }
        track(rawTarget, TrackOpTypes.GET, rawKey)
      }
      const { has } = getProto(rawTarget)
      const wrap = shallow ? toShallow : readonly ? toReadonly : toReactive
      if (has.call(rawTarget, key)) {
        return wrap(target.get(key))
      } else if (has.call(rawTarget, rawKey)) {
        return wrap(target.get(rawKey))
      } else if (target !== rawTarget) {
        // #3602：外层 readonly 不收集依赖，但内层 target 可能是 reactive(Map)。即便
        // 没找到键也要调用一次内层 get，让“当前不存在的键”建立依赖；以后 set 该键
        // 时，依赖 readonly(reactive(map)).get(key) 的 effect 才会重新运行。
        target.get(key)
      }
    },
    /**
     * 读取 size 时，可变模式订阅 ITERATE_KEY。新增、删除、非空清空都会通知它；
     * Map 已有键换值也会通知此依赖，不要求 size 数值发生变化。
     */
    get size() {
      const target = (this as unknown as IterableCollections)[ReactiveFlags.RAW]
      !readonly && track(toRaw(target), TrackOpTypes.ITERATE, ITERATE_KEY)
      return target.size
    },
    /** 检查键/成员是否存在，同时兼容查询值的代理与原始身份。 */
    has(this: CollectionTypes, key: unknown): boolean {
      const target = this[ReactiveFlags.RAW]
      const rawTarget = toRaw(target)
      const rawKey = toRaw(key)
      if (!readonly) {
        if (hasChanged(key, rawKey)) {
          track(rawTarget, TrackOpTypes.HAS, key)
        }
        track(rawTarget, TrackOpTypes.HAS, rawKey)
      }
      return key === rawKey
        ? target.has(key)
        : target.has(key) || target.has(rawKey)

          add(this: SetTypes, value: unknown) {
            const target = toRaw(this)
            const proto = getProto(target)
            const rawValue = toRaw(value)
            const valueToAdd =
              !shallow && !isShallow(value) && !isReadonly(value)
                ? rawValue
                : value
            const hadKey =
              proto.has.call(target, valueToAdd) ||
              (hasChanged(value, valueToAdd) &&
                proto.has.call(target, value)) ||
              (hasChanged(rawValue, valueToAdd) &&
                proto.has.call(target, rawValue))
            if (!hadKey) {
              // 只有真正新增成员才修改集合并触发 ADD，重复 add 不产生更新。
              target.add(valueToAdd)
              trigger(target, TriggerOpTypes.ADD, valueToAdd, valueToAdd)
            }
            return this
          },
          /**
           * 设置 Map/WeakMap 键值。已有 key 优先沿用其当前身份；找不到才尝试 raw key。
           * 新键触发 ADD，已有键且值实际变化触发 SET。
           */
          set(this: MapTypes, key: unknown, value: unknown) {
            if (!shallow && !isShallow(value) && !isReadonly(value)) {
              value = toRaw(value)
            }
            const target = toRaw(this)
            const { has, get } = getProto(target)

            let hadKey = has.call(target, key)
            if (!hadKey) {
              // 用户常以代理 key 调用 set，而深层集合通常保存 raw key；统一到已有身份。
              key = toRaw(key)
              hadKey = has.call(target, key)
            } else if (__DEV__) {
              // 若 raw/proxy 两种 key 已同时存在，任何一次 set 都可能产生歧义，开发期警告。
              checkIdentityKeys(target, has, key)
            }

            const oldValue = get.call(target, key)
            target.set(key, value)
            if (!hadKey) {
              trigger(target, TriggerOpTypes.ADD, key, value)
            } else if (hasChanged(value, oldValue)) {
              trigger(target, TriggerOpTypes.SET, key, value, oldValue)
            }
            return this
          },

完整方法 · effectScope.ts · EffectScope.stop() 
  stop(fromParent?: boolean): void {
    if (this._active) {
      this._active = false
      let i, l
      for (i = 0, l = this.effects.length; i < l; i++) {
        this.effects[i].stop()
      }
      this.effects.length = 0

      for (i = 0, l = this.cleanups.length; i < l; i++) {
        this.cleanups[i]()
      }
      this.cleanups.length = 0

      if (this.scopes) {
        const scopes = this.scopes.slice()
        for (i = 0, l = scopes.length; i < l; i++) {
          scopes[i].stop(true)
        }
        this.scopes.length = 0
      }

      // 解除父子引用，防止已停止的嵌套作用域仍被父级持有而无法回收。
      if (!this.detached && this.parent && !fromParent) {
        // 用父数组末项填补当前位置，实现 O(1) 删除。
        const last = this.parent.scopes!.pop()
        if (last && last !== this) {
          this.parent.scopes![this.index!] = last
          last.index = this.index!
        }
      }
      this.parent = undefined
    }
  }
所有权清单：先把 active 置 false 保证幂等；停止 effects、执行 scope cleanups、递归停止子 scopes；最后解除父子引用。Demo 的 watch cleanup(2) 发生在其 ReactiveEffect.stop → onStop。

Vue 3.5.41 的常量 computed 刷新路径

01 · CREATEcomputed(() → spy())只创建实例；getter 尚未执行，deps 为空
02 · FIRST READspy: 0 → 1首次 refresh 执行 getter；设置 EVALUATED，结果写缓存；仍无 deps

06 · ASSERTspy === 1回归测试证明无关全局写入不会重算常量 computed

① globalVersion 只是一层粗筛

globalVersion 变化说明有触发路径递增了它，不表示 c1 的输入一定变化。先比全局版本，再检查自己的 deps；同值 setter 不触发，而手动 triggerRef 可在值不变时递增版本。

② 无 deps 比逐边 isDirty 更短

从当前依赖图看，没有任何能通知它的响应式输入；非 SSR 且未被手工标脏时，无需扫描不存在的 Link，直接复用缓存。非响应式闭包变量本来就不受这套自动失效契约保证。

③ EVALUATED 防止首次误跳

没求值过时同样没有 deps；只有已经 EVALUATED，才能进入无 deps 快路，返回已经保存的缓存。

④ SSR 跳过这层依赖快路

本例是非 SSR computed，已经 EVALUATED、没有 deps 且未被手工标脏，因此直接复用缓存。SSR 仍可记录 deps，但跳过这层判断，继续依靠全局版本快路或执行 getter。

连续原文 · effect.ts · refreshComputed 无 deps 快路 
  // SSR 求值仍收集并保留依赖 Link，但 !computed.isSSR 会跳过下面的依赖版本快路径。
  // 全局版本相同仍复用缓存；全局版本变化后，即使自身依赖版本没变，也会重新求值。
  // issue #12337 场景：`computed(() => constant)` 不读取任何响应式数据。它求值一次后
  // 非 SSR 下，已发布结果、无 deps 且未设置兼容 _dirty 的 computed 会直接复用缓存，
  // 不因别处触发使 globalVersion 增长而再次执行 getter。
  if (
    !computed.isSSR &&
    computed.flags & EffectFlags.EVALUATED &&
    ((!computed.deps && !(computed as any)._dirty) || !isDirty(computed))
  ) {
    return
  }

十条结论，重新理解 Vue 响应式

回到最初的读写问题，下面十条结论分别对应 01–08 的机制与用例。

阅读下一步

从下面的结论返回对应章节，再按源码入口定位完整实现；需要继续读某个分支时，可从末尾的问题导航进入。

  1. 响应式的核心产物不是代理对象，而是由真实执行路径生成的依赖图。
  2. reactive 对象由 Proxy 把语言操作翻译成 track/trigger；Ref 直接持有 Dep。两种入口都不负责最终调度。
  3. 一个 Dep 表示一个可独立观察的位置，通常是原始 target 的某个 key，也可以是 Ref.value。
  4. Link 先进入 Subscriber 的依赖链；Subscriber 带有 TRACKING 时，再接入 Dep 的通知链。保留元数据与接收通知是两种状态。
  5. 活动 effect 每次运行都会重新确认依赖；条件分支改变后，本轮未再读取的旧 Link 会被移除。
  6. TriggerOpTypes 与抽象迭代键把对象、数组、Map/Set 的结构变化显式建模。
  7. 通知表达可能失效；内部 batch 去重并冲刷。默认 effect 通过版本检查决定是否重跑，自定义 scheduler 则直接收到调度调用。
  8. computed 同时消费上游并提供输出 Dep；读取 .value 与下游依赖检查都可刷新它。正常重算结果未变时，输出版本保持不变，默认消费者可跳过重跑；首次求值由 dep.version === 0 发布第 1 版。
  9. watch 是建立在 ReactiveEffect 上的策略层；deep 的本质是主动遍历读取，而不是免费能力。
  10. WeakMap 不强留 target，动态清理删除未读 Link；stop 与 effectScope 停止 effect／watcher，并解除它们带来的通知关系。
Vue 响应式最值得借鉴的并不是 Proxy 技巧，而是它把“关系发现、失效传播、执行策略、生命周期” 拆成了边界清晰的四个问题，并允许每一层独立演进。

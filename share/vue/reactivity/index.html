01

响应式到底在解决什么问题？

数据变化本身并不神秘。困难在于：系统怎样知道哪些计算和副作用依赖这次变化， 并且只让真正受影响的部分重新工作？

核心命题

Vue 不理解“购物车总价”或“按钮是否可用”这样的业务概念。它只在函数执行期间记录： 当前订阅者读取了哪个原始对象的哪个位置。响应式系统因此不是一个值同步器， 而是一套运行时依赖分析与失效传播机制。

本文只跟一条链：src → c1 → c2 → effect。src 是源值，c1 计算奇偶性，c2 在 c1 上加 1，effect 消费最终结果。 命令式写法要求我们逐层记住谁该重算；响应式系统则维护这张关系网。

Vue 的选择是让依赖关系在运行时自然暴露。某个函数执行时读取了 src.value，就说明它依赖这个位置；以后 src 改变，系统沿着已经记录的边 找回函数。开发者只声明“结果如何由状态得到”，依赖图则由真实执行路径生成。

链式 computed 如何阻断无效更新

直接采用测试用例 chained computed avoid re-compute。 src 连续变化三次，但奇偶性始终为 0；测试验证 c1 必须检查三次，而 c2 与最终 effect 一次都不应多执行。

完整测试 · COMPUTED.SPEC.TS:650 
import { expect, test, vi } from 'vitest'
import { computed, effect, ref } from '../src'

// 场景：上游连续变化，但中间派生值始终相同。
// 验证：下游 computed 与 effect 不做无意义重算。
test('chained computed avoid re-compute', () => {
  const effectSpy = vi.fn()
  const c1Spy = vi.fn()
  const c2Spy = vi.fn()

  const src = ref(0)
  const c1 = computed(() => {
    c1Spy()
    return src.value % 2
  })
  const c2 = computed(() => {
    c2Spy()
    return c1.value + 1
  })

  effect(() => {
    effectSpy(c2.value)
  })

  expect(effectSpy).toHaveBeenCalledTimes(1)

  src.value = 2
  src.value = 4
  src.value = 6

  expect(c1Spy).toHaveBeenCalledTimes(4)
  expect(c2Spy).toHaveBeenCalledTimes(1)
  expect(effectSpy).toHaveBeenCalledTimes(1)
})

最小心智模型只有一句话：读操作建立边，写操作让边另一端的消费者失效。 Proxy 负责看见读写，Dep 保存“一个位置”的订阅者，Link 表示一条关系， Subscriber 决定收到通知后怎么做。

Dep一个可独立追踪位置的依赖桶，例如 src.value。

PRINCIPLE / 01

透明代理

Proxy + Reflect 保持普通对象的使用方式，在 get/set/has/ownKeys 等语言操作中插入追踪与触发。

PRINCIPLE / 02

属性级粒度

依赖并不挂在整个对象上，而是挂在具体 key 上。数组长度、对象遍历、Map 键遍历另有专门的抽象依赖键。

PRINCIPLE / 03

按需深层转换

创建 reactive 时不会递归遍历对象；只有属性读取到嵌套对象时，才继续把返回值包装为代理。

PRINCIPLE / 04

延迟计算

computed 失效时优先标脏，不立即求值。只有消费者再次读取 .value，才判断是否真正需要重算。

PRINCIPLE / 05

身份归一化

依赖存储尽量基于原始对象；集合键同时兼容 raw 与 reactive 身份，避免同一实体产生两套订阅关系。

PRINCIPLE / 06

可回收的图

依赖关系必须能增量复用，也必须能在分支变化、停止 effect 或结束 scope 时解绑，避免过期触发与内存泄漏。

Constraint A

依赖必须来自真实执行，而不是静态猜测

对 ok ? state.a : state.b 而言，依赖会随分支切换。Vue 每次执行订阅者时重新确认实际读取过的 Dep，并删除本轮没有再次出现的旧 Link。 这使依赖图与控制流始终一致，也解释了为什么 effect 不能只在首次执行时收集一次。

Constraint B

“可能变化”与“结果已变化”必须分开

上游写入只能说明 computed 可能过期，并不能证明新结果不同。Vue 先把计算属性标脏，等消费者读取时再求值；只有新旧结果确实不同， 它自己的 Dep 版本才变化。这个区分避免无效派生结果向下游扩散。

i

阅读时不要把 reactive 当成“数据自动变了”。数据本来就会变；响应式层真正增加的是： 记录读取关系、识别写入类型、安排订阅者重新执行。

02

Proxy 是对象入口，不是响应式引擎

reactive 对象从 Proxy 进入，Ref 从 .value 进入；两条路径最终汇入同一套 Dep、Link 与 Subscriber 图。

很多响应式介绍停在 new Proxy(target, { get, set })， 仿佛拦截器本身就完成了响应式。实际 Proxy 只是把语言操作翻译成内部事件： 读取属性变成 track(target, GET, key)，写入属性变成 trigger(target, SET/ADD, key)。如果没有活动订阅者， 一次普通读取甚至不会创建 Dep。

这种分层让容器语义与调度策略彼此独立。代理层负责保持 JavaScript 行为； 依赖层不知道对象是通过普通属性、数组方法还是 Map API 被访问；effect 层也不关心变化来自哪个容器。各层只通过“目标、键、访问类型与操作类型”这组协议协作。

JavaScript 操作→Proxy / Instrumentation→track / trigger→Dep / Link→Subscriber

对象入口 · Proxy

  • state.count 由 Proxy getter/setter 拦截。
  • track/trigger(target, key) 在 targetMap 中定位 Dep。
  • 适合对象、数组与 Map/Set；一个容器通常对应多个 key Dep。

值入口 · Ref

  • src.value 直接进入 RefImpl getter/setter。
  • Ref 自带一个 Dep，直接调用 dep.track()/trigger()。
  • 它不是 Proxy；ReactiveFlags.IS_REF 只是统一身份标记。

Identity and lazy conversion

身份稳定是正确性条件

  • reactive(raw) === reactive(raw) 必须成立，否则同一个对象会出现多个代理身份。
  • 可变、浅可变、只读、浅只读语义不同，因此分别使用四个 WeakMap 缓存。
  • WeakMap 不会阻止原始对象被回收，代理缓存不会永久留住业务对象。

深层响应是惰性的

  • 创建 reactive 时不会递归遍历整棵对象树。
  • getter 读到嵌套对象后，才调用 reactive/readonly 返回代理。
  • 创建成本只与根对象相关，真正访问到的分支才承担包装成本。
为什么 Map / Set 需要另一套 handler？

集合方法依赖内部槽，直接让代理充当原生方法的 this 会出现 incompatible receiver。 Vue 返回一组 instrumentations：它们先取得 raw target，再完成追踪、身份归一化和返回值包装。 这不是偶然的“特判”，而是 JavaScript 集合语义对代理实现提出的要求。

→

这一层的关键结论：Proxy 不保存订阅者，也不决定 effect 何时运行；Ref 则绕过 targetMap，直接持有 Dep。 两种入口只负责生成足够精确的读写事件，关系和执行策略仍由图内核处理。

Read line by line · 逐行认识角色

先别急着记 Dep、Link。这个测试只在问一个很朴素的 问题：上游原值变化，但经过第一层计算后结果没变，下游还要不要 重做？这里三个 spy 像三只计数器，分别装在第一层计算、第二层计算 和最终副作用里。哪一层真的执行了，计数就加一。

测试源码 它扮演什么角色 这一行预期什么
effectSpy / c1Spy / c2Spy 三层“实际执行次数”探针，不测通知次数，只测函数真的跑了几次。 最后用 4 / 1 / 1 把每一层的工作量分别钉死。
const src = ref(0) 唯一可变源头。它自己的 Dep 直接保存在 Ref 实例上。 初值 0；后续依次写 2、4、6，每次原值都确实变化。
c1 = computed(() => src.value % 2) 第一道失效边界：读取 src，只保留奇偶性。 0、2、4、6 的派生结果始终是 0；它必须检查，但结果不必发布为新版本。
c2 = computed(() => c1.value + 1) 第二层派生，只依赖 c1.value，不直接知道 src。 只要 c1.dep.version 没变，getter 就无需再执行。
effect(() => effectSpy(c2.value)) 最终消费者。effect() 创建后会立即执行一次并完成建图。 首次收到 1；偶数写入之后不应再次调用。
expect(effectSpy)...(1) 确认“创建 effect 会立即运行”以及整条计算链完成首次求值。 此时三个 spy 实际都已经各执行 1 次。
src.value = 2 / 4 / 6 三个独立的同步写入；每条赋值各自触发并结束一轮 batch。 不是把三次写入合并后只检查一次：c1 会再检查三次。
expect(...).toHaveBeenCalledTimes(...) 最终证明三层工作量：上游边界被检查，下游无效工作被截断。 c1Spy = 4、c2Spy = 1、effectSpy = 1。
!

先记住测试契约：“收到可能失效通知”不等于“getter 或 effect 已经重跑”。通知链会一路把下游叫醒，但下游真正执行前还要逐层 核对版本。这个区别正是 4 / 1 / 1 能成立的原因。

Vocabulary · 术语先定义

下面流程只需要六个词。把它们想成一张带版本号的有向图： Dep 是被读的数据节点，Subscriber 是会重新工作的消费者，Link 是两者之间那条带快照的边。computed 特别之处在于它同时站在两边： 对上游是 Subscriber，对下游又通过自己的 dep 成为 Dep。

术语 在本测试里是谁 只需记住的职责
Dep src.dep、c1.dep、c2.dep 保存当前值版本 version，并能沿订阅链发通知。
Subscriber c1、c2、外层 ReactiveEffect 接收通知、维护依赖 Link；computed 与 effect 都实现这个协议。
Link c1→src、c2→c1、effect→c2 link.version 记录上次确认过的 dep.version。
activeSub 嵌套求值时依次为 effect、c2、c1 告诉 Dep.track()：“当前这次读取应记到谁名下”。
DIRTY / NOTIFIED computed 的“可能失效”位 / 同批去重位 DIRTY 要求检查；NOTIFIED 防止同一轮重复入队，不代表值已变化。
globalVersion 以进入本测试时的值 G 为基线，依次变为 G+1、G+2、G+3 任意真实 trigger 都递增；若没变，computed 可直接复用缓存。

  fn: () => T,
  options?: ReactiveEffectOptions,
): ReactiveEffectRunner<T> {

    fn = (fn as ReactiveEffectRunner).effect.fn

  track(debugInfo?: DebuggerEventExtraInfo): Link | undefined {
    if (!activeSub || !shouldTrack || activeSub === this.computed) {
      return
    }

    let link = this.activeLink
    if (link === undefined || link.sub !== activeSub) {
      link = this.activeLink = new Link(activeSub, this)

      // 新 Link 按读取顺序追加到当前订阅者依赖链尾。
      if (!activeSub.deps) {
        activeSub.deps = activeSub.depsTail = link
      } else {
        link.prevDep = activeSub.depsTail
        activeSub.depsTail!.nextDep = link
        activeSub.depsTail = link
      }

      addSub(link)
    } else if (link.version === -1) {
      // 复用上轮 Link；它本就在 Dep 订阅链中，只需标记本轮已读取。
      link.version = this.version

      // 非尾节点说明本轮访问顺序改变，将其移到尾部，使依赖链始终反映本轮读取顺序。
      if (link.nextDep) {
        const next = link.nextDep
        next.prevDep = link.prevDep
        if (link.prevDep) {
          link.prevDep.nextDep = next
        }

        link.prevDep = activeSub.depsTail
        link.nextDep = undefined
        activeSub.depsTail!.nextDep = link
        activeSub.depsTail = link

        // 若移动的是原链表头，下一节点成为新头。
        if (activeSub.deps === link) {
          activeSub.deps = next
        }
      }
    }

    if (__DEV__ && activeSub.onTrack) {
      activeSub.onTrack(
        extend(
          {
            effect: activeSub,
          },
          debugInfo,
        ),
      )
    }

    return link
  }

  trigger(debugInfo?: DebuggerEventExtraInfo): void {
    this.version++
    globalVersion++
    this.notify(debugInfo)

   * 在批处理中通知当前 Dep 的所有订阅者，但不递增版本。
   *
   * 计算属性脏传播使用 `notify()`：其自身 Dep 的值尚未重新计算，不能提前递增版本，
   * 只需继续把“可能变化”传给下游。用 `finally` 配对批处理，调试钩子或通知抛错时
   * 也能正确冲刷/恢复批深度。

  notify(debugInfo?: DebuggerEventExtraInfo): void {
    startBatch()
    try {
      if (__DEV__) {
        // 生产通知从链尾逆序入栈，批结束后又按栈顺序执行，最终仍是原订阅顺序。
        // onTrigger 在此处立即调用，故开发模式额外从链头正序遍历才能保持相同顺序。
        for (let head = this.subsHead; head; head = head.nextSub) {
          if (head.sub.onTrigger && !(head.sub.flags & EffectFlags.NOTIFIED)) {
            head.sub.onTrigger(
              extend(
                {
                  effect: head.sub,
                },
                debugInfo,
              ),
            )
          }
        }
      }
      for (let link = this.subs; link; link = link.prevSub) {
        if (link.sub.notify()) {
          // 返回 true 表示订阅者是 computed；继续通知依赖 computed.value 的下游。

          ;(link.sub as ComputedRefImpl).dep.notify()

    }

生产源码 · 连续原文 · src/effect.ts · batch/startBatch/endBatch 
export function batch(sub: Subscriber, isComputed = false): void {
  sub.flags |= EffectFlags.NOTIFIED
  if (isComputed) {
    sub.next = batchedComputed
    batchedComputed = sub
    return
  }
  sub.next = batchedSub
  batchedSub = sub
}

/**
 * 开始一层批处理。嵌套调用只增加深度，由最外层 `endBatch()` 负责统一冲刷。
 *
 * @internal
 */
export function startBatch(): void {
  batchDepth++
}

/**
 * 结束一层批处理，并在最外层结束时运行所有待处理 effect。
 *
 * 先清空计算属性的入队标记，再执行普通 effect；执行期间新产生的 effect 会形成新一段
 * 链表，由外层 `while` 继续冲刷。某个 effect 抛错不会阻止其余 effect 执行，最终抛出
 * 捕获到的第一个错误。
 *
 * @internal
 */
export function endBatch(): void {
  if (--batchDepth > 0) {
    return
  }

  if (batchedComputed) {
    let e: Subscriber | undefined = batchedComputed
    batchedComputed = undefined
    while (e) {
      const next: Subscriber | undefined = e.next
      e.next = undefined
      e.flags &= ~EffectFlags.NOTIFIED
      e = next
    }
  }

  let error: unknown
  while (batchedSub) {
    let e: Subscriber | undefined = batchedSub
    batchedSub = undefined
    while (e) {
      const next: Subscriber | undefined = e.next
      e.next = undefined
      e.flags &= ~EffectFlags.NOTIFIED
      if (e.flags & EffectFlags.ACTIVE) {
        try {
          // ACTIVE 仅 ReactiveEffect 拥有，因此此处分支可安全收窄类型。
          ;(e as ReactiveEffect).trigger()
        } catch (err) {
          if (!error) error = err
        }
      }
      e = next
    }
  }

  if (error) throw error
}

function isDirty(sub: Subscriber): boolean {
  for (let link = sub.deps; link; link = link.nextDep) {
    if (
      link.dep.version !== link.version ||
      (link.dep.computed &&
        (refreshComputed(link.dep.computed) ||
          link.dep.version !== link.version))
    ) {
      return true
    }
  }
  // @ts-expect-error：兼容旧库手动设置 `_dirty`，例如 Pinia testing 模块。
  if (sub._dirty) {
    return true
  }
  return false
}

 * 按需刷新计算属性的缓存。
 *
 * 快速路径从便宜到昂贵依次为：仍在追踪且未标脏、全局版本没有任何变化、逐依赖版本
 * 检查后确认结果不可能变化；只有这些判断都失败才真正执行 getter。
 *
 * @returns 当前实现只返回 `undefined`；调用方通过计算属性 `dep.version` 判断值是否变化。
 * @internal
 */
export function refreshComputed(computed: ComputedRefImpl): undefined {
  if (
    computed.flags & EffectFlags.TRACKING &&
    !(computed.flags & EffectFlags.DIRTY)
  ) {
    return
  }
  computed.flags &= ~EffectFlags.DIRTY

  // 全局版本快速路径：上次刷新后整个响应式系统都没有触发过变化，无需扫描依赖链。
  if (computed.globalVersion === globalVersion) {
    return
  }
  computed.globalVersion = globalVersion

  // SSR 没有渲染 effect，computed 通常没有下游订阅者，也就不会维持可供 isDirty()
  // 使用的完整依赖订阅状态；因此 SSR 主要依赖上面的 globalVersion 缓存，否则重算。
  // issue #12337 场景：`computed(() => constant)` 不读取任何响应式数据。它求值一次后
  // 即使别处响应式状态让 globalVersion 增长，结果也不可能变化；无 deps 时直接复用，
  // 避免每次全局任意更新都重新执行这个常量 getter。
  if (
    !computed.isSSR &&
    computed.flags & EffectFlags.EVALUATED &&
    ((!computed.deps && !(computed as any)._dirty) || !isDirty(computed))
  ) {
    return
  }
  computed.flags |= EffectFlags.RUNNING

  const dep = computed.dep
  const prevSub = activeSub
  const prevShouldTrack = shouldTrack
  activeSub = computed
  shouldTrack = true

  try {
    prepareDeps(computed)
    const value = computed.fn(computed._value)
    // 只有首次求值或结果按 Object.is 语义真正变化，才递增自身 dep.version，
    // 从而让依赖 computed.value 的下游 effect 精确跳过“上游变、派生值未变”的更新。
    if (dep.version === 0 || hasChanged(value, computed._value)) {
      computed.flags |= EffectFlags.EVALUATED
      computed._value = value
      dep.version++
    }
  } catch (err) {
    // getter 抛错也递增版本；下次读取必须重试，不能把失败当作有效缓存。
    dep.version++
    throw err
  } finally {
    activeSub = prevSub
    shouldTrack = prevShouldTrack
    cleanupDeps(computed)
    computed.flags &= ~EffectFlags.RUNNING
  }
}
写 2 的精确落点：c1 的 src Link v0 与 src.dep v1 不同， 所以 c1 getter 执行；所得 0 与旧值 0 相等，未进入 dep.version++。返回 c2 后，c1.dep v1 仍等于 c2 的 Link v1， c2 走“已求值且 !isDirty”快速返回；effect 对 c2 同理。

Given

一条会折叠偶数变化的两层 computed 链

When

依次写入三个不同的偶数

写 2、4、6 每次都让 src.dep 与 globalVersion 递增，并同步传播到 effect； 每次也都迫使 c1 根据最新 src 重新求值，但余数一直是 0。

Then

第一层检查四次，后两层只执行首次

最终 c1Spy=4、c2Spy=1、 effectSpy=1。测试测的是函数实际调用次数，不是否收到过通知。

Mechanism

可能失效向下传播，确认后的结果版本向下裁决

notify 负责让整条链有机会检查；refreshComputed() 负责从下游 递归刷新上游；computed 结果按 Object.is 未变时不递增 dep.version； isDirty() 据 Link 快照相等而逐层返回 false，截断实际执行。

Counterexample · 如果改写 3 会怎样

用奇数做反例，能确认刹车不是“computed 永远不重算”。假设在首次建图后写 src.value = 3：src.dep 0→1；c1 检查得到 3 % 2 = 1，旧值 0→新值 1，因 hasChanged 为 true， c1.dep 1→2。c2 的 Link 仍是 v1，与 c1.dep v2 不同，于是 c2 getter 执行， 结果 1→2，c2.dep 1→2。effect 的 Link v1 又与 c2.dep v2 不同，最终 ReactiveEffect.run() 执行，effectSpy(2) 被调用。

src.dep 0→1→c1: 0→1 / dep 1→2→c2: 1→2 / dep 1→2→effectSpy(2)
一句话心智模型

写入先广播“你可能过期了”；执行前再沿 Link 追到真正变化的源头；每层 computed 只有在派生结果真的变化时才发布新版本。版本没穿过哪一层， 实际重算就停在哪一层之后。

Boundary · 本用例没有证明什么

第一，本例只覆盖普通深层 Ref、只读 computed 链和无 scheduler 的同步 effect；暂停 effect、SSR、getter 抛错、可写 computed 都有额外分支。 第二，reactivity 的 batch/endBatch 负责同一通知栈内去重与冲刷， 不等同于 runtime-core 的组件 job queue；组件更新何时进入微任务由运行时 调度章节解释。第三，测试最终只断言调用次数，版本账本是根据 Vue 3.5.41 当前实现逐步推导的源码事实，不应外推成所有未来版本都必须保持相同内部字段。

Link：一条边，服务两种遍历方向

Vue 3.5 不再把订阅关系简单理解成 Dep 内部的一个 Set。 每个 Dep—Subscriber 关系都是独立的 Link，并同时存在于两条双向链表中。

依赖图需要回答两个相反的问题。状态变化时，要从 Dep 出发找到“谁依赖我”； effect 停止或切换分支时，又要从 Subscriber 出发找到“我依赖谁”。如果只在 Dep 中保存订阅者 Set，第二种操作就需要额外索引，动态清理也会频繁创建临时集合。

Link 把这两个方向合并在一个节点中。prevSub/nextSub 把它串进 Dep 的订阅者链；prevDep/nextDep 把它串进 Subscriber 的依赖链。任一方向都能 O(1) 摘除已知节点，同时 Link 还能携带版本号和嵌套追踪上下文。

为什么需要每轮确认

条件一变，旧依赖就必须退出

首轮读取 obj.run 和 obj.prop；把 run 改成 false 后，本轮只读取 run，prop 的旧 Link 必须删除。 因此随后写入 obj.prop 不会再次触发 effect。

① prepareDeps

运行前把旧 Link 的 version 置为 -1，并把 Link 安装到 Dep.activeLink，作为本轮可复用索引。

② dep.track

再次读取旧 Dep 时 O(1) 找回 Link 并恢复版本；新读取则创建 Link 并追加到两条链。

③ cleanupDeps

运行后从尾向前扫描；仍为 -1 的 Link 同时从 Dep 链与 Subscriber 链摘除。

④ 维护最新顺序

复用的 Link 会按本轮访问顺序移动到尾部，依赖链始终反映最近一次真实执行。

sc 是 Link 引用计数，不是 computed 订退开关

Dep 的 sc 统计引用当前 Dep 的 Link，包括 computed 为懒订阅保留但暂时不在触发链中的连接。最后一个引用离开时，Dep 可以从所属 key→Dep Map 中删除。computed 是否接入或退出上游触发链， 判断的是它自己的 dep.subs 是否从空变非空或重新变空； 退出时只软移除上游订阅，所以不会误减这些保留 Link 的 sc。

05

Computed 为什么既是消费者，又是数据源？

reactive、ref、computed、watch 看起来是不同 API，底层却只是对同一张图的不同角色封装。 其中 computed 是理解失效传播和缓存策略的关键。

普通 effect 只有“消费依赖”的一面；ref 只有“提供依赖”的一面。computed 同时拥有两种身份：执行 getter 时，它作为 Subscriber 读取上游；外部读取 computed.value 时，它又通过自己的 Dep 成为下游的数据源。 所以计算属性是依赖图中的中间节点，而不只是一个带缓存的函数。

src 从 0 写成 2 时，c1、c2 先后收到通知并设置 DIRTY，但都不立即执行 getter。批处理结束后，effect 的脏检查沿 c2、c1 逐层调用 refreshComputed()；c1 重新得到 0，自身 Dep.version 不变，因此 c2 与 effect 都可停止。写成 3 时结果逐层变化，版本才继续向下游推进。

快速路径 1 · 未标脏

仍在 TRACKING 且没有 DIRTY，说明上游没有发出失效通知，直接返回缓存。

快速路径 2 · 全局未变化

自身保存的 globalVersion 等于全局版本，说明系统中没有任何响应式写入，无需扫描依赖。

快速路径 3 · 依赖版本未变

即使全局其他地方变化，只要自己的所有 Link 版本仍匹配，也可以复用结果。

最终路径 · 执行 getter

只有前面判断都失败才重算；新旧结果按 Object.is 语义不同，才递增自身 Dep 版本。

常量 computed 为什么只计算一次？

computed(() => 42) 没有任何上游 deps。首次成功求值后， 即使别处写入让 globalVersion 增长，其结果也不可能受影响。Vue 直接复用缓存， 这对应 #12337 / #12341 一类“无依赖计算属性被无关更新反复执行”的优化场景。

  • 读取时使用 globalVersion 与依赖版本做快速路径。

watch 先把不同来源统一为 getter，再用 ReactiveEffect 追踪；scheduler 决定回调在何时执行，cleanup 在下一轮或停止时调用。

  • reactive 来源默认深层遍历；getter 来源只追踪真实读取。
  • 数组来源逐项求值并判断任一元素是否变化。
  • pause/resume 保留脏状态，恢复时补执行一次，不丢失期间变化。
SceffectScope批量生命周期边界

作用域用紧凑数组保存 effect、cleanup 与子作用域。停止父作用域时递归停止全部资源，解决组件卸载或组合函数销毁后的遗留副作用。

  • 嵌套 scope 默认挂到当前活动 scope。
  • detached scope 拥有独立生命周期。
  • 移除子 scope 时用尾项覆盖空位，避免线性搬移。
Watch is a policy layer

watch 没有另起炉灶。它先把 Ref、reactive 对象、getter 或多来源数组统一成一个 getter，再交给 ReactiveEffect 追踪。区别在于：effect 关注“依赖失效后重新执行函数”，watch 还要维护新旧值比较、immediate、once、deep、 cleanup 和 scheduler 等回调政策。

深度监听并不是“神奇地监听对象内部”。traverse() 会主动递归读取 对象、数组、Ref、Map 和 Set 的可观察成员，从而人为建立深层依赖。代价也因此很直接： 被遍历的属性越多，初始收集和后续重跑成本越高。getter 精确选择字段通常比无界 deep watch 更可控。

watch 的 cleanup 解决什么

  • 取消上一轮尚未完成的请求，避免旧结果覆盖新状态。
  • 移除旧事件监听与定时器，防止重复注册。
  • 清理发生在下一次有效执行前或 watcher 永久停止时。

effectScope 解决什么

  • 把一组 effect、watcher 与 cleanup 绑定到同一生命周期。
  • 父 scope 停止时递归停止子 scope；detached scope 独立存在。
  • 组件卸载和组合函数销毁不必逐个保存并调用停止句柄。

枚举不是常量表，而是模块间协议

Proxy、Dep、Effect、Computed 与 Watch 通过少量枚举交换语义。 它们把大量隐式分支收束成可组合的操作类型和状态机。

TrackOpTypes 回答“发生了哪种读取”，TriggerOpTypes 回答“发生了哪种写入”，ReactiveFlags 回答“眼前这个值暴露了哪种响应式身份”， EffectFlags 则回答“订阅者此刻处于什么阶段”。把它们看作跨文件协议， 比记忆枚举值更容易理解源码。

ACTIVE 与 TRACKING 不完全相同

ReactiveEffect 活动时通常两者都有；computed 可以保留缓存和依赖元数据，却在没有下游时退出 TRACKING 链。

它触发进一步版本检查，不等价于结果一定变化。computed 的新旧结果比较会给出最终答案。

NOTIFIED 是批内去重锁

Subscriber 第一次入队时设置；批处理冲刷前清除。同一批被多个 Dep 命中也只有一个队列节点。

RUNNING 防止默认自递归

运行中的 effect 修改自身依赖时默认不再次入队；只有显式 ALLOW_RECURSE 的调度场景允许。

07

主流程很短，正确性藏在边界里

数组会隐式读写 length，Map 的键可能同时存在 raw 与 proxy 身份， readonly 还可能包着 reactive。Vue 的工程成熟度主要体现在这些语义交叉处。

如果只实现普通对象的 get/set，一个响应式原型大约几十行就够了； 但它还不是可以支撑框架的内核。生产实现必须保证代理对象尽量遵守原生 JavaScript 的直觉，同时把每种操作映射到正确的依赖集合，并避免响应式系统自身的读写造成递归更新。

Array / #2137

数组原型方法可能意外追踪 length

push/splice 内部既读 length 又写 length。若在 effect 中执行，错误追踪会形成“自己写、自己触发”的循环，所以变更方法期间要暂停 tracking，并配合 batch 合并通知。

Collection / #3604

readonly(reactive(Map)) 仍需保持响应性

只读代理禁止写入，不代表它不应该响应底层 reactive Map 的更新。集合 handler 需要正确穿透代理层并在真实响应式来源上建立读取依赖。

Array / #11760

用户扩展 Array 的重写方法

Array 子类可以重写 find 等方法，其参数顺序与类型不再受原生签名约束。 插桩检测到方法不是 Array.prototype 上的原实现时，必须以代理 self 直接调用用户方法， 既尊重子类语义，也保留方法内部的响应式读取。

Memory / #11979

长期存活 target 的动态 key

外层 targetMap 虽是 WeakMap，但只要 target 仍存活，内部 key→Dep Map 就会一直存在。动态表格短暂追踪大量 key 时，最后一个订阅者离开就应删除对应 Dep， 否则内部 Map 只增不减。

Prototype chain

只由真正持有写入的代理触发

setter 要比较 target === toRaw(receiver)。若写入只是沿原型链落到子对象，父代理不应重复触发，否则一次赋值会造成两轮通知。

Iteration

遍历依赖不等于单键依赖

Object.keys、for...in、Map 的 keys() 与 values/entries 对结构变化的敏感度不同，因此 Vue 使用 ITERATE_KEY 与 MAP_KEY_ITERATE_KEY 分开建模。

// which leads to infinite loops in some cases (#2137)
function noTracking(
  self: unknown[],
  method: keyof Array<any>,
  args: unknown[] = [],
) {
  pauseTracking()
  startBatch()
  const res = (toRaw(self) as any)[method].apply(self, args)
  endBatch()
  resetTracking()
  return res
}

09

十条结论，重新理解 Vue 响应式

如果把实现细节暂时收起，Vue 3.5 响应式内核可以归纳为下面十个判断。 它们也是检验是否真正理解源码的最小集合。

  1. 响应式的核心产物不是代理对象，而是由真实执行路径生成的依赖图。
  2. reactive 对象由 Proxy 把语言操作翻译成 track/trigger；Ref 直接持有 Dep。两种入口都不负责最终调度。
  3. 一个 Dep 表示一个可独立观察的位置，通常是原始 target 的某个 key，也可以是 Ref.value。
  4. Link 是 Dep 与 Subscriber 之间的边，同时加入两条双向链表，以支持通知和清理两种方向。
  5. effect 每次运行都会重新确认依赖；条件分支改变后，旧分支的 Link 会被移除。
  6. TriggerOpTypes 与抽象迭代键把对象、数组、Map/Set 的结构变化显式建模。
  7. 通知只表达“可能失效”；批处理、scheduler 与版本检查共同决定消费者何时真正执行。
  8. computed 既订阅上游又向下游提供 Dep；它通过延迟求值和版本快路径阻止无效传播。
  9. watch 是建立在 ReactiveEffect 上的策略层；deep 的本质是主动遍历读取，而不是免费能力。
  10. 一张长期运行的依赖图必须可回收：WeakMap、动态 Link 清理、stop 与 effectScope 都服务于此。
Vue 响应式最值得借鉴的并不是 Proxy 技巧，而是它把“关系发现、失效传播、执行策略、生命周期” 拆成了边界清晰的四个问题，并允许每一层独立演进。

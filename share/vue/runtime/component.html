Chapter 02 · Component Model

一个组件怎样真正“活起来”

组件文件只是一份定义。真正显示到页面时，Vue 会为每个使用位置创建独立实例：它记住自己的输入、状态、子内容、渲染结果和生命周期。

卸载不是一句 scope.stop：它有明确的同步与 post 阶段

renderer.ts · unmountComponent（连续源码） 
  const unmountComponent = (
    instance: ComponentInternalInstance,
    parentSuspense: SuspenseBoundary | null,
    doRemove?: boolean,
  ) => {
    if (__DEV__ && instance.type.__hmrId) {
      unregisterHMR(instance)
    }

    const { bum, scope, job, subTree, um, m, a } = instance
    invalidateMount(m)
    invalidateMount(a)

    // beforeUnmount 在 effect 仍有效、子树仍存在时同步执行。
    if (bum) {
      invokeArrayFns(bum)
    }

    if (
      __COMPAT__ &&
      isCompatEnabled(DeprecationTypes.INSTANCE_EVENT_HOOKS, instance)
    ) {
      instance.emit('hook:beforeDestroy')
    }

    // 停止 setup/render/watch 等归属于组件 scope 的全部响应式 effect。
    scope.stop()

    // 异步 setup 尚未完成时可能没有 render job，subTree 可已是占位 VNode。
    // 此处分支仅在 job 存在时递归卸载渲染子树。
    if (job) {
      // 即使任务已经入队，DISPOSED 也让调度器跳过。
      job.flags! |= SchedulerJobFlags.DISPOSED
      unmount(subTree, instance, parentSuspense, doRemove)
    }
    // unmounted 排在逻辑卸载后的 post 阶段；若元素 leave 延迟删除，它不等待动画完成。
    if (um) {
      queuePostRenderEffect(um, parentSuspense)
    }
    if (
      __COMPAT__ &&
      isCompatEnabled(DeprecationTypes.INSTANCE_EVENT_HOOKS, instance)
    ) {
      queuePostRenderEffect(
        () => instance.emit('hook:destroyed'),
        parentSuspense,
      )
    }
    queuePostRenderEffect(() => {
      instance.isUnmounted = true
    }, parentSuspense)

进入组件内部与源码层

ComponentInternalInstance 是运行时控制块

VNode 描述“希望有一个组件”，实例记录“这个组件当前运行到哪里”。它不是用户通过 ref 看到的公共实例，而是 renderer 与各子系统共享的内部控制块。

字段组 代表字段 职责
树关系 uid、parent、root、appContext 建立父子顺序、依赖注入链和应用级配置边界
声明与结果 vnode、next、subTree、type 保存当前输入、待更新输入和 render 生成的子树
组件状态 props、attrs、slots、refs、setupState、data、ctx 支撑 setup、Options API、模板与公共代理的属性查找
更新系统 effect、update、job、render、renderCache 把响应式渲染、调度任务和缓存绑定到同一实例
生命周期 bm/m/bu/u/bum/um、scope、isMounted、isUnmounted 登记钩子、停止组件级副作用并保护失效任务
异步边界 suspense、asyncDep、asyncResolved 让 async setup 向最近 Suspense 登记依赖
Renderer、scheduler、props/slots 与生命周期处理共享同一个内部实例。 各阶段把输入、渲染结果、任务与清理状态保存在对应字段中，下一阶段据此继续执行。

创建阶段：只搭骨架，不执行 render

createComponentInstance(vnode, parent, suspense) 主要完成三件事：

  1. 从 parent 或根 VNode 继承 appContext，建立 root、provides、scope 等上下文。
  2. 规范化 propsOptions 与 emitsOptions，并创建公共代理的 ctx target。 accessCache 此时为 null，要到 setupStatefulComponent 才创建。
  3. 把 emit 绑定到实例，但暂不初始化 props、slots，也不执行 setup。

“创建”与“setup”分开非常关键。Renderer 需要先拿到一个可引用实例，Suspense、HMR、Devtools 和错误处理才能在后续用户代码执行时拥有明确归属。

完成挂载后的 对象引用与更新快照 展示实例如何继续持有 effect、job 和当前子树。

setupComponent：把 VNode 输入转换为可执行组件

有状态组件按以下顺序完成初始化：

initProps
先把 rawProps 拆成已声明 props 与 fallthrough attrs，并完成 default/Boolean 转换。
initSlots
再依据 shapeFlag 和编译器 slot flag 规范化 children，使 setup 能读取 slots。
setupStatefulComponent
创建访问缓存与公共 Proxy； 暂停追踪，设置 currentInstance 和活动 scope，再调用用户 setup。
恢复 setup 调用上下文
用户 setup 同步调用返回后， 立即恢复 tracking、currentInstance 和 scope，再分派返回值；Promise 也先退出此窗口。
handleSetupResult
函数结果成为 render；对象结果通过 proxyRefs 成为 setupState。
finishComponentSetup
若仍无 render，使用组件 render 或运行时编译 template；应用 Options API 时另开实例与暂停追踪的窗口， 并用 finally 恢复该窗口。

为什么 setup 调用前要暂停依赖追踪

setup 创建响应式对象和 computed，并不等于组件 render 读取了它们。如果 setup 自身被当前外层 effect 追踪，会把初始化读取错误归属给别的 effect。Vue 在调用用户 setup 前暂停 tracking，同时把当前实例的 effect scope 设为 active。

setup 返回 Promise 时发生什么

SSR 会等待 async setup；客户端若存在 Suspense，则把 Promise 作为 asyncDep 登记到边界，在隐藏容器中保留占位并等待 resolve。没有 Suspense 时开发环境会提示，因为组件无法同步完成首次 render。

resolve 回调先检查 instance.isUnmounted、suspense.isUnmounted， 以及 suspense.pendingId !== instance.suspenseId；任一命中就返回。 通过后才标记 asyncResolved、处理 setup 结果并建立 render effect，最后清除占位； 注册时参与 pending 计数的依赖全部完成后，边界再 resolve。

Props 与 Slots：组件更新的两类输入

PROPS / ATTRS

声明决定归属

命中 propsOptions 的 key 进入 props；其余进入 attrs。emit listener 不属于普通 attrs。更新时编译器 dynamicProps 可走快速路径，否则完整比较。

SLOTS

函数决定执行上下文

slot 是延迟执行的 render 函数。withCtx 恢复声明方的资源解析与 scopeId 上下文，并控制 block tracking；响应式依赖仍由调用插槽时的活动 effect 收集。

props 是值输入，slots 是可执行输入。shouldUpdateComponent 必须同时判断 props 变化和 slot 稳定性：稳定编译 slot 通常不要求子组件因父更新重渲染；手写或动态 slot 则需要保守更新。

default 与 Boolean：先补默认值，再做布尔转换

normalizePropsOptions 预先把需要 default 或 Boolean 转换的键放进 needCastKeys。setFullProps 先写普通 props，再逐个调用 resolvePropValue，所以默认值工厂收到的是当前正在初始化的 props 对象。

输入与声明 解析结果 决定分支
值为 undefined，声明了 default 使用默认值；显式 null 保留 先判断 hasDefault 与 value === undefined
default 为函数，type 不是 Function 且未设 skipFactory 调用工厂并按实例、prop 缓存；以后再次需要默认值时复用结果 propsDefaults[key]；执行时设置 currentInstance，支持 inject
type 为 Function，default 为函数 函数本身成为默认值 跳过工厂调用
Boolean prop 缺失，且未声明 default false isAbsent && !hasDefault
Boolean prop 的值为空串或连字符形式的同名字符串 单独声明 Boolean 或 Boolean 先于 String 时转为 true；[String, Boolean] 保留字符串 normalizePropsOptions 按类型顺序设置 shouldCastTrue

源码摘录：componentProps.ts · resolvePropValue，Vue 3.5.41 连续函数原文。 

function resolvePropValue(
  options: NormalizedProps,
  props: Data,
  key: string,
  value: unknown,
  instance: ComponentInternalInstance,
  isAbsent: boolean,
) {
  const opt = options[key]
  if (opt != null) {
    const hasDefault = hasOwn(opt, 'default')
    // 只有值为 undefined 时应用 default；显式 null 会保留。
    if (hasDefault && value === undefined) {
      const defaultValue = opt.default
      if (
        opt.type !== Function &&
        !opt.skipFactory &&
        isFunction(defaultValue)
      ) {
        const { propsDefaults } = instance
        if (key in propsDefaults) {
          value = propsDefaults[key]
        } else {
          const reset = setCurrentInstance(instance)
          value = propsDefaults[key] = defaultValue.call(
            __COMPAT__ &&
              isCompatEnabled(DeprecationTypes.PROPS_DEFAULT_THIS, instance)
              ? createPropsDefaultThis(instance, props, key)
              : null,
            props,
          )
          reset()
        }
      } else {
        value = defaultValue
      }
      // #9006：自定义元素的默认 prop 也需反射进 VueElement 内部状态，否则元素属性未传
      // 值时组件与宿主 `_props` 会不一致。
      if (instance.ce) {
        instance.ce._setProp(key, value)
      }
    }
    // Boolean 缺失且无 default → false；空串或同名 attribute → true（除非 String 优先）。
    if (opt[BooleanFlags.shouldCast]) {
      if (isAbsent && !hasDefault) {
        value = false
      } else if (
        opt[BooleanFlags.shouldCastTrue] &&
        (value === '' || value === hyphenate(key))
      ) {
        value = true
      }
    }
  }
  return value
}

componentProps.spec.ts · boolean casting 断言缺失、空串、同名字符串与其他字符串的结果； default value 断言 Function 类型保留默认函数，以及父更新后默认对象引用和工厂调用次数不变。 默认对象缓存的 watcher 用例还断言：只更新 bar 时，监听 foo 的回调次数仍为零。

slot 快路径：稳定性标记约束更新方式

编译 slots 对象的 _ 是 SlotFlags；插槽函数的 _c 是另一种标记，供 renderSlot 等调用方控制 block tracking。 STABLE 表示插槽能在执行时收集自身依赖，并不保证父 render 每次产生相同函数引用。

updateSlots 输入 映射更新 旧键清理
optimized 且编译标记为 STABLE 跳过复制 跳过
动态编译 slots，或未优化的稳定编译 slots 直接复制已标准化函数 删除新输入中已不存在的 slot
手写 slots，没有编译标记 规范化值和函数，绑定声明方渲染上下文 $stable 为真时跳过，否则删除消失的键
开发环境父模板 HMR 强制复制，并触发读取 $slots 的依赖 继续检查

源码摘录：componentSlots.ts · updateSlots，Vue 3.5.41 连续函数原文。 

export const updateSlots = (
  instance: ComponentInternalInstance,
  children: VNodeNormalizedChildren,
  optimized: boolean,
): void => {
  const { vnode, slots } = instance
  let needDeletionCheck = true
  let deletionComparisonTarget = EMPTY_OBJ
  if (vnode.shapeFlag & ShapeFlags.SLOTS_CHILDREN) {
    const type = (children as RawSlots)._
    if (type) {
      // 编译 slots 携带稳定性标志。
      if (__DEV__ && isHmrUpdating) {
        // 父模板 HMR 后内容/函数可能改变，强制复制并通知读取 `$slots` 的依赖。
        assignSlots(slots, children as Slots, optimized)
        trigger(instance, TriggerOpTypes.SET, '$slots')
      } else if (optimized && type === SlotFlags.STABLE) {
        // 稳定编译 slots 能在执行时收集自身依赖；优化更新跳过映射复制和删除检查。
        // STABLE 不保证父组件每次 render 生成的 slot 函数引用相同。
        needDeletionCheck = false
      } else {
        // 动态编译 slots 或未启用优化的稳定 slots：复制映射，函数无需再次标准化。
        assignSlots(slots, children as Slots, optimized)
      }
    } else {
      needDeletionCheck = !(children as RawSlots).$stable
      normalizeObjectSlots(children as RawSlots, slots, instance)
    }
    deletionComparisonTarget = children as RawSlots
  } else if (children) {
    // 直接值 children 作为 default slot，删除比较目标只含 default。
    normalizeVNodeSlots(instance, children)
    deletionComparisonTarget = { default: 1 }
  }

  // 动态键集合可能缩小，清除旧函数避免 `$slots.foo` 残留。
  if (needDeletionCheck) {
    for (const key in slots) {
      if (!isInternalKey(key) && deletionComparisonTarget[key] == null) {
        delete slots[key]
      }
    }
  }
}

componentSlots.spec.ts 的编译动态 slot 用例把 one 切成 two，断言旧键删除、新键写入；两个 $stable 用例断言 props 不变时的子组件渲染次数不同，props 改变时两者仍更新。 components/Suspense.spec.ts · async component should receive updated props/slots when resolved 断言异步 setup 完成后使用父级等待期间更新的输入。

props 值比较会跳过已声明事件监听器的函数变化；完整比较仍先检查原始 props 键数， 所以新增或删除监听器可能触发子组件更新。手写 slots 的 $stable 是调用方的稳定性提示， 不是编译器推导；错误地声明为真会跳过必要的更新或旧键清理。

公共实例 Proxy：为何需要访问缓存

模板 render 中的 _ctx.foo 可能来自 setupState、data、props、ctx 或 globalProperties。每次都按顺序执行 hasOwn 会让高频属性访问付出重复成本，因此 PublicInstanceProxyHandlers 使用 accessCache 记录 key 的来源。

SETUP优先读取 setupState；script setup binding 不通过 Options API this 暴露。
DATA读取 data() 返回的响应式对象。
PROPS读取声明 props；set 时拒绝写入并发出警告。
CONTEXTmethods、computed、inject 和内部 ctx 字段。
PUBLIC $xxx$el、$attrs、$slots、$emit 等公共实例映射。
GLOBALapp.config.globalProperties 作为最终扩展来源。

inject、methods、data 初始化期间暂时禁止把未命中的 key 缓存为 OTHER，避免 data() 中提前访问尚未建立的 data 字段后跳过后续查找；已找到来源的 key 仍可缓存。 data 初始化完成就恢复 OTHER 缓存，然后才创建 computed。computed 位于 ctx； 即使 key 已缓存为 OTHER，getter 仍继续检查 ctx 和 globalProperties。

Render Effect：组件模型与 Renderer 的交接点

组件准备好 render 后，控制权回到 renderer。setupRenderEffect 创建 ReactiveEffect，把 componentUpdateFn 作为 effect 主体，把 queueJob(job) 作为 scheduler。

首次执行：调用 renderComponentRoot 得到 subTree，执行 patch(null, subTree)，把 subTree.el 写回组件 vnode.el，最后把 mounted 钩子排入 post 队列。
后续执行：若 instance.next 存在，先用新 VNode 更新 props/slots；调用 render 得到 nextTree，再 patch(prevTree, nextTree)，最后更新 vnode.el 与 queued hooks。

effect 首次运行同时追踪 render 读取的响应式依赖。依赖变化时，reactivity 不直接调用 update，而是调用 scheduler 将 job 入队；这正是下一章 renderer 与调度篇的连接点。

Chapter 10 · Evolution

为什么成熟的 Runtime 还在不断修复

主流程早已稳定，但真实浏览器里仍有慢网速输入、异步结果晚到、资源重复加载和节点移动等边界。版本历史记录了 Vue 怎样把这些用户问题变成可靠规则。

跨度：2020—2026基线：v3.5.41上游 Git 证据

先看四个“页面看着简单，实现却会出错”的故事

慢网速输入

用户刚输入，文字被水合覆盖

HTML 先显示，JS 后接管。用户在间隙输入时，水合不能机械恢复服务器旧值。

异步晚到

旧页面请求覆盖新页面

用户已经切换路由，旧组件的 Promise 才完成；过期结果不能再提交。

资源副作用

修正属性导致图片重复请求

某些 src/href 写入不只是改值，还会触发网络，水合校验必须谨慎。

节点搬家

Custom Element 移动时被误卸载

浏览器移动元素会短暂触发断连再连接，不能把“搬家”当成“销毁”。

成熟框架的大量代码，不是在实现快乐路径，而是在保护现实世界中的时间差、平台差和组合边界。

读历史真正要找什么

用户做了什么
慢网速输入、切路由、移动节点，而不是先看 commit 改了哪行。
哪个假设失效
例如“水合前用户不会操作”“Promise 完成时组件仍存在”。
新规则保护什么
既修当前故障，也要保证普通挂载、后续更新与错误恢复不退化。
测试怎样锁住场景
最小复现成为长期行为契约，防止未来重构重新引入问题。
进入版本时间线、提交与源码层

怎样读演进，而不把源码读成更新日志

把变更分成四层，会比按日期逐 commit 浏览更有效：

CAPABILITY

新增能力

Custom Element、Suspense 协议、懒水合、deferred Teleport。问：旧抽象缺了哪个接入点？

PERFORMANCE

数据结构优化

block tree、patch flags、scheduler bit flags。问：基线正确路径是什么，优化如何安全回退？

CORRECTNESS

边界修复

过期异步结果、水合用户输入、命名空间、事件时序。问：哪个不变量被现实场景打破？

ERGONOMICS

开发者接口

useId、useTemplateRef、defineCustomElement 配置。问：Runtime 增加了哪些可追踪状态？

组件实例、VNode/Block、平台无关 Renderer、Scheduler、Teleport/Suspense/KeepAlive 和 runtime-dom 分层成为 Vue 3 的基础。核心判断从“运行时猜变化”转向“编译器标记 + 运行时回退”。

编译与运行时协同成熟

围绕性能、SSR 和 Web Components 的能力继续扩展。defineCustomElement（8610e1c9e）把组件实例生命周期映射到浏览器 Custom Element 协议。

2023-05-11 · v3.3.0 · 483a4e7e3

异步边界组合能力增强

Suspense 的 suspensible 支持（cb37d0b9f）让嵌套异步边界能选择是否把依赖交给祖先，体现“边界隔离还是向上聚合”的显式协议。

2023-12-29 · v3.4.0 · d702b6648

性能与内部状态继续收敛

Runtime 优化更强调紧凑状态和稳定快路径。随后 scheduler 的布尔字段逐步改为 bit flags（55660b0cf / db4040d13），减少 job 对象字段与重复状态组合。

2024-09-03 · v3.5.0 · 6402b9840

SSR 与应用级能力明显扩张

useTemplateRef、useId、deferred Teleport 与 lazy hydration 进入 Runtime。共同主题是：为 SSR 稳定身份、启动时机和跨容器提交提供一等协议。

2026-08-05 · v3.5.41 · d2c458be2

成熟期的边界修复

主结构稳定后，提交更集中于浏览器差异、组合场景、类型与回归测试。代码中的许多小分支，往往对应真实用户输入、资源加载或命名空间问题。

什么一直没变：设计的承重墙

承重墙 长期价值 新特性如何接入
RendererOptions 宿主抽象 renderer、组件与 Diff 通过宿主接口提交；包内 DOM hydration 是例外 新 namespace、静态内容与 scope id 通过宿主接口扩展
VNode 作为共享 IR 组件、编译器、renderer 和内置组件交换同一计划 新增 flag、hydrate strategy、transition/dirs 等字段或协议
组件 render effect 状态边界与提交边界统一 新的 ref、id、async setup 仍围绕实例生命周期建立
统一 patch/move/unmount 所有 VNode 类型遵守相同 container/anchor 语义 Teleport/Suspense/KeepAlive 通过 internals 接入而非另起炉灶
调度三阶段 父子顺序、批处理与 DOM 后副作用可预测 新的 watcher/lifecycle 只需选择 pre/main/post 时机

好架构并不意味着文件不增长，而是新需求可以表达成原有不变量上的局部扩展。Vue Runtime 的历史大体如此：container/anchor、VNode identity、job ordering 这些词反复出现，因为它们是不同能力的共同坐标。

四条能力演进线

从“可封装组件”到“可嵌入任意页面”

Custom Element 不只是换一个 mount 容器。VueElement 必须桥接 property/attribute、DOM event、Shadow DOM、样式、slot 和连接生命周期。后续“可配置 app”等扩展，说明应用上下文也需要开放但受控的注入点。

设计模式：外部协议由适配层承接，内部仍复用 createApp、组件实例与 renderer。

从“尽快水合”到“按业务时机水合”

早期目标是正确认领 SSR DOM；3.5 的 lazy hydration 把“何时创建交互能力”变成策略接口。hydrateOnIdle/Visible/MediaQuery/Interaction 是标准策略，自定义策略可接业务调度。

设计模式：把触发时机外置，但保留 cleanup、过期检查与 hydrate 实体流程。

从一个 pending branch 到可组合边界

Suspense 要与 Transition、KeepAlive、嵌套 Suspense 和 SSR 共存。suspensible 等选项本质是在决定依赖计数和 effects 应由哪个边界拥有。

设计模式：用 pendingId/dep count 建立事务身份，让晚到的异步结果可以被安全忽略。

从多个布尔字段到位标志

PRE、QUEUED、ALLOW_RECURSE、DISPOSED 等状态组合频繁出现在热路径。bit flags 使判断和存储更紧凑，但外部语义仍是父先子后、去重、可递归控制与错误后恢复。

设计模式：优化表示层，不改变排序与清理不变量；每个 return/throw 路径都必须正确清 flag。

问题驱动的修复：小分支背后的大场景

主题 真实场景 被破坏的不变量 修复时必须同时验证

VNode children 被覆盖
#15194 · 684a8defd 		render 函数同时传入 innerHTML/textContent 与 children，浏览器 property 会静默丢弃 children 同一个元素的内容必须只有一个权威来源 文本、数组、空 children、组件 slot 与 SSR 输出
异步/卸载竞态 loader、Suspense 或懒水合完成前节点被替换 过期结果不得提交到新树 实例 isUnmounted、pendingId、清理函数、DOM 范围

阅读 issue 修复时，应把测试当作修复契约：最小复现描述“以前哪里错”，相邻断言描述“修复不能破坏什么”。只读变更的 if 分支，很容易错过维护者真正保护的边界。

  // 与 children 并用，但手写 render 没有编译检查，所以在 VNode 创建时补充警告。
  if (__DEV__ && props && vnode.shapeFlag & ShapeFlags.ELEMENT) {
    const overwritingProp =
      props.innerHTML != null
        ? 'innerHTML'
        : props.textContent != null
          ? 'textContent'
          : null
    if (overwritingProp && hasContentChildren(vnode.children)) {
      warn(
        `The \`${overwritingProp}\` prop on <${vnode.type as string}> will ` +
          `override its children. Remove either the \`${overwritingProp}\` ` +
          `prop or the children.`,
      )
    }
  }
  // 元素的 innerHTML/textContent 与有内容的 children 并用时给出开发警告。
  describe('children overridden by innerHTML / textContent', () => {
    // innerHTML 会覆盖文本 children，因此开发模式给出警告。

      expect(

      ).toHaveBeenWarned()
    })

    // innerHTML 与非空 children 数组并用时也会警告。
    test('warn on array children', () => {
      createVNode('div', { innerHTML: '<span/>' }, [createVNode('span')])
      expect(
        `The \`innerHTML\` prop on <div> will override its children`,
      ).toHaveBeenWarned()
    })

    // textContent 与文本 children 并用时给出警告。
    test('warn on textContent', () => {
      createVNode('div', { textContent: 'text' }, 'hello')
      expect(
        `The \`textContent\` prop on <div> will override its children`,
      ).toHaveBeenWarned()
    })

    // innerHTML/textContent 为 null 或 undefined 时不警告。
    test('no warning when the prop is nullish', () => {

    // 没有 children、空字符串或空数组都不构成内容冲突。

      expect(`will override its children`).not.toHaveBeenWarned()

从历史中抽出的六种演进模式

先建立完整正确路径
普通 patch 是基线；block、patchFlag 缩小比较范围，显式 BAIL 等条件退回通用比较。 LIS 在节点匹配后减少移动，不参与 BAIL 判定。
用身份令牌解决异步过期
pendingId、job flags、VNode key 都在回答“这个结果还属于当前状态吗”。
把外部差异留在边界层
DOM property 例外、namespace、Custom Element 生命周期集中在 runtime-dom。
副作用推迟到状态稳定
mounted、字符串/Ref 对象的非空赋值、Suspense effects、deferred Teleport 都使用调度阶段而非随意 Promise。
组合能力共享少量原语
patch、move、unmount、container、anchor 比为每种组合写专用路径更可维护。
回归测试与修复同生
issue 场景进入 spec 后，历史原因才不会在后续重构中消失。

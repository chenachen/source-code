Chapter 06 · Hydration

页面已经显示了，Vue 怎样把交互接上去

SSR 页面常常在 JavaScript 下载完成前就已经可见。水合不是重新创建页面，而是让客户端组件认领这些现有 HTML，补上状态、事件和后续更新能力。

如果服务器和客户端算出的页面不一样

比如服务器显示“早上好”，客户端按本地时间算出“晚上好”。Vue 会报告失配：文字不同可以直接修正；标签结构不同则不能安全认领，需要局部删除并由客户端重新创建。

差异 处理 例子
文本 / children 不同 保留父节点，修正文案并增删缺失或多余的子节点 本地时间、条件分支数量
class / style / 已知 attribute 不同 失配检查负责诊断，不因检查本身自动校正；应修复服务端与客户端输入 主题 class、静态 title、内联样式
身份不同 放弃错误节点，局部重建 服务器是 div，客户端是 button
水合完成的标准：不是“HTML 看起来没变”，而是组件实例、VNode、事件和现有 DOM 已建立与普通首次挂载相同的运行关系。
进入水合游标、失配恢复与源码层

先分清 mount、patch 与 hydrate

入口 已有输入 核心问题 结果
mount VNode，没有宿主节点 该创建哪些节点、按什么次序插入？ 创建完整 DOM，并写回 vnode.el
patch 旧 VNode、新 VNode、已有 DOM 两次声明之间有什么差异？ 最少修改已有 DOM
hydrate 新 VNode、服务端 DOM，没有旧 VNode DOM 是否可被当前 VNode 认领？ 复用 DOM，建立运行时关联

水合没有一棵可供比较的旧 VNode 树，因此它不能执行普通 Diff。它沿 DOM 的 nextSibling 向前扫描，同时递归消费 VNode；函数返回值通常是“当前 VNode 消费完后，下一个尚未认领的 DOM 节点”。这条游标协议是理解 Fragment、Teleport 和组件水合的钥匙。

入口与游标：hydrate 如何走完整棵树

检查容器
容器为空说明没有可复用的 SSR 输出，开发模式报警后退回普通 patch。
从 firstChild 开始
hydrateNode(container.firstChild, vnode) 让根 VNode 认领第一个 DOM 节点。
按 VNode 类型分派
Text、Comment、Static、Fragment、Element、Component、Teleport、Suspense 各有自己的消费规则。
子树各自推进游标
Element children、Fragment 等分支会接住 hydrateNode 返回的下一个兄弟并处理各自范围内的多余节点；根入口本身不做通用尾节点扫描。
提交水合副作用
执行 post-flush 生命周期与 ref，容器记录 _vnode，以后进入普通更新流程。 
// 不是源码逐字复制，而是水合游标的概念骨架
function hydrateNode(node, vnode): Node | null {
  vnode.el = node
  switch (vnode.type) {
    case Text: return hydrateText(node, vnode)
    case Fragment: return hydrateFragment(node, vnode)
    default:
      if (isElement(vnode)) return hydrateElement(node, vnode)
      if (isComponent(vnode)) return hydrateComponent(node, vnode)
  }
  return nextSibling(node)
}

返回下一个节点而不是返回当前节点，使父层无需知道子树包含多少真实 DOM。组件可能渲染一个元素，也可能是 Fragment；Suspense 可能当前展示 fallback；调用方只需接住统一游标。

根入口的边界：hydrate() 调用 hydrateNode(container.firstChild, vnode) 后没有接住返回值，因此不能据此推出“根 VNode 后的额外 sibling 会被统一删除”。 多余节点清理是 hydrateElement、Fragment 等具体范围的职责；根容器额外兄弟是另一条边界，不能套用 element children 的保证。

节点类型矩阵：每一种 VNode 如何被认领

VNode 匹配依据 水合动作 常见失配
Text DOM nodeType === TEXT 写回 el；文本不同则修正 node.data 空 Text 通常没有 SSR 节点，客户端补建；空条件分支是 Comment
Comment COMMENT，且不是 Fragment 起点 直接认领 SSR 控制标记被误当普通注释
Static 由静态节点数量决定范围 在缺少客户端静态字符串时，从 DOM 回收内容 静态范围被外部脚本改写
Fragment <!--[--> 到 <!--]--> 逐个水合 children，并维护结束 anchor 锚点丢失、children 数量不同
Element DOM nodeType 与 tagName 推导 namespace 上下文，补事件/动态属性；递归水合 children tag、文本、class/style/attr 不同
Component 由其 subTree 决定节点范围 创建实例、运行 setup/render、用 DOM 水合 subTree 服务端与客户端分支不同
Teleport 主树锚点 + target 内标记 分别恢复逻辑位置与真实目标位置 目标不存在、多个 Teleport 顺序不一致
Suspense 当前已解析分支的 DOM 以 pendingBranch = ssContent 水合；依赖清零后转为 activeBranch 客户端依赖状态与服务端不同

Suspense 的服务器渲染器输出默认内容分支并等待其中异步组件，失败交给错误处理， 不按 timeout 自动输出 fallback。客户端水合时先创建 isHydrating 边界， 将 ssContent 记为 pendingBranch 并认领已显示的 SSR DOM；此时 activeBranch 仍为空。 依赖清零后 resolve 跳过普通卸载和移动，只把该分支记为 activeBranch、清空 pendingBranch， 再释放已缓冲的提交后副作用。

元素与组件：水合不是“什么都不做”

元素水合要补齐客户端行为

SSR HTML 能表达标签和属性，却不能携带 JavaScript 事件监听器。元素水合会根据 patchFlag、事件 key、指令与 vnode hook 决定需要执行哪些 hostPatchProp。静态属性通常不必重设；事件、需要属性语义的值以及可能发生失配检查的字段必须处理。

  • children 是文本：比较 textContent，失配时以客户端值修正。
  • children 是数组：从 firstChild 开始逐个水合；DOM 少了就 mount 缺失子树，多了则移除剩余节点。
  • 指令与 vnode hooks：beforeMount 在认领阶段执行，mounted 排入 post-render 队列。
  • ref：非空字符串 ref 和 Ref 对象赋值排入 post-render； 函数 ref 在当前节点水合后同步调用，此时其他兄弟或异步子树可能仍未完成。

组件水合仍会创建完整实例

组件不是从 SSR 中“反序列化”出来的。客户端依然创建实例、解析 props/slots、执行 setup()、调用 render 得到 subTree；区别只是第一次组件 effect 调用 hydrateNode，而非 patch(null, subTree)。完成后组件拥有与 CSR 相同的更新能力。

因为 setup 会重新执行，SSR 代码必须满足同构约束：不要在 render 中依赖随机数、当前时间或只在客户端存在的环境状态；需要时把服务端结果序列化成稳定输入。

失配恢复：警告只是表象，关键是重新获得可信 DOM

失配可分为“内容仍可复用”和“节点身份不可复用”两类，恢复策略并不相同：

RECONCILABLE CONTENT

文本与 children：保留父节点并修正

文本不同时写入客户端文本；children 少了就 mount，children 多了就移除。父元素身份仍可复用。

CHECK-ONLY PROPS

class / style / 已知 attribute：报告来源问题

propHasMismatch 比较 class、style 以及已知 HTML/SVG 属性的归一化结果并发出警告， 但检查本身不校正 DOM；此处不会逐一诊断 aria-*、data-* 等任意属性。只有事件、动态 prop、表单值等原本就必须水合的字段，才会因各自规则另走 patchProp。

STRUCTURAL MISMATCH

移除节点，客户端重挂载

tag、节点类型、Fragment 边界等不一致。Vue先确定旧 DOM 范围和下一游标，再以普通 patch 创建正确子树。 

// 结构失配的概念流程
next = locateNextAfterMismatchedRange(node)
removeMismatchedDom(node)
patch(null, vnode, container, next)
return next

这里最容易出 bug 的是 next 必须在删除前确定，且 Fragment/组件可能占据多个 DOM 节点。若只删除起点或计算错 anchor，后续兄弟会被重复认领或插错位置。

跨函数机制选段 · 解释性改写 · 非连续源码 
// 下面拼接 hydrateElement、propHasMismatch、handleMismatch 的机制，
// 不是 hydration.ts 中可复制的连续源码。三类失配不是同一种恢复。
if (textContent !== clientText) {
  el.textContent = vnode.children // 文本会校正
}

if (propHasMismatch(el, key, props[key], vnode, parentComponent)) {
  logMismatchError() // class/style/attribute 检查本身只诊断
}

// handleMismatch：节点身份不可信，先保存游标，再重挂载
const next = nextSibling(node)
remove(node)
patch(null, vnode, container, next, ...)

propHasMismatch 的警告原文明确说明这是 check-only；handleMismatch 则先算 next，再删除错误范围并以该游标作 anchor。Fragment 会先定位结束锚点，避免只删起始注释。

本地：hydrateElement / handleMismatch v3.5.41：文本、children 与 props v3.5.41：handleMismatch v3.5.41：propHasMismatch

data-allow-mismatch：声明“差异是设计的一部分”

某些页面故意让服务端与客户端不同，例如用户时区格式、本地化相对时间、浏览器扩展注入 class。Vue 允许在元素上按类型抑制 mismatch：text、children、class、style、attribute。允许失配会抑制读取该声明的 检查路径中的警告，不会跳过认领流程；元素文本仍会改成客户端值，多余 children 仍会被清理。

元素文本内容和 children 结构差异从本元素向上查找最近一处 data-allow-mismatch，不合并多个祖先的配置。例如外层允许 children、内层只允许 class，内层文本差异不会继承外层的允许规则。 class、style 和 attribute 只读本元素上的声明。独立 Text VNode 的检查则直接警告： h('div', 'bar') 的元素文本路径会读取 text 声明， h('div', null, [createTextVNode('bar')]) 的独立 Text 路径不会读取它。

调试失配时先找第一个警告，而不是最后一个。父层结构错位会让游标偏移，随后产生一串看似无关的子节点警告。

真实场景：为什么水合修复常常很细

场景 错误做法 正确边界 用户可见后果
用户在水合前输入表单 无条件用 VNode value 覆盖 DOM 区分 SSR 初值与浏览器中已变化的实时值，避免丢失交互 慢网速下刚输入的内容突然消失
资源元素属性 为校验而重复设置 src/href 对可能触发网络请求的属性谨慎比对与提交 图片、脚本或 iframe 重复请求
SVG/MathML 只按 HTML tagName 判断 tagName 负责当前 Element 的匹配；namespace 继续约束属性与 children 的宿主语义 节点被错误替换，属性语义失真
自定义元素 假设属性与 property 完全等价 延续 runtime-dom 的 prop/attr 决策，并尊重升级时机 setter 未执行或值被字符串化

这些修复通常不是“加一个 if”这么简单。水合处在 HTML 解析器、浏览器实时状态、Vue VNode 和应用副作用的交界处；修复必须同时保证首次认领正确、后续 patch 正确，以及不会引入重复网络或交互丢失。

懒水合：推迟的是组件认领，不是服务端可见内容

Vue 3.5 的异步组件可配置 hydration strategy。HTML 仍由服务端输出，页面也能展示。客户端会先创建异步 wrapper；若组件尚未解析，还会先执行 loader。loader resolve 后才注册 hydration strategy，条件触发时再认领内部组件的 SSR DOM。它推迟的是内部组件水合，不是 wrapper 创建，也不是异步模块下载。

策略 触发条件 适合 风险
hydrateOnIdle requestIdleCallback / timeout 首屏以下的非关键组件 设备长期繁忙时交互能力延后
hydrateOnVisible IntersectionObserver 滚动进入视口的卡片、图表 需合理 rootMargin，避免看见后才卡顿
hydrateOnMediaQuery matchMedia 命中 仅特定布局需要的交互 媒体条件变化时要正确清理监听
hydrateOnInteraction click、focus 等事件 低频但必须“点即响应”的控件 触发事件需在水合后重放，不能被吞掉
自定义策略 用户定义调度器 业务优先级、实验性加载策略 创建监听器、observer 或定时任务时返回清理函数；Vue 在 beforeUnmount 调用它
01AsyncComponentWrapper 已创建组件实例和外层 render effect 已存在，SSR DOM 仍未由内部组件认领。__asyncHydrate(el, instance, hydrate)
02resolvedComp ? 直接继续 : load()未解析时先启动 loader；resolve 后还要检查 instance 未卸载。load().then(...doHydrate)
03注册 hydration strategy策略拿到 performHydrate 和 DOM 范围遍历器；teardown 挂到 beforeUnmount。idle / visible / media / interaction
04条件触发 → performHydrate仍连在 DOM、且等待期间没有被父更新接管，才执行 hydrate。hydrate()
父树先更新beforeUpdate 把 patched 置 true；后续策略触发只警告并跳过过期水合，客户端 patch 已接管。
loader 期间卸载instance.isUnmounted 阻止策略注册；若策略已经注册，beforeUnmount 执行 teardown。
节点已断开起点原本连接但触发时不再 isConnected，或已无 parentNode，直接退出。
正常触发认领服务端节点；interaction 策略还会重放最初事件，避免用户第一次点击被吞掉。
关键竞态：等待水合期间父组件可能更新 props、移动节点或直接卸载。实现必须以“触发时的最新 vnode 与真实 DOM”继续，而不能闭包捕获旧输入。
连续源码：loader → strategy → trigger，以及 patched/unmounted/disconnected 旁路 
    __asyncHydrate(el, instance, hydrate) {
      // 延迟水合等待期间组件可能已被父级 patch 或节点已被移除。两种情况下都不能再
      // 用旧 SSR DOM 执行 hydrate，否则会覆盖新状态或操作脱离文档的节点。
      const wasConnected = el.isConnected
      let patched = false
      ;(instance.bu || (instance.bu = [])).push(() => (patched = true))
      const performHydrate = () => {
        // 组件已在延迟期间更新，说明客户端渲染已接管，跳过过期水合。
        if (patched) {
          if (__DEV__) {
            warn(
              `Skipping lazy hydration for component '${getComponentName(resolvedComp!) || resolvedComp!.__file}': ` +
                `it was updated before lazy hydration performed.`,
            )
          }
          return
        }
        if (!el.parentNode || (wasConnected && !el.isConnected)) return
        hydrate()
      }
      const doHydrate = hydrateStrategy
        ? () => {
            // 策略返回的 teardown（如事件监听器/IntersectionObserver）挂到
            // beforeUnmount，组件未等到激活便卸载时也能释放外部资源。
            const teardown = hydrateStrategy(performHydrate, cb =>
              forEachElement(el, cb),
            )
            if (teardown) {
              ;(instance.bum || (instance.bum = [])).push(teardown)
            }
          }
        : performHydrate
      if (resolvedComp) {
        doHydrate()
      } else {
        load().then(() => !instance.isUnmounted && doHydrate())
      }

function mountWithHydration(html: string, render: () => any) {
  const container = document.createElement('div')
  container.innerHTML = html
  const app = createSSRApp({
    render,
  })
  return {
    vnode: app.mount(container).$.subTree as VNode<Node, Element> & {
      el: Element
    },
    container,
  }
}

Given：jsdom 容器先写入服务端 HTML <div>foo</div>；客户端 render 返回文本为 bar 的同类型 div。

When：createSSRApp().mount(container) 进入 hydrate；测试没有调用普通 render 来覆盖容器。

Then：测试直接断言容器 HTML 变成 <div>bar</div>，并且开发态记录一次文本内容失配警告； 它没有保存旧 div 引用，因此不直接断言节点身份。

Mechanism：源码显示元素类型可认领，所以走 hydrateElement 的 TEXT_CHILDREN 分支，直接改已认领 div 的 textContent，不走结构失配的删除重挂；“节点被保留”是源码结论， 不是该测试单独证明的身份断言。

Source：hydration.ts → hydrateNode → hydrateElement；测试前置通过 beforeEach 清空 body，Vitest/jsdom 在用例后回收局部容器。

下段是 packages/runtime-core/src/hydration.ts 连续原文。 对本例真正有决定力的是：比较规范化文本、按配置决定是否警告，最后无条件把 el.textContent 写成客户端值。注意 data-allow-mismatch="text" 只压掉警告，仍会修正文本。 

      } else if (shapeFlag & ShapeFlags.TEXT_CHILDREN) {
        // #11873：HTML 解析器会吞掉 `<pre>`/`<textarea>` 源码开头第一个换行。比较时
        // 从客户端期望值移除该换行，避免把浏览器规范行为误报成水合不匹配。
        let clientText = vnode.children as string
        if (
          clientText[0] === '\n' &&
          (el.tagName === 'PRE' || el.tagName === 'TEXTAREA')
        ) {
          clientText = clientText.slice(1)
        }
        const { textContent } = el
        if (
          textContent !== clientText &&
          // DOM 解析会把 CRLF/CR 统一为 LF，比较时接受这种等价规范化。
          textContent !== clientText.replace(/\r\n|\r/g, '\n')
        ) {
          if (!isMismatchAllowed(el, MismatchTypes.TEXT)) {
            ;(__DEV__ || __FEATURE_PROD_HYDRATION_MISMATCH_DETAILS__) &&
              warn(
                `Hydration text content mismatch on`,
                el,
                `\n  - rendered on server: ${textContent}` +
                  `\n  - expected on client: ${clientText}`,
              )
            logMismatchError()
          }
          el.textContent = vnode.children as string
        }
      }

3. 同一用例的完整执行流程

SAME CASE · <div>foo</div> → <div>bar</div>
准备container.innerHTML 写入 SSR 节点 foo
→
认领hydrateNode 发现 DOM/VNode 都是 div
→
比较hydrateElement：foo !== bar
→
恢复warn + el.textContent = 'bar'
→
断言DOM 为 bar；失配警告存在
  1. 准备阶段：helper 先创建真实 DOM；这就是 hydrate 与 mount 的关键输入差异。
  2. 认领阶段：标签相同，VNode 的 el 指向原 div；不会新建 div。
  3. 比较阶段：浏览器会规范化换行，所以源码先接受 CRLF/CR 与 LF 的等价形式。
  4. 恢复阶段：未允许该失配时警告；不论警告是否被允许，文本都以客户端 VNode 为准。
  5. 提交阶段：mount 返回后容器已是可信客户端结构，之后进入普通组件更新链。
异常、失配与清理边界：若标签类型不同，handleMismatch 会删除错误宿主范围并调用普通 patch 重挂；若服务端 children 过多，游标循环 remove(cur)；若懒水合组件在触发前卸载，策略注册的 observer/事件清理函数 必须先撤销。三条路径不能和本例的“保留父元素、只改文本”混为一谈。

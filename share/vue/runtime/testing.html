页面看起来一样，为什么还可能是错的

Runtime 测试不只比较最终 HTML。它还要验证节点复用、组件状态归属、回调顺序，以及具体异常路径的清理与后续恢复。

结果、身份、顺序、恢复runtime-test + jsdomVitest

两个页面截图相同，内部可能完全不同

身份复用

复用原输入框可保持节点身份与当前 value。焦点、选区是否保留还取决于宿主移动操作；本版 DOM 使用 insertBefore，移动焦点节点可能失焦。

节点重建

删除旧输入框，再创建外观相同的新节点，节点身份已经变化；未同步到应用状态的输入内容可能丢失。

因此 Runtime 至少要测试四类结果：

画页面结果文字、属性和 children 是否正确。result
人节点身份应该复用的 DOM 和组件实例是否还是同一个对象。identity
序执行顺序父子更新、生命周期和 watcher 是否按承诺运行。order
还有第四类：失败后恢复

对 render、事件或调度任务的错误，分别检查上下文恢复、队列标志清理与下一次更新。 主 job 的 finally 会清理 QUEUED；裸 post 回调继续外抛时可能中断后续状态清理，不能把主队列用例推广到所有异常。

测试用例就是一句完整的产品规则

给定：一组 keyed 输入框；当：列表顺序变化；那么：同 key、同 type 的输入框仍复用原节点，当前 value 保留。焦点与选区是独立的浏览器行为，不能由节点身份断言推出。

这比“Diff 应该工作”更有价值。它说明用户场景、动作和必须保持的节点身份。交互状态应另用浏览器断言核对。
进入测试分层、命令与调试层

源码展示实现路径，测试锁住不能退化的外部行为

一段生产代码可能同时保护六个场景，函数名看不出优先级。测试会把输入、动作、输出和回归背景拆开：这正是阅读那些“看起来多余”的 condition、flag 清理和 anchor 修正的证据。

RESULT

结果正确

文本、属性、children 与组件输出符合预期，是最表层契约。

IDENTITY

身份正确

同 key DOM/组件是否复用，ref 与实例状态是否保持，错误节点是否被销毁。

ORDER

时序正确

父子更新、watch flush、生命周期、Transition 和 Suspense effects 的先后。

RECOVERY

失败后可恢复

render/handler/async setup 抛错后，flags、currentInstance、队列和 DOM 仍处于可信状态。

测试分层：先选最小的可观察平台

层 典型位置 观察对象 适合验证
纯函数/协议 runtime-core 单文件 spec 返回值、flags、调用数组 normalize、props、slots、scheduler 排序
runtime-test renderer packages/runtime-test 内存节点树与操作记录 Renderer、Diff、组件、Teleport、Suspense、KeepAlive
jsdom DOM runtime-dom tests 真实 DOM API 的模拟 attribute/property、事件、指令、Transition、hydration
SSR + hydration server-renderer / hydration specs HTML 字符串 + 客户端 DOM 标记协议、mismatch、懒水合与同构状态
类型测试 dts-test / typeTest 编译成功与预期错误 公共泛型、props/emit/CE 类型推断

测 Diff 时优先 runtime-test，因为可以判断节点对象身份和操作序列，避免 jsdom 的字符串结果掩盖“DOM 被删掉又重建”。只有要验证浏览器 property、事件或 namespace 时，才进入 runtime-dom。

runtime-test：把宿主平台变成可观察内存树

runtime-test 实现 core 所需的内存宿主 RendererOptions，节点是 JavaScript 对象：Element 保存 tag、props 与 children，Text 保存 text，insert/remove 修改数组关系。这样 core 算法可在 Node 环境中测试，并观察提交操作；焦点、真实事件冒泡和浏览器样式行为由 DOM 或 E2E 测试验证。 

// 概念化的测试宿主节点
interface TestElement {
  type: 'element'
  tag: string
  props: Record<string, unknown>
  children: TestNode[]
  parentNode: TestElement | null
}

// 同一个 key 是否复用，直接比较对象身份
const before = root.children[0]
render(nextVNode, root)
expect(root.children[1]).toBe(before)

它比 snapshot 更有价值的地方

  • 可断言 身份：toBe 判断复用，而非只比较相同字符串。
  • 内置操作记录：render 前调用 resetOps()， 之后用 dumpOps() 取得并清空记录。已挂载节点移动记为 INSERT，内部脱离旧父级不另记 REMOVE；结合旧节点身份区分挂载与移动。
  • 可构造 非 DOM 平台：证明 core 不意外依赖 window/document。
  • 结果格式简洁：序列化树用于快速理解最终结构，失败 diff 更聚焦。

一个高价值测试的解剖方式

Given：建立最小旧状态
首次 render、保存节点/实例引用、准备 spy 或 deferred Promise。
When：只做一个关键变化
替换 children 顺序、修改 reactive value、resolve Promise、触发事件。
Flush：推进正确时钟
同步 renderer 无需等待；组件 job 用 nextTick；Transition 用 fake timers/nextFrame；async setup 要 await。
Then：分层断言
先最终结构，再节点身份，再 hooks/操作顺序，最后确认没有额外副作用。
Regression：写清旧故障
issue 编号旁应说明用户场景和错误表现，让未来维护者知道哪些简化不可做。

代码性质：下面是教学伪用例，只演示 Given / When / Then 的断言层次；list、root 与 imports 被刻意省略，因此不是仓库测试原文，也不能直接运行。完整仓库测试及 imports 请先看端到端主章的真实测试。 

it('移动 keyed 节点时复用已有宿主节点，而不是重建', async () => {
  // Given：保存 A/B 的真实节点身份
  render(list(['a', 'b']), root)
  const a = root.children[0]

  // When：只调整顺序
  render(list(['b', 'a']), root)

  // Then：结构正确，A 的对象身份仍相同
  expect(serializeInner(root)).toBe('<li>b</li><li>a</li>')
  expect(root.children[1]).toBe(a)
})

完整仓库用例：把 key=1 从最前面移到 key=3 后面

现在不再靠上面的教学骨架。下面直接使用 Vue 3.5.41 rendererChildren.spec.ts 的真实上下文和完整测试体，跟踪 [1, 2, 3, 4] → [2, 3, 1, 4]。这个测试证明最终顺序与节点数； “宿主节点复用而不是重建”则必须结合紧随其后的 renderer 源码判断，不能把测试没写的 身份断言说成它已经证明。

1. imports、helper、共享准备与完整测试体

性质：仓库真实测试，四段都能在同一文件中直接连续定位。 test / describe / beforeEach / expect 来自 Vitest globals。 

import {
  type TestElement,
  TestNodeTypes,
  h,
  nodeOps,
  render,
  serialize,
  serializeInner,
} from '@vue/runtime-test'
/** 把测试数据转成 span VNode；非字符串值同时作为 key，以驱动 keyed diff。 */
function toSpan(content: any) {
  if (typeof content === 'string') {
    return h('span', content.toString())
  } else {
    return h('span', { key: content }, content.toString())
  }
}

/** 将测试渲染器容器的子树序列化为便于断言的字符串。 */
const inner = (c: TestElement) => serializeInner(c)
// renderer 的 keyed children diff、移动与复用。
describe('renderer: keyed children', () => {
  let root: TestElement
  let elm: TestElement
  /** 把数字列表转为同 key 的 span 并渲染到本例 root，返回 div 宿主方便检查 children。 */
  const renderChildren = (arr: number[]) => {
    render(h('div', arr.map(toSpan)), root)
    return root.children[0] as TestElement
  }

  beforeEach(() => {
    root = nodeOps.createElement('div')
    render(h('div', { id: 1 }, 'hello'), root)
  })
  test('moving single child forward', () => {
    elm = renderChildren([1, 2, 3, 4])
    expect(elm.children.length).toBe(4)

    elm = renderChildren([2, 3, 1, 4])
    expect(elm.children.length).toBe(4)
    expect((elm.children as TestElement[]).map(inner)).toEqual([
      '2',
      '3',
      '1',
      '4',
    ])
  })

Given：beforeEach 创建全新的 runtime-test 宿主根；首次 render 生成 key 为 1、2、3、4 的四个 span。

When：第二次 render 只把顺序改为 2、3、1、4；同步测试宿主不需要 nextTick。

Then：children 仍为 4 个，序列化顺序精确等于 2、3、1、4。

Mechanism：尾部 key=4 先同步，中段建立 key map；旧 key=1 将最大新下标设为 2，随后 key=2 映到 0，检测出逆序并计算 LIS，最终只移动不在 LIS 中的 key=1。

Source：runtime-core/src/renderer.ts → patchKeyedChildren。每个用例得到独立 root；需要显式验证卸载时，同文件的 remove all children from parent 会把 children 清到 0。

2. 中段映射、patch、LIS 与 move 的完整实现

下段是 patchKeyedChildren 内部一段连续原文。它完整覆盖本例进入未知中段后 如何匹配、何时卸载、怎样发现乱序、何时创建新节点，以及最终怎样只移动必要节点。 

      // 5.1 为新中段建立 key → 新下标映射，旧 keyed 节点可 O(1) 找到去向。
      const keyToNewIndexMap: Map<PropertyKey, number> = new Map()
      for (i = s2; i <= e2; i++) {
        const nextChild = (c2[i] = optimized
          ? cloneIfMounted(c2[i] as VNode)
          : normalizeVNode(c2[i]))
        if (nextChild.key != null) {
          if (__DEV__ && keyToNewIndexMap.has(nextChild.key)) {
            warn(
              `Duplicate keys found during update:`,
              JSON.stringify(nextChild.key),
              `Make sure keys are unique.`,
            )
          }
          keyToNewIndexMap.set(nextChild.key, i)
        }
      }

      // 5.2 遍历旧中段：找到新位置便 patch；找不到说明已删除，立即卸载。
      let j
      let patched = 0
      const toBePatched = e2 - s2 + 1
      let moved = false
      // 新下标不再单调递增即说明至少一个复用节点需要移动。
      let maxNewIndexSoFar = 0
      // `newIndexToOldIndexMap` 按新中段位置保存旧下标 + 1。0 专门表示新节点没有旧节点，
      // 同一数组随后也作为最长递增子序列输入，找出无需移动的最大稳定集合。
      const newIndexToOldIndexMap = new Array(toBePatched)
      for (i = 0; i < toBePatched; i++) newIndexToOldIndexMap[i] = 0

      for (i = s1; i <= e1; i++) {
        const prevChild = c1[i]
        if (patched >= toBePatched) {
          // 所有新节点都已匹配，剩余旧节点只能是删除项。
          unmount(prevChild, parentComponent, parentSuspense, true)
          continue
        }
        let newIndex
        if (prevChild.key != null) {
          newIndex = keyToNewIndexMap.get(prevChild.key)
        } else {
          // 无 key 节点线性寻找尚未占用、type 相同且同样无 key 的新节点。
          for (j = s2; j <= e2; j++) {
            if (
              newIndexToOldIndexMap[j - s2] === 0 &&
              isSameVNodeType(prevChild, c2[j] as VNode)
            ) {
              newIndex = j
              break
            }
          }
        }
        if (newIndex === undefined) {
          unmount(prevChild, parentComponent, parentSuspense, true)
        } else {
          newIndexToOldIndexMap[newIndex - s2] = i + 1
          if (newIndex >= maxNewIndexSoFar) {
            maxNewIndexSoFar = newIndex
          } else {
            moved = true
          }
          patch(
            prevChild,
            c2[newIndex] as VNode,
            container,
            null,
            parentComponent,
            parentSuspense,
            namespace,
            slotScopeIds,
            optimized,
          )
          patched++
        }
      }

      // 5.3 挂载全新节点，并移动不属于最长稳定子序列的复用节点。
      // 只有检测到乱序时才计算 LIS，常见仅内容更新路径省去 O(n log n) 工作。
      const increasingNewIndexSequence = moved
        ? getSequence(newIndexToOldIndexMap)
        : EMPTY_ARR
      j = increasingNewIndexSequence.length - 1
      // 从后向前处理，右侧节点已处于最终位置，可直接作为当前节点插入锚点。
      for (i = toBePatched - 1; i >= 0; i--) {
        const nextIndex = s2 + i
        const nextChild = c2[nextIndex] as VNode
        const anchorVNode = c2[nextIndex + 1] as VNode
        const anchor =
          nextIndex + 1 < l2
            ? // #13559/#14173：未解析异步组件没有 el，沿其包装子树寻找注释 placeholder
              // 作为锚点，避免新节点被插到异步组件预留位置之后。
              anchorVNode.el || resolveAsyncComponentPlaceholder(anchorVNode)
            : parentAnchor
        if (newIndexToOldIndexMap[i] === 0) {
          // 映射值 0：新节点没有旧节点，直接在已确定锚点前挂载。
          patch(
            null,
            nextChild,
            container,
            anchor,
            parentComponent,
            parentSuspense,
            namespace,
            slotScopeIds,
            optimized,
          )
        } else if (moved) {
          // j < 0 表示 LIS 中可保留的位置已处理完；其余不在 LIS 的节点需要移动。
          // 非空的完全逆序复用序列仍有长度为 1 的 LIS，可保留一个节点。
          if (j < 0 || i !== increasingNewIndexSequence[j]) {
            move(nextChild, container, anchor, MoveType.REORDER)
          } else {
            j--
          }
        }
      }

3. 同一数组的完整执行图

[1, 2, 3, 4] → [2, 3, 1, 4]
头同步1 ≠ 2，立即停
→
尾同步4 = 4，patch 并保留
→
中段映射newIndexToOld = [2, 3, 1]
→
LIS索引 [0, 1]：保留 key 2、3
→
移动key 1 插到 key 4 前；得到 2,3,1,4
  1. 头尾收缩：头部不匹配；尾部 key=4 匹配，所以未知区间只剩前三项。
  2. 旧项找新位：依旧序遍历 1、2、3，记录到新序中的位置，得到 [2, 3, 1]（值是旧下标 + 1）。
  3. 发现移动：位置序列从 2 降到 0 时，moved 置 true；所有三项仍会先 patch 复用。
  4. 最小移动：LIS 对应 key 2、3；逆序提交时只把 key 1 插到 key 4 前。
  5. 断言：测试只断言数量与顺序；若要证明对象身份，需另加 expect(after[2]).toBe(before[0])，这行不是仓库原测试。
失败、异常与清理：重复 key 会在开发态警告且映射后写覆盖前写， 因而 key 必须唯一；旧 key 在新树找不到时立即 unmount；新项的映射值为 0 时走 patch(null, ...)；异步组件没有 el 时改用 placeholder 作 anchor。测试失败时先区分“最终顺序错”“复用身份错”还是“宿主 move 次数过多”。

核心模块该测试什么场景

模块 基础行为 边界/回归 不能只断言什么
VNode / block normalize、clone、shape/patch flag 已 mount VNode 复用、dynamicChildren 回退 只看 type/children
Component props/slots/setup/render/lifecycle setup error、fallthrough attrs、recursive update 只看最终 HTML
Keyed Diff append/remove/reorder 空节点、重复 key、Fragment/组件 move、LIS 只看顺序；还要看身份和操作数
Scheduler 去重、uid 排序、pre/post 插队、dispose、recursive、throw 后 flags 清理 只看某 job 被调用
Hydration 认领 Text/Element/Component mismatch、用户输入、资源属性、namespace 只看警告；还要看恢复后的 DOM/更新
Teleport target mount、disabled、target change 共享 target、defer、hydrate、Transition 只看 target innerHTML
Suspense fallback/resolve/effects 旧 Promise 晚到、嵌套、timeout、unmount 只 await 最终内容
runtime-dom class/style/event/attr/prop IME、事件冒泡时新增监听、SVG/MathML、CE 只看 attribute 字符串

四种“等待”不是一回事

等待工具 推进什么 典型用途 常见错误
nextTick() 当前 scheduler flush promise 组件更新、post watcher、updated 以为它会自动完成任意网络 Promise
Promise.resolve() 微任务队列 CE 断连确认、简单 async continuation 与 Vue job 时机混为一谈
vi.runAllTimers() fake timeout/interval Transition duration、Suspense timeout 没启用 fake timers 或漏掉 rAF
nextFrame / rAF 浏览器渲染帧语义 CSS class 从 from 切换到 to 只 flush 微任务，动画状态仍未推进

不稳定测试常常不是实现有竞态，而是测试推进了错误的时钟。读失败用例时先标注副作用属于同步栈、Vue flush、Promise 微任务、timer 还是 animation frame。

如何使用这份中文注释源码

  1. 先读本指南建立模型：知道当前文件在系统中的输入、输出与不变量。
  2. 再读函数头：中文 TSDoc 说明调用时机、参数语义、返回值和关键场景。
  3. 进入长代码块：块注释解释阶段目标，不要求逐行翻译语法。
  4. 遇到 issue 注释：先打开相邻测试理解复现，再看修复分支如何维护更大契约。
  5. 自己改一个小实验：让用例失败，观察断言保护了身份、时序还是恢复；随后撤销实验。

注释不是源码的替代物。最理想的阅读循环是：指南给地图，函数注释给路标，测试给行为证据，调试器给实时状态，Git 历史解释路为什么这样修。

完成一个 Runtime 主题的自测清单

  • 能用一句话说出该模块不负责什么。
  • 能画出关键状态对象，以及谁写入、谁读取。
  • 能解释至少一个 fast path 的前提和 fallback。
  • 能举出一个异步/卸载/移动导致的边界场景。
  • 能找到对应 spec，并说明它在断言结果、身份、顺序还是恢复。
  • 能从用户动作一路跟到 host operation，再跟到 post effect。
如果六项都能回答，你已经不是“看过这个文件”，而是拥有了可迁移的 Runtime 心智模型。

Chapter 07 · Built-in Protocols

弹窗、骨架屏、页面缓存和动画改变了什么

四个内置组件分别改变节点放在哪里、何时显示、离开后是否销毁，以及删除要等多久。先从产品场景理解，再进入它们与 Renderer 的特殊协议。

建议阅读 45 分钟先修：Renderer / Scheduler四套协议

普通组件做不到的四类产品需求

TELEPORT · 位置

弹窗放进 body

弹窗逻辑上属于当前组件，真实 DOM 却要离开被 overflow 裁剪的父容器。

SUSPENSE · 等待

先显示骨架屏

真实内容要等异步数据或组件；准备好之前展示 fallback，完成后整体切换。

KEEPALIVE · 记忆

切走页面但别丢状态

返回列表页时，希望筛选条件和滚动状态还在，所以组件离开时暂存而非销毁。

TRANSITION · 时间

离开前先播完动画

逻辑上节点已经消失，物理 DOM 还要保留到 leave 动画完成后才能删除。

它们改变的是 Renderer 的默认规则

默认规则 被谁改变 新规则
子节点放在父节点内部 Teleport 逻辑关系不变，DOM 可去另一个容器
组件挂载可以同步完成 Suspense 先准备隐藏分支，依赖完成后提交

删除决定后立即 remove Transition 动画回调完成后才真正删除
这四个能力之所以属于 Runtime，不是因为它们“常用”，而是因为它们必须介入创建、移动和删除节点的过程。
组合时的统一问题：节点现在属于哪个组件、真实放在哪个容器、何时可见、离开时是缓存还是销毁。
进入四套内置组件协议与源码层

为什么不能只用 setup + render 实现

普通组件最终只返回一棵 subTree，由 renderer 决定 mount、move 与 unmount。四个内置能力恰好要影响这些动作本身：Teleport 要把 children 插到另一容器；KeepAlive 要“停用而非销毁”；Transition 要把删除推迟到动画结束；Suspense 要先在隐藏容器试装异步分支。因此它们必须拥有受控的内部接口。

能力 改写的默认假设 接入点 核心状态
Teleport 逻辑父子与物理 DOM 父子相同 type.process / move / remove / hydrate target、targetStart、targetAnchor
Suspense 组件 mount 可同步完成 type.process / boundary.registerDep pendingBranch、activeBranch、deps、pendingId
KeepAlive 移出当前树就应 unmount renderer 注入 activate / deactivate cache、keys、storageContainer
Transition insert/remove 立即完成 VNode transition hooks / move type enter/leave callbacks、leavingVNodes
设计边界是“内置能力拿到恰好够用的 renderer internals”，而不是直接复制 renderer。这样所有特殊分支仍共享同一套 patch、move、unmount 和队列语义。

Teleport：一棵逻辑树，两套物理锚点

Teleport 的 children 在组件/VNode 关系上仍属于原父级，所以 provide/inject、事件组件链、卸载范围都不变；真实 DOM 却位于 to 指向的 target。为同时维护两套位置，主容器和目标容器都需要锚点。

LOGICAL TREE / PHYSICAL DOM
主容器teleport start … teleport end
保留逻辑位置与兄弟顺序。
目标容器targetStart … children … targetAnchor
隔离多个 Teleport 的区间。

首次挂载

在主容器创建 start/end
即使内容传送出去，原位置仍有稳定范围。
解析 to
字符串通过 querySelector 找 target，也可直接传宿主元素；找不到会给出开发警告。
在 target 建立锚点
多个 Teleport 指向同一 target 时，每个实例必须拥有独立区间。
按 disabled 决定容器
启用时挂到 target；disabled 时挂在主容器的结束锚点前。

更新时不是只有“patch children”

to 或 disabled 变化都可能触发整体移动：disabled false → true 把 children 拉回主树；target 改变则移到新目标；普通内容更新才在当前真实容器中 patch。defer 还允许目标在同一次更新周期稍后出现，解析动作进入 post-render 时机，但必须核对 Teleport 没在等待期间被卸载。

高频误区：Teleport 不会改变组件父子链，也不新建应用上下文。它移动的是宿主节点，不是 VNode 所属关系。

水合为何更难

水合主树时只能先认领 Teleport 占位符，再去 target 寻找对应锚点。多个 Teleport 共享 target 时要按 SSR 输出顺序推进目标游标；否则第二个实例可能误认领第一个实例的 children。

Suspense：异步依赖计数器 + 双分支提交事务

Suspense 同时维护 pendingBranch 与 activeBranch。新内容先挂到离屏 hiddenContainer：如果同步完成就一次性显示；若发现异步 setup 依赖，则继续展示旧分支或 fallback，等依赖数归零再 resolve。

normalize 两个 slot
default 是 content，fallback 是等待界面，每个都归一化为单根 VNode。
离屏 patch content
子组件遇到 async setup 后向最近的 pending suspense 注册依赖，deps++。
决定是否显示 fallback
首次挂载存在依赖时展示 fallback；更新时可由 timeout 控制何时切换。
每个依赖完成
确认实例未卸载且 pendingId 仍匹配，完成组件 setup 和 subTree mount，再 deps--。
resolve
移除/过渡旧 activeBranch，把 pendingBranch 从隐藏容器移动到真实容器，统一冲刷延后的 effects。

pendingId 是关键的竞态令牌。若一次等待尚未完成，父组件已触发第二个 pending branch，第一批 Promise 即使随后 resolve 也不得提交旧结果。

状态 activeBranch pendingBranch 用户看到
同步完成 content null 直接看到内容
首次等待 fallback hidden content fallback
更新等待 旧 content 或 fallback 新 hidden content 由 timeout 决定
已 resolve 新 content null 内容原子切换

effects 为什么要延后

pendingBranch 虽已在 hiddenContainer mount，但还不可见。如果此时运行 mounted、指令或 ref，用户代码会误以为节点已提交到页面。Suspense 暂存这些 post-render effects，在 resolve 后交回正常调度队列；嵌套 Suspense 还要向未完成的祖先边界继续汇入。

KeepAlive：把“卸载”重定义为“停用”

KeepAlive 自身是组件，但它需要 renderer 配合。setup 时通过共享上下文拿到 move、patch、unmount，并向 renderer 暴露 activate / deactivate。renderer 看到相应 ShapeFlag 后不走普通 mount/unmount。

deactivate把子树 move 到 storageContainer；排入 deactivated hook；组件实例与 DOM 都保留。
activate把缓存子树 move 回真实容器；用最新 VNode patch 旧缓存；排入 activated hook。

缓存身份

默认 key 是组件类型；显式 key 可让同一组件类型拥有多个缓存实例。命中缓存时，新 VNode 继承旧 VNode 的 el 和 component，并打上 COMPONENT_KEPT_ALIVE。首次缓存则在 render 后将 subTree 写入 Map。

include / exclude / max

  • include/exclude：匹配组件 name；条件变化后在 post-flush 清理不再合格的缓存。
  • max：使用 keys Set 维护近似 LRU。缓存命中时删除再追加 key；超过上限时淘汰最旧 key。
  • 清缓存：不能简单 Map.delete。非当前分支要真正 unmount；当前分支则先清除 keep-alive flag，等正常生命周期接管。
KeepAlive 保留组件状态，也保留响应式 effect。停用组件仍可能被依赖触发更新；“不在页面中”不等于“完全暂停执行”。业务若需暂停订阅，应在 activated/deactivated 生命周期显式管理。

Transition：把时间维度注入 Renderer

runtime-core 的 BaseTransition 不知道 CSS，只负责状态机与 hook 协议；runtime-dom 的 Transition 把 CSS class、transitionend/animationend 和显式 duration 实现成 hooks。

阶段 Renderer 时机 典型动作 完成信号
beforeEnter hostInsert 之前 设置初始 class；取消同节点进行中的 leave 同步
enter 插入之后 post-render 下一帧切换 active/to class，等待过渡结束 done callback
leave 真正 hostRemove 之前 保留节点，运行动画 done 后调用 remove
move Keyed Diff 移动节点时 TransitionGroup 记录位置，使用 FLIP 动画 transitionend

leave 的难点是“逻辑上已离开，物理上暂时还在”。Renderer 不能立即删除 DOM，但下一轮又可能插入同 key 节点。leavingVNodes 以 type/key 记录回调，新 enter 可以主动结束旧 leave，避免重复节点与错误动画。

out-in 与 in-out

  • out-in：旧分支先离开，完成后触发组件重新更新，再进入新分支。
  • in-out：新分支先进入，旧分支的 leave 被延迟到 enter 完成。

模式说明 Transition 并非纯 CSS 包装：它能影响组件更新时机和节点删除时机，因此必须和 VNode clone、KeepAlive、Suspense 分支切换协作。

组合场景：真正的复杂度来自协议相遇

组合 需要回答的问题 源码中的共同语言
Teleport × Transition leave 时节点在哪个容器？target 改变时是 reorder 还是 enter/leave？ moveType、anchor、transition hooks
Suspense × Transition pending resolve 时先移除 fallback 还是先进入 content？ activeBranch、afterLeave、effects
KeepAlive × Transition 离开是 deactivate 还是 unmount？再次进入是否复用 DOM？ ShapeFlag、persisted、activate/deactivate
KeepAlive × Suspense 缓存的是 Suspense 外壳还是已解析 content？ getInnerChild、subTree、pendingBranch
Teleport × SSR 主树与 target 的锚点怎样一一对应？ hydrate、targetStart、targetAnchor
阅读组合 bug 时不要从某个组件名出发猜。先画三样东西：当前 active VNode、真实 DOM 所在 container、下一次操作使用的 anchor；大多数问题会落在这三者不同步。

E. 组合场景：弹窗里的异步缓存页正在过渡

这是教学组合推演，固定讨论 Teleport → Suspense(timeout: 0) → Transition(mode: out-in) → KeepAlive → 当前异步页 这一种嵌套；它不是仓库中的单一测试，也不声称所有嵌套顺序都有相同时间线。 图中箭头表示阅读时的责任传递，不把四份实现伪装成一个函数调用栈。

COMPOSED CASE · MODAL ROUTE
Teleport弹窗 DOM 在 body target；逻辑父级不变
→
Suspense新页 pending；弹窗内先显示 fallback
→
KeepAlive旧页 deactivate，实例进入 cache
→
Transition按 mode 协调旧页 leave / 新页 enter
→
Commitdeps=0 后 content 移入远端 target；hooks flush
  1. 先固定三个坐标：逻辑父树、Teleport 目标容器、Suspense hidden container；它们可能同时不同。
  2. 路由切换时 KeepAlive 决定旧实例是 deactivate 还是 unmount；Transition 决定真实节点何时允许移除。
  3. 异步新页只在当前 pendingId 仍有效且 deps 降为 0 时提交；过期结果不能覆盖新导航。
  4. 最终移动由各协议委托 renderer internals 完成；post effects 必须等正确的 Suspense/Transition 边界提交。

Given：远端弹窗 target 已存在，页面 A 已进入 KeepAlive 缓存，当前导航要显示异步页面 B，并配置立即 fallback。

When：导航改变使 B 的 async setup 注册到 Suspense；旧 active branch、fallback 与隐藏 pending branch 开始交接。

Then：只有仍属于当前 pendingId 的 B 能在 deps=0 后提交到 Teleport target；A 可由缓存恢复，过期 B 不得覆盖后来导航。

Mechanism：四个协议分别拥有容器、异步事务身份、实例缓存身份与节点移除时机；renderer internals 是交汇边界。

Source：证据来自上面四段独立源码与四个独立测试；组合顺序是显式推断，所以不加 data-source-file，也不冒充仓库测试。

组合清理审计：关闭弹窗时逐项确认 pending job/async branch 已失效、transition callback 已完成或取消、缓存实例最终能被 prune/unmount、Teleport 远端 children 与两套锚点均被移除。具体回调先后取决于嵌套和 mode；这里列的是 必须全部成立的清理后置条件，不硬编一个通用顺序。

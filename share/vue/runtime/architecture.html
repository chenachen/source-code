为什么 Vue 要把更新拆成不同层

页面更新包含两类完全不同的问题：应该改什么，以及在当前平台上怎样改。Vue 把它们分开，让组件和 Diff 不必知道浏览器细节。

建议阅读 25 分钟先修：无核心文件 6 个

先把贯穿用例完整放在桌面上

本章以后只追这一件事：一个 Counter 组件先渲染 <button id="counter">0</button>；测试代码连续调用两次 triggerEvent，在同一同步调用栈中完成两个处理器， nextTick() 后文本变成 2，最后卸载。它使用 Vue 仓库自己的 @vue/runtime-test 内存宿主，因此既能观察组件更新，也能证明 runtime-core 的 renderer、组件与 Diff 主线不依赖浏览器 DOM。 包内刻意保留的 hydration 例外会在后文单独说明。

这段测试从哪来：下面的用例由本教程新增，可放进 Vue 3.5.41 仓库直接运行，不是上游自带测试。它包含 imports、准备、动作、同步与异步断言， 以及 afterEach 卸载清理。
完整教程测试：counter-course.spec.ts 
import {
  type TestElement,
  h,
  nextTick,
  nodeOps,
  ref,
  render,
  serializeInner,
  triggerEvent,
} from '@vue/runtime-test'
import { afterEach, beforeEach, describe, expect, it } from 'vitest'

describe('runtime course: Counter', () => {
  let root: TestElement

  beforeEach(() => {
    root = nodeOps.createElement('div')
  })

  afterEach(() => {
    render(null, root)
    expect(serializeInner(root)).toBe('')
  })

  it('keeps DOM stale until nextTick, patches final text, then unmounts', async () => {
    const Counter = {
      setup() {
        const count = ref(0)
        const increment = () => count.value++
        return () =>
          h(
            'button',
            { id: 'counter', onClick: increment },
            String(count.value),
          )
      },
    }

    render(h(Counter), root)
    expect(serializeInner(root)).toBe('<button id="counter">0</button>')

    triggerEvent(root.children[0] as TestElement, 'click')
    triggerEvent(root.children[0] as TestElement, 'click')
    expect(serializeInner(root)).toBe('<button id="counter">0</button>')

    await nextTick()
    expect(serializeInner(root)).toBe('<button id="counter">2</button>')
  })
})

同一用例的架构执行图：谁决定，谁施工

按执行顺序再走一遍

  1. 组装：runtime-test 先把自己的 nodeOps 与 patchProp 交给 core，这一步定义“施工队会什么”。
  2. 闭包：createRenderer 只建立一组捕获宿主操作的函数，返回 render；没有 VNode 时不会创建任何节点。
  3. 决策：render/patch 只看 VNode 的 type、shapeFlag、key 与前后状态，决定组件或元素路径。
  4. 提交：到了创建、插入、改文本或属性时，core 调 host 别名；同一算法因此能跑在 DOM 和内存树上。
  5. 更新：两次点击只改变何时再次得到 button VNode；最终提交仍穿过同一 host 接口。
  6. 清理：render(null) 不创建空 VNode，而是卸载容器保存的旧树，并让宿主移除节点。

把 Counter 再翻译成两层职责

count 从 0 变成 2 后，Vue 要完成两次翻译：

第一层：决定改什么

按钮还是原来的按钮；id 与事件不变；只有文本 children 从 0 变成 2。

第二层：决定怎样改

在浏览器中写 textContent；在 runtime-test 中调用 setElementText 改内存节点。

runtime-core 像项目经理，决定做什么；runtime-dom 像浏览器施工队，决定具体怎么做。

图页面描述组件交出一份“现在应该长什么样”的轻量设计图。VNode
判通用决策比较设计图，决定创建、更新、移动还是删除。runtime-core / Renderer
做平台施工把决定落实成 DOM、Canvas 或测试内存树操作。runtime-dom / custom host
这样分层的直接收益：Vue 的组件、生命周期和 Diff 只写一次；浏览器差异集中在 runtime-dom；核心算法还能在不启动浏览器的环境中测试。

后面看到 hostInsert、hostRemove 时，只要翻译成“请当前平台插入或删除节点”即可。

进入架构与源码层

包边界不是目录整理，而是职责约束

Vue 3 将运行时拆成两个公开包，背后对应两种稳定性不同的知识：

@vue/runtime-core

以宿主无关语义为主

组件实例、VNode、Renderer、调度、指令生命周期、Teleport、Suspense、KeepAlive、BaseTransition；另有一个与 renderer 强耦合的 DOM hydration 例外。

@vue/runtime-dom

浏览器平台的具体实现

DOM nodeOps、patchProp、事件、v-model、v-show、CSS Transition、Custom Element，以及 HTML/SVG/MathML 类型。

renderer、组件与 Diff 主线不直接操作浏览器 DOM。它们保存一组 RendererOptions，需要创建节点时调用 hostCreateElement，需要插入时调用 hostInsert，需要更新属性时调用 hostPatchProp。runtime-dom 则负责把这些接口实现成真实 DOM 操作。

这里有一个刻意保留的例外：runtime-core/src/hydration.ts 会读取 Node、Element、nodeType、tagName 等 DOM 能力。源码说明它本应是 DOM 专属逻辑，但因与 renderer 内部函数紧密相连而留在 runtime-core；普通 createRenderer 不安装它，只有 createHydrationRenderer 才传入这组函数，未使用水合时仍可被 tree-shake。
PACKAGE DEPENDENCY ≠ RUNTIME CALLBACK
Compiler模板静态分析，生成 render、block、patchFlag。
→
runtime-core解释 VNode 与组件语义，决定增量提交步骤。
← import / 组装
runtime-dom导入 core，注入 nodeOps 与 patchProp，创建 DOM renderer。
运行时回调方向：core 的 patch → 注入的 hostCreateElement / hostInsert / hostPatchProp → DOM。
DOM hydration 例外：hydration.ts 留在 core，但只由 hydration renderer 按需接入。

因而要分清两支箭头：包依赖是 runtime-dom 导入并组装 runtime-core；renderer 闭包建好后，调用方向才是 core 回调 runtime-dom 注入的 host 操作。把两者都画成“core → dom”，会误以为 core 在源码层依赖 runtime-dom。

RendererOptions：整个架构的铰链

createRenderer(options) 不知道 Element、Text、Comment 是什么。它只知道“宿主节点”与“宿主元素”两个泛型，以及一组最小操作。典型接口可分成四类：

类别 代表接口 core 依赖的语义 DOM 实现
树结构 insert、remove、parentNode、nextSibling 插入到 anchor 前、移动已存在节点、寻找逻辑片段之后的位置 insertBefore、removeChild
节点创建 createElement、createText、createComment 按 VNode 类型得到可提交宿主节点 document.createElement/NS
内容更新 setText、setElementText 文本节点和元素文本 children 的快速更新 nodeValue、textContent
属性提交 patchProp 只表达 key、prev、next 和 namespace，不理解 DOM 细节 class/style/event/prop/attr 分派

这个抽象的收益不仅是“能做 Canvas Renderer”。更重要的是，core 的测试可以使用内存树验证算法，无需依赖浏览器；而 DOM 的复杂兼容逻辑也不会污染组件与 Diff 主流程。

抽象并非越多越好。RendererOptions 只抽离真正由平台决定的操作；VNode 身份、组件生命周期、children Diff 和任务顺序仍由 core 统一定义，否则跨平台组件语义会分裂。

VNode：模块之间共享的中间表示

VNode 不是“DOM 的轻量副本”。它同时承载声明式输入、运行时状态、编译器优化提示和跨模块协议。可以把字段分成四组：

角色 字段 谁写入 谁消费
身份 type、key、shapeFlag createVNode / normalizeVNode patch 分派、isSameVNodeType
声明输入 props、children、ref、dirs、transition render 函数与 helper 组件初始化、元素修补、指令与过渡
提交结果 el、anchor、component、target renderer / 内置组件 下一轮更新、move、unmount、水合
优化信息 patchFlag、dynamicProps、dynamicChildren 编译器与 block helper patchElement、patchBlockChildren

这解释了为什么 VNode 不能被随意复用：挂载后它已经携带 el、component 等可变状态。cloneIfMounted 会在普通 VNode 已有 el，或节点带 PatchFlags.CACHED 时克隆； memo 管理的节点是例外。这样两处逻辑节点不会竞争同一份提交结果。

从 h('button') 到 patch：中间没有凭空出现的 VNode

Counter 的手写 render 调用 h。h 只负责宽松参数重载，真正的创建入口仍是 createVNode；开发构建允许测试工具变换参数，随后进入 _createVNode。后者推断节点大类，再由 createBaseVNode 分配对象并调用 normalizeChildren。此时 el、component 等提交字段仍为空，直到 renderer 的 patch 挂载或复用节点后才回填。

连续源码 1：h 统一参数后调用 createVNode 
export function h(type: any, propsOrChildren?: any, children?: any): VNode {
  try {
    // #6913：h 创建期间临时降低 block tracking 计数，常规计数从 1 变为 0，使本次
    // createVNode 及 children 标准化期间产生的节点不进入外围 block；finally 恢复计数。
    // 调用 h 前已经求值的 children 不受这段开关影响。
    setBlockTracking(-1)
    const l = arguments.length
    if (l === 2) {
      if (isObject(propsOrChildren) && !isArray(propsOrChildren)) {
        // 单 VNode 是 children，不是 props；统一包成数组便于后续 children 标准化。
        if (isVNode(propsOrChildren)) {
          return createVNode(type, null, [propsOrChildren])
        }
        // 普通非数组对象按 props 处理。
        return createVNode(type, propsOrChildren)
      } else {
        // 数组或原始值表示省略 props，直接作为 children。
        return createVNode(type, null, propsOrChildren)
      }
    } else {
      if (l > 3) {
        children = Array.prototype.slice.call(arguments, 2)
      } else if (l === 3 && isVNode(children)) {
        children = [children]
      }
      return createVNode(type, propsOrChildren, children)
    }
  } finally {
    setBlockTracking(1)
  }
}

/**
 * 公开 VNode 创建入口。开发构建允许 test-utils 变换参数，生产构建直接指向热路径实现。

export const createVNode = (
  __DEV__ ? createVNodeWithArgsTransform : _createVNode
) as typeof _createVNode

/** 标准化类型、props、class/style 后创建任意类型 VNode 的内部实现。 */
function _createVNode(
  type: VNodeTypes | ClassComponent | typeof NULL_DYNAMIC_COMPONENT,
  props: (Data & VNodeProps) | null = null,
  children: unknown = null,
  patchFlag: number = 0,
  dynamicProps: string[] | null = null,
  isBlockNode = false,
): VNode {
  // 将类型大类编码进 shapeFlag，patch 时用位运算快速分派。
  const shapeFlag = isString(type)
    ? ShapeFlags.ELEMENT
    : __FEATURE_SUSPENSE__ && isSuspense(type)
      ? ShapeFlags.SUSPENSE
      : isTeleport(type)
        ? ShapeFlags.TELEPORT
        : isObject(type)
          ? ShapeFlags.STATEFUL_COMPONENT
          : isFunction(type)
            ? ShapeFlags.FUNCTIONAL_COMPONENT
            : 0

  if (__DEV__ && shapeFlag & ShapeFlags.STATEFUL_COMPONENT && isProxy(type)) {
    type = toRaw(type)
    warn(
      `Vue received a Component that was made a reactive object. This can ` +
        `lead to unnecessary performance overhead and should be avoided by ` +
        `marking the component with \`markRaw\` or using \`shallowRef\` ` +
        `instead of \`ref\`.`,
      `\nComponent that was made reactive: `,
      type,
    )
  }

  return createBaseVNode(
    type,
    props,
    children,
    patchFlag,
    dynamicProps,
    shapeFlag,
    isBlockNode,
    true,
  )
}
连续源码 3：createBaseVNode 先留空提交字段，再标准化 children 
function createBaseVNode(
  type: VNodeTypes | ClassComponent | typeof NULL_DYNAMIC_COMPONENT,
  props: (Data & VNodeProps) | null = null,
  children: unknown = null,
  patchFlag = 0,
  dynamicProps: string[] | null = null,
  shapeFlag: number = type === Fragment ? 0 : ShapeFlags.ELEMENT,
  isBlockNode = false,
  needFullChildrenNormalization = false,
): VNode {
  const vnode = {
    __v_isVNode: true,
    __v_skip: true,
    type,
    props,
    key: props && normalizeKey(props),
    ref: props && normalizeRef(props),
    scopeId: currentScopeId,
    slotScopeIds: null,
    children,
    component: null,
    suspense: null,
    ssContent: null,
    ssFallback: null,
    dirs: null,
    transition: null,
    el: null,
    anchor: null,
    target: null,
    targetStart: null,
    targetAnchor: null,
    staticCount: 0,
    shapeFlag,
    patchFlag,
    dynamicProps,
    dynamicChildren: null,
    appContext: null,
    ctx: currentRenderingInstance,
  } as VNode

  if (needFullChildrenNormalization) {
    normalizeChildren(vnode, children)
    // Suspense 还需把 default/fallback slots 分别标准化为 ssContent/ssFallback。
    if (__FEATURE_SUSPENSE__ && shapeFlag & ShapeFlags.SUSPENSE) {
      ;(type as typeof SuspenseImpl).normalize(vnode)
    }
  } else if (children) {
    // 编译器已保证原生元素 children 只可能是字符串或数组，可直接设置 shapeFlag。
    vnode.shapeFlag |= isString(children)
      ? ShapeFlags.TEXT_CHILDREN
      : ShapeFlags.ARRAY_CHILDREN
  }
export function normalizeChildren(vnode: VNode, children: unknown): void {
  let type = 0
  const { shapeFlag } = vnode
  if (children == null) {
    children = null
  } else if (isArray(children)) {
    type = ShapeFlags.ARRAY_CHILDREN
  } else if (typeof children === 'object') {
    if (shapeFlag & (ShapeFlags.ELEMENT | ShapeFlags.TELEPORT)) {
      // 原生元素和 Teleport 不持有 slots 对象，执行 default slot 得到普通 children。
      const slot = (children as any).default
      if (slot) {
        // `_c` 表示编译插槽；由 renderSlot 控制的调用可临时开启 block tracking。
        slot._c && (slot._d = false)
        normalizeChildren(vnode, slot())
        slot._c && (slot._d = true)
      }
      return
    } else {
      type = ShapeFlags.SLOTS_CHILDREN
      const slotFlag = (children as RawSlots)._
      if (!slotFlag && !isInternalObject(children)) {
        // 未标准化用户 slots 需记录声明上下文；编译/内部 slots 已经携带，无需覆盖。
        ;(children as RawSlots)._ctx = currentRenderingInstance
      } else if (slotFlag === SlotFlags.FORWARDED && currentRenderingInstance) {
        // 转发插槽自身稳定性取决于父组件收到的插槽：父级稳定则仍稳定，否则标成动态，
        // 并给当前组件加 patchFlag，不能因 props 未变跳过更新。
        if (
          (currentRenderingInstance.slots as RawSlots)._ === SlotFlags.STABLE
        ) {
          ;(children as RawSlots)._ = SlotFlags.STABLE
        } else {
          ;(children as RawSlots)._ = SlotFlags.DYNAMIC
          vnode.patchFlag |= PatchFlags.DYNAMIC_SLOTS
        }
      }
    }
  } else if (isFunction(children)) {
    if (shapeFlag & (ShapeFlags.ELEMENT | ShapeFlags.TELEPORT)) {
      normalizeChildren(vnode, { default: children })
      return
    }
    children = { default: children, _ctx: currentRenderingInstance }
    type = ShapeFlags.SLOTS_CHILDREN
  } else {
    children = String(children)
    // Teleport 的 children 需要逐节点搬移，纯文本也转成单元素 VNode 数组。
    if (shapeFlag & ShapeFlags.TELEPORT) {
      type = ShapeFlags.ARRAY_CHILDREN
      children = [createTextVNode(children as string)]
    } else {
      type = ShapeFlags.TEXT_CHILDREN
    }
  }
  vnode.children = children as VNodeNormalizedChildren
  vnode.shapeFlag |= type
}

两套 Flag：一个描述结构，一个描述变化

SHAPE FLAG · RUNTIME

“这个 VNode 是什么？”

元素、状态组件、函数组件、数组 children、slot children、Teleport、Suspense。创建 VNode 时由运行时推断，主要服务分派。

PATCH FLAG · COMPILER

“它的哪里可能变化？”

TEXT、CLASS、STYLE、PROPS、FULL_PROPS、STABLE_FRAGMENT 等。来自模板静态分析，主要服务更新快路径。

两者解决不同问题。一个元素 VNode 的 shapeFlag 永远说明它是元素；patchFlag 则可能说明本轮只需检查 class。把它们混为一谈，会很难理解 patch 为什么先按类型分派，再在 patchElement 内选择优化路径。

Block tree 为什么不是另一棵树

Block 是对原 VNode 树的动态节点索引。openBlock 开始收集，createElementBlock 把本层动态节点保存在 dynamicChildren。更新时，renderer 可以直接遍历动态数组，而不是重新走静态后代。

贯穿后续章节的设计原则

Renderer 主线通过宿主接口解耦
组件、patch 与 Diff 从注入的 host 操作提交；DOM hydration 是前文说明的包内例外。
先保持正确，再逐层缩小工作
完整 patch 是基线；patchFlag 与 block 缩小比较范围，LIS 在匹配完成后减少节点移动。
状态与提交分离
响应式只通知“需要更新”，scheduler 决定时机，renderer 决定差异，host 决定操作。
树结构依赖稳定锚点
Fragment、Teleport、Suspense 的复杂性很大程度来自跨轮次维护插入位置。
特殊能力通过协议接入
内置组件扩展 process/move/activate，而不是在 patch 中无限堆业务条件。
错误清理决定恢复边界
render 错误处理恢复渲染上下文， 主队列 finally 清理 QUEUED，水合 mismatch 按分支修补 DOM；各自的提前退出与再次抛错决定能否继续更新。

这套架构付出了什么代价

  • 参数很多：patch 需要 container、anchor、parentComponent、parentSuspense、namespace、slotScopeIds、optimized，因为它必须保持无全局上下文且可重入。
  • VNode 是可变对象：提交结果直接写回 VNode，更新速度快，但要求克隆与复用规则非常谨慎。
  • 内置组件交叉复杂：每个协议独立清晰，组合后却要共同维护锚点、生命周期和异步时序。
  • 编译器与运行时耦合：patchFlag 缩小比较范围。显式 BAIL、HMR 或动态数组不对应等条件会退回通用比较；运行时不会自动识别任意错误编译提示。

Chapter 01 · Architecture

为什么 Vue 要把更新拆成不同层

页面更新包含两类完全不同的问题：应该改什么，以及在当前平台上怎样改。Vue 把它们分开，让组件和 Diff 不必知道浏览器细节。

建议阅读 25 分钟先修：无核心文件 6 个

先把贯穿用例完整放在桌面上

本章以后只追这一件事：一个 Counter 组件先渲染 <button id="counter">0</button>；测试代码连续调用两次 triggerEvent，在同一同步调用栈中完成两个处理器， nextTick() 后文本变成 2，最后卸载。它使用 Vue 仓库自己的 @vue/runtime-test 内存宿主，因此既能观察组件更新，也能证明 runtime-core 并不依赖浏览器 DOM。

性质声明：下面是课程新增、可放进 Vue 3.5.41 仓库运行的完整 Vitest 教程测试，不冒充上游测试。它包含 imports、准备、动作、同步与异步断言， 以及 afterEach 卸载清理。
完整教程测试：counter-course.spec.ts 
import {
  type TestElement,
  h,
  nextTick,
  nodeOps,
  ref,
  render,
  serializeInner,
  triggerEvent,
} from '@vue/runtime-test'
import { afterEach, beforeEach, describe, expect, it } from 'vitest'

describe('runtime course: Counter', () => {
  let root: TestElement

  beforeEach(() => {
    root = nodeOps.createElement('div')
  })

  afterEach(() => {
    render(null, root)
    expect(serializeInner(root)).toBe('')
  })

  it('keeps DOM stale until nextTick, patches final text, then unmounts', async () => {
    const Counter = {
      setup() {
        const count = ref(0)
        const increment = () => count.value++
        return () =>
          h(
            'button',
            { id: 'counter', onClick: increment },
            String(count.value),
          )
      },
    }

    render(h(Counter), root)
    expect(serializeInner(root)).toBe('<button id="counter">0</button>')

    triggerEvent(root.children[0] as TestElement, 'click')
    triggerEvent(root.children[0] as TestElement, 'click')
    expect(serializeInner(root)).toBe('<button id="counter">0</button>')

    await nextTick()
    expect(serializeInner(root)).toBe('<button id="counter">2</button>')
  })
})

运行位置：保存到 vue/packages/runtime-core/__tests__/counter-course.spec.ts，在 vue/ 下执行 pnpm vitest --project unit packages/runtime-core/__tests__/counter-course.spec.ts。

本次验收：Node 24.5.0 定向执行同一测试，1 file / 1 test passed；临时测试文件随后删除。

同一用例的架构执行图：谁决定，谁施工

03render(h(Counter), root)从 root._vnode 取旧树；首次为 null，进入 patch(null, componentVNode)。renderer.ts · render/patch
04core 完成语义决策组件分支建立实例并得到 button VNode；元素分支决定 mount 或 update。processComponent/processElement
05hostCreateElement / hostPatchProp / hostInsert闭包别名调用 runtime-test 的 nodeOps/patchProp；core 不读取 TestElement 内部结构。injected host ops
06TestElement 树：button 0 → button 2点击后的调度与 diff 改变提交内容，但平台边界始终不变。serializeInner(root)

照图复述一遍

  1. 组装：runtime-test 先把自己的 nodeOps 与 patchProp 交给 core，这一步定义“施工队会什么”。
  2. 闭包：createRenderer 只建立一组捕获宿主操作的函数，返回 render；没有 VNode 时不会创建任何节点。
  3. 决策：render/patch 只看 VNode 的 type、shapeFlag、key 与前后状态，决定组件或元素路径。
  4. 提交：到了创建、插入、改文本或属性时，core 调 host 别名；同一算法因此能跑在 DOM 和内存树上。
  5. 更新：两次点击只改变何时再次得到 button VNode；最终提交仍穿过同一 host 接口。
  6. 清理：render(null) 不创建空 VNode，而是卸载容器保存的旧树，并让宿主移除节点。

决定性真实源码：抽象边界是怎样接上的

以下代码来自工作区 Vue 3.5.41。带 data-source-file 的代码块是连续原文；HTML 仅做实体转义， DOM 的 textContent 可在对应文件连续匹配。

证据 1：runtime-test 用真实 host options 创建 renderer

import {
  type CreateAppFunction,
  type RootRenderFunction,
  type VNode,
  createRenderer,
} from '@vue/runtime-core'
import { type TestElement, nodeOps } from './nodeOps'
import { patchProp } from './patchProp'
import { serializeInner } from './serialize'
import { extend } from '@vue/shared'

const { render: baseRender, createApp: baseCreateApp } = createRenderer(
  extend({ patchProp }, nodeOps),
)

export const render = baseRender as RootRenderFunction<TestElement>
export const createApp = baseCreateApp as CreateAppFunction<TestElement>

// convenience for one-off render validations
export function renderToString(vnode: VNode): string {
  const root = nodeOps.createElement('div')
  render(vnode, root)
  return serializeInner(root)
}

参数是完整的宿主能力对象；返回值的 render 被收窄为 TestElement 容器函数。状态变化是“尚无渲染器”变成“拥有一组捕获内存宿主操作的闭包”。

证据 3：root render 的正常、卸载与刷新出口

  const render: RootRenderFunction = (vnode, container, namespace) => {
    let instance

      isFlushing = false

正常路径非 null 根 VNode 进入 patch；Counter 首次 mount 走这条根入口。点击后的组件 job 直接执行 patch(prevTree, nextTree)，不会再次进入根 render。
提前退出null VNode 且容器没有 _vnode 时，不调用 unmount；相同 VNode 对象进入 patch 后也立即 return。
错误路径宿主操作违反 anchor/parent 契约并抛错时，core 不提供事务回滚；错误向上传播，宿主实现必须维护原子性。
清理路径render(null) 卸载旧树、停止组件 scope、标记 job DISPOSED、调用 hostRemove，并把容器 _vnode 置空。

把 Counter 再翻译成两层职责

count 从 0 变成 2 后，Vue 要完成两次翻译：

第一层：决定改什么

按钮还是原来的按钮；id 与事件不变；只有文本 children 从 0 变成 2。

第二层：决定怎样改

在浏览器中写 textContent；在 runtime-test 中调用 setElementText 改内存节点。

runtime-core 像项目经理，决定做什么；runtime-dom 像浏览器施工队，决定具体怎么做。

图页面描述组件交出一份“现在应该长什么样”的轻量设计图。VNode
判通用决策比较设计图，决定创建、更新、移动还是删除。runtime-core / Renderer
做平台施工把决定落实成 DOM、Canvas 或测试内存树操作。runtime-dom / custom host
这样分层的直接收益：Vue 的组件、生命周期和 Diff 只写一次；浏览器差异集中在 runtime-dom；核心算法还能在不启动浏览器的环境中测试。

后面看到 hostInsert、hostRemove 时，只要翻译成“请当前平台插入或删除节点”即可。

进入架构与源码层

包边界不是目录整理，而是职责约束

Vue 3 将运行时拆成两个公开包，背后对应两种稳定性不同的知识：

@vue/runtime-core

与宿主平台无关的语义

组件实例、VNode、Renderer、调度、水合协议、指令生命周期、Teleport、Suspense、KeepAlive、BaseTransition。

@vue/runtime-dom

浏览器平台的具体实现

DOM nodeOps、patchProp、事件、v-model、v-show、CSS Transition、Custom Element，以及 HTML/SVG/MathML 类型。

core 不导入浏览器 DOM API。它只保存一组 RendererOptions，需要创建节点时调用 hostCreateElement，需要插入时调用 hostInsert，需要更新属性时调用 hostPatchProp。runtime-dom 则负责把这些接口实现成真实 DOM 操作。

PACKAGE TOPOLOGY
Compiler模板静态分析，生成 render、block、patchFlag。
→
runtime-core解释 VNode 与组件语义，决定增量提交步骤。
→
runtime-dom把宿主指令翻译为浏览器 DOM 操作。
Reactivity 从左下方驱动组件 render effect。
Server Renderer 生成可被 hydration renderer 认领的 HTML。

RendererOptions：整个架构的铰链

createRenderer(options) 不知道 Element、Text、Comment 是什么。它只知道“宿主节点”与“宿主元素”两个泛型，以及一组最小操作。典型接口可分成四类：

类别 代表接口 core 依赖的语义 DOM 实现
树结构 insert、remove、parentNode、nextSibling 插入到 anchor 前、移动已存在节点、寻找逻辑片段之后的位置 insertBefore、removeChild
节点创建 createElement、createText、createComment 按 VNode 类型得到可提交宿主节点 document.createElement/NS
内容更新 setText、setElementText 文本节点和元素文本 children 的快速更新 nodeValue、textContent
属性提交 patchProp 只表达 key、prev、next 和 namespace，不理解 DOM 细节 class/style/event/prop/attr 分派

这个抽象的收益不仅是“能做 Canvas Renderer”。更重要的是，core 的测试可以使用内存树验证算法，无需依赖浏览器；而 DOM 的复杂兼容逻辑也不会污染组件与 Diff 主流程。

抽象并非越多越好。RendererOptions 只抽离真正由平台决定的操作；VNode 身份、组件生命周期、children Diff 和任务顺序仍由 core 统一定义，否则跨平台组件语义会分裂。

VNode：模块之间共享的中间表示

VNode 不是“DOM 的轻量副本”。它同时承载声明式输入、运行时状态、编译器优化提示和跨模块协议。可以把字段分成四组：

角色 字段 谁写入 谁消费
身份 type、key、shapeFlag createVNode / normalizeVNode patch 分派、isSameVNodeType
声明输入 props、children、ref、dirs、transition render 函数与 helper 组件初始化、元素修补、指令与过渡
提交结果 el、anchor、component、target renderer / 内置组件 下一轮更新、move、unmount、水合
优化信息 patchFlag、dynamicProps、dynamicChildren 编译器与 block helper patchElement、patchBlockChildren

这解释了为什么 VNode 不能被随意复用：挂载后它已经携带 el、component 等可变状态。Vue 遇到已挂载或 hoisted VNode 时会克隆，以避免两处逻辑节点竞争同一份提交结果。

本地：vnode.ts GitHub：vnode.ts

两套 Flag：一个描述结构，一个描述变化

SHAPE FLAG · RUNTIME

“这个 VNode 是什么？”

元素、状态组件、函数组件、数组 children、slot children、Teleport、Suspense。创建 VNode 时由运行时推断，主要服务分派。

PATCH FLAG · COMPILER

“它的哪里可能变化？”

TEXT、CLASS、STYLE、PROPS、FULL_PROPS、STABLE_FRAGMENT 等。来自模板静态分析，主要服务更新快路径。

两者解决不同问题。一个元素 VNode 的 shapeFlag 永远说明它是元素；patchFlag 则可能说明本轮只需检查 class。把它们混为一谈，会很难理解 patch 为什么先按类型分派，再在 patchElement 内选择优化路径。

Block tree 为什么不是另一棵树

Block 是对原 VNode 树的动态节点索引。openBlock 开始收集，createElementBlock 把本层动态节点保存在 dynamicChildren。更新时，renderer 可以直接遍历动态数组，而不是重新走静态后代。 

// 概念模型：真实编译产物会包含更多 helper
openBlock()
return createElementBlock('div', null, [
  createElementVNode('span', null, 'static'),
  createElementVNode('p', null, ctx.msg, PatchFlags.TEXT)
])

贯穿后续章节的设计原则

平台无关核心
宿主接口由注入得到，核心算法只维护抽象树与组件语义。
先保持正确，再逐层缩小工作
完整 patch 是基线，patchFlag、block、LIS 都是可回退优化。
状态与提交分离
响应式只通知“需要更新”，scheduler 决定时机，renderer 决定差异，host 决定操作。
树结构依赖稳定锚点
Fragment、Teleport、Suspense 的复杂性很大程度来自跨轮次维护插入位置。
特殊能力通过协议接入
内置组件扩展 process/move/activate，而不是在 patch 中无限堆业务条件。
错误路径也必须可恢复
异步 reject、render throw、水合 mismatch 后，队列标志和当前实例都要恢复到可继续运行的状态。

这套架构付出了什么代价

  • 参数很多：patch 需要 container、anchor、parentComponent、parentSuspense、namespace、slotScopeIds、optimized，因为它必须保持无全局上下文且可重入。
  • VNode 是可变对象：提交结果直接写回 VNode，更新速度快，但要求克隆与复用规则非常谨慎。
  • 内置组件交叉复杂：每个协议独立清晰，组合后却要共同维护锚点、生命周期和异步时序。
  • 编译器与运行时耦合：patchFlag 能显著降本，但错误的优化提示必须允许 BAIL 回退，否则会牺牲正确性。

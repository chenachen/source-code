一次点击，怎样变成屏幕上的新内容

用户点击“添加任务”，业务代码只改了数组；几十毫秒后，页面多出一个列表项。我们放慢这段过程，像看分镜一样跟完 Vue Runtime 的每一次交接。

组件里的代码可能只有一行：

tasks.value.push({ id: 4, title: '学习 Diff' })

业务代码表达“状态变了”；Runtime 负责推导“页面哪里要变”，并安全地完成这次修改。

先认识这次旅程中的六个角色

暂时不用记英文名，把它们当成一个配合工作的团队。

📒 状态记录员 知道哪些组件读过任务数组。数组变化时，它通知相关组件。 Reactivity
🗓 任务调度员 不让每一次小修改都立刻重画页面；它合并工作、安排先后。 Scheduler
✎ 界面设计员 组件用最新数据重新计算，得到“现在应该有四项”的页面描述。 Component render
⌕ 变化检查员 比较前后描述，认出前三项没变，只有第四项需要新增。 Renderer + Diff
🔧 浏览器施工员 把“新增一项”翻译成真实 DOM 操作、属性和事件处理。 runtime-dom
✓ 收尾协调员 DOM 提交后处理模板 ref、updated 与 post watcher；整轮 flush（含 post 队列）结束后，nextTick 才继续。 Post flush
这些角色不会同时乱跑。每一站只接收上游结果，完成自己的决定，再把控制权交给下一站。

第一站：Vue 怎么知道该更新哪个组件

TodoList 上次生成界面时读取过 tasks.value。Vue 记下“这个组件依赖任务数组”。现在数组增加一项，Vue 不需要扫描所有组件，只通知曾经读取它的组件。

可以把它想成订阅：

组件阅读数据时自动订阅；数据修改时通知订阅者。通知的含义只是“你需要重新计算”，不是“立刻修改 DOM”。

读完能回答：为什么修改一个局部状态，不会让整个应用的所有组件都重新渲染？因为 Vue 保存了数据与使用者之间的依赖关系。
源码层：这一站叫什么？
响应式系统通过 dep 记录订阅关系，数据 trigger 后通知组件的 render effect。effect 的 scheduler 再把组件更新任务交给 queueJob，而不是直接执行组件更新。

第二站：为什么不马上更新页面

一段业务代码常常连续修改多个值：

tasks.value.push(newTask)
total.value++
message.value = '添加成功'

如果每改一次就重新生成页面并操作 DOM，三行代码可能产生三轮重复工作。Vue 先把“TodoList 需要更新”放进队列；当前同步代码运行完后，再统一刷新。相同组件在一轮里通常只更新一次。

没有调度 改 tasks → 更新页面
改 total → 再更新页面
改 message → 再更新页面
Vue 的方式 改三个值 → 记录一次 TodoList 更新
同步代码结束 → 统一生成和提交

nextTick() 等待的就是这次“统一刷新”完成。它不是固定延迟，也不保证任意网络请求完成。

源码层：队列还保证什么？
Scheduler 还按组件 uid 保证父组件通常先于子组件，区分更新前、主队列和更新后三个阶段，并在任务抛错后清理排队标志，使后续更新仍可继续。

第三站：组件重新回答“页面应该长什么样”

队列轮到 TodoList 后，组件重新运行自己的界面计算。旧数组三项，旧描述里有三个列表项；新数组四项，新描述里有四个列表项。

旧的页面描述
  • li · key 1 · 买牛奶
  • li · key 2 · 回复邮件
  • li · key 3 · 学习 Vue
新的页面描述
  • li · key 1 · 买牛奶
  • li · key 2 · 回复邮件
  • li · key 3 · 学习 Vue
  • li · key 4 · 学习 Diff

这些“说明卡”就是 VNode。它们很轻，只说明节点类型、属性、文字、children 和身份；此时浏览器页面尚未改变。

render 不是渲染到屏幕。它只计算新的 VNode 描述；真正修改屏幕发生在后面的提交阶段。
源码层：组件保存了什么旧状态？
组件实例把上次生成的 VNode 子树保存在 instance.subTree。本轮得到 nextTree 后，Renderer 执行 patch(prevTree, nextTree)。

第四站：Vue 比较的是“身份”，不只是文字

新旧描述放在一起后，Vue 看见 key 为 1、2、3 的任务仍然存在，于是继续使用原来的 DOM 节点和组件实例；key 为 4 是全新身份，需要创建。

任务 旧描述 新描述 决定
买牛奶 · key 1 有 有 复用原节点
回复邮件 · key 2 有 有 复用原节点
学习 Vue · key 3 有 有 复用原节点
学习 Diff · key 4 无 有 创建新节点

如果列表重新排序，key 仍能告诉 Vue“它只是换了位置”。这能保留输入框状态、组件内部状态和 DOM 引用。复杂列表怎样减少移动，在独立的 Diff 算法专题 中完整推演。

源码层：这一站的两个词
patch 是让旧节点变成新节点的总过程；patchKeyedChildren 是数组 children 的一条分支。Diff 先保证身份与最终顺序正确，再用最长递增子序列减少不必要移动。

第五站：决定完成后，浏览器才真正改变

变化检查员给出一条很小的施工单：

本轮 DOM 施工单

保留：前三个 li，不删除、不重建。

创建：一个文本为“学习 Diff”的 li。

插入：放到列表末尾。

事件：给新项补上复选框或删除按钮的监听器。

runtime-core 不直接依赖浏览器，它只说“创建、插入、设置属性”。runtime-dom 再把这些命令翻译成 createElement、insertBefore、DOM property、attribute 和 addEventListener。

为什么要分两层：“该改什么”是 Vue 通用规则；“怎样改浏览器”是 DOM 平台规则。分开后，同一套组件系统也能驱动测试内存树或自定义渲染平台。

第六站：DOM 之后仍有两道时间边界

“watch、ref、updated、nextTick 都在一起”并不准确。默认 watch（flush: 'pre'）在所属组件更新前进入主队列；组件 job 随后 render、patch DOM。DOM 提交后，模板 ref、updated 与 flush: 'post' watcher 才进入 post-flush 阶段。

默认 watch：主队列 PRE
与组件共享 uid，排在该组件 render job 前，因此读到的是更新前 DOM。
组件 job：render + patch
这一段真正创建、移动或更新 DOM，并在执行中登记后置任务。
post-flush：ref / updated / post watch
非空字符串或 Ref 型模板 ref 使用 id = -1，会先于普通 post callback； updated 与 post watcher 都在此阶段，不应依赖二者的笼统固定先后。
nextTick：flush Promise 之后
flushJobs 连同 post callbacks 与刷新中新增任务全部收敛后， await nextTick() 才恢复。

上面的“模板 ref”特指常见的字符串或 Ref 型非空赋值；函数 ref 会在 patch 调用 setRef 时同步执行，卸载时的 null 清理也同步完成。 

tasks.value.push(newTask)

await nextTick()
// 组件 DOM、模板 ref、updated 与本轮 post watcher 均已处理
// 但不代表浏览器已经完成绘制，也不等待业务 Promise

到这里，一次普通更新结束。以后每次状态变化都会重复“通知 → 排队 → 描述 → 比较 → 提交 → 收尾”的循环。

场景 普通流程哪里不同 用户看到什么

nextTick 绑定的是 currentFlushPromise；Promise 只有在上面整个 flushJobs 返回后才解决。因此 post 回调不是与 nextTick 并列执行，而是 nextTick 的前置阶段。模板 ref 的 id = -1 则解释了为何 post watcher 能读到已更新 ref。

出现问题时，先判断旅程卡在哪一站

现象 先检查 源码入口
数据变了，组件完全不更新 组件有没有真正读取该响应式值 trigger / effect scheduler
组件更新次数过多 任务是否去重、是否产生递归修改 queueJob / job.flags
列表输入状态串位 key 是否代表稳定业务身份 isSameVNodeType / patchKeyedChildren
页面正确但事件仍是旧逻辑 invoker.value 是否更新 patchEvent
nextTick 后仍不是预期 等待的是 Vue 更新还是业务 Promise currentFlushPromise

现在你应该能讲出的完整答案

数据变化时，Vue 根据依赖关系找到需要更新的组件；调度器把重复工作合并；组件用最新状态生成新的 VNode 描述；Renderer 比较新旧描述并用 key 维护身份；runtime-dom 只执行必要的浏览器操作；DOM 提交后处理 ref、生命周期与 post watcher，整轮 flush 结束后 nextTick 再继续。

不需要记住函数名，只要能顺着这六站讲清控制权怎样传递，就已经建立了完整 Runtime 心智模型。

7.1 RefImpl.set value 先判断“真的变了吗”

先补一个 JavaScript 细节：count.value++ 不是“只调用 setter”，而是先 调 getter 取 0，计算 1，再调 setter 写回。教程 handler 前面的 console.log 也读了一次 getter；但事件处理器运行时 activeSub 为空，所以这两次 dep.track() 都会提前返回， 不会把 handler 错记成订阅者。真正已有的订阅者来自首次组件 render。

set value(newValue) {

  const useDirectValue =
    this[ReactiveFlags.IS_SHALLOW] ||
    isShallow(newValue) ||

}

ReactiveEffect.notify() 用 NOTIFIED 去重并 batch(this)；最外层 endBatch() 调 ReactiveEffect.trigger()。本例 effect 有 scheduler，所以 直接调用 scheduler；这里还没有先跑 isDirty。 以下来自 packages/reactivity/src/effect.ts：前两段为连续原码摘录； endBatch 为真实源码删节摘录，只省略 computed 标志清理。 

notify(): void {
  if (
    this.flags & EffectFlags.RUNNING &&
    !(this.flags & EffectFlags.ALLOW_RECURSE)
  ) {
    return
  }
  if (!(this.flags & EffectFlags.NOTIFIED)) {
    batch(this)
  }
}

// ... 省略 ReactiveEffect 其余方法与批处理状态声明

export function batch(sub: Subscriber, isComputed = false): void {
  sub.flags |= EffectFlags.NOTIFIED
  if (isComputed) {
    sub.next = batchedComputed
    batchedComputed = sub
    return
  }
  sub.next = batchedSub
  batchedSub = sub
}
export function endBatch(): void {
  if (--batchDepth > 0) {
    return
  }

  // ... 省略 batchedComputed 的 NOTIFIED 清理

  let error: unknown
  while (batchedSub) {
    let e: Subscriber | undefined = batchedSub
    batchedSub = undefined
    while (e) {
      const next: Subscriber | undefined = e.next
      e.next = undefined
      e.flags &= ~EffectFlags.NOTIFIED
      if (e.flags & EffectFlags.ACTIVE) {
        try {
          ;(e as ReactiveEffect).trigger()
        } catch (err) {
          if (!error) error = err
        }
      }
      e = next
    }
  }

  if (error) throw error
}
trigger(): void {
  if (this.flags & EffectFlags.PAUSED) {
    pausedQueueEffects.add(this)
  } else if (this.scheduler) {
    this.scheduler()
  } else {
    this.runIfDirty()
  }
}

setupRenderEffect 早已把 scheduler 设成 () => queueJob(job)。因此同步链准确写法是： 

RefImpl.set
→ Dep.trigger / Dep.notify
→ ReactiveEffect.notify
→ batch / endBatch
→ ReactiveEffect.trigger
→ effect.scheduler()
→ queueJob(instance.job)

第八步：queueJob 为什么能合并更新

文件 / 符号：packages/runtime-core/src/scheduler.ts · queueJob/queueFlush。 输入：带组件 uid 的 instance.job。 状态：queue 增加任务，job 加 QUEUED，currentFlushPromise 从 null 变 Promise。 以下为连续原码摘录（源码说明注释未收录）： 

export function queueJob(job: SchedulerJob): void {
  if (!(job.flags! & SchedulerJobFlags.QUEUED)) {
    const jobId = getId(job)
    const lastJob = queue[queue.length - 1]
    if (
      !lastJob ||
      (!(job.flags! & SchedulerJobFlags.PRE) && jobId >= getId(lastJob))
    ) {
      queue.push(job)
    } else {
      queue.splice(findInsertionIndex(jobId), 0, job)
    }

    job.flags! |= SchedulerJobFlags.QUEUED

    queueFlush()
  }
}

function queueFlush() {
  if (!currentFlushPromise) {
    currentFlushPromise = resolvedPromise.then(flushJobs)
  }
}

同一同步栈里再写两次 count，第一次已把 job 标成 QUEUED；后两次在最外层 if 处退出。父组件 uid 通常更小，排序还能让父先更新；若父更新时 卸载子组件，子 job 会被标记 DISPOSED，出队时跳过。

微任务到来：job 先 runIfDirty

flushJobs 逐项调用 job；组件 job 正是 effect.runIfDirty.bind(effect)，所以此时才执行 isDirty → effect.run → componentUpdateFn。以下是 flushJobs 的真实源码删节摘录；只省略开发 check 的初始化，主 try/finally 与异常清理完整保留： 

function flushJobs(seen?: CountMap) {
  // ... 省略 __DEV__ seen 与 check 初始化

  try {
    for (flushIndex = 0; flushIndex < queue.length; flushIndex++) {
      const job = queue[flushIndex]
      if (job && !(job.flags! & SchedulerJobFlags.DISPOSED)) {
        if (__DEV__ && check(job)) {
          continue
        }
        if (job.flags! & SchedulerJobFlags.ALLOW_RECURSE) {
          job.flags! &= ~SchedulerJobFlags.QUEUED
        }
        callWithErrorHandling(
          job,
          job.i,
          job.i ? ErrorCodes.COMPONENT_UPDATE : ErrorCodes.SCHEDULER,
        )
        if (!(job.flags! & SchedulerJobFlags.ALLOW_RECURSE)) {
          job.flags! &= ~SchedulerJobFlags.QUEUED
        }
      }
    }
  } finally {
    for (; flushIndex < queue.length; flushIndex++) {
      const job = queue[flushIndex]
      if (job) {
        job.flags! &= ~SchedulerJobFlags.QUEUED
      }
    }

    flushIndex = -1
    queue.length = 0

    flushPostFlushCbs(seen)

    currentFlushPromise = null
    if (queue.length || pendingPostFlushCbs.length) {
      flushJobs(seen)
    }
  }
}

callWithErrorHandling 把组件更新异常送入组件错误管道；无论是否抛错， finally 都清剩余 QUEUED、清主队列、刷 post 队列。post callback 若又入队，函数递归收敛后才让本轮 Promise 完成。

第十一步：updated 为什么早于 nextTick

patch 完成后，componentUpdateFn 用 queuePostRenderEffect(u, parentSuspense) 登记 onUpdated。随后控制权回到 flushJobs.finally：

  1. 清主队列与 flags；
  2. flushPostFlushCbs(seen)，所以 onUpdated 此时读到 DOM=1；
  3. 若 post 又产生主任务，递归清空；
  4. flushJobs 返回，currentFlushPromise 才兑现；
  5. await nextTick() 的 continuation 才进入后续 Promise reaction。

packages/runtime-core/src/scheduler.ts · nextTick 连续原码摘录： 

export function nextTick<T, R>(
  this: T,
  fn?: (this: T) => R | Promise<R>,
): Promise<void | R> {
  const p = currentFlushPromise || resolvedPromise
  return fn ? p.then(this ? fn.bind(this) : fn) : p
}
nextTick 保证本轮 Vue 主队列与 post 队列已收敛；不保证浏览器已经 paint，也不等待 fetch、setTimeout 或任意业务 Promise。

第十二步：主线旁边的提前退出与异常

触发条件决定性源码分支状态结果本例若发生

最后，把整条链一口气讲清

初次 mount 创建组件 render effect，并直接运行一次：render 读 ref、建立依赖， patch(null, subTree) 创建 button，runtime-dom 绑定事件并插入 DOM。点击时， RefImpl 先同步改值并通过 Dep 通知 render effect；reactivity batch 结束后， effect.scheduler 把 runIfDirty job 放入 runtime-core 微任务队列。flushJobs 出队后重新 render，patch 复用原 button，修改文字和 aria；updated 在 post flush 看见新 DOM，整轮 flush 返回后 nextTick 才恢复。

继续读时按这条主线拆章： 组件与 render effect → scheduler → patch → DOM 平台层。列表增删移动再进入 keyed diff；它不是这个文本计数器主线的必经分支。

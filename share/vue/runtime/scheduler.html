Chapter 05 · Scheduler

为什么数据变了，页面却不是立刻变

Vue 会把同一瞬间发生的许多状态修改合并成一轮页面更新，并安排父组件、子组件和回调的正确顺序。Scheduler 就是这位时间管理员。

建议阅读 30 分钟353 行核心源码关键结构：SchedulerJob

三次修改，为什么通常只更新一次页面

count.value++
count.value++
count.value++

每次赋值都会通知组件“数据过期了”，但 Vue 不会立刻重画三次。它把同一个组件的更新任务去重，等当前同步代码结束后，用最终值统一更新一次。

立即执行

数据每改一次，就生成 VNode、比较并操作 DOM。中间两次结果用户根本看不到。

批量调度

三次通知合并成一个任务。组件读取最终 count = 3，只提交一次。

为什么还要排序

父组件更新可能让子组件换 props，甚至把子组件整个删除。如果子组件先更新，它可能用旧输入白做一次；父组件先执行后，已被删除的子任务可以直接跳过。

更新前
pre watcher 适合在组件 DOM 更新前响应数据。
主更新
父组件通常先于子组件，组件 job 在这里重新生成并提交页面。
更新后
updated、模板 ref、post watcher 此时可以读取稳定的新 DOM。
nextTick() 不是“等一毫秒”，而是等待当前这轮 Vue 更新队列完成。
核心目标有两个：少做重复工作；让必须发生的工作按正确顺序发生。异步微任务只是实现这两个目标的工具。
进入调度器数据结构与源码层

调度器维护的六条不变量

同一任务一轮只执行一次
多次状态写入通过 QUEUED 标志 O(1) 去重。
父组件先于子组件
组件 uid 作为 job.id；父实例先创建，因此 id 更小。
pre watcher 先于所属组件
相同 id 下 PRE 任务排在组件 render job 前。
post 回调看到已提交 DOM
mounted、updated、模板 ref 与 post watcher 在主队列结束后执行。
刷新期间新增任务仍会收敛
flush 末尾若队列不空，继续刷新而不是丢到未知时机。
异常不能污染下一轮
finally 清除队列与 QUEUED 位，错误后 nextTick 和后续更新仍可运行。

SchedulerJob：函数本身就是任务对象

Vue 不额外包装 Task 类，而是在函数上附加轻量元数据：

字段/标志 含义 典型来源
id 排序 ID；组件更新使用 instance.uid 组件 render job、pre watcher
i 所属组件实例，用于错误分类和递归诊断 组件 job
QUEUED 已在主队列或 post 队列，防止重复加入 所有调度任务
PRE 组件更新前任务；同 id 时排在 render job 前 默认 flush 的 watcher
ALLOW_RECURSE 执行期间允许再次入队 组件更新、watch callback
DISPOSED effect 或组件已停止，队列中仍存在也要跳过 停止 watcher、卸载组件

flags 使用位运算而不是多个 Boolean，一方面减少对象字段，另一方面让热路径能在一个整数上判断和清理状态。未初始化 flags 在位运算中会被视为 0。

queueJob：不做全量排序的有序插入

若新 job.id 不小于队尾 id 且不是 PRE，可以直接 push；否则通过二分查找插入位置。这样队列大部分时间保持有序，避免每轮 flush 前完整 sort。 

queueJob(job)
  if job.flags & QUEUED:
    return

  if 可以追加到队尾:
    queue.push(job)
  else:
    queue.splice(findInsertionIndex(jobId), 0, job)

  job.flags |= QUEUED
  queueFlush() // 只创建一个微任务

相同 id 下 PRE 为什么排前面

pre watcher 与所属组件 job 共用 uid。二分插入时，遇到相同 id 的 PRE 任务继续向后找，而普通 job 停在 PRE 之后，最终形成 [parent pre, parent render, child pre, child render]。

Watcher 的 flush 选项怎样映射到时间轴

配置 调度方式 能观察到的 DOM 适用场景
flush: 'pre' 带 PRE 标志进入主队列 所属组件更新前的 DOM 默认；根据状态派生下一步状态
flush: 'post' queuePostRenderEffect 组件本轮提交后的 DOM 测量布局、依赖模板 ref
flush: 'sync' trigger 时直接执行 尚未批量更新的 DOM 极少数同步桥接；可能重复执行

有 Suspense 时，post effect 不一定立即进入全局 post 队列。若当前分支仍 pending，它先缓存在 Suspense.effects，等分支 resolve 后再统一提交，保证钩子看到的是实际激活分支。

nextTick 等待的是当前 flush Promise

nextTick(fn?) 使用 currentFlushPromise || resolvedPromise。有更新时，它排在本轮 flushJobs 之后；没有更新时，它只是下一次微任务。它不是“等待浏览器绘制”，也不保证 requestAnimationFrame 已发生。 

state.value++
await nextTick()
// 组件主队列与 post 回调已经完成
// 但这不等价于浏览器已经完成一次视觉帧绘制

递归更新：允许合法收敛，拒绝无限循环

普通 effect 执行中再次触发自己通常是错误，例如读取数组时又 push。Vue 默认不允许自入队，但两类任务有合法需求：

  • 组件更新：父更新子 props，子的 pre watcher 又修改父 render 依赖，父可能需要再次调度才能收敛。
  • watch callback：回调本身不追踪依赖，用户可能有意把 source 分步归一化到稳定值。

ALLOW_RECURSE 只允许再次入队，开发模式的 CountMap 仍会限制同一 job 在一轮中的递归次数，并报告具体组件名。

2026 年的 #15143 修复了超大 post callback 数组导致的栈溢出。它说明调度器的成熟度不仅体现在顺序正确，也体现在任务规模增大时调用栈仍保持有界。

错误恢复为何是调度器的一等逻辑

job 通过 callWithErrorHandling 执行，但 flushJobs 自身仍使用 try/finally。原因是错误处理器可能选择继续抛出；即使如此，队列也必须重置长度、清 QUEUED、刷新已存在的 post callback，并让下一次 nextTick 获得新 Promise。

为什么不能在 catch 中简单 queue.length = 0？

当前索引之后的任务虽然不再执行，但它们的 QUEUED 位仍为真。若不逐个清理，后续相同任务永远无法再次入队，组件会永久停止更新。

为什么 post 回调也要按 id 排序？

组件生命周期与 ref 需要父子可预测顺序；嵌套 post callback 还可能在刷新期间加入新回调，因此必须统一去重和排序。

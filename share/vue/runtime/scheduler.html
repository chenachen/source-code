Chapter 05 · Scheduler

为什么数据变了，页面却不是立刻变

Vue 会把同一同步调用栈中的多次状态修改合并成一轮页面更新，并安排父组件、子组件和回调的执行顺序。 Scheduler 负责收集这些任务，在微任务中刷新。

建议阅读 30 分钟355 行核心源码关键结构：SchedulerJob

完整用例先行：同步触发两次 click，为什么只刷新一个组件 job

仍是同一个 Counter。测试在同一同步栈中连续调用两次 triggerEvent。第一次 click 把 count 写成 1 并将组件 job 入队；第二次 click 写成 2，但 job 已有 QUEUED 位，不重复加入。同步断言仍看到 button 0；微任务里的 flushJobs 执行 effect.runIfDirty 后才渲染 button 2；post 队列清空后 nextTick 才恢复。

沿源码看去重、微任务与 finally 恢复

以下为 Vue 3.5.41 连续原文，仅做 HTML 实体转义。

nextTick 等待当前 flush；没有 flush 时也让到微任务

export function nextTick<T, R>(
  this: T,
  fn?: (this: T) => R | Promise<R>,
): Promise<void | R> {
  const p = currentFlushPromise || resolvedPromise
  return fn ? p.then(this ? fn.bind(this) : fn) : p
}

QUEUED 位去重，并只创建一个刷新 Promise

export function queueJob(job: SchedulerJob): void {
  if (!(job.flags! & SchedulerJobFlags.QUEUED)) {
    const jobId = getId(job)
    const lastJob = queue[queue.length - 1]
    if (
      !lastJob ||
      // 常见父到子更新的 ID 单调递增，直接追加可避开二分与数组搬移。
      (!(job.flags! & SchedulerJobFlags.PRE) && jobId >= getId(lastJob))
    ) {
      queue.push(job)
    } else {
      queue.splice(findInsertionIndex(jobId), 0, job)
    }

    job.flags! |= SchedulerJobFlags.QUEUED

    queueFlush()
  }
}
function queueFlush() {
  if (!currentFlushPromise) {
    currentFlushPromise = resolvedPromise.then(flushJobs)
  }
}

flushJobs 用 try/finally 恢复主队列状态

scheduler.ts · flushJobs（完整连续函数） 
function flushJobs(seen?: CountMap) {
  if (__DEV__) {
    seen = seen || new Map()
  }

  // 开发分支必须在 try/catch 外决定。Rollup 会保守处理 try/catch 内代码，导致递归
  // 警告逻辑无法 tree-shaking；terser 也许能二次删除，但 esbuild #1610 等场景不会。
  // 提前选择 `check` 可让生产构建稳定消除整段开发逻辑。
  const check = __DEV__
    ? (job: SchedulerJob) => checkRecursiveUpdates(seen!, job)
    : NOOP

  try {
    for (flushIndex = 0; flushIndex < queue.length; flushIndex++) {
      const job = queue[flushIndex]
      if (job && !(job.flags! & SchedulerJobFlags.DISPOSED)) {
        if (__DEV__ && check(job)) {
          continue
        }
        if (job.flags! & SchedulerJobFlags.ALLOW_RECURSE) {
          job.flags! &= ~SchedulerJobFlags.QUEUED
        }
        callWithErrorHandling(
          job,
          job.i,
          job.i ? ErrorCodes.COMPONENT_UPDATE : ErrorCodes.SCHEDULER,
        )
        if (!(job.flags! & SchedulerJobFlags.ALLOW_RECURSE)) {
          job.flags! &= ~SchedulerJobFlags.QUEUED
        }
      }
    }
  } finally {
    // 即使中途出错，也清掉尚未执行任务的 QUEUED 位，使它们之后仍可重新入队。
    for (; flushIndex < queue.length; flushIndex++) {
      const job = queue[flushIndex]
      if (job) {
        job.flags! &= ~SchedulerJobFlags.QUEUED
      }
    }

    flushIndex = -1
    queue.length = 0

    flushPostFlushCbs(seen)

    currentFlushPromise = null
    // post 回调可能触发新更新；递归清空，保证 `nextTick()` resolve 前系统已稳定。
    if (queue.length || pendingPostFlushCbs.length) {
      flushJobs(seen)
    }
  }
}

三次修改，为什么通常只更新一次页面

count.value++
count.value++
count.value++

每次赋值都会通知组件“数据过期了”，但 Vue 不会立刻重画三次。它把同一个组件的更新任务去重，等当前同步代码结束后，用最终值统一更新一次。

立即执行

数据每改一次，就生成 VNode、比较并操作 DOM。中间两次结果用户根本看不到。

批量调度

三次通知合并成一个任务。组件读取最终 count = 3，只提交一次。

为什么还要排序

父组件更新可能让子组件换 props，甚至把子组件整个删除。如果子组件先更新，它可能用旧输入白做一次；父组件先执行后，已被删除的子任务可以直接跳过。

更新前
pre watcher 适合在组件 DOM 更新前响应数据。
主更新
父组件通常先于子组件，组件 job 在这里重新生成并提交页面。
更新后
updated、模板 ref、post watcher 此时可以读取稳定的新 DOM。
nextTick() 不是“等一毫秒”，而是等待当前这轮 Vue 更新队列完成。
核心目标有两个：少做重复工作；让必须发生的工作按正确顺序发生。异步微任务只是实现这两个目标的工具。
进入调度器数据结构与源码层

调度器维护的六条不变量

普通任务尚未出队时只保留一份
多次状态写入通过 QUEUED 标志 O(1) 去重；带 ALLOW_RECURSE 的任务是显式例外，可在执行前清标志并于同一轮再次入队。
父组件先于子组件
组件 uid 作为 job.id；父实例先创建，因此 id 更小。
pre watcher 先于所属组件
相同 id 下 PRE 任务排在组件 render job 前。
post 回调看到已提交 DOM
mounted、updated、模板 ref 与 post watcher 在主队列结束后执行。
刷新期间新增任务仍会收敛
flush 末尾若队列不空，继续刷新而不是丢到未知时机。
主队列异常后可重新入队
finally 清除剩余主任务的 QUEUED 位与主队列；post flush 正常返回后重置刷新 Promise，后续更新仍可运行。

SchedulerJob：函数本身就是任务对象

Vue 不额外包装 Task 类，而是在函数上附加轻量元数据：

字段/标志 含义 典型来源
id 排序 ID；组件更新使用 instance.uid 组件 render job、pre watcher
i 所属组件实例，用于错误分类和递归诊断 组件 job
QUEUED 单个主队列或 post job 已排队，防止重复加入；生命周期 hook 数组不会逐项设置此位 组件 render job、watch job、单个 post callback
PRE 组件更新前任务；同 id 时排在 render job 前 默认 flush 的 watcher
ALLOW_RECURSE 执行期间允许再次入队 组件更新、watch callback
DISPOSED 任务已被显式作废，队列中仍存在也要跳过 组件卸载；失效的 mount/post/ref/Teleport 回调

flags 使用位运算而不是多个 Boolean，一方面减少对象字段，另一方面让热路径能在一个整数上判断和清理状态。未初始化 flags 在位运算中会被视为 0。

queueJob：不做全量排序的有序插入

若新 job.id 不小于队尾 id 且不是 PRE，可以直接 push；否则通过二分查找插入位置。这样队列大部分时间保持有序，避免每轮 flush 前完整 sort。

相同 id 下 PRE 为什么排前面

pre watcher 与所属组件 job 共用 uid。二分插入时，遇到相同 id 的 PRE 任务继续向后找，而普通 job 停在 PRE 之后，最终形成 [parent pre, parent render, child pre, child render]。

一次 flush 的完整时间线

这里的“递归继续 flush”是队列层面的收敛，不等于允许单个 job 无限触发自己。后者由 ALLOW_RECURSE 与递归次数上限单独控制。

Watcher 的 flush 选项怎样映射到时间轴

配置 调度方式 能观察到的 DOM 适用场景
flush: 'pre' 带 PRE 标志进入主队列 所属组件更新前的 DOM 默认；根据状态派生下一步状态
flush: 'post' queuePostRenderEffect 组件本轮提交后的 DOM 测量布局、依赖模板 ref
flush: 'sync' trigger 时直接执行 尚未批量更新的 DOM 极少数同步桥接；可能重复执行

有 Suspense 时，post effect 不一定立即进入全局 post 队列。若当前分支仍 pending，它先缓存在 Suspense.effects，等分支 resolve 后再统一提交，保证钩子看到的是实际激活分支。

nextTick 等待的是当前 flush Promise

nextTick(fn?) 使用 currentFlushPromise || resolvedPromise。有更新时，它排在本轮 flushJobs 之后；没有更新时，它只是下一次微任务。它不是“等待浏览器绘制”，也不保证 requestAnimationFrame 已发生。

递归更新：允许合法收敛，拒绝无限循环

普通 effect 执行中再次触发自己通常是错误，例如读取数组时又 push。Vue 默认不允许自入队，但两类任务有合法需求：

  • 组件更新：父更新子 props，子的 pre watcher 又修改父 render 依赖，父可能需要再次调度才能收敛。
  • watch callback：回调本身不追踪依赖，用户可能有意把 source 分步归一化到稳定值。

ALLOW_RECURSE 只允许再次入队，开发模式的 CountMap 仍会限制同一 job 在一轮中的递归次数，并报告具体组件名。

#15143 把超大 post callback 数组的展开传参改成逐项追加。 普通入队和嵌套合并的百万回调用例都覆盖了这条路径，避免因函数参数过多产生栈溢出。

错误恢复为何是调度器的一等逻辑

job 通过 callWithErrorHandling 执行，但 flushJobs 自身仍使用 try/finally。主队列 job 的错误若经错误管道继续抛出，finally 仍会清除剩余主任务的 QUEUED 位、清空主队列并调用 post flush。 post flush 正常返回后先把 currentFlushPromise 置空，再同步递归处理新任务； 先前取得的 nextTick 仍要等整次 flushJobs 返回才兑现。

若 post 回调继续向外抛错，flushPostFlushCbs 中没有 finally 兜底，活动 post 队列与 currentFlushPromise 的复位会被中断。 此时刷新 Promise 拒绝并被保留，后续 queueFlush 无法预约新刷新。 因此上面的错误恢复用例覆盖主队列抛错且 post flush 能正常返回的路径。

为什么不能在 catch 中简单 queue.length = 0？

当前索引之后的任务虽然不再执行，但它们的 QUEUED 位仍为真。若不逐个清理，后续相同任务永远无法再次入队，组件会永久停止更新。

为什么 post 回调也要按 id 排序？

非空模板 ref 的赋值任务使用 id=-1，排在普通 post 回调前， 因此 mounted 和 post watcher 可以读取已赋值的模板引用。 mounted、updated 与普通 post watcher 通常没有 id，排序值为 Infinity， 相同值保持入队顺序。父子生命周期的子先父后来自 patch 的递归入队顺序， 并不是用组件 uid 排出来的。

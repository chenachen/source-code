照图复述一遍

  1. 先用 type+key 从两端收缩确定区，本例只锁住共同尾 key4。
  2. 新未知中段建 key→newIndex 表，让每个旧 keyed VNode O(1) 找到去向。
  3. 映射存“旧下标+1”，所以 0 可以无歧义表示全新节点；本例没有 0。
  4. 旧节点的新下标不再单调时，才设置 moved 并计算 LIS；没有乱序就省掉 O(n log n)。
  5. LIS [0,1] 表示 key2/key3 相对顺序已正确，保留它们能让 move 数最少。
  6. 倒序提交保证右侧 anchor 已经可靠；只需把 key1 插到 key4 前。

源码阶段 5.1/5.2：新 key 表、旧下标映射与 moved 检测

      const s1 = i // 旧未知中段起点。
      const s2 = i // 新未知中段起点。

      // 5.1 为新中段建立 key → 新下标映射，旧 keyed 节点可 O(1) 找到去向。
      const keyToNewIndexMap: Map<PropertyKey, number> = new Map()
      for (i = s2; i <= e2; i++) {
        const nextChild = (c2[i] = optimized
          ? cloneIfMounted(c2[i] as VNode)
          : normalizeVNode(c2[i]))
        if (nextChild.key != null) {
          if (__DEV__ && keyToNewIndexMap.has(nextChild.key)) {
            warn(
              `Duplicate keys found during update:`,
              JSON.stringify(nextChild.key),
              `Make sure keys are unique.`,
            )
          }
          keyToNewIndexMap.set(nextChild.key, i)
        }
      }

      // 5.2 遍历旧中段：找到新位置便 patch；找不到说明已删除，立即卸载。
      let j
      let patched = 0
      const toBePatched = e2 - s2 + 1
      let moved = false
      // 新下标不再单调递增即说明至少一个复用节点需要移动。
      let maxNewIndexSoFar = 0
      // `newIndexToOldIndexMap` 按新中段位置保存旧下标 + 1。0 专门表示新节点没有旧节点，
      // 同一数组随后也作为最长递增子序列输入，找出无需移动的最大稳定集合。
      const newIndexToOldIndexMap = new Array(toBePatched)
      for (i = 0; i < toBePatched; i++) newIndexToOldIndexMap[i] = 0

      for (i = s1; i <= e1; i++) {
        const prevChild = c1[i]
        if (patched >= toBePatched) {
          // 所有新节点都已匹配，剩余旧节点只能是删除项。
          unmount(prevChild, parentComponent, parentSuspense, true)
          continue
        }
        let newIndex
        if (prevChild.key != null) {
          newIndex = keyToNewIndexMap.get(prevChild.key)
        } else {
          // 无 key 节点只能线性寻找尚未占用、type 相同的新节点。
          for (j = s2; j <= e2; j++) {
            if (
              newIndexToOldIndexMap[j - s2] === 0 &&
              isSameVNodeType(prevChild, c2[j] as VNode)
            ) {
              newIndex = j
              break
            }
          }
        }
        if (newIndex === undefined) {
          unmount(prevChild, parentComponent, parentSuspense, true)
        } else {
          newIndexToOldIndexMap[newIndex - s2] = i + 1
          if (newIndex >= maxNewIndexSoFar) {
            maxNewIndexSoFar = newIndex
          } else {
            moved = true
          }
          patch(
            prevChild,
            c2[newIndex] as VNode,
            container,
            null,
            parentComponent,
            parentSuspense,
            namespace,
            slotScopeIds,
            optimized,
          )
          patched++
        }
      }

keyToNewIndexMap 是查找表； newIndexToOldIndexMap 才是 LIS 输入。本例按旧节点顺序写成 [2,3,1]；newIndex 从 2 降到 0 时 moved 变为 true，之后不会再变回 false。

核心算法：getSequence 返回的是下标序列

function getSequence(arr: number[]): number[] {
  const p = arr.slice()
  const result = [0]
  let i, j, u, v, c
  const len = arr.length
  for (i = 0; i < len; i++) {
    const arrI = arr[i]
    if (arrI !== 0) {
      j = result[result.length - 1]
      if (arr[j] < arrI) {
        p[i] = j
        result.push(i)
        continue
      }
      u = 0
      v = result.length - 1
      while (u < v) {
        c = (u + v) >> 1
        if (arr[result[c]] < arrI) {
          u = c + 1
        } else {
          v = c
        }
      }
      if (arrI < arr[result[u]]) {
        if (u > 0) {
          p[i] = result[u - 1]
        }
        result[u] = i
      }
    }
  }
  u = result.length
  v = result[u - 1]
  while (u-- > 0) {
    result[u] = v
    v = p[v]
  }
  return result
}

参数是旧下标+1数组，0 被忽略；返回值是原数组位置。对 [2,3,1]，result 先变 [0,1]，读到 1 后只把长度 1 候选尾替换成位置 2，最终回溯仍得到 [0,1]。

正常复杂路径两边中段都非空：建表、patch/卸载旧项、按需 LIS、倒序 mount/move。
提前退出路径头尾同步后旧序列先耗尽，只挂新增；新序列先耗尽，只卸载旧项；moved=false 时完全跳过 getSequence。
错误/退化路径开发环境重复 key 发出警告，后写 key 覆盖前写映射，身份不再可靠；无 key 节点退化为线性寻找，宿主 move 抛错则向上传播且无事务回滚。
清理路径旧 key 在新表找不到立即 unmount；所有新节点已匹配后剩余旧节点也逐个 unmount，组件 scope/ref/钩子随递归清理。

先操作列表，观察 Vue 要做的决定

下面每个任务都有一个稳定 id，也就是模板中的 key。点击不同变化，注意“复用、移动、新建、删除”不是一回事。每项显示的 DOM 编号来自真实 li 对象；编号不变就表示节点没有重建。

任务列表

    Diff 不是重新画列表，而是给每个旧节点安排去向：留下、更新、移动或离开。

    不用算法术语，也能先理解四条规则

    先确认身份
    同一种节点且 key 相同，才可能是原来的任务；文字相同不代表身份相同。
    两边没变的先跳过
    列表开头和结尾经常保持不变，先处理它们，真正困难的范围会迅速缩小。
    中间按 key 找旧朋友
    新列表给出 key 的新位置；扫描旧列表就能知道谁消失、谁留下、谁换了位置。
    能不移动的尽量不移动
    留下的节点中，总有一批相对顺序已经正确。Vue 保持这批节点，移动其余节点。
    把列表想成重新排座位

    学生胸牌是 key。老师先确认门口和窗边没换的人；再给中间学生查新座位；找到一条已经按新顺序坐好的最长队伍，让他们不动；最后把新同学和位置不对的人从后往前安排到已有同学前面。

    读完主线用例与源码后应能回答：key 用来说明身份；Diff 先复用、再删除/新增、最后减少移动；最长递增子序列只是寻找“最多可以不动的人”。

    为什么 Renderer 需要专门的 Diff

    每次 render 都会生成一棵新的 VNode 树。如果直接删除旧 DOM、重建新 DOM，界面结果可能正确，但会丢失大量运行时状态：输入框选区、滚动位置、原生元素状态、组件实例、KeepAlive 缓存、Transition 阶段，以及用户持有的节点引用。

    因此 Diff 的目标不是单纯追求最少编辑距离，而是同时满足四个约束：

    IDENTITY

    身份正确

    type + key 相同的 VNode 才能代表同一逻辑节点，组件实例和 DOM 才允许复用。

    ORDER

    最终顺序正确

    新 children 的逻辑顺序必须映射到真实宿主顺序，包括 Fragment 锚点范围。

    MINIMAL HOST WORK

    减少宿主操作

    VNode 比较很便宜，真实 DOM 创建、删除和移动更昂贵，应尽量复用并少 move。

    LIFECYCLE

    生命周期正确

    新增才 mount，消失才 unmount，移动不能触发组件重新创建。

    Vue 的 Diff 是带业务语义的树协调算法。它比较的不只是标签字符串，还要维护组件、指令、ref、Transition、Teleport 和 Suspense 的运行时协议。
    本地：renderer.ts 本地：rendererChildren.spec.ts GitHub：patchKeyedChildren

    第一原则：key 参与定义节点身份

    isSameVNodeType(n1, n2) 的核心判断是 n1.type === n2.type && n1.key === n2.key。type 相同但 key 不同，仍被视为两个节点；key 相同但 type 不同，也不能复用。

    旧 VNode 新 VNode 是否复用 原因
    <li key="a"> <li key="a"> 是 type 与 key 都相同
    <li key="a"> <li key="b"> 否 逻辑身份不同
    <Foo key="a"> <Bar key="a"> 否 组件类型不同
    <Foo> <Foo> 通常是 无 key 时按位置和 type 猜测身份

    为什么数组索引通常不是好 key

    当列表插入、删除或排序后，同一索引对应的数据已经变了，但 key 仍相同。Renderer 会复用错误的组件实例或 DOM 状态。key 应表示数据的稳定业务身份，而不是它本轮所在的位置。

    key 的主要作用不是“让 Map 查找更快”，而是向 Runtime 声明身份。查找优化只是这个声明带来的副产品。

    进入 keyed diff 前，先排除简单形态

    patchChildren 先根据 shapeFlag 区分文本、数组与空 children。只有“旧数组 → 新数组”才需要列表 Diff。

    旧 children 新 children 处理 是否进入 keyed diff
    文本 文本 比较字符串，必要时 setElementText 否
    数组 文本 unmountChildren，再设置文本 否
    文本/空 数组 清空文本，mountChildren 否
    数组 空 unmountChildren 否
    数组 数组 按 patchFlag 选择 keyed、unkeyed 或保守 Diff 是/可能

    keyed 与 unkeyed 的根本区别

    UNKEYED

    位置就是临时身份

    按相同索引 patch 公共长度，再新增或删除尾部。适合节点只按位置更新、不会重排的列表。

    KEYED

    key 是稳定身份

    节点可跨索引复用，算法需要查找新位置、识别移动，并维护真实 DOM 顺序。

    Vue 3 keyed diff 的整体思路

    Vue 3 并不是简单沿用 Vue 2 的“四指针交叉比较”。它先同步稳定的头尾，再对中间未知区间使用 key Map 和最长递增子序列。

    PATCH KEYED CHILDREN · 8 PHASES
    同步头部
    从左向右 patch 连续相同节点。
    同步尾部
    从右向左 patch 连续相同节点。
    旧序列耗尽
    剩余新节点全部 mount。
    新序列耗尽
    剩余旧节点全部 unmount。
    建立 key Map
    记录未知新区间 key → newIndex。
    扫描未知旧区间
    复用可匹配节点，删除不存在节点。
    计算 LIS
    只在确实 moved 时寻找可保持原位的最大集合。
    倒序提交
    新增缺失节点，移动不在 LIS 中的节点。 
    // 机制伪代码：只列阶段，不是 Vue 源码
patchKeyedChildren(c1, c2, container, parentAnchor, ...)
  i = 0
  e1 = c1.length - 1
  e2 = c2.length - 1

  sync from start
  sync from end

  if old exhausted: mount remaining new
  else if new exhausted: unmount remaining old
  else:
    build keyToNewIndexMap
    scan old unknown range
    build newIndexToOldIndexMap
    if moved: increasingNewIndexSequence = getSequence(map)
    walk new unknown range backwards
      mount missing nodes
      move reused nodes not in LIS

    阶段一、二：同步头尾不是双端乱猜

    很多真实更新只改变列表局部。例如尾部追加、头部插入、中间替换。连续同步头尾能用 O(k) 成本排除大量稳定区域，并直接 patch 它们。

    EXAMPLE · STABLE EDGES
    旧 children
    abcdefg
    新 children
    abechfg

    a、b 从头部同步，g、f 从尾部同步。未知区间被缩小为旧 [c,d,e] 与新 [e,c,h]。注意：Vue 3 的尾部同步只比较“旧尾与新尾”，不会像 Vue 2 那样在这一阶段尝试旧头与新尾交叉匹配。

    提前结束的两个快路径

    • 若头尾同步后 i > e1，旧区间耗尽：把剩余新节点插到已知 anchor 前。
    • 若 i > e2，新区间耗尽：卸载剩余旧节点。

    只有两边都还有未知节点，才进入最复杂的中间区间处理。

    阶段五、六：把未知区间转成索引问题

    1. 建立 keyToNewIndexMap

    Vue 先遍历新未知区间，把有 key 节点记录为 key → newIndex。开发模式还会检查重复 key，因为两个新节点声明同一身份会让复用关系不确定。 

    // 手算记号，不是 Vue 源码
新未知区间 [e, c, h]

keyToNewIndexMap = {
  e → 2,
  c → 3,
  h → 4
}

    2. 创建 newIndexToOldIndexMap

    数组长度等于待 patch 新节点数量，初始全为 0。值记录“该新节点对应的旧索引 + 1”。加 1 是因为旧索引 0 是合法值，而 0 需要保留为“没有旧节点”的哨兵。

    3. 扫描旧未知区间

    有 key 的旧节点通过 Map O(1) 找新索引；无 key 的旧节点只能在新未知区间寻找尚未匹配且 type 相同的节点。找不到新位置的旧节点立即 unmount；找到则 patch，并把旧索引写入映射。

    SCAN RESULT
    旧 c → 新索引 3可复用，patch(c, c)；记录到映射第二格。
    旧 d → 找不到新列表已不存在 d，立即 unmount。
    旧 e → 新索引 2可复用，patch(e, e)；但新索引从 3 回退到 2，说明发生移动。
    新 h → 没有旧来源映射保持 0，最后一阶段再 mount。

    newIndexToOldIndexMap = [5, 3, 0]

    moved 如何被快速发现

    扫描旧节点时记录目前见过的最大 newIndex。若下一个匹配节点的新索引小于最大值，说明旧节点顺序映射到新列表后不再单调递增，至少有节点要移动。没有回退则无需计算 LIS。

    阶段七：最长递增子序列到底解决什么

    此时算法已经知道每个旧节点的新位置，Diff 的正确性已经确定。LIS 只用于减少 DOM move：从 newIndexToOldIndexMap 找到值递增的最长子序列，这些节点在旧树中的相对顺序与新树一致，可以保持原位。

    LIS 不是 Vue Diff 的全部，也不负责找新增和删除。它只在未知中间区间、确认发生移动之后，用来选择“最大的不移动集合”。

    为什么忽略 0

    0 代表新节点没有旧来源，必然需要 mount，不属于可复用节点序列。

    getSequence 的 O(n log n) 思路

    • result 保存不同长度递增子序列的最小尾值索引。
    • 当前值大于 result 尾值时直接追加。
    • 否则二分查找第一个不小于当前值的位置并替换，使未来更容易延长。
    • p 保存前驱索引，最后从 result 尾部回溯出真实子序列索引。 
    // 手算记号，不是 Vue 源码；输入是索引映射，不是 key 本身
newIndexToOldIndexMap = [5, 3, 0]

忽略 0 后，5 → 3 不是递增
LIS 长度为 1，算法会保留其中一个节点原位
其余已复用节点通过 hostInsert 移动

    即使 LIS 有多个同长度答案，选择任意一个都能得到最少移动次数；具体保留哪个节点由 getSequence 的更新策略决定。

    阶段八：为什么必须倒序插入和移动

    新未知区间从右向左处理。当前节点的 anchor 是“新列表中的下一个节点”的 el；若当前已是整个 children 尾部，则使用 parentAnchor。 

    // 机制伪代码：省略参数与边界，不是 Vue 源码
for (i = toBePatched - 1; i >= 0; i--) {
  nextIndex = s2 + i
  nextChild = c2[nextIndex]
  anchor = nextIndex + 1 < l2 ? c2[nextIndex + 1].el : parentAnchor

  if (newIndexToOldIndexMap[i] === 0)
    patch(null, nextChild, container, anchor) // 新增
  else if (moved && i 不在 LIS)
    move(nextChild, container, anchor)        // 移动
}

    倒序的关键是：处理当前节点时，它右侧的新节点已经处于正确位置，因此 anchor 一定可靠。若从左向右，当前节点的“下一个新兄弟”可能尚未移动或挂载。

    DOM move 为什么可以复用 insertBefore

    对已经在 DOM 中的节点再次调用 insertBefore(node, anchor)，浏览器会移动节点，而不是复制。Renderer 的 move 再根据 VNode 类型扩展这条语义：组件移动 subTree，Fragment 移动整个锚点范围，Teleport 与 Suspense 走自己的协议。

    迁移练习：把主线方法用于第二组输入

    这一节不是新的主证据链，而是读完 [1,2,3,4]→[2,3,1,4] 后的扩展练习：从 [a,b,c,d,e,f,g] 到 [a,b,e,c,h,f,g]。先自己填写变量，再与下面过程核对。

    同步头尾

    a、b 从头部复用；g、f 从尾部复用。剩余旧 [c,d,e] 与新 [e,c,h]。

    abcdefg

    新 key Map 与索引表

    keyToNewIndexMap = {e→2, c→3, h→4}；newIndexToOldIndexMap 初始 [0,0,0]。

    e:0c:0h:0

    扫描旧未知区间

    c 匹配并 patch；d 无匹配，unmount；e 匹配并 patch。索引表变为 [5,3,0]，且 newIndex 发生回退，所以 moved = true。

    e:5c:3h:0d

    从右向左提交

    1. h 没有旧来源：在 f 前 mount h。
    2. c 位于 LIS：保持不动。
    3. e 不在 LIS：移动到 c 前。
    abechfg
    整个过程中 a、b、c、e、f、g 的 VNode 都执行 patch 并复用原节点；d 才真正卸载，h 才真正创建，e 只执行移动。这就是身份与最少宿主操作同时成立的结果。

    复杂度与性能边界

    阶段 时间复杂度 额外空间
    同步头尾 O(n) O(1)
    建立新 key Map O(m) O(m)
    扫描旧未知区间 有 key 通常 O(n)；无 key 可能退化 O(m)
    最长递增子序列 O(m log m) O(m)
    倒序提交 O(m) O(1) 额外

    对稳定唯一 key 的常见列表，整体可视为 O(n log n)，且 LIS 只在 moved 为真时计算。无 key 节点混入 keyed 列表时，为寻找相同 type 的未匹配节点可能出现嵌套扫描，因此稳定 key 同时提升语义可靠性和性能可预测性。

    编译器怎样帮 Diff 跳过不必要判断

    KEYED_FRAGMENT

    明确存在 key

    Renderer 直接调用 patchKeyedChildren，不再猜测 children 类型。

    UNKEYED_FRAGMENT

    明确按位置更新

    使用 patchUnkeyedChildren，只 patch 公共长度和处理尾部差异。

    STABLE_FRAGMENT

    结构稳定

    结合 dynamicChildren 执行 patchBlockChildren，不完整遍历静态后代。

    BAIL

    优化前提失效

    回退完整 Diff，确保手写 render、动态 slot 或异常边界仍保持正确。

    编译器优化没有创造另一套 Diff 语义，而是提前证明某些分支不可能发生。Runtime 仍保留完整算法作为正确性基线。

    七个常见误解

    1. “Vue 使用双端 Diff，所以会比较旧头和新尾”

    这是常见的 Vue 2 描述。Vue 3 先同步同向头尾，再对未知区间使用 Map + LIS，不依赖四种头尾交叉启发式。

    2. “key 只是性能提示”

    key 是身份声明。错误 key 会复用错误状态，即使最终 DOM 文本看起来正确，也可能污染组件实例、输入状态和过渡。

    3. “LIS 就是 Vue Diff”

    LIS 只负责减少已复用节点的移动。身份匹配、新增、删除、patch 与 anchor 都由其他阶段完成。

    4. “没有 key 就会全部重建”

    无 key 列表按索引 patch 公共长度，仍会复用同位置同 type 节点；问题是数据重排时身份无法可靠保持。

    5. “移动节点等于删除再创建”

    DOM insertBefore 可以移动已有节点；组件 move 的是 subTree，不会重新 setup 或触发 mount/unmount。

    6. “Diff 只比较 DOM 元素”

    VNode 还可能是组件、Fragment、Teleport 或 Suspense。move/unmount 会继续分派到各自运行时协议。

    7. “算法追求理论最小编辑距离”

    Vue 选择线性扫描、Map 与 LIS 的工程折中，重点是稳定 O(n log n) 行为、最少 DOM move 和可维护的组件语义。

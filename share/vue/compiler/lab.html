01 / Setup

先学会只跑相关测试

整个 compiler 测试很快，但单文件/单标题更适合反复观察。

运行前提：从 source-code-analysis 项目根执行一次 cd vue，进入能看到 pnpm-workspace.yaml 的目录。使用 Node.js 20.x（至少 20.19）或 22.12 及以上版本，以及仓库锁定的 pnpm，并先执行 pnpm install。后续命令与路径均从这个目录计算。

cd vue

# 后续命令均在这个目录执行
node --version        # Node 20.x 至少 20.19，或 22.12+
pnpm --version
test -d node_modules  # 失败则先 pnpm install

# 类型检查
pnpm check

# 四个 compiler 包
node node_modules/vitest/vitest.mjs run \
  packages/compiler-core/__tests__ \
  packages/compiler-dom/__tests__ \
  packages/compiler-sfc/__tests__ \
  packages/compiler-ssr/__tests__ \
  --project unit

# 单个测试文件
node node_modules/vitest/vitest.mjs run \
  packages/compiler-core/__tests__/transforms/vFor.spec.ts \
  --project unit

# 只跑匹配标题
node node_modules/vitest/vitest.mjs run \

标题过滤是正则并匹配包含文件/suite 前缀的完整测试名，因此只锚定末尾； 本命令在 3.5.41 应显示 defineProps > w/ type 且汇总为 1 passed。只看退出码不够： 拼错 -t 时，Vitest 可能报告 0 tests，却仍未替你验证目标断言。

优先复制现有测试

它已经准备好 compiler options、AST 断言与快照规范，减少环境噪音。

同时看三个结果

parse AST、transform/codegenNode、最终 code。不要只盯字符串快照。

一次改变一个变量

静态指令参数 :id → 动态参数 :[name]、顶层绑定 → 局部绑定、单根 → 多根，差异最清晰。

02 / Lab 0 · Guided Start

第一遍别跳步：亲手编译一个 button

这一节提供可直接运行的测试、固定输入、逐阶段检查点、真实输出和失败诊断。 完成后再进入后面五组自由实验。

完成标准

不要求背 API。你要能回答五个问题：parser 留下了什么；transform 改了什么；三个 helper 为什么出现；数字 9 为什么是 TEXT | PROPS；非法表达式如何从 parser 交给调用方。

第 0 步：确认你站在正确目录

完成上面的准备后，继续在 source-code-analysis/vue/ 目录执行，无需再次切换目录。先让测试自己打印当前 3.5.41 的真实 render 产物，不手抄预期。 

# Node 20.x 至少 20.19，或 22.12+。
node --version

VUE_COMPILER_TUTORIAL_TRACE=1 \
node node_modules/vitest/vitest.mjs run \
  packages/compiler-dom/__tests__/tutorial.spec.ts \
  --project unit --reporter=verbose
先核对终点：应看到 Test Files 1 passed、Tests 2 passed，以及一份 export function render。若只看到 0 tests，当前目录、文件路径或 --project unit 至少有一项不对。

第 1 步：只读输入，先写下预测

同一输入故意执行两次：parse() 保存未经转换的阶段快照； compile() 内部重新 parse，并原地 transform 第二棵树。若只保留 result.ast，你看到的表达式已经加了 _ctx.，也已经有 codegenNode，不能再冒充 Parse AST。

先预测 props

:disabled 应是 Directive(bind)，arg=disabled，exp=busy； @click 应是 Directive(on)，arg=click，exp=count++。

先预测 children

button 有 Text(Count: ) 和 Interpolation(count) 两个 child。parser 此时不决定 patchFlag。

先预测动态维度

busy 改变会写 DOM prop，count 改变会写文本；click handler 不捕获 v-for/v-slot 局部量，可以按组件实例缓存。

第 2 步：核对 Parse AST，不看生成代码

路径 当前值 为什么现在只能知道这些
root.children[0] Element(button) parser 识别模板结构，不创建运行时 VNode。
button.props[0] bind / disabled / busy 指令名、参数、表达式都保留源码语义。
button.props[1] on / click / count++ 是否缓存要等 transform 检查作用域和选项。
button.children Text + Interpolation transformText 稍后才会把相邻文本拼成复合表达式。
表达式 content busy / count++ / count 原始 parse 快照尚未执行自由标识符前缀改写。
常见误判：AST 里出现 Directive 不代表运行时一定保留指令。 v-bind、v-on 都能在编译期降成普通 props；只有 transform 返回 needRuntime 或遇到自定义指令时，才需要 withDirectives。

第 3 步：沿真实总装线走到 transform

3.1 先建立转换顺序

core 先放结构、作用域、表达式、元素和文本转换；compiler-dom 再把平台转换追加进 options，并用 DOM 版 on/model 覆盖同名指令转换。

3.2 进入阶段先改表达式

transformExpression 把自由名字改成 _ctx.busy、_ctx.count。若名字在 v-for/v-slot 局部作用域中，identifiers 计数会阻止前缀。

3.3 退出阶段汇总元素

transformElement 返回 exit callback，等 children 已处理完再构造 VNodeCall。这样它能同时看到复合文本、props、缓存表达式和 patchFlag。

3.4 Root 固化账本

transform 结束把 context 中 helpers、hoists、cached 写回 RootNode。generate 无需再遍历模板判断动态性，只打印账本和 codegenNode。

同一份 SOURCE 在四个阶段中的身份

模板文本button + bind + on + interpolation
→
Parse AST原始名字、节点、loc
→
Transform_ctx / helpers / cache / flag
→
Generaterender(_ctx, _cache)

第 4 步：手算三个账本

账本 本例结果 逐项来源
helpers 3 Interpolation 登记 toDisplayString；单元素动态根转为 block，登记 openBlock 与 createElementBlock。
cached 1 click 表达式只引用组件上下文 count，不捕获模板局部量； cacheHandlers 允许放入 _cache[0]。
hoists 1 动态 prop 名集合稳定，提升为 const _hoisted_1 = ["disabled"]；busy 的值仍在每次 render 求值。
patchFlag 9 1 /* TEXT */ | 8 /* PROPS */ = 9。事件已缓存，不再让 onClick 成为每轮动态 prop。

第 5 步：逐段读真实生成结果

教程测试在 Vue 3.5.41 打印的完整 code 
import { toDisplayString as _toDisplayString, openBlock as _openBlock, createElementBlock as _createElementBlock } from "vue"

const _hoisted_1 = ["disabled"]

export function render(_ctx, _cache) {
  return (_openBlock(), _createElementBlock("button", {
    disabled: _ctx.busy,
    onClick: _cache[0] || (_cache[0] = $event => (_ctx.count++))
  }, "Count: " + _toDisplayString(_ctx.count), 9 /* TEXT, PROPS */, _hoisted_1))
}
  1. 1
    imports 是 helper 账本的打印结果。没有调用的 runtime 能力不会导入；事件本例被编译成普通函数，不需要额外 helper。
  2. 2
    _hoisted_1 只保存动态 prop 名。runtime 用它直接定位 disabled；它不是把整个 button 或动态值提升出 render。
  3. 3
    _cache 属于组件实例。第一次 render 创建 handler，之后 render 复用同一函数身份；count 仍在事件触发时从 _ctx 读取。
  4. 4
    patchFlag 和 dynamicProps 是运行时协议。更新时可跳过完整 props/children 比较，只更新文本与 disabled。

第 6 步：故意制造一个错误

const errors = []
const result = compile('<div :id="user +"></div>', {
  mode: 'module',
  prefixIdentifiers: true,
  onError: error => errors.push(error),
})

// errors[0].code === ErrorCodes.X_INVALID_EXPRESSION
// errors[0].loc.start.offset === 10
// errors[0].loc.source === ''：这里是表达式起点的零长度诊断位置
// result.code 仍可检查，因为调用方选择了“收集”，没有采用默认抛错处理器。
错误链：prefixIdentifiers 让 parser 预解析表达式 → Babel 在 user + 末尾失败 → emitError(X_INVALID_EXPRESSION) 用表达式起点构造零长度 loc → 自定义 onError 收集诊断 → transform 看到 exp.ast === false，不重复报告。删除 onError 后，默认处理器会立刻抛错。

第 7 步：一次只改一个变量

只做这项修改 运行前预测 重点核对
删除 @click="count++" cached 从 1 变 0 输出不再出现 _cache[0]；9 仍由 TEXT|PROPS 构成。
把 :disabled="busy" 改成静态 disabled PROPS 消失，只剩 TEXT patchFlag 变 1；动态 prop 名数组不再需要。
把 button 外包一层 v-if="ok" 出现条件分支和注释占位 观察 IfNode、分支 key、createCommentVNode 与根 codegenNode。
把 click 放进 v-for="item in items" 并读取 item handler 不能跨迭代缓存 item 不加 _ctx；hasScopeRef 阻止复用捕获不同 item 的闭包。
卡住时按症状定位

  • 报找不到测试文件：确认当前目录是 vue/，不是 share/vue/compiler/。
  • 测试数为 0：保留完整文件路径和 --project unit，不要只看退出码。
  • 生成 code 与本页不同：先检查 package.json version 和当前 commit； 其他 Vue 版本应以该版本源码与测试为准。
过关自测：合上本页，尝试只凭模板写出 raw Directive/Interpolation、三个 helper、一个 cache、一个 hoist 和数字 9 的来源；再打开测试逐项核对。五项都能解释，才进入 Lab 1。

03 / Lab 1

Parse：手画 AST，再看 location

目标是区分 tokenizer 边界、parser 组装与平台 options，而不是记住所有状态。 

<svg>
  <foreignObject>
    <div :id="key">{{ value }}</div>
  </foreignObject>
</svg>

先预测节点类型

Root → Element(svg) → Element(foreignObject) → Element(div) → Interpolation。

预测 namespace

svg 与 foreignObject 属于 SVG；foreignObject 的 child div 回到 HTML。

拆 Directive

:id 归一化为 Directive(bind)，arg 是静态属性名 id，exp 是动态属性值 表达式 key。只有 :[key]="value" 的 arg 才是动态参数。

核对 location

检查 div、arg、exp、interpolation 的 source 与 offset 是否只覆盖对应片段。

制造残缺输入

删除最后两个结束标签，观察 errors 与恢复 AST；再比较 IDE 为什么仍可使用该结构。

观察点：namespace 是 parser options 的父上下文计算；Directive 的拆分由 tokenizer 状态完成；错误恢复后 root.loc 仍覆盖完整输入。
用半开区间核对坐标 
<div :id="key">{{ value }}</div>
01234567890123456789012345678901

Directive.loc  [5, 14)  → :id="key"
arg.loc        [6,  8)  → id

04 / Lab 2

Transform：证明顺序为什么不能交换

选择同时包含 v-for 局部变量、事件闭包与动态文本的模板。

<button
  v-for="(item, index) in items"
  :key="item.id"
  @click="select(item, index)"
>
  {{ item.label }}
</button>

进入 v-for 后

  • 原 Element 被 ForNode 包裹。
  • source=items。
  • item/index 加入 identifiers。
  • 子元素保留 key 指令等待元素转换。

离开子元素后

  • item/index 不加 _ctx。
  • items/select 加上下文访问。
  • handler 捕获循环 scope，不能全局 cache。
  • Fragment 根据 key 选择 KEYED_FRAGMENT。
尝试变化 预期变化 对应源码
删除 :key Fragment 从 KEYED 变 UNKEYED vFor.ts
handler 不引用 item/index 在允许条件下更可能 cache vOn.ts + hasScopeRef
把 item.label 换静态文本 子 VNode 不再需要 TEXT flag transformText / transformElement
外套 v-if 结构转换形成 IfNode 与 ForNode 嵌套 vIf.ts + vFor.ts 顺序

06 / Lab 4

SSR：比较产物，不比较实现

用同一模板对照 DOM render 与 SSR _push，找出两边共同维护的节点协议。 

<ul v-if="ok" class="list">
  <li v-for="item in items" :key="item.id">
    {{ item.name }}
  </li>
</ul>
语义 客户端 SSR
v-if 条件 VNode block 与分支 key if statement；无 else 时注释占位
v-for renderList + keyed Fragment ssrRenderList + Fragment 注释边界
静态 class 静态 props，可提升 直接进入开始标签字符串
插值 toDisplayString + TEXT flag ssrInterpolate + HTML 转义
key 参与客户端 diff 通常不输出 HTML 属性，但节点顺序仍要一致
核心问题：哪些差异只是目标不同，哪些差异会破坏 hydration？key 不出现在 HTML 中是正常差异；漏掉列表 Fragment 边界可能是拓扑错误。

07 / Lab 5

Issue：从最小回归倒推不变量

选择已有 issue 注释，不先看修复代码，按失败类型建立假设。

读测试标题与中文场景注释

提取输入、错误表现、涉及的两个以上特性。

归类失败模式

状态泄漏、作用域误判、结构邻接、平台修正、优化过度、同构错位。

找最早错误阶段

先比较 descriptor/parse AST，再比较 codegenNode，最后才看生成代码。

预测修复点

是补 reset/cache key，还是调整 transform enter/exit，或降低 ConstantTypes？

再看上游 git blame/log

在 vuejs/core 的完整克隆中查看该处历史，确认修复为何位于该层，并检查后续是否有同类回归。

推荐一：表达式作用域

从 transformExpressions、vOn 或 props destructure 中选择函数参数/解构 issue。

推荐二：类型缓存

从 resolveType 中选择 global scope、tsconfig 或先后编译顺序 issue。

推荐三：Hydration

从 TransitionGroup、HTML nesting、fallthrough attrs 中选择边界 issue。

10 / Glossary

核心术语

这些词在不同文件中反复出现；理解协议含义比翻译名称更重要。

Template AST

parser 产出元素、属性/指令、文本、插值等原始模板节点及 location；transform 再把结构指令改为 IfNode/ForNode，并追加 codegenNode。

Codegen Node

transform 挂到模板节点上的输出意图；通常是 VNodeCall 或 JS AST 节点。

NodeTransform

在 AST 进入阶段执行、可返回退出回调的插件。顺序和退出逆序都具有语义。

DirectiveTransform

按指令名调用，返回 props 和可选 runtime directive；平台可覆盖同名实现。

TransformContext

遍历共享账本：位置、作用域、helpers、components、hoists、cache 与树操作。

Runtime Helper

以 symbol 登记的运行时能力，如 createElementBlock、renderList、toDisplayString。

PatchFlag

编译器给 runtime 的动态维度位标记，决定精确 patch 分支。

Block

收集动态后代的 VNode 边界；运行时可跳过中间静态树。

ConstantTypes

表达式/节点静态性等级，决定 skip patch、cache、hoist 或 stringify。

Binding Metadata

SFC 脚本给模板的变量身份表，区分 props、ref、maybe ref、let、const。

SFCDescriptor

完整 .vue 的结构描述，连接 parse、script/template/style 编译与 HMR。

TypeScope

compiler-sfc 类型解析作用域，保存声明、imports、owner、文件、依赖与缓存。

ScopeId

scoped CSS 的 data-v-* 标识，需要在 CSS、客户端 VNode、SSR 与 slot 中一致传播。

Hydration Boundary

SSR 用注释/元素表示的节点范围，使客户端能把 VNode 树对齐到现有 DOM。

Hoist

把值提升出 render。Vue 3.5.41 主要用于稳定 props 与 dynamicProps 键名数组；稳定 VNode/children 改用实例 _cache，不要把两者混为一谈。

Preamble

render 主体之前的 helper imports、hoists 与 setup inline 序言。

11 / FAQ

常见理解误区

把这些边界分清，源码阅读会少绕很多路。

为什么 codegen 看起来没有太多“智能”？
因为动态性、结构、helper 和 codegenNode 已由 transform 决定。codegen 的责任是稳定打印与映射，而不是重新分析模板。
compiler-dom 为什么还要依赖 compiler-core 的 v-model？
core 先处理可赋值表达式、modelValue 与 update handler；DOM 再按元素类型选择表单 helper。两层分别表达通用组件协议与原生控件语义。
script setup 宏为什么只能在顶层使用？
宏参与组件 options 与 setup 签名生成，需要静态、唯一且可提升地分析。嵌套在条件/函数中会让编译期无法建立稳定组件契约。
为什么 SSR 还需要 VNode fallback？
组件 slot 在某些无 _push 的调用路径仍要提供普通 VNode 形式。SSR 直接输出和 VNode fallback 共享 slot 语义，但目标不同。
为什么测试里有大量看似非法的模板？
IDE 编辑时模板经常处于临时非法状态；parser 必须尽量恢复稳定 AST 和 location。另一些输入用于锁定 HTML 标准容错或安全边界。
阅读时要不要把所有枚举值背下来？
不用。先掌握分类与消费者：NodeTypes 连接 AST 分派，ErrorCodes 连接诊断，PatchFlags 连接 runtime，State 连接 tokenizer。遇到分支再查具体成员。

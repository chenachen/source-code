前四章分别解释模块内部；这一章用一份完整 SFC 跟踪 descriptor、binding metadata、Template AST、PatchFlags、CSS vars、source map 与 SSR 输出如何在模块间传递。

案例：props + model + list + component + scoped CSS客户端与 SSR 双目标
本章说明四个入口怎样传递数据

每个模块章已经解释各自机制；这里把四个入口放回同一条链。先说清一个容易误会的边界：parse() 不会自动接着编译三个 block。构建工具从 descriptor 取出内容和元数据，再分别调用 script/template/style API，最后组装它们的返回值。

可执行语句来自四个当前文件；“……”表示从原数组或对象中裁掉的连续条目。这里把模块之间传递的数据并排展示，各入口的上下文在对应模块页展开。

descriptor 是三条分支的数据源

compileScript() 直接接收 descriptor。调用方把 template 的 content/AST/map、bindings、scoped/slotted，以及 SSR 所需的 cssVars 传给 compileTemplate()；每个 style block 的 content/map/scoped 与同一 id 则传给 compileStyle()。 后两个 API 都不直接接收 descriptor，compileStyle() 也不消费 descriptor.cssVars。

名字的身份要由调用方接过去

模板里的 selected 只是 Identifier，本身看不出它是 ref。compileScript 产出 bindingMetadata；分离编译时，构建工具把它放进 compilerOptions.bindingMetadata 再调用 compileTemplate。只有 compileScript 的 inlineTemplate 分支会在包内自动完成这次交接。

DOM 和 SSR 共享语言前半段

两者都使用 DOM parserOptions、结构指令与表达式作用域。差异从“如何表示输出”开始：客户端建 VNodeCall/patchFlag，SSR 建 _push/IfStatement/TemplateLiteral。

构建工具负责调度，compiler-* 负责语言语义

Vite/vue-loader 决定何时调 parse/compileScript/compileTemplate/compileStyle，并组装返回片段；宏、作用域、 patch 规则和 hydration 边界仍由 compiler-* 保持一致。

01 / Source

示例组件

它故意组合多个特性，但每个特性都能映射到明确的编译阶段。

<script setup lang="ts">
import { computed } from 'vue'
import UserCard from './UserCard.vue'

const { users, accent = '#42b883' } = defineProps<{
  users: Array<{ id: number; name: string; active: boolean }>
  accent?: string
}>()
const selected = defineModel<number | null>('selected')
const activeUsers = computed(() => users.filter(user => user.active))
</script>

<template>
  <section class="people">
    <UserCard
      v-for="user in activeUsers"
      :key="user.id"
      :user="user"
      :class="{ selected: user.id === selected }"
      @click="selected = user.id"
    />
    <p v-if="!activeUsers.length">暂无用户</p>
  </section>
</template>

<style scoped>
.people { color: v-bind(accent); }
.selected { font-weight: 700; }
</style>
阅读约定：后面的生成代码为突出关键参数而适度简化；实际 helper 别名、props 细节和开发标记以当前源码快照为准。
02 / Data Flow

先看清谁把数据交给谁

这不是一个从头跑到底的单函数，而是构建工具围绕四个公开 API 做的一次编排。

执行顺序：先切分，再分叉，最后由构建工具会合

→

→
三条编译分支script / template / style
descriptor + id同一份结构事实；同一个组件 id
↗

↘
compileScript

输入 descriptor；返回 content、bindings、imports、map、deps。

compileTemplate

输入 template content/AST/map、bindings、scope 信息；返回 render、AST、map、errors/tips。

compileStyle

输入 style content/map、id、scoped；返回 CSS、map、dependencies、errors。

这段代码只表达真实参数交接，省略空 block、预处理器、异步 CSS Modules、客户端/SSR 双产物和构建缓存。它刻意不冒充仓库源码：Vue 仓库只定义编译 API，具体调度在 Vite 插件、vue-loader 或其他调用方。

跨阶段数据 谁产生 谁消费 传错时会看到什么
descriptor / block loc parse 调用方、compileScript；template/style 接收拆出的字段 block 选错，或诊断映射到错误行列。
bindingMetadata compileScript compiler-core 的表达式与元素转换 ref/props/局部变量访问方式错误，甚至生成不可写的赋值。
id / scoped / slotted / cssVars 调用方生成 id；descriptor 保存其余样式事实 script、template、style、SSR CSS 已生成，却匹配不到 DOM；slot 或 SSR 的 scope 也会错位。
block source map parse 未预处理的 template、style 与最终 bundler map 报错和调试位置停在 block 或生成代码；模板预处理器只返回文本，本身没有可继续复合的 map。
deps / dependencies script 类型解析、style 预处理器与 PostCSS 构建工具文件监听 外部类型或样式依赖变化后，缓存没有失效；compileTemplate 不返回模板预处理依赖。
顺序不是“一律串行”：parse 必须最先；模板若要利用 bindings，就要等 script 分析完成；style 通常可以并行。CSS Modules 或异步 PostCSS 插件必须走 compileStyleAsync，普通同步 style 不需要等待 Promise。

04 / Script Branch

第二阶段：宏、类型与绑定分类

compileScript 解析 TS，改写 defineProps/defineModel，并把结果反馈给模板编译。

登记 imports

computed 识别为 Vue API；UserCard 是 setup const，并在 template 中作为组件使用。

处理 defineProps

resolveTypeElements 展开对象类型；users 推导 Array 且 required，accent 推导 String 且 optional/default。

处理 props 解构

后续 users/accent 读取改向 __props；accent 默认值进入 props 默认值生成逻辑。

处理 defineModel

生成 selected、selectedModifiers 两个 prop，登记 update:selected emit，并把宏调用改成 useModel(__props, 'selected')。

分析 activeUsers

computed 调用结果分类为 SETUP_REF；其闭包中的 users 改为 __props.users。

生成 metadata

UserCard=SETUP_CONST，users/accent=PROPS，selected=SETUP_REF，activeUsers=SETUP_REF。

实际 script 关键产物

export default _defineComponent({
  props: _mergeModels({
    users: { type: Array, required: true },
    accent: { type: String, required: false, default: '#42b883' }
  }, {
    selected: { type: [Number, null] },
    selectedModifiers: {}
  }),
  emits: ['update:selected'],

  setup(__props, { expose: __expose }) {
    useCssVars(_ctx => ({
      "demo-accent": _ctx.accent
    }))
    const selected = useModel(__props, 'selected')
    const activeUsers = computed(
      () => __props.users.filter(user => user.active)
    )
    return { selected, activeUsers, UserCard }
  }
})

取自本页 SFC 的实际编译结果，只去掉 helper 别名、 __name、类型标注和 __expose() 样板。

传给模板的关键 metadata

{
  computed: SETUP_CONST,
  UserCard: SETUP_CONST,
  users: PROPS,
  accent: PROPS,
  selected: SETUP_REF,
  activeUsers: SETUP_REF
}

模板因此可直接访问 setup 参数，不必全部经 _ctx；ref 读写也能选择正确代码路径。

跨模块关键点：如果 script binding 分类错误，模板 AST 仍可能正确，但生成的读取/赋值代码会错。例如把 selected 当普通 const，就无法正确生成 model ref 写入。
05 / Template Branch

第三阶段：把模板结构编成客户端 render

调用方把兼容的 descriptor AST、block map 与 binding metadata 交给 compileTemplate；它追加资产转换，再调用 compiler-dom/baseCompile。

Parse AST：描述源码结构

  • Root
    • Element(section)
      • Element(UserCard) v-for / key / user / class / on
      • Element(p) v-if

结构转换之后

  • Element(section)
    • ForNode
      • Component(UserCard)
    • IfNode
      • IfBranch(p)

转换顺序中的关键决策

转换 本例发生什么 生成结果
v-for activeUsers 读取为 setup ref；user 登记为局部变量 renderList + keyed Fragment。
transformExpression user 不加上下文前缀；selected 按 setup ref 读取 正确的局部/绑定访问。
transformElement UserCard 解析为 setup 组件；props/事件/class 汇总 Component VNodeCall + CLASS/PROPS 信息。
v-on selected 写入按 ref 赋值；handler 捕获循环 user 不能错误提升到循环外。
v-if 建立空态分支并注入分支 key 条件 block。
cacheStatic section 的稳定 props 可提升为 _hoisted_1；section VNode 与循环组件不提升 props hoist、实例 cache 与运行时 patch 边界。

生成的客户端执行形态（概念化）

同一案例的 client render（3.5.41，省略 imports） 
const _hoisted_1 = { class: "people" }
const _hoisted_2 = { key: 0 }

export function render(_ctx, _cache, $props, $setup, $data, $options) {
  return (_openBlock(), _createElementBlock("section", _hoisted_1, [
    (_openBlock(true), _createElementBlock(
      _Fragment,
      null,
      _renderList($setup.activeUsers, user =>
        (_openBlock(), _createBlock($setup["UserCard"], {
          key: user.id,
          user,
          class: _normalizeClass({ selected: user.id === $setup.selected }),
          onClick: $event => ($setup.selected = user.id)
        }, null, 8 /* PROPS */, ["user", "class", "onClick"]))
      ),
      128 /* KEYED_FRAGMENT */
    )),
    (!$setup.activeUsers.length)
      ? (_openBlock(), _createElementBlock("p", _hoisted_2, "暂无用户"))
      : _createCommentVNode("v-if", true)
  ]))
}

这是把本页 template、descriptor AST/map、binding metadata 和 scopeId=data-v-demo 一起交给 compileTemplate 后得到的实际 3.5.41 产物；这里只省略 helper imports，并把对象属性简写做了等价整理。稳定 class/key props 被提升，列表仍是 keyed Fragment，循环 handler 留在每次迭代的闭包里。

为什么循环中的 click handler通常不能全局缓存：它捕获 user。若错误缓存，后续迭代会复用第一个 user 的闭包。作用域追踪与 hasScopeRef 共同阻止这种优化。
06 / Style Branch

第四阶段：scoped 与 CSS vars 会合

compileStyle 改写选择器与 v-bind；compileScript 用同一 shortId 生成 CSS 变量写入；compileTemplate 接收 longId；构建工具再把 __scopeId 挂到组件模块上。

同一个 id 串联 CSS 与 DOM

CSS source.people / .selected / v-bind
→
PostCSS pluginscssVars + scoped
→
生成 CSS[data-v-id] + var(--id-accent)
↔
组件模块/setup__scopeId + useCssVars

概念化 CSS 输出

.people[data-v-demo] {
  color: var(--demo-accent);
}
.selected[data-v-demo] {
  font-weight: 700;
}

概念化变量注入

useCssVars(_ctx => ({
  "demo-accent": _ctx.accent
}))

同一 shortId 保证 CSS custom property 名和运行时写入键一致。

scopeId 不是 CSS 编译器单方面决定：样式选择器、客户端 VNode、SSR 元素、slot/slotted 内容必须使用同一传播规则，否则 CSS 看似生成正确却匹配不到实际 DOM。
07 / Assembly

第五阶段：构建工具组装模块

compiler-sfc 返回编译片段，不直接创建最终应用 bundle。Vite/vue-loader 等调用各 API，并把结果组装成组件模块。

构建工具的概念组装

compiled script组件 options + setup
+
render客户端模板产物
+
scopeId / HMR构建期附加元数据
→
组件模块交给 bundler 打包

脚本提供

默认组件对象、setup、props/emits、bindings 和依赖。

模板提供

render/ssrRender、helper imports、hoists、map 与 errors/tips。

样式提供

CSS、map、dependencies、CSS Modules 映射与错误。

职责边界：同一 compiler-sfc 可被不同 bundler 使用；预处理器加载、文件读取、缓存策略和 HMR 调度由上层提供，而语言语义保持在 compiler 包内。
08 / SSR Branch

同一 descriptor，模板目标改变

compileScript 可按 SSR/inline 选项调整；compileTemplate 选择 compiler-ssr，CSS vars 也改走服务端 props/style 注入。

维度 客户端 SSR
模板函数 render(_ctx, _cache) ssrRender(_ctx, _push, _parent, _attrs)
列表 renderList + Fragment VNode block ssrRenderList + HTML/注释边界
动态 class normalizeClass + CLASS patch flag ssrRenderClass 后直接写 class 属性
点击事件 生成 onClick handler 原生 HTML 不序列化监听器；组件事件 prop 仍可传给子组件
空态 v-if 条件 VNode block if statement + 必要注释占位
CSS vars useCssVars 写 DOM style _cssVars 合并到可透传根 props
同一案例的 ssrRender（3.5.41，省略 imports） 
export function ssrRender(
  _ctx, _push, _parent, _attrs, $props, $setup, $data, $options
) {
  const _cssVars = { style: {
    ":--demo-accent": ($props.accent)
  }}
  _push(`<section${_ssrRenderAttrs(
    _mergeProps({ class: "people" }, _attrs, _cssVars)
  )} data-v-demo><!--[-->`)
  _ssrRenderList($setup.activeUsers, user => {
    _push(_ssrRenderComponent($setup["UserCard"], {
      key: user.id,
      user,
      class: { selected: user.id === $setup.selected },
      onClick: $event => ($setup.selected = user.id)
    }, null, _parent))
  })
  _push(`<!--]-->`)
  if (!$setup.activeUsers.length) {
    _push(`<p data-v-demo>暂无用户</p>`)
  } else {
    _push(`<!---->`)
  }
  _push(`</section>`)
}

SSR 产物来自同一 template 与 binding metadata。它把父级 _attrs 和 _cssVars 合并到 section。当前元素获得 scopeId，列表范围用成对注释标记。:--demo-accent 前面的冒号是 SSR 内部标记；server-renderer 的 ssrResetCssVars() 在序列化 style 时会去掉它并规范化变量值。原生 HTML 不写浏览器监听器；组件调用仍接收 onClick prop。

客户端与服务端不需要生成相同代码：客户端预期的节点拓扑、属性与 scope 归属必须和服务端实际 HTML 一致。两套产物可以完全不同，但 hydration 所需结果必须一致。
09 / Incremental Build

改一处源码，哪些分支需要重跑

SFCDescriptor、依赖与 import 使用分析帮助构建工具缩小失效范围。

这张表描述调用方常见调度，不是 compiler-sfc 的统一调度器：包内能直接确认的 HMR 判定只有 descriptor.shouldForceReload(prevImports) 等窄接口；是否重编译 CSS、替换 render 或整模块重载，仍由构建工具决定。
变化 通常重编译 额外失效范围或升级条件
仅 template compileTemplate TS setup import 从未使用变为模板使用，影响脚本返回/裁剪。
仅 style compileStyle 若 scoped、descriptor.slotted 或 descriptor.cssVars 集合改变，调用方还要重编 template、client script 或 SSR template；是否整模块重载由调用方决定。
script setup compileScript + 通常 template bindings、组件 imports、宏声明或类型依赖变化。
外部类型文件 依赖它的 compileScript runtime props/emits 推导改变。
style 预处理器或 PostCSS dependency 对应 compileStyle 分支 输出 CSS、source map 或 scoped 选择器变化。

它只处理一个方向：旧脚本产物曾裁掉某个 TS setup import，而新模板开始使用它。只替换 render 无法把这个名字补回 setup 返回对象，所以必须重编脚本。反方向与非 TS setup 在这里直接返回 false；这不等于整个 HMR 系统什么都不做。

10 / Debugging

端到端问题追踪法

先判断哪一份中间结果出错，再进入对应模块；从最终 bundle 反向搜索通常会混入压缩、拼接和运行时辅助代码。

  1. 1
    Descriptor 对吗？block、attrs、loc、template AST 与 cssVars 是否正确。
  2. 2
    Binding metadata 对吗？宏是否识别，类型是否展开，ref/props/let 分类是否准确。
  3. 3
    Template AST 对吗？parser 是否已经误解标签、指令或 namespace。
  4. 4
    codegenNode 对吗？结构转换、props、PatchFlags、helper 与 scope 是否正确。
  5. 5
    平台产物对吗？DOM helper/SSR attr 与 runtime 消费者是否匹配。
  6. 6
    映射与缓存对吗？是否复用了不兼容 AST/scope，location 是否叠加正确。
11 / Smaller Cases

</li>

const { color = 'red' }
  = defineProps<Props>()

Module 03 · Single File Component Orchestrator

compiler-sfc

SFC 编译器把一个 .vue 文件变成可由构建工具组装的脚本、渲染函数和样式。它既是协调器，也是 编译宏实现；为了从类型式 props/emits 生成运行时声明，它还实现了所需的一部分 TypeScript AST 分析，并负责串联多层 source map。

输入：完整 .vue工具：Babel AST + MagicString + PostCSS输出：script/template/style 三分支基线：Vue 3.5.41 · 11cd09cf

01 / Parse

parse 的输出：SFCDescriptor

parse() 不编译 JavaScript 或 CSS；它只切分顶层 block，记录属性、位置、映射与构建元数据。

parse(source, options)

缓存键包含 compiler.parse

key 是 source + JSON.stringify(options)；函数会先 toString()。compiler 特意只保留 parse，因为 parse 阶段不调用 compile。相同源码下， delimiters、filename、pad 或 sourceMap 的值变化会产生不同 key。 函数只按文本进入 key，所以相同函数文本中的不同闭包状态不会被区分。 命中时没有克隆，调用方若修改缓存结果，也会影响下一次命中。

SFC mode 保护 script/style 原文

根级非 template block 的内容按原始文本读取，所以 JS 中的 < 和 CSS 中的大括号不会被模板 parser 误解成标签语法。

模板 AST 可以复用

只要 template 没有 src，parse 就把 children 包成 RootNode；Pug 这类 block 此时通常只是一个原始文本节点。真正能省掉 template 二次解析的，是没有预处理、compiler 协议相同，而且 AST 还没被改写的情况。预处理器或自定义 compiler 会放弃这份 AST。

errors 是数组，不是异常终点

IDE 编辑中的 SFC 常处于暂时未闭合状态。可恢复的结构错误被收集，descriptor 仍尽量构造，这样语法高亮和其他 block 的诊断不会全部失效。不过错误不等于“什么都保留”：非法 <script setup src> 会记录错误并把 descriptor.scriptSetup 置回 null；与 setup 共存的普通 <script src> 也会被丢弃。

为什么 parse 返回 errors 而不直接 throw：重复 block、非法 src/setup 组合与暂时语法错误可能同时存在。IDE 需要尽量得到 descriptor，并一次显示多个诊断。
block 解析阶段规则 后续处理者
template 最多一个；空 template 也保留；无 src 时保存 children AST compileTemplate
script 普通与 setup 各最多一个；空且无 src 时默认忽略 compileScript / normalScript
style 允许多个；记录 scoped/module/lang compileStyle
custom block 保留 tag、attrs、content；空且无 src 时默认忽略 上层构建插件

顺序有含义：先修正非法 script 组合，再为留下的 block 建 map，最后从所有 style 原文提取 CSS v-bind() 和 scoped :slotted() 标记。cssVars 是按首次出现顺序去重的表达式列表；slotted只看带 scoped 的 style。两者都还没有生成任何 JS 或 CSS。

parse 状态 触发 结果
cache hit 源码与序列化后的解析选项相同 立即返回缓存的 { descriptor, errors }。
可恢复错误 模板语法、重复 block、过时 functional/vars 追加 errors；继续处理其余根节点。
非法跨 block 组合 setup 使用 src，或普通 src script 与 setup 共存 追加 errors，并把有歧义的 script 字段清空。
无入口 block template、script、scriptSetup 全为空 返回 descriptor，同时追加“至少需要一个”的错误。
缓存容量与清理：Node 构建使用最大 500 项的 LRU；浏览器/global 构建退化为普通 Map。公共入口导出了 parseCache，上层可显式 clear/delete。源码变化本身已进入 key， 因而通常不需要“按文件名”失效。

02 / Script

compileScript：先用 AST 分析，再改写原文件

它不是只收一个 script 字符串，而是收整个 descriptor：模板决定哪些 import 要暴露以及哪些 reactive const 必须降成 let；style 提供 CSS vars；inline template 时还要读取 scoped 状态。跨 block 信息都在这里第一次会合。

ScriptCompileContext

集中保存 Babel AST、MagicString、宏状态、imports、bindings、parser plugins、错误定位与类型解析上下文。

Babel AST

负责“理解”JS/TS 语法：导入、声明、类型、函数作用域、宏调用和顶层 await。

MagicString

负责“修改”完整 SFC：move、remove、overwrite、prepend，并保留源位置以生成 map。

主流程分成五步

五步按数据依赖划分。每一步都会留下下一步需要的 AST、宏状态或 bindingMetadata；这样比照着文件里的循环逐行读更容易看清因果关系。

01 · 检查输入并建立上下文

先检查普通 script 与 setup 的语言是否一致。没有 setup 时走 normalScript；自定义脚本语言原样交还上层。主路径再建立 Babel AST、MagicString 和宏状态。

02 · 整理 imports 与普通 script

普通 script 的 import 只登记，setup import 移到模块顶层；随后去重、检查局部名冲突。普通 script 的默认导出改成 __default__，留到最后与 setup 结果合并。

03 · 处理宏和需要作用域信息的改写

扫描 setup 顶层声明，记录并消除编译宏；然后用完整作用域信息改写 props 解构和顶层 await，并检查会被提升到 setup 外的宏参数是否引用了 setup 局部变量。检查完成后才删除非脚本 block。

04 · 汇总 bindings，并读取其他 block 的信息

合并 Options API、imports、普通 script、setup、props/model 的绑定分类；再读取模板里的简单 v-model 目标，必要时把 reactive const 改成 let。客户端 CSS v-bind() 也在这一步根据 style 提取结果注入脚本。

05 · 生成 setup、组件选项和 source map

非 inline 模式生成 setup 返回对象；inline 模式把 compileTemplate 的 render 直接放进 setup。最后合并 name、props、emits、用户 options 与 setup，并生成 helper import 和 map。

最容易漏掉的因果关系：模板扫描发生在生成 setup 返回值之前；genRuntimeProps()又发生在 inline template 之前。否则 import 不知道该不该暴露，类型式 prop 也来不及写入 bindingMetadata，render 会走错读取路径。
最小 script setup 编译前后（概念产物） 
<script setup lang="ts">
import { ref } from 'vue'
const props = defineProps<{ title: string }>()
const count = ref(0)
</script>

↓ 核心产物

import { defineComponent as _defineComponent, ref } from 'vue'
export default _defineComponent({
  props: { title: { type: String, required: true } },
  setup(__props) {
    const props = __props
    const count = ref(0)
    return { props, count }
  }
})

这段为了突出关键结果，合并了实际产物中的 helper import，并省略非测试构建会加的 __returned__.__isScriptSetup 标记；不是 snapshot。真实不变量是：宏调用消失、props 进入组件选项、defineProps() 使用位置改成 __props、模板可见绑定从 setup 返回或被 inline render 捕获。

__isScriptSetup 使公开实例代理和 Options API 不把这些绑定当普通 setup 状态暴露或修改；独立 render 仍通过 $setup 访问它们，包括以 $ 或 _ 开头的名字。

入口形态 compileScript 行为 失败/返回契约
没有任何 script 无法建立脚本产物 直接 throw：SFC contains no <script> tags。
只有普通 JS/TS script 走 processNormalScript；分析 Options API，必要时改写默认导出并注入 CSS vars 返回普通 SFCScriptBlock。Babel 解析在上下文构造时完成，语法错误直接 throw；后续绑定分析或改写异常才由 processNormalScript 的 catch 返回原块。
只有非 JS/TS 的普通 script compiler-sfc 不认识该语言 原普通 script block 返回给上层插件，不做 Babel 改写。
存在非 JS/TS 的 setup（可同时有同 lang 普通 script） 先通过两 block 的 lang 一致性检查，再跳过主编译 返回 setup block；不会替自定义语言合并两个 block。
普通 script + setup 要求两个 lang 完全相同，再进入完整合并路径 不相同先 throw，不会拿错误 parser 勉强解析。
setup 宏/语法错误 ScriptCompileContext 把 block offset 换回完整 .vue code frame throw；不像 parse/compileStyle 那样统一放进 errors 数组。
inline template 编译错误 取 compileTemplate().errors[0]，补完整 SFC code frame 再次 throw；compileScript 不返回半成品 script。

普通默认导出怎么并进来

export default {...} 先改成 const __default__ = {...}。最终 TS 产物用 defineComponent({ ...__default__, ...defineOptions, props, emits, setup })；JS 产物用 Object.assign(__default__, defineOptions, generatedOptions)。用户显式 name/render 会阻止相应自动推导分支。

谁负责默认导出之后的拼装

默认是 export default；传 genDefaultAs 时改为局部 const name =，让 Vite/vue-loader 继续挂 render、scopeId 等属性。这也说明 compiler-sfc 的单个 API 产物不是最终模块的全部内容。

为什么不能把 compileScript 看成文本替换：宏可以被 TS assertion 包裹，变量可能在嵌套函数中遮蔽，var 会提升，import 有类型/值双重身份。所有这些都要求真实 AST 与作用域模型。

03 / Macros

编译宏不是运行时函数

这些名字无需从 Vue 导入；compiler-sfc 在顶层识别并擦除/替换调用，把声明转换为组件 options 与 setup 上下文参数。

宏 编译期输入 输出/改写 关键限制
defineProps 运行时对象/数组或 TS 类型 __props 参数、runtime props、binding metadata 类型式与运行时式不能混用；只能调用一次。
withDefaults 类型式 defineProps + defaults 静态默认值内联；动态对象生成 mergeDefaults 仅能包裹类型式 props；与解构同用会警告并关闭响应式解构。
defineEmits 事件数组/对象或类型签名 runtime emits 与 __emit 提取调用签名/具名 tuple；禁止重复或混用。
defineModel 名称、类型与 options 同名 prop + modifiers prop + update event + useModel() 同一模型名不能重复；静态无 spread/computed 的 options 才能把 get/set 与 prop 配置精确拆开。
defineExpose 暴露对象 替换为 setup context 的 expose 只能一次；未调用时生成 expose() 保持默认封闭。
defineOptions 一个运行时 options 表达式 提升并合并默认导出 不能引用仍留在 setup 内的局部；已提升的 LITERAL_CONST 可以使用。也不能重复声明 props/emits 等专用项。
defineSlots 仅类型参数 结果被使用时改成 useSlots()；否则整句删除 不接受运行时参数；类型参数只服务 TS/IDE，不生成 runtime slots 选项。

同一个宏通常要走完“识别 → 记状态 → 延迟生成”

→
写入 contextAST、decl、bindings、flags

检查跨阶段约束重复、互斥、提升引用

识别失败时继续尝试 withDefaults

AST 顶层可能是 withDefaults(...) 而不是 defineProps CallExpression。包装宏再递归要求第一个参数必须是 defineProps，避免把普通函数误当宏。

运行时声明和类型声明互斥

defineProps<T>({ foo: String }) 同时给出两份完整事实，它们可能对 required/default/type 产生冲突，所以编译器不尝试“智能合并”。

运行时 key 立即成为 PROPS 绑定

数组或对象里可静态读取的键当场写入 bindingMetadata，模板编译就知道这些名字应读取 props，而不是未知的公开实例属性。

解构只先记录，后统一改写

此处不立即遍历后续代码，只保存 public key、local alias 和 default。等全部顶层声明被了解后，transformDestructuredProps 才能用完整作用域信息安全重写。 嵌套解构和动态计算键会报错；字符串或数字字面量计算键可以解析。

类型式 defineProps

const props = defineProps<{
  title: string
  count?: number
}>()

// 生成概念：
// props: { title: { type: String, required: true },
//          count: { type: Number, required: false } }

defineModel

const title = defineModel<string>('title')

// 生成概念：
// prop: title
// emit: update:title
// const title = useModel(__props, 'title')

还差的第四处在 genRuntimeEmits()：每个模型追加 update:${modelName}，再用 mergeModels 与用户 defineEmits 合并。也就是说，defineModel 不是把名字换成 useModel 就结束；script 表达式、binding 身份、props 和 emits 必须一致。只有 options 是不含 spread/computed key 的对象字面量时，编译器才能删出两份精确子集；动态表达式会整体复用于 prop 和 useModel，交给运行时忽略自己不关心的键。

宏参数什么时候不能捕获 setup 局部变量：会进入 runtime props/emits/组件 options 的那一部分被提升到 setup 外，此时 setup 局部值尚不存在，编译器会遍历相关 AST 提前报错；已提升到模块层的 LITERAL_CONST 可以引用。defineModel 只对能静态拆分的对象 options 收集并检查 prop 配置；get/set 留在 setup 内传给 useModel，可以捕获局部变量。动态 options 不经过同样的 prop 选项检查，这项诊断只覆盖可静态拆分的对象配置。

04 / Props Destructure

解构后的读取如何改回 __props

普通 JavaScript 解构会把 prop 复制成局部值。Vue 通过编译期把后续读取改回 __props，使简洁语法保持响应性。

用户源码

const { foo: localFoo = 1, bar, ...rest }
  = defineProps<Props>()

watchEffect(() => {
  console.log(localFoo, bar, rest.baz)
})

概念改写

const __props = ...
const rest = createPropsRestProxy(__props, ['foo', 'bar'])

watchEffect(() => {
  console.log(__props.foo, __props.bar, rest.baz)
})

为什么读取改成 __props

JavaScript const { foo } = obj 只在声明时取一次值；组件更新 props 时局部 foo 不会变。所有读取回到 __props.foo，才会每次取当前值。

对象简写要保留 key

把 { foo } 整个替换成 { __props.foo } 是非法 JS，也丢失了对象键名。正确结果是 { foo: __props.foo }，因此需要根据父节点语义展开 shorthand。

赋值在编译期失败

如果把 foo++ 默默改成 __props.foo++，就绕过了 props 单向数据流。编译器用原始 id 位置直接报只读错误，比运行时警告更精确。

watch 需要 getter，不是当前值

表达式重写只能把 watch(foo) 变成 watch(__props.foo)，但这仍是一次取值。因此编译器单独识别 watch/toRef 并要求 watch(() => foo)，让响应式系统能在 getter 内跟踪依赖。

改写必须尊重 JavaScript 作用域

语法 期望 原因
函数参数同名 函数内使用局部参数 参数遮蔽顶层解构 prop。
catch (foo) catch body 使用局部错误变量 catch 建立独立作用域。
for (const foo of list) 循环内局部，循环后恢复 prop 进入/离开循环要成对登记。
对象 shorthand key 保留 foo，value 改 __props.foo 同一 Identifier 同时承担两个语义。
对解构 prop 赋值 编译错误 prop 只读，不能把重写变成隐式 mutation。
默认值是函数 结合类型推导和默认值 AST 决定工厂与 skipFactory 推导类型包含 Function 时直接保留默认值；运行时式声明的函数或外部标识符默认值生成 skipFactory，阻止运行时调用。其他非字面量默认值才包工厂。
var 提升也必须考虑：即使 var 声明写在后面，它在函数作用域内仍遮蔽 prop。相关 issue 修复说明这里执行的是接近 JavaScript 绑定语义的静态分析，而非简单按源码顺序替换。

05 / Type Resolution

从 TypeScript 类型推导运行时声明

defineProps/defineEmits 的类型在运行时不存在。compiler-sfc 必须展开足够多的 TypeScript 语义，生成可用但保守的 runtime props/emits。

resolveTypeElements / inferRuntimeType

宏类型节点interface / alias / literal
→
TypeScope本地声明 + imports + owner scope
→
展开类型元素泛型 / union / intersection / mapped
→
runtime typeString / Number / Boolean / Object...

先选定类型节点的 ownerScope，再分派节点类型；遇到泛型引用时，把实参映射到声明的类型形参后递归展开。

这不是 TypeScript checker

算法只实现生成 props/emits 所需的 AST 可见类型展开，不执行完整类型检查、控制流程缩窄或任意条件类型求值。Node/CJS 下解析包名、paths 与 project references 时仍可能加载 TypeScript peer dependency，但用的是模块解析能力，不是启动 Program/TypeChecker 给宏做任意求值。

ownerScope 决定名字从哪里查

展开外部 BaseProps 后，其成员类型里的别名与 import 应在 BaseProps 所在文件解析，而不是在当前 .vue 文件。每个属性因此保留 _ownerScope。

带泛型实参时不可直接缓存

Box<string> 和 Box<number> 共用同一个 Box 声明 AST，结果却不同。实现会为成员建立带实参映射的临时 child scope，并把 isGenericScope 设为 true；只有不依赖 typeParameters 的展开才能挂到 node 上复用。

缓存命中只补回 ownerScope 依赖

命中已展开的类型结果时，当前 context 会从各属性的 _ownerScope.filename 补回依赖，并不会重放首次展开时的整条 import 路径。例如 facade → middle → leaf 的转导出链中，字段最终属于 leaf；再次编译可记录 facade 和 leaf，却漏掉中间的 middle。因此这条缓存路径返回的 deps 不能保证包含所有中间转导出文件。

类型信息如何变成运行时选项 
interface Props extends Base {
  title: string
  count?: number
}

↓ resolveTypeElements + inferRuntimeType

props: {
  ...Base 中可解析的字段,
  title: { type: String, required: true },
  count: { type: Number, required: false }
}

文件与作用域

TypeScope 记录 filename、source、offset、imports、types、declares、exportedTypes/exportedDeclares 与 resolvedImportSources。依赖集合属于 compile context；global/module 语义靠两份独立文件缓存区分，不是 TypeScope 上一个布尔字段。

跨文件解析

通过 fs 读取相对类型文件；包名和 alias 在 Node/CJS 下交给 TS 处理 tsconfig paths 与 project references；另支持 namespace 与显式 globalTypeFiles。

缓存与失效

文件 scope、模块解析和 tsconfig 结果会缓存；依赖路径返回给构建工具，用于 HMR/监听。

支持维度 示例 处理策略
接口/别名 interface Props extends Base 递归合并 type elements。
泛型 Box<string> 建立临时 child scope，把类型参数映射到实参。
联合/交叉 A | B、A & B 合并属性与更宽 runtime 类型，保守处理未知分支。
映射/索引访问 Pick、Omit、T[K] 解析静态 key 集合并回到源属性。
工具类型 Partial、Required、Readonly、Pick、Omit 内建展开 props 结构，调整 required 或筛选 key。Record 仅在字段运行时类型推导中归为 Object，不作为顶层 props 结构展开。
跨文件类型 import type { Props } 模块解析 + scope 缓存 + deps 记录。
“保守”不等于所有失败都静默降级：类型结构本身无法展开时， resolveTypeElements() 通常通过 ctx.error() 抛错；部分 interface extends 可用显式 /* @vue-ignore */ 接受退化。结构能展开、但某个字段无法推成 运行时构造器时，才会落到 Unknown，随后生成 null 或 skipCheck。生产模式仍保留会影响 Boolean 强制转换、Function 默认值及 Custom Element 属性转换的类型信息。

06 / Binding Metadata

script 与 template 的桥梁

binding metadata 让模板编译器知道每个名字来自哪里、是否可能是 ref、读取与赋值该采用哪条路径。

绑定类型 典型来源 inline template 独立 render
PROPS defineProps 字段 通过 __props 读取，不允许直接赋值。 通过 $props 读取，不允许直接赋值。
PROPS_ALIASED { foo: localFoo } 响应式 props 解构 借 __propsAliases 把 localFoo 还原为公共键，访问 __props.foo。 还原公共键后访问 $props['foo']。
SETUP_REF ref()、computed() 读取/写入 .value。 $setup.name，由运行时 setupState 解包与写入。
SETUP_MAYBE_REF 普通 const 调用结果 读取 unref；普通赋值、更新与解构赋值直接写 .value；v-model 单独生成 isRef 判断。 $setup.name，由运行时 setupState 解包与写入。
SETUP_LET let 绑定 读取 unref；普通赋值/更新用 isRef 区分 .value 与绑定本身；解构赋值直接写绑定。 $setup.name，由运行时 setupState 解包与写入。
SETUP_REACTIVE_CONST const state = reactive(...)、props rest proxy reactive 对象内容可变，props rest 通过 getter 读取当前 props。Identifier 声明的 reactive const 直接成为 v-model 目标时降为 SETUP_LET；ObjectPattern 声明的 props rest proxy 不经过这项降级。 通过 $setup.name 访问；声明降级条件同左。
LITERAL_CONST 字面量 const 直接使用；静态字面量声明可提升到模块层。 $setup.name。
SETUP_CONST 函数、稳定对象、import 直接使用，不走实例代理。 $setup.name。
OPTIONS / DATA 普通 script 的 inject/computed/methods/setup/data 通过 _ctx.name 访问。 分别通过 $options.name / $data.name 访问。

自动接线只发生在 inlineTemplate 分支。构建工具分别调用 compileScript 与 compileTemplate 时，必须把前者返回的 bindings 放进后者的 compilerOptions.bindingMetadata；compiler-sfc 不会跨两次独立 API 调用隐式保存这份状态。

Import Usage Check：只优化能安全看懂的模板

非 inline 模式必须决定“哪些 setup import 放进 return 对象”。JS 路径保守地把值 import 都当成需要；TS/TSX 且 template 为内联 HTML 时，才调用 isImportUsed() 精确扫描。template 有 src、有预处理语言，或 inline render 已能直接捕获 import 时，不走这条裁剪判断。扫描对象包括组件标签、用户指令、插值、动态参数、无值 v-bind 简写、静态 ref 名和表达式标识符。

缓存实际以什么为 key

templateAnalysisCache 只用 template content。轻量 v-model 扫描只缓存 vModelIds；后来需要完整 usedIds 时会重算。AST 若已经被 compileTemplate 原位标成 transformed，resolveTemplateAST() 会从完整 SFC source 重解析一棵干净树。

谁负责失效

这份内部缓存没有 filename/options 维度，也没有自动按 HMR 事件清除的公开 API。当前测试在改变 delimiters 并复用 transformed AST 的场景里显式 templateAnalysisCache.clear()。因此不能把它写成“所有模板选项都自动参与 key”。

Top-level Await：保住的不是 Promise，而是组件上下文

const data = await load() 的编译期展开

withAsyncContext() => load()
→
[__temp, __restore]awaitable + 恢复函数
→
await __tempsetup 标为 async

compileScript 的 AST walker 一遇到函数节点就 skip()，所以只改 setup 自身控制流里的 await；用户写的 async 函数自己管理生命周期。表达式形式要把解析值重新放回 __temp，语句形式不需要。某些根级表达式前加分号是为防 ASI 把生成的 (...) 黏到上一行；单行 if (ok) await foo() 又必须避免乱加分号切断 body。

模板扫描不是普通文本搜索：组件 PascalCase/kebab-case、动态参数、对象 key、局部 slot 参数、纯类型位置都可能造成误判。importUsageCheck 的测试集中覆盖这些边界。

DOM/SSR 从默认 compiler 分叉

默认 compiler 的选择确实集中在 ssr ? CompilerSSR : CompilerDOM，但 SSR 不只换函数：它还把 ssrCssVars 变成 compiler-ssr 需要的表达式，并在缺少对应列表时警告。显式传入 compiler 会覆盖默认选择；compiler-sfc 不会强行把自定义实现换回 SSR。

资产 URL 是模板转换，不是字符串替换

<img src="./logo.png"> 会转成 import 绑定，而外链、data URL 与 :src 保留。hash 不是一概保留：<use href="#icon">是当前文档 fragment，会跳过；普通资源属性的 hash-only 值仍可作为模块请求处理。srcset 还含多个 URL/密度描述，必须逐候选解析。

选项展开顺序允许高层调整

compilerOptions 可以覆盖 mode、prefix、hoist、cache、scopeId、sourceMap 等前置默认值。随后 hmr、filename、onError/onWarn 和 nodeTransforms 又由 SFC 层收口；nodeTransforms 固定为“资产转换在前，用户转换追加在后”。

source map 是两段函数的复合

只有传入字符串且同时有 inMap 时，才用 mapLines(code→block, block→SFC) 合并映射并回补错误的行号与 offset；mapLines 保留模板编译器的原始列， patchErrors 也不调整错误 column。若直接复用 descriptor AST，节点 location 本来就基于完整 .vue，编译器生成的 map 可直接使用。

错误位置回补：如果传入的是 template block 字符串而非完整 SFC AST，编译错误 location 先相对 block；compileTemplate 根据 inMap 中的源码查找模板字符串，补回 line 与 offset。内容紧跟 <template> 出现在同一行时，column 仍是 block 坐标，不会加上标签占用的列。
模板预处理的 map 边界：这里的 consolidate 适配器只返回预处理后的字符串，没有返回“Pug → HTML”之类的 source map，也没有 dependencies 字段。 inMap 只能提供调用方已有的 block → SFC 映射；缺失的语言转换映射无法凭空补出。

同步边界也要记住：compileTemplate()是同步 API。preprocess()调用 consolidate 风格的 render(source, options, callback) 后立刻读取回调写入的字符串；它只适用于同步触发 callback 的模板引擎。真正异步的模板预处理器不能靠这个入口等待完成。

template 分支 返回/异常 调用方应怎样理解
浏览器/global 构建请求预处理，却没给 customRequire 立即 throw 这是 API 配置错误，尚未进入结构化结果。
找不到声明的预处理器 空 render + 一条 tip + 一条字符串 error 构建器仍拿到固定结果形状，可显示安装提示。
预处理器执行抛错 空 render + Error 放入 errors 原 source 原样保留在结果中，AST/map 不存在。
模板 compiler 通过 onError/onWarn 报告 errors 保留 CompilerError；warnings 转成带 code frame 的 tips compileTemplate 自己不因普通模板诊断 throw。
自定义 compiler 自己 throw 无预处理时向外 throw；可用预处理器分支中返回空 render 与 errors 预处理分支的外层 try 同时包住预处理与后续编译；加载预处理器的 customRequire 调用在 try 之外，其自身抛错仍向外传播。
缺 id / SSR 缺 cssVars warnOnce 后继续 这两项不进入 results.errors。
调用方必须显式完成的接线（解释性伪代码） 
compileTemplate({
  source: descriptor.template.content,
  ast: descriptor.template.ast,
  inMap: descriptor.template.map,
  id: scopeHash,                         // 上层生成，不在 descriptor 中
  scoped: descriptor.styles.some(s => s.scoped),
  slotted: descriptor.slotted,
  ssrCssVars: descriptor.cssVars,         // SSR 时需要

  },
})

08 / Style

compileStyle：一条 PostCSS 插件管线

预处理语言先把源码变成 CSS；随后按 CSS vars → 用户 PostCSS plugins → trim → scoped → CSS Modules 注册插件。PostCSS 按 Once、 节点访问与 OnceExit 分阶段调用它们，数组顺序不表示每个插件整体先后执行。

预处理与 PostCSS 插件注册顺序

PreprocessorSass / Less / Stylus
→
CSS v-bind表达式 → var(--id-name)
→
用户 plugins在 Vue vars 之后
→
trim + scoped清理规则并注入 data-v-id
→
Modules + result异步 class JSON / code / map / deps

预处理在 PostCSS 之前

Sass/Less/Stylus 先把自己的语法降成 CSS，后续 cssVars/scoped/modules 插件只需处理统一 CSS AST。预处理器 map 会作为 PostCSS map 的 prev 继续串联。

注册顺序与 hook 时机一起决定输入

cssVars 在 Declaration 中把 v-bind(theme.color) 改为 var(--id-name)。用户插件的 Declaration 注册在它之后， 因而读到改写后的值；用户 Once 则在节点访问之前执行，仍可能读到原始 v-bind。trim 使用 Once，scoped 使用 Rule/AtRule 与 OnceExit，需按 各自 hook 理解调用时序。

CSS Modules 为什么强制异步

类名 JSON 是 postcss-modules 的 getJSON 回调产物，只有整个 PostCSS promise 完成后才可当作最终结果读取。源码因此在安装插件前明确要求 isAsync，同步 API 直接 throw，不尝试返回半成品 modules。

dependencies 是 HMR 的输出

Sass @use 和 PostCSS dependency message 都被汇总。当其中一个外部文件变化时，Vite/vue-loader 依此重编译该 style block。预处理器依赖集合会先删除与 filename 完全相同的项；随后用户 PostCSS plugin 报出的 dependency message 再追加，因此插件若主动报告当前文件，仍可能加回来。

scoped + CSS vars 产物 
输入：.card { color: v-bind(theme.color) }
scope：data-v-a1b2

CSS：.card[data-v-a1b2] { color: var(--a1b2-theme\.color) }
Script：_useCssVars(_ctx => ({
  "a1b2-theme\.color": _ctx.theme.color
}))

选择器隔离与动态值注入通过同一 scope id 会合。

Scoped 选择器重写

  • 普通选择器插入 [data-v-id]。
  • :deep() 改变 scope 属性插入边界。
  • :slotted() 使用 slotted scope id。
  • :global() 退出局部作用域。
  • keyframes 与 animation 名同步加后缀。

CSS v-bind()

  • parse 阶段从所有 style 提取表达式。
  • 开发名可读，生产名使用稳定 hash。
  • PostCSS 改为 CSS custom property。
  • script 注入 useCssVars 计算值。
  • SSR 通过模板/props 路径注入。

普通 selector 把属性插到“最后一个仍属于当前组件”的节点；deep 把边界停在参数之前；slotted 改用 -s，并禁止再加普通 id；global 直接把局部分支替掉。:is/:where/:has中 deep 与普通分支混在一起，且当前不在 deep 上下文、伪类前无 scope 锚点、后有尾随 节点时，源码才克隆并拆开 selector，使尾随节点只在普通分支加 scope。 没有尾随节点时，递归改写伪类内部即可。keyframes 则先收集这张映射：原名 → 原名-shortId，在 OnceExit 同步改写本 style block 内的 animation-name/animation；跨 style block 不共享这张映射。

dependencies 汇总预处理器 import 与 PostCSS dependency messages，构建工具据此监听 HMR。资产 URL 不会进入这份 Set；模板生成的 import 交给模块图追踪，二者不是同一种依赖协议。

阶段 输入 → 输出 map / dependencies
SCSS/Sass compileString 或旧 renderSync → CSS loadedUrls/includedFiles；有 inMap 时与 Sass map 合并。
Less 强制 syncImport: true 的 render → CSS result.imports；有 inMap 时合并 result.map。
Stylus 同步 render → CSS ref.deps()；按需打开 sourcemap。
PostCSS 预处理 CSS 或原 CSS → 最终 code/rawResult 前一层 map 作为 prev；dependency messages 追加到 Set。
CSS Modules 最终 selector → 局部类名 JSON 只在 async API 返回 modules；如何暴露为 $style 属于上层构建器。

错误不是一种形态：有的返回，有的直接 throw

触发位置 同步 compileStyle 异步 compileStyleAsync
预处理器正常返回 errors 先累加 errors，仍以预处理器返回的 code（失败时通常为空串）继续 PostCSS。
加载预处理器 / browser 缺 customRequire 发生在 PostCSS try/catch 之前，异常向外 throw。
CSS Modules 用错 API 或 browser/global 构建启用 modules 安装插件前直接 throw；不会包装进 results.errors。
PostCSS 处理错误 catch 后返回 code: ''、errors、可能仍有 LazyResult rawResult。 promise catch 后返回 code: ''、无 map/rawResult、保留已知 dependencies。
成功 读取 result.css 强制同步执行；异步插件会在这里失败。 await 完整 Result，再返回 code/map/modules/messages。
跨阶段小坑：parse 从原始 style block 提取 descriptor.cssVars，compileStyle 则在预处理后的 CSS 上改写 v-bind。若 additionalData 或预处理输出凭空加入新的 v-bind()，style 侧会生成 custom property，但 script 侧列表并不知道它。同理，预处理阶段新增的 :slotted() 不会回写 descriptor.slotted。上层不能假设 parse 的汇总状态会在 compileStyle 后自动同步。

09 / Bundler Boundary

交给构建器的产物、状态与失效线索

compiler-sfc 是底层库，不负责启动开发服务器或组装最终模块。它返回分支产物、依赖和 诊断线索，由 Vite/vue-loader 等调用方继续处理。

四个 API 怎样交接数据

source: App.vue
  │
  └─ parse(source, parseOptions)
       │
       ├─ descriptor ────────────────→ compileScript(descriptor, { id, ... })
       │                                ├─ content / map / imports
       │                                ├─ bindings ───────────────────────┐
       │                                └─ deps(type files)                │
       │                                                                     │
       ├─ template.{content, ast, map} ──────────────────────────────────┐   │
       ├─ styles.some(scoped) + descriptor.slotted ──────────────────────┤   │
       ├─ descriptor.cssVars（SSR）───────────────────────────────────────┤   │
       ├─ 上层生成的 id ──────────────────────────────────────────────────┤   │
       └─ compileScript 返回的 bindings ──────────────────────────────────┘   │
                                          │                                  │

       styles[i].{content,map,lang,scoped} + 同一个 id

上层构建器最后组装 script + render + scopeId，并把 CSS 交给自己的样式管线。

compileScript 的第一个参数是完整 SFCDescriptor；compileTemplate 与 compileStyle 都只接 options。不存在一个隐藏的“compileAll(descriptor)”替调用方传 bindings、id 和 flags。

同一个 App.vue 如何通过四个 API

这段代码到此只得到三个分支产物。它没有把 render 挂到组件、写入 __scopeId、加载模板生成的资源 import，也没有把 CSS 注入页面； 这些是上层构建插件的后续工作。后三个编译 API 使用同一个 id；parse() 不接收这个参数。而 scoped 是从各 style block 计算或逐块传入的，不是 descriptor 上的汇总字段。

阶段 进入时的关键状态 离开时发生了什么
parse 一份完整字符串 template AST/map；scriptSetup；scoped style；cssVars=['title']；slotted=false。
compileScript descriptor + id title → PROPS，count → SETUP_REF；生成运行时 prop/default；客户端 CSS vars 代码生成 "a1b2-title": (_ctx.title)。
上层转交 compiledScript.bindings + descriptor flags + id 把名字身份、scope 协议和原 template 输入装成 compileTemplate options。
compileTemplate AST/content/map + bindings + id + scoped 相对 logo 变模块 import；title/count 走已知 binding 路径；render 携带 scoped codegen 协议。
compileStyle style content/map + id + scoped .card[data-v-a1b2]；v-bind(title) → var(--a1b2-title)。
构建器组装 script、render、CSS、scope id、各自依赖 把 render/scopeId 挂到组件，交给模块图与 CSS 管线；此步不在 compiler-sfc 三个函数内部。
同一个 CSS 变量名如何在 JS、CSS 和 SSR 间对齐 
style 原文 ──parse──→ descriptor.cssVars = ['title']
                         ├─→ compileScript(client)
                         │     └─→ useCssVars(_ctx => ({ "a1b2-title": _ctx.title }))
                         └─→ compileTemplate(SSR)  ─→ ssrCssVars 首屏注入

style content ─→ 预处理器 ─→ compileStyle/cssVarsPlugin ─→ var(--a1b2-title)

上层生成的同一个 id = a1b2
  ├─→ compileScript    生成 JS 侧变量名
  ├─→ compileTemplate  生成 scope/SSR 协议
  └─→ compileStyle     生成 CSS 变量名与 scoped selector

client script 与 CSS 使用同一名字后，运行时才能把实例值写进元素 custom property；SSR 没有客户端 setup 注入那一步，所以 compileTemplate({ ssr: true }) 需要额外收到 ssrCssVars。这份列表仍由 descriptor 提供，但转交动作属于调用方。

跨阶段状态所有权：值从哪里来，谁负责转交

状态 生产者 消费者 关键不变量
descriptor parse compileScript 直接接收；上层拆字段给另两 API 它是结构快照，不包含最终 scope id，也不会自动编译三个分支。
bindings compileScript compileTemplate.compilerOptions.bindingMetadata inlineTemplate 自动转交；独立调用时由构建器转交。
id / scoped id 由上层生成；scoped 来自 style block script CSS vars、template scope codegen、style selector 三个分支必须用同一短 id；descriptor 只在每个 style block 上保存 scoped，没有汇总后的 scoped 字段。
slotted parse 扫 scoped style 原文 compileTemplate 的 slotted option；compileStyle 直接改 :slotted selector template 侧与 style 侧最终都围绕 data-v-id-s 协作。
cssVars parse 汇总 style 原文 compileScript 客户端注入；compileTemplate SSR 注入 compileStyle 不吃该数组，而是自己在实际 CSS 中找 v-bind；id 负责让两侧同名。
deps compileScript / compileStyle 分别产生 上层 watcher/HMR 类型依赖和样式依赖是两个集合；模板资产 import 不在其中。
errors 每个阶段 上层诊断系统 parse/template/style 常返回数组；script 与配置型错误常 throw，不能统一假设。

Source Map 也分三条链

产物 真实映射链 边界
script MagicString 生成代码 → 完整 .vue source MagicString 从完整 SFC 初始化，删除 block 外壳后仍保留原坐标；inline render map 再按插入行偏移合并。

缓存与失效逐项核对

缓存 key / 值 命中与失效边界

SFC block map 的具体坐标 
1 | <template>
2 |   <p>{{ msg }}</p>
3 | </template>
4 | <script>
5 | const msg = 'ok'
6 | </script>

template block (line 2, column 2) → App.vue (line 2, column 2)
script block   (line 2, column 6) → App.vue (line 5, column 6)

Source Map API：line 从 1 开始，column 从 0 开始。

上例先展示 parse 生成的 block → 完整 SFC 映射。compileTemplate 走字符串输入时，可把模板编译器的“render → template string”与这层 map 复合；走 descriptor AST 时则直接使用完整 SFC 坐标。这里的 script 是普通 block；script setup 不生成 parse block map，而由 compileScript 用完整 SFC 初始化 MagicString 并生成映射。模板预处理 缺少自己的语言转换 map。compileScript 的 MagicString map 从一开始就以 App.vue 为 source。

HMR 这条回调的边界：shouldForceReload 假设调用方已经确认 script 未变，只比较“旧 TS/TSX setup import 曾未被模板使用，而新模板开始使用”。这种 import 旧产物里可能已被裁掉，仅替换 render 补不回来，所以要求重载组件模块。

为什么 reactive const 仍可能需要重新赋值

reactive() 返回的对象本身可修改属性，但组件 v-model 的 update 事件语义是 name = $event，即替换整个绑定。const 不允许这种赋值。

修复跨越 script 和 template

单看 script 只能得到 SETUP_REACTIVE_CONST；compileScript 还会扫描已缓存的 template AST，发现 name 是 v-model 目标后，把声明从 const 改为 let，并把 bindingMetadata 同步降级为 SETUP_LET。

断言同时保护三层结果

content 保护生成 JS 可赋值，bindings 保护模板稍后采用可写路径，warning 则让用户知道源声明被编译器调整。只比较代码 snapshot 会漏掉后两个协议。

以 defineProps 为例，相关步骤是：processDefineProps → resolveTypeElements → genRuntimeProps → bindingMetadata → compileTemplate transformExpression → runtime props 校验。只看宏文件会漏掉一半语义。

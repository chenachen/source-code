02 / Foundation

第一阶段：先把平台与协议拆开

Vue 3 编译器的关键不是“换一个 parser”，而是让编译输出直接参与运行时优化。

core / platform 分层

通用模板语义进入 compiler-core，HTML/DOM 规则进入 compiler-dom，SSR 只复用适用部分。

AST 成为共享协议

parser、transform、codegen 通过明确节点类型协作，平台扩展无需复制整条管线。

编译期指导 runtime

PatchFlags、block tree、hoist 与 helper symbols 把动态性直接编码进产物。

演进结论：模块化不是为了目录整洁，而是为了让 parser、平台语义与运行时优化各自演进，同时依靠稳定中间协议连接。
03 / SFC Expansion

第二阶段：SFC 从容器变成静态分析中心

script setup 与类型宏让 compiler-sfc 不再只是 block splitter，而要理解 JavaScript/TypeScript 绑定与生命周期。

职责增长路径

Block parsetemplate/script/style
→
Script rewriteimports / default export / setup
→
Type-driven macrosprops / emits / model / slots
→
Cross-file analysistsconfig / cache / deps / HMR

为什么使用 Babel AST + MagicString

AST 负责正确理解作用域与类型语法，MagicString 负责尽量保留用户源码和 source map。重新打印整棵 JS AST 会改变格式、注释与映射。

为什么不直接调用完整 TypeScript checker

compiler-sfc 需要跨环境、快速、可由构建器注入 fs 的有限静态推导。它实现宏所需子集，遇到不确定类型保守退化。

04 / Parser Evolution

第三阶段：解析器更快，也更靠近编辑态

指令直接进入 tokenizer 意味着更少二次切分，但 tokenizer 状态与错误位置必须覆盖更多边界。

性能压力

单遍状态机、字符码和回调减少 token 对象与字符串分配，适合构建和 IDE 高频解析。

语法压力

动态参数、修饰符、简写、实体、RAW/RCDATA 与 SFC mode 组合形成大量状态迁移。

IDE 压力

用户输入经常处于未闭合状态；parser 要恢复稳定根结构，并把错误定位到准确字符。

重构 parser 的真正风险：不是合法模板能否生成相同 AST，而是非法/半成品模板的恢复树、错误码和 location 是否漂移。parse.spec.ts 的大矩阵就是演进护栏。
05 / Hardening

第四阶段：功能稳定后，问题转向组合边界

近期修复往往不是新增语法，而是某个特性在另一个作用域、缓存顺序、默认值或 SSR 拓扑中失效。

边界类型 典型组合 为什么难
作用域 props 解构 + 函数参数/catch/for/var 必须准确模拟 JavaScript 遮蔽与提升。
类型与运行时 defineModel default + getter/setter 类型 类型可更宽/更窄，但 runtime prop 与 emit 仍要匹配。
缓存上下文 global type 先加载，再作为模块导入 同一文件在不同 owner/asGlobal 语境下语义不同。
优化与身份 v-for handler、静态数组、VNode clone 看似可缓存的值可能携带迭代闭包或 DOM 引用。
SSR 拓扑 TransitionGroup + comments + hydration 服务器字符串与客户端过滤/展平行为必须同步。
06 / Design Drivers

推动架构变化的六种力量

理解这些力量，可以解释源码中大量看似“过度谨慎”的分支。

  1. P
    Performance。减少 parser 分配、render 创建、patch 遍历和 SSR helper 调用。
  2. D
    Developer Experience。script setup、类型宏、精确错误、IDE 残缺输入和 HMR。
  3. C
    Correctness。作用域、引用身份、默认值、浏览器 HTML 修正与 hydration。
  4. S
    Security。SSR 属性名/值转义、客户端副作用标签与 v-html 边界。
  5. B
    Bundle Size。构建标志、runtime helper 按需导入、浏览器/Node 实现分离。
  6. E
    Extensibility。compiler options、custom compiler、预处理器、fs 注入与平台 transforms。
07 / Issue Taxonomy

Issue 注释背后的重复模式

修复编号本身不是知识；能迁移到下一次排查的，是它属于哪种失效模式。

模式 A：状态泄漏

parser/tokenizer 或缓存把上一次编译状态带入下一次。检查 reset、cache key 与 owner context。

模式 B：作用域误判

局部变量被加 _ctx、props 被错误改写、handler 错误缓存。检查进入/退出登记是否成对。

模式 C：结构邻接

v-else、slot、注释、空白或节点删除改变兄弟关系。检查游标、过滤规则和分支 key。

模式 D：平台修正

浏览器会重排 HTML、表单控件语义不同、SVG/MathML namespace 切换。检查 platform options。

模式 E：优化过度

提升/缓存改变引用身份、捕获变量或保留 DOM 引用。先降低静态性，再证明可优化。

模式 F：同构错位

SSR 少/多一个注释、属性或 Fragment。比较真实 DOM 与客户端 VNode 拓扑。

修复往往是增加一个协议位

needArraySpread、SETUP_LET 和空 push 都不是新功能 API，而是把原先隐含的 “读取会被变异”、“模型需写回”、“slot 分支已输出”显式写入中间协议。

最小代码可能保护很长的因果链

needArraySpread = true 只有一行，背后却跨越 compiler cache、VNode clone、mountChildren、v-for/HMR 与 DOM 引用释放。只看 diff 会低估这一行的设计重量。

回归测试必须保留原组合

这三类问题都不是单个 API 的基本路径，而是缓存+v-for+HMR、 reactive+component v-model、slot+Transition+false branch 的交叉。把测试简化成单一特性会丢掉真正不变量。

08 / Trade-offs

当前实现接受了哪些取舍

好的源码解读不仅说“怎么做”，还应说明为什么没有选择看似更简单的方案。

取舍 获得 代价
原地 AST transform 少分配、插件可协作、容易挂 codegenNode 必须谨慎维护遍历游标与 currentNode。
模块级 parser 状态 热路径更少对象分配 reset 不完整会造成跨编译泄漏。
手写有限类型解析 轻量、跨环境、可注入 fs 只支持宏所需 TypeScript 子集。
MagicString 局部改写 保留用户格式、注释与映射 偏移计算和移动区间更复杂。
SSR 两遍转换 复用 core 语义并得到线性输出 需要第一遍元数据与第二遍上下文协议。
大量编译标记 runtime 极快路径 编译器与 runtime 必须同步维护协议。
09 / Practice

如何沿 Git 历史读一个设计

不要只看最终 diff；把引入、稳定、回归与后续修复连成一条小时间线。

定位当前 symbol

从函数、错误码、helper 或测试标题出发，明确今天的行为。

找首次引入

用 path/symbol/commit message 搜索最早实现，记录当时的最小目标。

找稳定节点

观察实验开关、警告和 release commit 何时移除，区分提案与稳定契约。

聚类后续修复

把 issue 按作用域、缓存、类型、平台或 hydration 分类，而不是逐条记忆。

回到测试

确认每次修复新增了哪条最小用例；测试通常比 commit 描述更精确。 

# 示例：沿路径看最早提交
git log --reverse --date=short --format='%h %ad %s' \
  -- packages/compiler-core

# 示例：追 script setup / defineModel
git log --all --grep='script setup' -i
git log --all --grep='defineModel' -i

# 示例：看某行为何存在
git blame packages/compiler-sfc/src/script/resolveType.ts
历史证据边界：本页只使用当前仓库本地 Git 可核对的信息。不同分支、backport 与尚未发布提交可能让时间线与其他 checkout 不同。

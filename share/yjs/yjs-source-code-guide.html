1. 先看结论

确定性

收敛点在 Item.integrate()

同一逻辑位置的并发插入不依赖消息到达顺序；origin、rightOrigin 与 (client, clock) 决定唯一链表顺序。

原子边界

已集成写入都经过事务

挂入 Doc 后的嵌套写入复用当前事务。observer、GC、结构合并、update 事件和子文档清理在最外层事务结束后统一执行。

状态差

同步不要求中心服务器

状态向量只描述每个 client 已知的下一个 clock；发送方据此编码缺失 struct，接收方缓存尚缺因果前驱的部分。

源码事实 一次公开 YType.insert() 先构造 lib0 Delta，再进入 YType.applyDelta()； 后者开启事务、创建 Item 并调用 integrate()。所以“数组、文本、属性”是同一套 CRDT 结构的不同视图，不是三套同步算法。

版本提醒：本仓库 main 已是 v14 RC 形态：src/index.js 导出统一的 Type，测试也使用 doc.get()、insert()、setAttr()。 根目录 README 与 INTERNALS 中仍可见 Y.Array、AbstractType 等旧叙事；本文只把它们用于有源码印证的算法背景。

3. 原问题与有证据的演进

协同编辑的难点不是“把最新 JSON 发过去”，而是离线副本都能产生操作、消息可能乱序或重复， 最终仍须得到相同结果。Yjs 把可编辑内容压成带稳定 ID 的列表 struct；删除成为单调集合事实， 状态向量用于只传对方缺少的 struct。

2016 · YATA 背景

仓库文档INTERNALS.md 指向 YATA 论文，并说明 Yjs 额外保存 originRight，用于改善大量并发插入同一位置时的处理。

列表统一数据模型

仓库文档数组是任意元素列表，文本是字符/格式标记列表，映射是同 key 条目的列表； 连续字符可压在一个跨多个 clock 的 Item 中，必要时再切分。

v14 · 单一共享类型

commit 69131b76提交信息明确写出“expose a single Yjs type only using lib0@v1 delta”； 随后的 301d3836 继续简化类型系统。当前入口只导出 YType as Type。

v14 · RDT 与 Renderer

commit 856d5b29把 YType 接入 lib0 RDT； 当前源码维护深层 Delta 缓存，并允许 Renderer 把 tombstone 渲染为带插入/删除归因的可见内容。

当前 HEAD · 资源清理

commit ceae18f4 / #797UndoManager.destroy() 取消文档 destroy 监听，修复销毁后仍保留 handler 的生命周期问题。

4. 核心对象：谁持有谁

Doc

根状态容器。持有顶层 share、StructStore、当前事务、待清理事务队列与子文档集合。网络 provider 不在核心仓库内。

YType

统一公开共享类型。列表内容由 _start 链表承载，属性由 _map 指向同 key 当前 Item；嵌套时自身由父 Item 的 ContentType 持有。

Transaction

一次原子变化的收集器。记录 insertSet、deleteSet、直接变化类型、祖先深层事件、待合并 struct 与子文档变化。

StructStore

按 client 分组、按 clock 递增保存 Item/GC/Skip；另持有已删除集合及缺因果依赖的 pending 更新。

Item

CRDT 的可定位结构单元。既处在文档序双向链表，也处在 client-clock 插入序；保存 origin、rightOrigin、parent、内容与状态位。

IdSet / IdMap

IdSet 用区间压缩插入/删除事实；IdMap 在相同 ID 范围上附加归因属性。快照、更新、Renderer、Undo 都复用它们。

6. 事务：原子性真正发生在哪里

Doc.transact() 只是转发。核心函数检查 doc._transaction： 没有活动事务才创建 Transaction；内层调用直接拿同一对象。最外层函数无论正常返回还是抛错， 都在 finally 中交给 cleanup。observer 在 cleanup 中再次写文档时，新事务进入同一队列，顺序清理而非递归嵌套。

源码摘录 · src/utils/Transaction.js · transact 省略类型注释 
export const transact = (doc, f, origin = null, local = true) => {
  const transactionCleanups = doc._transactionCleanups
  let initialCall = false
  let result = null

  if (doc._transaction === null) {
    initialCall = true
    doc._transaction = new Transaction(doc, origin, local)
    transactionCleanups.push(doc._transaction)
    if (transactionCleanups.length === 1) {
      doc.emit('beforeAllTransactions', [doc])
    }
    doc.emit('beforeTransaction', [doc._transaction, doc])
  }

  try {
    result = f(doc._transaction)
  } finally {
    if (initialCall) {
      const finishCleanup = doc._transaction === transactionCleanups[0]
      doc._transaction = null
      if (finishCleanup) cleanupTransactions(transactionCleanups, 0)
    }
  }
  return result
}

WHY：observer 先于 GC

observer 需要读取变化前后关联的 Item 与内容来计算事件 Delta；物理内容回收必须等通知阶段结束。随后 finally 仍保证异常 observer 不会跳过 GC、merge 与 update 清理。

失败与重入边界

回调异常会向调用方传播，但 cleanup 仍执行。observer 触发的新事务排到 _transactionCleanups 后方；这避免以 JavaScript 调用栈深度表达事务级联。

7. Item：把“到达顺序”变成“文档顺序”

Item 同时属于两套坐标：文档序由 left/right 双向链表示； 插入序由 (client, clock) 在 StructStore 中定位。 origin 与 rightOrigin 保存创建时看到的左右锚点。远端重放时先恢复这些依赖，再执行同一套冲突扫描。

字段作用关键约束
id(client, clock) 稳定地址；一个 Item 可覆盖连续多个 clock同 client 范围单调、不重叠
origin/rightOrigin创建时的左右逻辑锚点跨副本不因当前链表位置变化
left/right当前已集成文档序双向指针互相对应
parent/parentSub列表父类型或属性 key属性 key 的最右存活 Item 是当前值
infokeep、countable、deleted 位删除单调；可见长度只计未删除 countable 内容

连续内容为何能压成一个 Item

字符串或普通值数组可让一个 Item 覆盖多个 clock，降低对象数量。删除/插入命中中间位置时， getItemCleanStart/End 调用 split() 切出精确边界，ID 仍沿原 clock 区间连续。

删除为何不是“移出链表”

delete() 置 deleted 位、减少父可见长度并写 transaction.deleteSet；tombstone 仍提供因果锚点。 cleanup 在允许时把内容换成轻量 ContentDeleted 或 GC，不丢稳定地址。

异常/退化路径 若远端 Item 的 parent 无法定义，integrate() 用同 ID/长度集成 GC； 若缺的只是因果前驱，外层 integrateStructs() 不会走这里，而是先把 struct 留在 pending update。

重复

ss.exclude(knownState) 在集成前去掉本地已有范围；相同 update 重放不会再创建 Item。

乱序

若依赖也在本批 update 中，栈先切换到依赖 client；依赖完成后弹栈继续原 Item。

缺包

若前驱不在本地也不在本批，记录最小缺失 clock，把剩余 struct 重新编码到 pendingStructs.update。

发送侧：全量与最小差异其实是同一函数

9. Delta、事件与 Renderer：同一历史的不同视图

v14 的公开写接口先统一成 lib0 Delta。列表插入、文本格式、属性设置和嵌套修改最终都由 applyDelta() 分派；未集成的 YType 先把 Delta 累积进 _prelim， 挂入 Doc 后再重放。已删除且普通视图不可见的子类型拒绝变化；若 Renderer 仍显示该 tombstone， 方法返回逆 Delta，让调用方把未真正写入 CRDT 的界面变化撤回。

事件有两条兼容通道

传统 YEvent

transaction.changed 驱动直接类型 observer；callTypeObservers() 同时沿父链把事件加入 changedParentTypes，供 observeDeep。远端变化还会清空 search marker 并请求格式清理。

RDT Delta

cleanup 遍历同一 changedParentTypes，计算以各祖先为根的深层 Delta，更新 live cache 并发 delta 事件。因而嵌套变化在两套 API 中采用相同冒泡边界。

Renderer 不改历史，只改“哪些 tombstone 可见”

普通视图跳过 deleted Item；SnapshotRenderer、DiffRenderer、AttributionsRenderer 可把某些已删除内容投影成 带 attribution 的正向 insert/retain。由于一个物理 Item 可能被 Renderer 切成多段，光标推进、格式范围和相对位置 都必须调用 rendererContentLength()，不能直接使用 Item.length。

源码摘录 · src/ytype.js · typeApplyRendererChange Renderer 自身变化路径 
export const typeApplyRendererChange = (type, changes, origin) => {
  const hasDeltaListeners =
    (type._observers.get('delta')?.size ?? 0) > 0

  if ((type._delta === null && !hasDeltaListeners) || type.doc == null) {
    return
  }
  const change = type.toDelta({
    renderer: type._renderer,
    deep: true,
    itemsToRender: changes,
    retainInserts: true,
    retainDeletes: true
  })
  if (!change.isEmpty()) {
    type._delta?.apply(change)
    if (hasDeltaListeners) type.emit('delta', [change, origin])
  }
}

这里没有 Yjs Transaction：接受/拒绝建议可能只改变 attribution overlay。它只修正维护中的 Delta cache 与 RDT 监听者， 不触发传统 YEvent，也不创建 CRDT update。

10. Snapshot、RelativePosition 与 Undo：三种“回到过去”

能力锚点会否改当前历史关键限制
Snapshotstate vector + delete IdSet读取不改；恢复会构造新 Doc原 Doc 必须 gc:false
RelativePosition根 key/嵌套 type ID + item ID + assoc不会目标 struct 必须已同步；Renderer 会改变可见长度
UndoManager捕获事务的 insert/delete IdSet会，产生新事务受 scope、origin、captureTimeout 与并发覆盖约束

Snapshot：不是复制整棵对象树

源码摘录 · src/utils/Snapshot.js · snapshot / createDocFromSnapshot 关键边界

export const createDocFromSnapshot = (
  originDoc, snapshot, newDoc = new Doc()

    )
  }

Snapshot 的 state vector 决定“当时已出现哪些插入”，delete set 决定“当时哪些已删除”。 GC 一旦丢弃内容，就算 ID 仍在也无法重建旧值，所以恢复函数直接拒绝 gc:true 的原文档。

RelativePosition：把裸 index 换成稳定 ID

源码摘录 · src/utils/RelativePosition.js · createRelativePositionFromTypeIndex 左右吸附 
export const createRelativePositionFromTypeIndex = (
  type, index, assoc = 0, renderer = null
) => {
  let item = type._start
  if (assoc < 0) {
    if (index === 0) return createRelativePosition(type, null, assoc)
    index--
  }
  while (item !== null) {
    const len = rendererContentLength(renderer, item)
    if (len > index) {
      return createRelativePosition(
        type,
        createID(item.id.client, item.id.clock + index),
        assoc
      )
    }
    index -= len
    if (item.right === null && assoc < 0) {
      return createRelativePosition(type, item.lastId, assoc)
    }
    item = item.right
  }
  return createRelativePosition(type, null, assoc)
}

assoc < 0 锚向左字符，非负值锚向右字符。并发内容插入在锚点处时，两者会落在新内容两侧； 测试 testRelativePositionAssociationDifference 精确断言 index 1 与 2。

Undo：删除本次插入，重做本次删除

机制骨架 · 根据 src/utils/UndoManager.js 两个函数删节改写 不可直接执行 
// 捕获阶段
const insertions = transaction.insertSet
stack.push(new StackItem(insertions, transaction.deleteSet))
iterateStructsByIdSet(transaction, transaction.deleteSet, item => {
  if (item instanceof Item && inScope(item)) keepItem(item, true)
})

// 弹栈阶段
iterateStructsByIdSet(transaction, stackItem.inserts, struct => {
  if (struct instanceof Item && !struct.deleted && inScope(struct)) {
    itemsToDelete.push(struct)
  }
})
iterateStructsByIdSet(transaction, stackItem.deletes, struct => {
  if (struct instanceof Item && !stackItem.inserts.hasId(struct.id)) {
    itemsToRedo.add(struct)
  }
})
itemsToRedo.forEach(struct => redoItem(transaction, struct, itemsToRedo, ...))
for (let i = itemsToDelete.length - 1; i >= 0; i--) {
  itemsToDelete[i].delete(transaction)
}

上段是从两个真实函数拼接的源码骨架；inScope 与省略号代表原函数中重复的 scope/filter 参数， 不可直接执行。关键顺序未改：先重做删除，再从子到父逆序删除插入。

为何 keep tombstone UndoManager 捕获删除后对范围内 Item 调用 keepItem(item, true)，阻止 GC 丢掉待恢复内容； 清空栈时再解除 keep。Undo 因此是对 CRDT 历史做补偿操作，不是替换当前快照。

11. 完整执行链：A 写入，B 只收缺失差异

下面是可在仓库根目录直接执行的最小 ESM 示例。它从真实测试 tests/y-array.tests.js::testBasicUpdate 扩展出 state vector 差分与重复应用断言； 不依赖 provider，直接展示核心库负责的边界。

教程可运行示例 · 在 yjs 仓库根目录执行 包含初始化、输入、断言与清理 
import assert from 'node:assert/strict'
import * as Y from './src/index.js'

const docA = new Y.Doc()
const docB = new Y.Doc()

try {
  const listA = docA.get('items')
  listA.insert(0, ['A'])

  const stateVectorB = Y.encodeStateVector(docB)
  const missingForB = Y.encodeStateAsUpdate(docA, stateVectorB)

  Y.applyUpdate(docB, missingForB, 'from-A')
  assert.deepEqual(docB.get('items').toArray(), ['A'])

  // 同一更新重复到达：已知 ID 范围被排除，结果不变。
  Y.applyUpdate(docB, missingForB, 'duplicate')
  assert.deepEqual(docB.get('items').toArray(), ['A'])
} finally {
  docA.destroy()
  docB.destroy()
}
阶段变化前触发变化后 / 外部效果
公开写A 的 items 为空insert(0, ['A'])产生 Delta；尚未编码网络消息
CRDT 写store 无 A 的 structItem.integrate链表出现 Item；insertSet 记录其 ID 范围
事务提交observer 尚未调用最外层回调退出observer → GC/merge → 可选 update 事件

远端集成B 不认识该 IDapplyUpdatelocal=false 事务集成 Item；B 可见 ['A']

12. 并发插入手算：为什么两种到达顺序相同

为了手算，假设 client 10 与 client 20 都在空列表位置 0 离线插入一个元素。 两个 Item 的 origin = null、rightOrigin = null， ID 分别为 (10,0) 与 (20,0)。

副本 P：先收到 B，再收到 A

先集成
B (20,0)
→
集成 A 时
20 < 10 为假
→
同 rightOrigin
立即 break

A 的 left 保持 null，所以 A 插到 B 前：A, B。

副本 Q：先收到 A，再收到 B

先集成
A (10,0)
→
集成 B 时
10 < 20 为真
→
left = A
继续扫描

B 插到 A 后：仍是 A, B。

这不是“client 小者永远在左”的全部算法，只是同 origin、同 rightOrigin 的最小冲突分支。 若 origin 图不同，itemsBeforeOrigin 与 conflictingItems 会把因果依赖已在前方的 Item 作为可越过边界，避免把一个操作插进它未曾看到的依赖组内部。

时间

单次 Item 集成最坏扫描当前冲突区间 k，为 O(k)；按 client-clock 找 struct 使用二分定位。

空间

tombstone 与稳定 ID 换取离线因果锚点。GC 可丢内容但保留轻量结构；Undo 用 keep 保护待恢复内容，Snapshot 恢复则要求原文档全局 gc:false。

索引优化

裸链表按 index 查找是线性；YType 最多缓存 80 个 search marker，优先从接近目标的位置继续扫描。

当前实现推断 80 个 marker 是对编辑局部性的经验性优化，不改变任何 CRDT 结果；测试 #297 的长度回归同时断言 length === toArray().length，防止缓存位置与真实可见链漂移。

14. 边界、审计结果与继续阅读

核心库明确不做

  • 网络连接、重连、awareness、持久化与 provider 调度。
  • 用户认证、写权限、应用 schema 校验与富文本 XSS 清洗。
  • 把不可信 peer 的二进制 update 安全地“筛掉某些字段”。
  • 为所有输入自动设置消息大小、CPU 或内存上限。

使用时必须记住

  • Snapshot 恢复旧值要求原文档保留内容，即 gc:false。
  • Undo 只捕获 scope 与 trackedOrigins 接受的事务，不是全局历史回退。
  • Renderer 展示 tombstone 不等于撤销删除，也不会产生 CRDT update。
  • 本教程针对 v14 RC 当前 commit，不能套用到稳定版 v13 的类层次。

安全边界：THREAT_MODEL.md 明确把 Yjs 定位为可信写 peer 间的 CRDT。 有写权限的恶意 peer 可以永久写入破坏性操作；服务端选择性过滤二进制 update 不是可靠安全边界。 建议/不可信用户应在独立文档 fork 工作，由可信方审阅合并。入口处仍应做认证、消息大小限制与畸形输入防护。

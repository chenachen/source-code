1. 先看结论

确定性

收敛点在 Item.integrate()

同一逻辑位置的并发插入不依赖消息到达顺序；origin、rightOrigin 与 (client, clock) 决定唯一链表顺序。

通知批次

已集成写入都经过事务

挂入 Doc 后的嵌套写入复用当前事务。内容立即改变，observer、GC、结构合并、update 事件和子文档处理等到最外层回调退出；抛错不会回滚此前的写入。

状态差

同步不要求中心服务器

状态向量描述每个 client 连续已知前缀的末端；发送方据此裁剪 struct，并另发删除集合。接收方缓存尚缺因果依赖的部分。

这里的 Delta 是一次有顺序的编辑描述：retain(n) 越过 n 个位置，也可修改这些位置的格式； insert 在当前位置插入内容，delete(n) 删除 n 个位置，属性操作则按 key 设置或删除值。 它面向共享类型的内容；后面用于同步的 binary update 还包含 CRDT 的 ID 与因果关系，是另一种表示。

源码事实 一次公开 YType.insert() 先构造 lib0 Delta，再进入 YType.applyDelta()； 后者开启事务、创建 Item 并调用 integrate()。所以“数组、文本、属性”是同一套 CRDT 结构的不同视图，不是三套同步算法。

版本提醒：本地源码包为 @y/y 14.0.0-rc.24：src/index.js 导出统一的 Type，测试也使用 doc.get()、insert()、setAttr()。 根目录 README 与 INTERNALS 中仍可见 Y.Array、AbstractType 等旧叙事；本文只把它们用于有源码印证的算法背景。

3. 协同编辑的问题与当前数据模型

协同编辑的难点不是“把最新 JSON 发过去”，而是离线副本都能产生操作、消息可能乱序或重复， 最终仍须得到相同结果。Yjs 把可编辑内容压成带稳定 ID 的列表 struct；删除成为单调集合事实， 状态向量用于只传对方缺少的 struct。

2016 · YATA 背景

仓库文档INTERNALS.md 指向 YATA 论文，并说明 Yjs 额外保存 originRight，用于改善大量并发插入同一位置时的处理；当前源码字段名为 rightOrigin。

列表统一数据模型

仓库文档数组是任意元素列表，文本是字符/格式标记列表，映射是同 key 条目的列表； 连续字符可压在一个跨多个 clock 的 Item 中，必要时再切分。

v14 · 单一共享类型

src/index.js / src/ytype.js当前入口导出 YType as Type。 同一类型承载列表与属性，公开写入先转成 lib0 Delta，再创建对应内容的 Item。

v14 · RDT 与 Renderer

src/ytype.js / Renderer.jsYType 实现 lib0 RDT 的 applyDelta、delta 与事件接口；Renderer 决定历史内容的可见投影，深层 Delta 缓存随事务或视图变化更新。

4. 核心对象：谁持有谁

Doc

根状态容器。持有顶层 share、StructStore、当前事务、待清理事务队列与子文档集合。网络 provider 不在核心仓库内。

YType

统一公开共享类型。列表内容由 _start 链表承载，属性由 _map 指向同 key 当前 Item；嵌套时自身由父 Item 的 ContentType 持有。

Transaction

一次变化批次的收集器。记录 insertSet、deleteSet、直接变化类型、祖先深层事件、待合并 struct 与子文档变化。

StructStore

按 client 分组、按 clock 递增保存 Item/GC/Skip；另持有已删除集合及缺因果依赖的 pending 更新。

Item

CRDT 的可定位结构单元。既处在文档序双向链表，也处在 client-clock 插入序；保存 origin、rightOrigin、parent、内容与状态位。clock 是该 client 的内容地址：普通值数组按元素占用，字符串按 UTF-16 代码单元占用，格式项与嵌套类型各占一个。

IdSet / IdMap

IdSet 用区间压缩插入/删除事实；IdMap 在相同 ID 范围上附加归因属性。快照、更新、Renderer、Undo 都复用它们。

6. 事务：写入与通知如何分批

Doc.transact() 只是转发。核心函数检查 doc._transaction： 没有活动事务才创建 Transaction 并排入清理队列；内层调用直接拿同一对象。 写入当场改变链表与 store，事务负责合并通知，不提供回滚。最外层写入回调正常返回或抛错时， finally 都会清空活动事务并启动 cleanup。observer 再次写文档会创建新事务， 加到同一队列后方，等当前清理完成后再处理。

源码摘录 · src/utils/Transaction.js · transact 省略类型注释 
export const transact = (doc, f, origin = null, local = true) => {
  const transactionCleanups = doc._transactionCleanups
  let initialCall = false
  let result = null

  if (doc._transaction === null) {
    initialCall = true
    doc._transaction = new Transaction(doc, origin, local)
    transactionCleanups.push(doc._transaction)
    if (transactionCleanups.length === 1) {
      doc.emit('beforeAllTransactions', [doc])
    }
    doc.emit('beforeTransaction', [doc._transaction, doc])
  }

  try {
    result = f(doc._transaction)
  } finally {
    if (initialCall) {
      const finishCleanup = doc._transaction === transactionCleanups[0]
      doc._transaction = null
      if (finishCleanup) cleanupTransactions(transactionCleanups, 0)
    }
  }
  return result
}

回调退出后，清理按以下阶段执行

beforeObserverCalls 后先通知 type、deep、delta 与 afterTransaction，随后执行 GC、merge 和 clientID 检查，再发 afterTransactionCleanup、有内容且已监听的 update 及子文档事件。队列最后一项完成后才发 afterAllTransactions。

observer 为什么先于 GC

observer 需要读取事务涉及的 Item 与内容来计算事件 Delta，所以内容回收安排在通知之后。通知阶段进入的 finally 会继续尝试 GC、merge 与 update 编码；清理阶段自身的监听器若抛错，后面的步骤仍可能被中断。

失败与重入边界

写入回调抛错时，已发生的修改仍会进入清理与通知。observer 触发的新事务不会立即嵌套执行 cleanup；当前事务收尾后，cleanupTransactions(queue, i + 1) 递归处理下一项，队列为空才发 afterAllTransactions。

写入回调中的嵌套，与 observer 中的重入

下面把两个时机放在同一张队列图中：外层事务 T1 插入 A，写入回调中的嵌套 transact() 复用 T1；T1 的 observer 只在第一次通知时追加 B，形成 T2。这里注册了 update 监听，所以两笔有内容的事务各自编码并发出更新。

7. Item：把“到达顺序”变成“文档顺序”

Item 同时属于两套坐标：文档序由 left/right 双向链表示； 插入序由 (client, clock) 在 StructStore 中定位。 origin 与 rightOrigin 保存排序所需的因果锚点。远端重放时先恢复这些依赖， 若恢复出的左右邻居已经被并发项隔开，再扫描冲突区间确定插入位置；邻居仍相邻时可以直接连接。

字段作用关键约束
id(client, clock) 稳定地址；一个 Item 可覆盖连续多个 clock同 client 范围单调、不重叠
origin/rightOrigin创建时的左右逻辑锚点并发插入不会让锚点随链表漂移；切分右段或裁剪前缀时会派生更精确的 origin
left/right当前已集成文档序双向指针互相对应
parent/parentSub父类型与可选属性 key属性 map 指向版本链最右 Item；该项被删除后不回退到旧版本
infokeep、countable、deleted、marker 位deleted 单向设置；keep 保护内容不被 GC；原始列表长度只计未删除 countable 内容

冲突扫描用各副本一致的 ID 与 origin 关系仲裁，而不是按消息先后排列。找到左邻居后，函数重连链表、 更新 _start 或属性 map、调整可见长度、写入 transaction.insertSet 与 StructStore， 再调用内容对象的 integrate()。属性新项若成为最右项，会删除前一版本； 若排在另一个属性版本左侧，它自身立即成为墓碑。因此同 key 的并发赋值最后只留下排序胜出的当前值。

连续内容为何能压成一个 Item

字符串或普通值数组可让一个 Item 覆盖多个 clock，降低对象数量。删除/插入命中中间位置时， getItemCleanStart/End 调用 split() 切出精确边界，ID 仍沿原 clock 区间连续。

删除为何不是“移出链表”

delete() 置 deleted 位、减少父可见长度并写 transaction.deleteSet；tombstone 仍提供因果锚点。 cleanup 在允许时把内容换成轻量 ContentDeleted 或 GC，不丢稳定地址。

异常/退化路径 若远端 Item 的 parent 无法定义，integrate() 用同 ID/长度集成 GC； 若缺的只是因果前驱，外层 integrateStructs() 不会走这里，而是先把 struct 留在 pending update。

8. 更新协议：乱序、重复与缺依赖如何处理

V1/V2 只是二进制布局不同，语义主线相同：读取 struct block，排除本地已知 ID， 按因果依赖集成可用 struct；再读取删除 ID 集。状态向量是 client → nextClock： clock 之前的结构已经连续掌握。存在 Skip 空洞时，getStateVector() 停在最早空洞，发送方才不会把空洞后的结构误当作对方已完整拥有。store.getClock() 则读取存储数组尾端，两者在有 Skip 时不同。

重复

ss.exclude(knownState) 在集成前去掉本地已有的真实结构范围，Skip 空洞除外；相同 update 重放不会再创建 Item，删除集合仍按幂等规则处理。

乱序

若依赖也在本批 update 中，栈先切换到依赖 client；依赖完成后弹栈继续原 Item。

缺包

若因果依赖不在本地也不在本批，记录缺失 client 的存储尾 clock，把无法集成的依赖链编码到 pendingStructs.update。不依赖该缺口的结构仍可集成，必要时用 Skip 补齐存储 clock 空洞。

后续 update 若携带旧 pending 缺失的 client，或该 client 的存储尾 clock 已推进， readUpdateV2() 会先清空 pending 槽，再在当前事务内重新应用合并后的 V2 字节； 依赖仍不齐时会重新保存余量。删除也可能先于被删 Item 到达：已存在的范围立即删除， 剩余范围写入 pendingDs，每次接收 update 都会在结构集成后重新尝试。

export const encodeStateAsUpdateV2 = (
  doc,
  encodedTargetStateVector = new Uint8Array([0]),
  encoder = new UpdateEncoderV2()
) => {
  const targetStateVector = decodeStateVector(encodedTargetStateVector)
  writeStateAsUpdate(encoder, doc, targetStateVector)
  const updates = [encoder.toUint8Array()]

  if (doc.store.pendingDs) updates.push(doc.store.pendingDs)
  if (doc.store.pendingStructs) {
    updates.push(diffUpdateV2(
      doc.store.pendingStructs.update,
      encodedTargetStateVector
    ))
  }
  if (updates.length > 1) {
    if (encoder.constructor === UpdateEncoderV1) {
      return mergeUpdates(updates.map((update, i) =>
        i === 0 ? update : convertUpdateFormatV2ToV1(update)
      ))
    } else if (encoder.constructor === UpdateEncoderV2) {
      return mergeUpdatesV2(updates)
    }
  }
  return updates[0]
}

空 state vector 会发送全部结构；给出目标 state vector 则裁掉对方连续掌握的结构前缀。 状态向量不记录删除，所以 writeStateAsUpdate() 始终写入完整的 store.ds， 这不是所有数据的最小差异。pending 结构和删除也会被带上，中继节点因此能转发它暂时无法集成的历史。 pending 在 store 中固定保存为 V2；若调用的是 V1 入口，合并前会把 pending 字节转换成 V1。

9. Delta、事件与 Renderer：同一历史的不同视图

v14 的公开写接口先统一成 lib0 Delta。列表插入、文本格式、属性设置和嵌套修改最终都由 applyDelta() 分派；未集成的 YType 先把 Delta 累积进 _prelim， 挂入 Doc 后再重放。已删除且普通视图不可见的子类型拒绝变化；若 Renderer 仍显示该 tombstone， 方法返回逆 Delta，让调用方把未真正写入 CRDT 的界面变化撤回。

机制骨架 · 根据 src/ytype.js · insert / applyDelta 删节 省略嵌套 fix 与属性分支，不可直接执行 
insert (index, content, format) {
  this.applyDelta(
    delta.create()
      .retain(index)
      .insert(content, format)
      .done()
  )
}

applyDelta (d, origin = null, { renderer = this._renderer } = {}) {
  if (d.isEmpty()) return null
  if (this.doc == null) {
    (this._prelim || (this._prelim = delta.create())).apply(d)
    return null
  }
  if (this._item !== null && this._item.deleted) {
    if (rendererContentLength(renderer, this._item) > 0) {
      const inv = delta.inverse(d, this.toDeltaDeep({ renderer }))
      return inv.isEmpty() ? null : inv
    }
    return null
  }
  return transact(this.doc, transaction => {
    const currPos = new ItemTextListPosition(
      null, this._start, 0, new Map(), renderer
    )
    for (const op of d.children) {
      if (delta.$textOp.check(op)) {
        insertContent(transaction, this, currPos, new ContentString(op.insert), op.format || {})
      } else if (delta.$insertOp.check(op)) {
        insertContentHelper(transaction, this, currPos, op.insert, op.format || {})
      } else if (delta.$retainOp.check(op)) {
        currPos.formatText(transaction, this, op.retain, op.format || {})
      } else if (delta.$deleteOp.check(op)) {
        deleteText(transaction, currPos, op.delete)
      }
      // modify / 属性分支见原函数。
    }
  }, origin)
}

事件有两条兼容通道

传统 YEvent

transaction.changed 驱动直接类型 observer；callTypeObservers() 同时沿父链把事件加入 changedParentTypes。cleanup 为每个祖先调用 observeDeep 时，使用以该祖先为 target 的 YEvent。 远端变化还会清空 search marker；涉及格式的类型会请求后续格式清理。

RDT Delta

cleanup 遍历同一 changedParentTypes，计算以各祖先为根的深层 Delta，更新 live cache 并发 delta 事件。因而嵌套变化在两套 API 中采用相同冒泡边界。

Renderer 不改历史，只改“哪些 tombstone 可见”

普通视图跳过 deleted Item；SnapshotRenderer、DiffRenderer、AttributionsRenderer 可把某些已删除内容投影成 正向内容。DiffRenderer 与 AttributionsRenderer 还会附上插入/删除归因。一个物理 Item 可以渲染成多段， rendererContentLength() 用来读取 Renderer 提供的计长结果。 length、get() 和 slice() 仍按未删除 countable 内容的原始坐标工作， 而 toDelta() 与 toArray() 可以包含 Renderer 展示的墓碑；使用建议视图时要区分这两种坐标。 SnapshotRenderer 还有一处区别：它对当前存活 Item 的计长直接使用 item.length， 而内容渲染会按快照 state vector 隐藏后来的片段，因此不能把它当作所有索引 API 的历史坐标适配器。

例如 client 7 在 gc:false 的文档中插入 A、B、C，再删除 B。给 B 的 ID 范围添加 Bob 的删除归因并安装 AttributionsRenderer 后，同一份链表可投影成下面两种结果。

源码摘录 · src/ytype.js · typeApplyRendererChange Renderer 自身变化路径 
export const typeApplyRendererChange = (type, changes, origin) => {
  const hasDeltaListeners =
    (type._observers.get('delta')?.size ?? 0) > 0

  if ((type._delta === null && !hasDeltaListeners) || type.doc == null) {
    return
  }
  const change = type.toDelta({
    renderer: type._renderer,
    deep: true,
    itemsToRender: changes,
    retainInserts: true,
    retainDeletes: true
  })
  if (!change.isEmpty()) {
    type._delta?.apply(change)
    if (hasDeltaListeners) type.emit('delta', [change, origin])
  }
}

这条路径响应 Renderer 发出的变化，不创建 Yjs Transaction。它计算视图增量、原地更新已维护的 Delta cache， 并通知 RDT delta 监听者，不触发传统 YEvent 或 CRDT update。 另一个入口 useRenderer() 切换整个视图时会重新渲染，并替换已有缓存对象。 归因属性变化表示展示方式变化；要把接受或拒绝建议写入共享历史，还需要相应的 CRDT 操作。

10. Snapshot、RelativePosition 与 Undo：历史切面、稳定位置与撤销

能力锚点会否改当前历史关键限制
Snapshotstate vector + delete IdSet读取不改；恢复默认写入新 Doc源 Doc 必须 gc:false 且所需历史内容仍在；非空目标不会被回滚
RelativePosition根 key/嵌套 type ID + item ID + assoc不会内容锚点必须已同步；解析可按 Renderer 计长，类型末尾端点用原始 _length

Snapshot：不是复制整棵对象树

export const createDocFromSnapshot = (

Snapshot 的 state vector 决定“当时已出现哪些插入”，delete set 决定“当时哪些已删除”。 GC 一旦丢弃内容，就算 ID 仍在也无法重建旧值，所以恢复函数直接拒绝 gc:true 的原文档； 事后改成 gc:false 也不能找回已经回收的内容。函数把快照边界内的结构及当时的删除集编码为 update， 再应用到目标 Doc。默认目标为空，因而可重建旧切面；传入非空目标时只是合并，目标已有的后续操作不会被撤销。

RelativePosition：把裸 index 换成稳定 ID

源码摘录 · src/utils/RelativePosition.js · createRelativePositionFromTypeIndex 左右吸附 
export const createRelativePositionFromTypeIndex = (
  type, index, assoc = 0, renderer = null
) => {
  let item = type._start
  if (assoc < 0) {
    if (index === 0) return createRelativePosition(type, null, assoc)
    index--
  }
  while (item !== null) {
    const len = rendererContentLength(renderer, item)
    if (len > index) {
      return createRelativePosition(
        type,
        createID(item.id.client, item.id.clock + index),
        assoc
      )
    }
    index -= len
    if (item.right === null && assoc < 0) {
      return createRelativePosition(type, item.lastId, assoc)
    }
    item = item.right
  }
  return createRelativePosition(type, null, assoc)
}

assoc < 0 锚向左字符，非负值锚向右字符。在同一边界插入新内容时，两者会落在新内容两侧； 测试 testRelativePositionAssociationDifference 精确断言 index 1 与 2。 内容锚点被删除后仍可解析为折叠位置，不会仅因 deleted 就失效。两侧转换使用 Renderer 时应传入同一个实例； 当前实现中，非负 assoc 的类型末尾端点直接返回 type._length，并不累计 Renderer 展示的墓碑长度。

Undo：删除本次插入，重做本次删除

机制骨架 · 根据 src/utils/UndoManager.js 两个函数删节改写 不可直接执行 
// 捕获阶段
const insertions = transaction.insertSet

  if (item instanceof Item && inScope(item)) keepItem(item, true)

// 弹栈阶段

  if (struct instanceof Item && !struct.deleted && inScope(struct)) {
    itemsToDelete.push(struct)
  }
})
iterateStructsByIdSet(transaction, stackItem.deletes, struct => {
  if (struct instanceof Item && !stackItem.inserts.hasId(struct.id)) {
    itemsToRedo.add(struct)
  }
})
itemsToRedo.forEach(struct => redoItem(transaction, struct, itemsToRedo, ...))
for (let i = itemsToDelete.length - 1; i >= 0; i--) {
  itemsToDelete[i].delete(transaction)
}

上段是从两个真实函数拼接的源码骨架；inScope 与省略号代表原函数中重复的 scope/filter 参数， 不可直接执行。关键顺序未改：先重做删除，再逆序删除候选插入项，通常使子项先于父项删除。

捕获先检查 captureTransaction、scope 与 trackedOrigins。 默认 trackedOrigins 包含 null，所以通常捕获未指定 origin 的编辑；它没有额外检查 transaction.local，远端应用也应带上用于区分来源的 origin。 相邻普通事务可在 captureTimeout 内合并，stopCapturing() 强制下一次另起一步。 栈项记录整笔事务的 ID 集，设置 keep 以及弹栈执行时才逐 Item 检查 scope。 恢复尚未重做的删除项时，redoItem() 不清除原 Item 的 deleted 位，而是复制内容、分配新 ID， 再把原项的 redone 指向新项。撤销事务以 UndoManager 自身为 origin，被捕获到 redo 栈；重做则捕获回 undo 栈。

把撤销的 ID 变化展开来看：client 10 先写入文本 A，然后创建 UndoManager。初始插入不会入栈；删除、撤销、重做各执行一步，下图记录每次调用返回后的状态。

为何 keep tombstone UndoManager 捕获删除后对范围内 Item 调用 keepItem(item, true)，阻止 GC 丢掉待恢复内容； 清空栈时再解除 keep。Undo 因此是对 CRDT 历史做补偿操作，不是替换当前快照。

12. 并发插入手算：为什么两种到达顺序相同

为了手算，假设 client 10 与 client 20 都在空列表位置 0 离线插入一个元素。 两个 Item 的 origin = null、rightOrigin = null， ID 分别为 (10,0) 与 (20,0)。

上述比较适用于同 origin、同 rightOrigin 的冲突，不能把整条列表按 client ID 排序。 origin 不同时，itemsBeforeOrigin 保存已扫描过的全部 Item， conflictingItems 保存自上次确定左边界以来的冲突项。 若候选项的 origin 在已扫描前缀中且已离开当前冲突集合，就可以把 left 推进到该候选项； 若 origin 仍在冲突集合中，扫描继续但不推进 left；origin 不在已扫描前缀则停止。 这让由先前插入派生的后续插入跟随其因果位置，而不是再次按自己的 client 大小跨过整个区间。

时间

一次冲突扫描最多遍历当前冲突区间的 k 个 Item，扫描成本为 O(k)；按 client-clock 找 struct 使用二分定位。

空间

tombstone 与稳定 ID 换取离线因果锚点。GC 可丢内容但保留轻量结构；Undo 用 keep 保护待恢复内容，Snapshot 恢复则要求原文档全局 gc:false。

索引优化

裸链表按 index 查找是线性。findMarker() 最多维护 80 个 search marker，供 get() 与旧列表定位助手从邻近位置扫描。当前公开 insert/applyDelta 从列表起点创建游标，不通过该函数定位。

源码与测试 marker 只缓存位置，不参与 Item 的并发排序。测试 #297 在交错插入、删除和嵌套事务后多次断言 length === toArray().length，检查当前公开写入路径维护的可见长度。缓存定位使用另一条 findMarker() 路径。

  • 网络连接、重连、awareness、持久化与 provider 调度。
  • 用户认证、写权限、应用 schema 校验与富文本 XSS 清洗。
  • 把不可信 peer 的二进制 update 安全地“筛掉某些字段”。
  • 为所有输入自动设置消息大小、CPU 或内存上限。

使用时必须记住

  • Snapshot 恢复要求原文档 gc:false 且仍保留所需内容；默认向空 Doc 重建历史切面。
  • Undo 的捕获受 scope、trackedOrigins 和 captureTransaction 控制，撤销后仍保留其他事务的操作。
  • Renderer 展示 tombstone 不等于撤销删除，也不会产生 CRDT update。
  • 本教程针对本地 @y/y 14.0.0-rc.24 的统一 Type API；v13 的 Array/Text/Map 类层次不同。

安全边界：THREAT_MODEL.md 明确把 Yjs 定位为可信写 peer 间的 CRDT。 有写权限的恶意 peer 可以永久写入破坏性操作；服务端选择性过滤二进制 update 不是可靠安全边界。 建议/不可信用户应在独立文档 fork 工作，由可信方审阅合并。入口处仍应做认证、消息大小限制与畸形输入防护。

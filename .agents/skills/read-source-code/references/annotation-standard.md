# 源码注释标准

注释优先回答源码本身难以表达的问题：当前职责、上下游、设计原因、状态变化、不变量、失败边界和已证实的历史场景。只记录有证据、能长期成立的信息；推断必须标记。

## 声明级覆盖门禁

完整任务编辑前必须建立声明级清单，编辑后重新审计。至少盘点：

- 命名函数、方法、构造器、getter/setter 和函数值属性；
- 类、接口、类型别名、枚举及其成员；
- 类或类型字段、顶层常量；
- 关键算法块、状态迁移块和代表性测试。

每项记录文件、符号、类别和状态：`已有且充分`、`已翻译扩写`、`新补充`、`豁免`。`豁免`必须带具体原因；未归类项必须为零。不得用“已处理主要文件”“核心路径基本覆盖”等文件级描述替代声明级结果。

使用 `../scripts/audit-comment-coverage.mjs` 做结构筛查。示例：

```bash
node .agents/skills/read-source-code/scripts/audit-comment-coverage.mjs \
  --root /path/to/repository \
  --path src \
  --path test \
  --typescript /path/to/repository/node_modules/typescript/lib/typescript.js \
  --exemptions /path/to/comment-exemptions.json \
  --fail-on-missing
```

脚本使用目标仓库的 TypeScript 编译器解析 JS、JSX、TS 和 TSX；若依赖不在默认位置，用 `--typescript` 指定。脚本无法加载兼容解析器或存在解析错误时，审计失败，不得静默退回不完整统计。脚本只检查注释结构是否存在，不能判断中文质量、机制准确性或注释是否充分；这些必须人工复核。

豁免文件格式：

```json
{
  "exemptions": {
    "src/example.ts#field#Example.value": "字段语义完全由公开字面量联合类型限定"
  }
}
```

生成文件、第三方 vendored 代码和明确排除的声明文件优先从扫描路径排除。完整任务中，命名函数、方法和构造器不得以“简单”“私有”或“薄包装”为由豁免；用简短 TSDoc 说明其职责或转发关系。

## 函数与 TSDoc

为扫描范围内全部命名函数、方法、构造器、getter/setter 和函数值属性补 TSDoc。简单 getter、薄包装和语义清晰的私有函数也保留一行职责说明；复杂函数再展开上下游、WHY、状态和边界。匿名内联回调仅在承载关键状态、异步、错误恢复或资源清理语义时补注释。

首句概括职责；按需补充上下游、WHY、副作用、状态变化和边界。`@param` 不重复类型，只解释领域语义、单位或约束。不要机械填满模板。

```ts
/**
 * 将已验证的批次提交给调度器。
 *
 * @remarks
 * 上游：批次解析器校验成功后调用。
 * 下游：写入待执行队列，并唤醒调度循环。
 * WHY：先持久化再唤醒，避免任务已通知但尚未落盘。
 * 状态：批次从 `validated` 转为 `queued`。
 * 边界：空批次直接返回；重复批次由幂等键去重。
 *
 * @param batch - 已通过结构和权限校验的批次。
 * @returns 实际进入队列的任务数量。
 */
```

已有英文解释性注释时，保留准确信息并改写为更清楚的中文解释；不能因为已有英文短句就计为完成。不得翻译或删除许可证、`eslint`/TypeScript 指令、工具 magic comments、生成标记和外部 API 要求保留的注释。

## 常量、类型与枚举

- **常量**：解释业务含义、单位、来源、阈值原因和适用边界。
- **类型**：解释领域角色、所有权、生命周期和字段间不变量。
- **枚举**：解释各成员的语义、关键转移和终态。
- **字段**：完整任务中逐项审查；不能从名称与类型直接理解的语义或约束必须注释，其余项在清单中说明充分或豁免原因。

不要写同义翻译，例如“`Pending` 表示等待中”。

## 关键代码块

在非直观算法、顺序依赖、并发控制、缓存、回退、错误恢复和性能取舍前补块级注释。解释约束与意图，不逐行复述控制流。

```ts
// WHY：必须先登记订阅者再读取快照，否则更新可能发生在两步之间并永久丢失。
// 状态：此块结束后，订阅者要么收到新事件，要么持有同一版本快照。
// 边界：取消订阅可能与分发并发，因此 cleanup 必须幂等。
```

已确认 issue 时写清触发场景及可追溯引用。没有可靠证据时，只描述可观察场景；不编造 issue 编号、历史原因或作者意图。

## 测试用例

把测试视为设计证据。复杂用例按 Given–When–Then 说明场景、唯一触发动作、可观察结果和验证机制。

```ts
/**
 * Given：队列已有相同幂等键的任务。
 * When：再次提交同一批次。
 * Then：不创建新任务，并返回原任务标识。
 *
 * 验证机制：同时断言返回值与存储层写入次数，证明结果不是重复写入后的偶然一致。
 * 对应源码：`enqueueBatch()` 的幂等分支。
 */
```

避免给每个 `expect` 写注释。重点解释 fixture 意义、触发点、断言为何足以证明目标机制。测试头通常只需说明场景和验证目标；只有复杂链路才展开完整模板。

## 源码摘录、完整示例与伪代码

- 可执行示例必须包含必要 import、初始化、输入、调用、断言和清理。
- 优先选最小但经典的仓库测试或官方示例，不用单行操作冒充完整 Demo。
- 省略依赖、配置或环境条件时，明确列出。
- 源码片段标为“源码摘录”，注明文件、符号和版本；省略部分显式标记。
- 改写真实实现时，说明改写目的与差异。
- 伪代码标为“伪代码（不可执行）”，不得伪装成仓库源码。

## 避免注释噪音

不要：

- 翻译变量名、函数名或语法；
- 为明显赋值、分支、循环逐行加注释；
- 重复类型系统已表达的信息；
- 在每层重复同一调用链说明；
- 写容易过期的行号或临时实现细节；
- 用注释掩盖命名混乱；
- 写未经源码、测试、issue 或历史支持的 WHY。

优先注释稳定意图、关键不变量和失败边界。

## 验证策略

纯注释变更至少重新运行声明级覆盖审计并检查 diff，确认未分类缺口为零、只有注释变化、位置正确、术语和引用准确。人工抽查每类声明和所有关键机制，避免用空泛 TSDoc 通过结构检查。不要仅因补注释机械运行完整测试套件。

仅在以下情况运行针对性检查：

- 修改了代码或测试逻辑；
- 新增或修改可执行 Demo；
- TSDoc、文档生成器、lint 或仓库规则会解析本次注释；
- 注释位置可能影响语法或构建产物。

未运行测试时明确报告：`未运行测试（仅注释/文档变更）`。不得把未执行测试描述为通过。

# Read Source Code

把源码转化为可验证的机制解释。默认使用中文；所有结论来自已检查的目标版本源码、测试、运行结果、提交历史或权威版本资料，不凭记忆补全。

## 选择任务路径与完成定义

按用户授权组合以下路径，不擅自扩大范围：

- **讲解**：只读分析模块、对象、算法和调用链，不修改仓库。
- **注释**：只增加或修正解释性注释，不改变运行语义。
- **诊断**：沿真实调用链定位根因；用户只要求分析时，不实施修复。
- **教程**：把证据整理为脱离仓库也能理解的分享级文档。

把“完整读源码”“完整源码学习”“完整搞懂一个框架”及同义要求解释为完整任务，按以下顺序推进：

`模块拆分 → 声明盘点 → 源码注释 → 测试注释与作证 → 调用链串联 → 教程 → 覆盖验收`

开始前记录任务清单：模式、目标版本、包含与排除目录、允许编辑的文件、交付物、完成门禁。只有用户明确要求“只读”“只要分析/教程”或“不要修改源码”时，才跳过注释；交付时明确标为只读结果，不得称为完整注释任务。

若“完整学习”与“只允许生成文档”“禁止修改 `src`/测试”等约束同时出现，先指出完成定义冲突并请求选择，不得静默降级后宣告完整。用户给出的禁止修改约束始终优先。

窄任务只执行已授权阶段，但仍使用对应阶段的验收标准。

## 1. 固定证据基线

1. 读取仓库约定和工作区状态，保护用户现有改动。
2. 记录仓库、分支、tag、commit、依赖版本、关键配置和分析范围。
3. 若存在 `.codegraph/`，先用 CodeGraph 定位符号、源码和调用路径；否则用 `rg`、入口导出、构建配置和测试定位。
4. 区分“源码事实”“测试证明”“历史资料”“合理推断”。动态分派、宏、反射、代码生成或运行时注入无法静态确认时，明确标记推断。
5. 范围不明确时，先从最可能入口推进并说明假设；只有不同选择会显著改变结果时才询问用户。

## 2. 拆分模块并规划阅读顺序

识别对外入口、核心抽象与实现、配置和状态、调度与生命周期、扩展点、I/O 和缓存边界、测试与示例。

按职责和依赖关系拆模块，而非按文件名机械罗列。每个模块说明：

- 解决什么问题，不负责什么；
- 上游输入、下游输出和依赖模块；
- 核心对象、入口函数、状态与不变量；
- 推荐阅读顺序及原因；
- 能证明机制的代表性测试。

先找贯穿系统的主线，再补边界功能。避免平均用力扫描整仓库。

## 3. 追踪真实调用链

从真实入口追到最终返回值或副作用，至少覆盖：

`入口 → 路由/分派 → 核心实现 → 状态变化 → I/O/回调 → 返回、异常或清理`

同时记录：

- 关键参数、返回值和所有权变化；
- 同步、异步、事件或线程边界；
- 接口到具体实现的动态分派；
- 缓存、失效、重试、回滚和资源释放；
- 正常路径、关键分支和失败路径。

重要结论附目标版本中的文件与符号；行号稳定且有帮助时再附行号。先解释因果关系，再展示细节。

## 4. 补充源码与测试注释

完整任务或用户要求编辑注释时，先完整读取 [源码注释标准](references/annotation-standard.md)。

编辑前使用 [注释覆盖审计脚本](scripts/audit-comment-coverage.mjs) 建立声明级清单。清单至少覆盖命名函数、方法、构造器、函数值属性、类、类型、接口、枚举及成员、字段和顶层常量。每项必须归类为“已有且充分”“已翻译扩写”“新补充”或“明确豁免并说明原因”；不得留下未归类声明。

完整任务中，命名函数、方法和构造器不能仅因实现简单而省略头部说明；使用一行 TSDoc 即可说明薄包装、getter 或转发关系。匿名内联回调只在承载关键状态、异步、错误或清理语义时补注释。

解释角色、上下游、状态、WHY、不变量、边界和已证实的 issue 场景；不逐行翻译语法，不猜作者意图。已有普通英文解释性注释必须翻译并按实际机制补足；许可证、工具指令和生成标记按标准保留。

保持项目原有风格和格式。完成后重新运行覆盖审计，人工复核注释质量，再检查 diff，确认没有修改运行语义或覆盖用户改动。结构覆盖审计不能替代内容复核。

## 5. 用测试和历史作证

对关键测试说明：

1. Given：场景和初始状态；
2. When：唯一关键操作；
3. Then：结果与断言；
4. Mechanism：断言证明的机制或不变量；
5. Source：对应核心函数与分支。

不要仅凭测试名推断行为，也不要把单个测试未覆盖的行为扩大为系统保证。

教程示例优先选仓库中的经典真实测试或官方示例。完整示例包含必要 import、初始化、输入、操作、断言和清理。源码摘录注明来源；删节、改写和伪代码必须明确标记。

设计动机、issue 场景和演进过程只能由注释、测试、issue、提交历史、release notes 或官方文档支撑。没有历史证据时，标记为“从当前实现推断”或省略。

## 6. 诊断真实问题

固定症状、触发条件、配置、版本和最小复现，再沿实际调用链找到决定行为的分支。使用以下因果链表达根因：

`触发条件 → 数据/状态变化 → 分支或不变量 → 用户可见症状`

区分表象、根因和放大因素；验证竞争性解释。比较版本时检查双方源码和权威变更资料，不用“升级”替代根因解释。

给出适用于当前版本的修复或规避方案、适用边界、风险和最小验证方法。需要改代码时，先服从用户授权范围。

## 7. 产出分享级教程

用户要求完整指南、教程或 HTML 时，先完整读取 [分享级教程标准](references/guide-standard.md)。

教程必须先分模块讲清，再串成端到端机制；不能只是文件索引、函数清单或阅读笔记。最低标准：读者不打开仓库也能理解系统目标、核心对象、主调用链和关键状态变化；每个关键机制章节必须配真实源码摘录，每条被称为“完整”的调用链必须包含入口、决定状态或副作用的核心实现、异常或清理路径及代表性测试证据。

用户未指定格式时，完整教程默认交付一个简洁、优雅、自包含的单 HTML，并集中放入仓库既有文档目录。用户指定 Markdown、多页面或其他格式时服从。

## 8. 按风险验证

- 只读讲解或规划：默认不运行测试；先用源码和现有测试内容作证。只有用户明确要求，或关键结论无法静态确认时，才运行最小针对性测试。
- 纯注释或文档改动：检查 diff、引用、术语、语法边界和格式；不机械运行完整测试套件。
- 修改了逻辑或测试：运行与变更路径匹配的针对性测试。
- 新增可执行 Demo：运行 Demo 或对应经典测试，保证输入和断言真实。
- HTML 教程：检查解析、锚点、链接、代码块、内联资源、窄屏布局，并从头到尾复读一次。

未运行测试时明确报告原因；不得把未执行的测试描述为通过。

## 交付检查

- 完整任务已交付任务清单和声明级覆盖统计；未分类缺口为零。
- 所有豁免都有具体原因；简单命名函数未被静默豁免。
- 版本、术语、源码、测试、Demo 和图示相互一致。
- 重要判断可追溯到证据；推断已标记。
- 源码摘录、教程改写和伪代码边界清楚。
- 注释 diff 未改变行为；文档未散落临时副本。
- 教程关键章节与完整调用链通过源码和测试证据门禁，不存在纯概述替代源码的章节。
- 发现局部问题后检查同类内容，避免只修一个例子。
- 读者能够复述“为什么这样设计”和“请求如何完整运行”，不只记住函数名。
